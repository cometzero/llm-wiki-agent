### 1.1. CPX의 변화: Groq 3 LPX로 진화 [9]

CPX 랙 개념의 진화 [10]

NVIDIA는 AI Infra Summit에서 장문맥 추론 가속을 위한 CPX 랙을 발표했다. [10]

CPX는 초기에는 Rubin GPU와 차별점이 불분명했으나, Groq 인수 후 LPX 랙으로 발전했다. [11]

LPX 랙은 CPX의 문맥 처리 초점에서 Groq의 실리콘 기반 디코드 가속 아키텍처로 변화했다. [15]

LPX 랙의 특징 및 성능 [16]

LPX 랙은 액체 냉각 방식이며, MGX 인프라를 기반으로 2026년 하반기에 출시될 예정이다. [16]

NVIDIA는 LPX 랙이 메가와트당 최대 35배 높은 추론 처리량과 조 단위 매개변수 모델에서 최대 10배 더 많은 수익 기회를 제공한다고 밝혔다. [17]

LPU는 기존 CUDA 스택 내에서 토큰 단위로 연산을 오프로드하는 가속기로 작동한다. [18]

NVIDIA는 LPU를 "디코드 모델 부스터"로 설명하며, 차세대 프리미엄 모델 서비스를 위해 AI 연구소와 협력할 예정이다. [19]

### 1.2. LPU(Language Processing Unit)의 이해 [21]

LPU의 핵심: 대규모 벡터 프로세서 [22]

LPU는 Groq가 설계한 맞춤형 AI 추론 가속기이다. [3]

LPU는 320바이트(INT8) 또는 640바이트(FP16)의 320개 요소 벡터를 기본 연산 및 통신 단위로 사용한다. [23]

모든 연산은 고정 크기 벡터로 처리된다. [23]

LPU 아키텍처의 구성 요소 [25]

LPU는 SIMD(Single Instruction, Multiple Data) 기능 단위와 경량 명령어 디스패치 유닛으로 구성된다. [25]

각 기능 단위는 특정 연산에 최적화된 4가지 유형으로 나뉜다. [26]

MXM(Matrix Execution Modules): 행렬-벡터 및 행렬-행렬 연산을 위한 주요 계산 장치이다. [27]

LPX 랙의 8개 Groq 3 LP30 칩은 칩당 1.2 PFLOPS의 FP8 연산을 제공하며, 트레이당 총 9.6 PFLOPS를 제공한다. [28]

VXM(Vector Execution Modules): 포인트별 산술, 논리 연산, 타입 변환, 활성화 함수를 처리한다. [29]

컴파일러가 여러 연산을 자동으로 연결하여 단일 패스로 복합 연산을 수행한다. [30]

SXM(Switch Execution Modules): 벡터의 순열, 회전, 분배, 전치 등 구조화된 데이터 이동을 수행한다. [31]

MEM(Memory Units): 캐시나 계층 구조가 없는 플랫한 SRAM 우선 메모리 아키텍처이다. [32]

Groq 3 LP30은 150 TB/s 대역폭의 500MB 온칩 SRAM을 제공한다. [33]

컴파일러는 프로그램 실행 중 모든 데이터의 정확한 위치를 파악하여 물리적 뱅크 위치를 직접 지정한다. [34]

데이터 흐름 [35]

각 기능 단위 유형의 여러 복사본이 칩의 가로 방향으로 배치된다. [35]

명령어는 위아래에서 중앙으로 흐르고, 데이터 스트림은 동서로 흐르며 기능 단위와 교차하여 연산을 수행한다. [36]

### 1.3. 1D 인터커넥트, 스트림 레지스터 및 결정론 [37]

스트림 레지스터와 1D 인터커넥트 [38]

LPU 내 기능 단위 간 통신은 단순한 1차원 인터커넥트인 스트림 레지스터를 통해 이루어진다. [39]

동쪽과 서쪽으로 흐르는 두 개의 통신 경로가 있으며, 각 스트림 레지스터는 단일 홉을 나타낸다. [40]

데이터는 클록 사이클당 정확히 한 홉씩 이동하므로, 컴파일러는 물리적 위치를 기반으로 기능 단위 간 이동 시간을 정확히 계산할 수 있다. [41]

인터커넥트 내에는 큐나 경쟁 메커니즘이 없어 스케줄링 문제가 단순화된다. [42]

컴파일러는 데이터가 10클록 사이클 후에 정확히 10홉 떨어진 곳에 있을 것이라는 것을 알 수 있어 모호함이나 추측이 없다. [44]

결정론(Determinism) [46]

LPU의 핵심 특징은 결정론이다. [47]

동적 스케줄링, 캐시 동작, 메모리 접근 경쟁으로 런타임 편차가 발생하는 기존 프로세서와 달리, LPU는 편차 없이 모든 기능 단위가 동기화되어 실행된다. [48]

하드웨어 인터록과 같은 기능을 제거하고 모든 의사 결정을 컴파일러로 옮겨 결정론을 달성한다. [49]

이 접근 방식은 모든 연산이 동일한 지연 시간으로 작동하며, 전력 소비도 예측 가능하다는 이점을 제공한다. [50]

Groq의 TruePoint 기술을 통해 수치적 결정론도 확장된다. [51]

이 기술은 FP16 입력에서 단일 반올림 단계를 거치는 320개 요소 융합 곱셈-누적을 통해 FP32 수준의 정확도를 제공한다. [51]

LLM 추론에서 수치적 결정론의 중요성은 Thinking Lab의 백서 "Defeating Nondeterminism in LLM Inference"에서 자세히 다룬다. [52]

## 2. LPU 연결 방식: RealScale, 어셈블리 라인 및 랙 토폴로지 [54]

LPU는 어셈블리 라인 방식의 데이터 이동과 RealScale C2C 인터커넥트를 통해 확장 가능한 랙 토폴로지를 구축하여 대규모 AI 모델을 효율적으로 처리한다.

### 2.1. 어셈블리 라인: 데이터 이동 방식 [55]

모델 컴파일 및 데이터 흐름 [56]

모델이 시스템용으로 컴파일되면, 컴파일러는 모델을 여러 단계로 분할하고 각 단계를 LPU 칩 그룹에 공간적으로 매핑한다. [57]

각 칩 그룹은 필요한 가중치 매개변수를 로컬 온칩 SRAM에 저장한다. [58]

추론 중에는 이전 단계의 중간 활성화 출력만 칩 그룹 간에 이동한다. [59]

데이터는 컨베이어 벨트의 제품처럼 칩에서 칩으로 흐르며, 각 스테이션은 할당된 계산을 수행하고 결과를 다음 스테이션으로 전달한다. [60]

GPU와의 차이점 [61]

GPU는 각 계산 단계에서 오프칩 HBM 메모리에서 전체 가중치 세트를 검색하고 결과를 다시 기록해야 한다. [61]

LPU에서는 가중치가 각 스테이션의 SRAM에 이미 상주하며, 활성화 텐서만 이동한다. [62]

### 2.2. C2C 링크: RealScale과 NVIDIA C2C의 차이점 [63]

RealScale C2C 인터커넥트 [65]

LPX 시스템 전체에 사용되는 칩-투-칩(C2C) 링크는 Groq의 RealScale C2C 인터커넥트이다. [65]

이는 NVIDIA의 C2C 기술과 다르며, RealScale C2C는 소프트웨어 스케줄링되는 결정론적 점대점 인터커넥트이다. [66]

네트워크 링크는 컴파일러에 의해 명시적으로 흐름 제어되며, 하드웨어 중재나 적응형 라우팅이 없다. [69]

패킷에는 소스 또는 대상 헤더가 없으며, 링크는 위상 정렬되어 칩 간에 고대역폭, 고정 지연 시간 와이어처럼 작동한다. [69]

NVIDIA C2C 인터커넥트 [68]

NVIDIA C2C는 캐시 일관성 인터커넥트로, CPU-GPU 링크와 같이 긴밀하게 결합된 모듈 내에서 두 가지 다른 칩 유형을 연결하도록 설계되었다. [68]

이는 단일 패키지 또는 모듈 내에서 이기종 칩 간 통신을 위해 일관성 프로토콜과 고속 SerDes를 사용한다. [68]

LPX 랙의 C2C 연결 [70]

LPX 랙의 모든 C2C 연결은 RealScale을 사용하며, 이는 GroqNode부터 사용된 동일한 기본 인터커넥트 기술이다. [70]

LPX 랙 유닛에 사용되는 C2C 링크는 Groq의 기술이며, NVIDIA의 다른 랙 스케일 시스템에 사용되는 C2C 링크와는 다르다. [73]

각 LPX 랙 유닛 전면의 4개 C2C 링크는 동일 레벨의 인접 랙 유닛에 연결된다. [74]

랙 내에서는 LPU 간에 전면 통신이 이루어진다. [75]

LPX 랙의 프로세서는 x86이다. [76]

### 2.3. 트레이 내 연결성 [77]

기본 구성 요소 [78]

Groq 네트워크 토폴로지의 기본 구성 요소는 GroqNode에서 NVIDIA Groq 3 LPX까지 동일하게 유지된다. [78]

각 1U 컴퓨팅 트레이에는 8개의 LP30 칩이 완전 그래프(all-to-all) 방식으로 밀접하게 상호 연결되어 있다. [79]

모든 칩은 동일한 속도로 다른 모든 칩과 직접 통신할 수 있다. [79]

LP30 칩의 대역폭 [81]

각 LP30 칩은 96개의 C2C 링크를 가지며, 각 링크는 112Gbps로 작동하여 칩당 2.5TB/s의 양방향 대역폭을 제공한다. [81]

8개 칩의 완전 그래프에서 각 칩은 7개의 이웃을 가진다. [82]

트레이 내 고유한 칩-투-칩 연결 수는 28개이다. [83]

NVIDIA의 사양에 따르면 트레이당 총 20TB/s의 스케일업 대역폭을 제공한다. [84]

이는 8개 칩 × 96개 링크 = 총 768개 링크에서 32개의 전면 패널 인터랙 링크를 제외한 736개 링크가 스케일업에 사용된다. [85]

112Gbps/링크로 계산하면 약 10.3TB/s(단방향) 또는 20.6TB/s(양방향)로 NVIDIA의 20TB/s와 일치한다. [87]

네트워크 토폴로지 [89]

이 8개 칩의 완전 그래프 그룹은 드래곤플라이 네트워크 토폴로지의 "로컬 그룹"을 형성한다. [89]

GroqChip 1은 카드당 11개의 C2C 링크(30Gbps/레인)로 총 330GB/s를 제공했다. [90]

Groq 3 LP30의 96개 링크(112Gbps)는 동일한 토폴로지 구조를 유지하면서 칩당 I/O 대역폭에서 엄청난 세대적 도약을 나타낸다. [91]

### 2.4. 랙 내 연결성 [92]

랙 내 상호 연결 [93]

단일 LPX 랙 내에서 32개의 컴퓨팅 트레이(총 256개 칩)는 백플레인의 4개 ETL 스파인을 통해 상호 연결된다. [93]

이 스파인은 트레이 간 RealScale C2C 트래픽을 전달하여 랙 스케일 스케일업 도메인을 생성한다. [94]

총 대역폭 [95]

전체 랙의 총 스케일업 대역폭은 640TB/s(32개 트레이 × 트레이당 20TB/s)이다. [95]

4개의 스파인에 분할하면 각 스파인은 약 160TB/s의 양방향 대역폭을 전달한다. [96]

### 2.5. 랙 간 연결성 [97]

전면 패널 포트 [98]

각 1U 컴퓨팅 트레이는 전면 패널에 4개의 QSFP C2C 포트를 노출하며, 랙 간 통신을 위해 총 32개 레인(포트당 8개 레인)을 제공한다. [98]

이 포트들은 대칭 패턴으로 인접 랙에 연결된다. [99]

각 U 위치는 인접 랙의 해당 U 위치에 연결된다. [100]

랙 간 대역폭 [102]

레인당 112Gbps로, 각 트레이의 32개 랙 간 레인은 트레이당 약 448GB/s의 랙 간 대역폭을 제공한다. [102]

전체 랙에 걸쳐 32개 트레이는 1,024개의 랙 간 레인을 제공한다. [103]

이는 인접 랙당 약 14.3TB/s의 단방향 대역폭에 해당한다. [104]

대역폭 밀도 및 토폴로지 [105]

랙 간 대역폭은 랙 내 대역폭보다 의도적으로 희소하다. [105]

랙 내에서는 640TB/s 스케일업 도메인이 스파인을 통해 밀도 높은 전면 통신을 제공한다. [106]

랙 간에는 전면 패널 링크가 드래곤플라이 토폴로지의 희소한 전역 연결을 제공한다. [107]

이는 GroqRack과 동일한 아키텍처 패턴으로, 낮은 네트워크 직경으로 다중 랙 시스템을 형성한다. [108]

### 2.6. 아키텍처 통합: 4배 향상된 밀도 [109]

밀도 향상 [110]

기존 4개 랙 GroqRack 배포에는 264개의 GroqChip 프로세서가 포함되었다. [110]

단일 LPX 랙은 256개의 LP30 칩을 하나의 MGX ETL 랙에 통합하여, 액체 냉각 및 케이블 없는 백플레인으로 칩 밀도를 약 4배 높였다. [111]

아키텍처 유지 [112]

8개 칩의 완전 그래프 로컬 그룹, 드래곤플라이 토폴로지, 소프트웨어 스케줄링 라우팅 패러다임은 모두 그대로 유지된다. [112]

기본 Groq 네트워킹 기술은 변경되지 않고 확장되었다. [113]

확장성 [114]

단일 랙의 SRAM 용량(256개 칩에 걸쳐 총 128GB)을 초과하는 모델의 경우, 전면 패널 C2C 포트를 통해 여러 LPX 랙 또는 랙 열을 상호 연결하여 어셈블리 라인을 확장할 수 있다. [114]

이는 실제 모델 크기에 대한 의미를 다음 섹션에서 더 자세히 다룬다. [115]

## 3. FFN 레이어의 중요성 및 NVIDIA의 오프로딩 전략 [116]

NVIDIA는 LLM 추론의 주요 병목인 FFN(Feed-Forward Network) 레이어를 LPX로 오프로드하여 디코드 지연 시간을 줄이고 효율성을 극대화한다.

### 3.1. 디코드 단계의 난이도 증가 [117]

AI 추론 워크로드의 복잡성 [119]

AI 추론은 단일하고 균일한 워크로드가 아니다. [119]

단일 요청 내에서 사전 채우기(프롬프트 수집 및 KV 캐시 구축) 단계와 디코드(토큰 하나씩 생성) 단계는 하드웨어에 매우 다른 요구 사항을 부과한다. [120]

이러한 요구 사항은 배치 크기, 문맥 길이, 모델 구조에 따라 달라진다. [120]

디코드 지연 시간의 병목 현상 심화 [121]

모델이 더 긴 추론 출력과 다단계 사고 체인을 생성함에 따라, 각 요청의 더 많은 부분이 순차적 디코드 단계로 이동한다. [121]

접두사 캐싱과 같은 기술은 요청 간 공유 프롬프트 상태를 재사용하여 사전 채우기 비용을 줄여 디코드의 상대적 비용을 더욱 두드러지게 만든다. [122]

문맥 창이 수십만 토큰으로 증가하면서 어텐션 계산 중 메모리 대역폭에 대한 압력이 커진다. [123]

에이전트 워크플로우에서는 많은 모델 호출, 도구 상호 작용 및 검증 루프에서 지연 시간이 누적된다. [124]

결과적으로 디코드 지연 시간은 사용자가 느끼는 병목 현상이 되고 있으며, 최대 집계 처리량에만 최적화된 하드웨어는 개별 요청에 대한 빠르고 예측 가능한 토큰 생성이 필요한 워크로드에 항상 최적화되지 않는다. [125]

낮은 지연 시간의 경제적 이점 [126]

Anthropic의 Fast Mode 출시에서 볼 수 있듯이, 낮은 지연 시간과 높은 토큰 처리량은 더 높은 수익을 창출한다. [126]

Anthropic의 빠른 추론 서비스는 일반 요청보다 6배 더 비싸다. [126]

FFN 레이어 오프로딩 [127]

NVIDIA는 LPX 발표를 통해 가장 큰 디코드 병목인 FFN(Feed-Forward Network) 레이어를 LPU로 오프로드할 계획임을 밝혔다. [127]

FFN이 목표가 되는 이유와 그 규모를 이해하기 위해 인기 있는 오픈소스 모델의 FFN 매개변수 수를 분석했다. [128]

### 3.2. FFN 레이어의 지배적인 역할 [129]

트랜스포머 레이어의 구성 [130]

모든 트랜스포머 레이어는 어텐션 블록과 FFN 블록의 두 가지 주요 블록으로 구성된다. [130]

어텐션 블록은 토큰이 시퀀스의 다른 토큰에서 정보를 보고 혼합할 수 있도록 한다. [131]

FFN 블록은 각 토큰에 독립적으로 작동한다. [132]

토큰의 표현을 더 높은 차원 공간으로 투영하고, 비선형성을 적용한 다음 다시 축소한다. [132]

이는 모델의 지식 저장소로, 사실적 연관성과 학습된 변환이 저장되는 곳으로 생각할 수 있다. [133]

MoE(Mixture of Experts) 아키텍처 [134]

MoE 아키텍처는 DeepSeek R1, Kimi K2, Qwen3-235B, GLM-5, MiniMax M2.5, OpenAI의 GPT-OSS 120B 등 오늘날 주요 오픈소스 대규모 언어 모델에서 지배적인 아키텍처로 부상했다. [134]

MoE 모델 내에서는 특히 FFN 블록이 수백 개의 더 작은 독립적인 복사본(전문가)으로 복제되는 반면, 어텐션은 공유된다. [135]

경량 학습 라우팅 함수는 토큰 단위로 활성화할 전문가의 작은 하위 집합을 동적으로 선택한다. [136]

결과적으로 엄청난 총 매개변수 수를 저장하지만 토큰당 일부만 활성화하여, 비례적인 계산 비용 없이 규모의 품질 이점을 얻는다. [137]

FFN 레이어의 가중치 지배 [138]

FFN 레이어는 모델 가중치의 대부분을 차지한다. [138]

MoE 모델의 경우, 이는 모델 가중치의 최대 90%에 달할 수 있다. [139]

### 3.3. DeepSeek R1 사례 분석 [140]

DeepSeek R1의 구조 [141]

DeepSeek R1 모델은 61개의 트랜스포머 레이어를 가지며, 숨겨진 차원(H)은 7,168이다. [141]

처음 3개 레이어는 표준 밀집 FFN을 사용하고, 나머지 58개는 MoE를 사용한다. [141]

최신 LLM은 두 개의 가중치 행렬 대신 세 개의 가중치 행렬을 사용하는 SwiGLU 변형을 사용한다. [142]

순방향 패스는 w2(SiLU(w1(x)) ⊙ w3(x))를 계산하며, w1(게이트 투영)과 w3(업 투영)은 숨겨진 차원을 H에서 중간 크기 I로 확장하고, w2(다운 투영)는 다시 압축한다. [143]

이 행렬에는 바이어스 항이 없으므로, 각 SwiGLU FFN 블록은 정확히 3 × H × I 매개변수를 포함한다. [145]

매개변수 계산 [147]

DeepSeek R1의 밀집 레이어(처음 3개)의 중간 차원은 18,432이며, 레이어당 3 × 7,168 × 18,432 = 3억 9,640만 매개변수를 제공한다. [147]

MoE 레이어의 경우, 256개의 라우팅된 전문가 각각은 더 작은 중간 차원(2,048)을 가진 완전한 SwiGLU 블록이며, 각 전문가는 3 × 7,168 × 2,048 = 4,400만 매개변수를 가진다. [148]

256명의 전문가를 곱하면 레이어당 라우팅된 전문가만으로 112억 7천만 매개변수가 된다. [149]

또한, 각 MoE 레이어에는 하나의 공유 전문가(동일한 4,400만 매개변수 SwiGLU 블록), 라우터 게이트(256, 7168 형태의 선형 투영 = 180만 매개변수), 라우팅 중 부하 분산을 위한 256개의 FP32 값으로 구성된 작은 바이어스 벡터가 있다. [150]

FFN의 압도적인 비중 [151]

전체 FFN은 약 6,691억 매개변수를 가진다. [151]

FP8 E4M3 형식(가중치당 1바이트)으로 변환하면 약 623.1GB의 FFN 데이터가 된다. [152]

이는 모델의 예상 총 디스크 크기의 97.7%에 해당한다. [153]

나머지 약 2.3%는 어텐션 가중치, 임베딩, 출력 헤드, 레이어 정규화 및 FP8 스케일 메타데이터이다. [154]

## 4. 디코드 분리(Decode Disaggregation) [155]

NVIDIA의 디코드 분리(AFD) 아키텍처는 GPU와 LPU의 강점을 결합하여 LLM 추론의 디코드 단계를 최적화하고, 특히 긴 문맥 길이에서 효율성을 높인다.

### 4.1. 디코드 단계의 분리 [156]

프리필과 디코드의 차이점 [157]

NVIDIA는 디코드 단계를 단일 작업이 아닌, 하드웨어 병목 현상을 다르게 강조하는 반복적인 토큰별 루프로 정의한다. [156]

프리필 단계는 대규모 입력을 수집하고 KV 캐시를 구축하는 데 주로 사용되며, 이는 밀집 병렬 계산과 대용량 메모리에서 이점을 얻는다. [157]

Vera Rubin NVL72는 특히 프롬프트가 방대하고 가변적인 긴 문맥 워크로드에 대해 이를 효율적으로 처리한다. [158]

디코드의 특성 및 AFD 아키텍처 [160]

디코드는 다르다. [160]

각 새 토큰에 대해 시스템은 전체 누적 KV 캐시에 대한 어텐션을 실행한 다음, 어텐션 출력에 대해 FFN/MoE 계산을 실행해야 한다. [161]

NVIDIA의 어텐션-FFN 분리(AFD) 아키텍처에서는 이 두 단계가 두 개의 엔진으로 분할된다. [162]

Rubin GPU는 디코드 어텐션을 처리한다. [163]

HBM에서 KV 캐시를 읽고, 어텐션 점수를 계산하며, 중간 활성화를 생성한다. [163]

이 활성화 텐서는 LPX로 전달되어 FFN 또는 MoE 전문가 계산을 극단적인 대역폭과 결정론적 지연 시간으로 실행한 다음, 결과를 GPU로 반환하여 토큰 생성을 계속한다. [164]

프로세서별 강점 활용 [165]

이 핸드오프는 모든 단일 토큰에 대해 발생한다. [165]

GPU와 LPU 간에 교환되는 활성화 텐서는 가중치 데이터에 비해 작으며, 이는 LPU의 거의 제로 오버헤드 네트워킹이 탁월한 영역이다. [166]

이 분할은 각 프로세서의 근본적인 강점을 활용한다. [167]

GPU는 대규모 KV 캐시에 대한 가변 길이 어텐션에 필요한 HBM 용량과 유연한 실행을 제공한다. [167]

LPU는 대역폭 제한적이고 정적으로 스케줄링 가능한 FFN 가중치에 필요한 SRAM 대역폭과 결정론적 스케줄링을 제공한다. [167]

문맥 길이에 따른 스케일링 속성 [169]

문맥 길이가 증가함에 따라 어텐션 연산의 계산 및 메모리 요구 사항도 함께 증가한다. [170]

KV 캐시는 문맥의 각 추가 토큰에 따라 선형적으로 확장되며, 각 새 디코드 단계는 전체 누적 캐시에 주의를 기울여야 한다. [170]

그러나 FFN은 문맥과 함께 전혀 증가하지 않는다. [171]

FFN 가중치 행렬은 모델 아키텍처의 고정 상수이다. [172]

문맥이 1,000토큰이든 1,000,000토큰이든 크기는 동일하며, 각 토큰은 독립적으로 통과한다. [173]

이는 AFD 아키텍처에서 문맥 창이 계속 증가함에 따라 GPU 측이 증가하는 비용(KV 캐시를 위한 더 많은 HBM, 어텐션을 위한 더 많은 계산)을 흡수하는 반면, LPX 측은 완전히 정적으로 유지됨을 의미한다. [174]

모델의 FFN을 서비스하는 데 필요한 LPX 랙 수는 모델 아키텍처에 의해서만 결정되며, 서비스 구성의 문맥 길이에 따라 결정되지 않는다. [175]

이는 SRAM 전용 가속기의 가장 큰 과제 중 하나였던, 증가하는 문맥 요구 사항이 고정된 온칩 메모리 용량을 초과하는 문제를 깔끔하게 해결한다. [176]

AFD 분할에서 문맥 의존적 작업은 확장 가능한 HBM을 가진 하드웨어에 유지되고, LPU는 고정 SRAM에 자연스럽게 맞는 문맥 독립적 작업만 처리한다. [177]

### 4.2. NVIDIA Dynamo: 이기종 디코드의 운영 [178]

Dynamo의 역할 [179]

이 두 엔진 루프를 프로덕션에서 작동시키려면 하드웨어 이상의 것이 필요하다. [179]

NVIDIA의 Dynamo 오케스트레이션 레이어는 이기종 디코드를 실용적으로 만든다. [180]

Dynamo는 AFD에 필요한 토큰별 분류, 라우팅 및 활성화 전송을 처리하여 GPU 및 LPU 백엔드 간의 분리된 서비스를 조정한다. [181]

Dynamo의 작동 방식 [183]

Dynamo는 프리필을 GPU 워커로 라우팅하여 입력을 처리하고 KV 캐시를 구축한다. [183]

디코드 중에는 Dynamo가 AFD 루프를 조율한다. [184]

GPU는 누적 KV 캐시에 대한 어텐션을 실행한다. [184]

중간 활성화는 FFN/MoE 실행을 위해 LPU로 전달된다. [184]

출력은 토큰 생성을 계속하기 위해 GPU로 반환된다. [184]

결과적으로 두 개의 분리된 시스템이 아닌 단일하고 일관된 서비스 경로가 생성된다. [185]

Dynamo의 추가 기능 [186]

Dynamo는 KV 인식 라우팅(관련 KV 캐시가 이미 상주하는 워커로 요청을 보냄), 지연 시간 목표 기반 스케줄링(대화형 세션이 긴 대기열에 들어가지 않도록 함), 낮은 오버헤드 전송 관리도 제공한다. [186]

이러한 기능은 가변 문맥 길이, 혼합 요청 유형 및 버스트성 동시성을 가진 실제 프로덕션 트래픽에서 오케스트레이션 레이어가 꼬리 지연 시간을 안정적으로 유지하고 교차 테넌트 지터가 사용자 경험을 저하시키는 것을 방지하기 때문에 중요하다. [187]

## 5. 주요 오픈소스 모델의 FFN 크기 및 LPX 사이징 [188]

LPX는 대부분의 LLM에서 95% 이상을 차지하는 FFN 매개변수를 효율적으로 처리하여, 단일 랙으로 소규모 모델을, 여러 랙을 연결하여 대규모 모델을 지원한다.

FFN 매개변수 분석 결과 [190]

인기 모델의 FFN 매개변수 및 디스크 크기를 분석한 결과, FFN 매개변수가 총 모델 크기의 95%에서 99%를 차지하는 것으로 확인되었다. [191]

Kimi K2는 레이어당 384개의 라우팅된 전문가로 FFN이 1조 개 이상의 매개변수와 총 모델의 거의 99%를 차지하는 가장 극단적인 사례이다. [192]

가장 작은 모델인 OpenAI의 GPT-OSS 120B(128개 전문가, MXFP4 저장)도 FFN이 총 모델의 95.4%를 차지한다. [193]

디스크 크기는 GPT-OSS 120B의 53GB(4비트 양자화 덕분)에서 GLM 5의 거의 1.4TB(BF16 저장, 양자화 없음)까지 다양하다. [194]

## 6. LPX를 활용한 추측 디코딩 가속화 [200]

LPX는 추측 디코딩에서 초안 생성 엔진으로 활용되어, 빠르고 예측 가능한 토큰 생성을 통해 LLM 추론의 지연 시간을 크게 줄인다.

추측 디코딩의 개념 [201]

추측 디코딩은 LLM 추론에서 지연 시간을 줄이는 데 점점 더 중요해지는 기술이다. [202]

더 작고 빠른 초안 모델이 여러 후보 토큰을 미리 생성하고, 더 큰 대상 모델이 이를 병렬로 검증하고 수락한다. [203]

초안 모델의 예측이 정확할 경우(일반적인 텍스트에서 자주 발생), 단일 검증 단계에서 여러 토큰을 한 번에 커밋할 수 있다. [204]

결과적으로 초당 유효 토큰 수가 크게 증가하고 최종 사용자가 인지하는 지연 시간이 줄어든다. [205]

기존 GPU 설정의 한계 [207]

추측 디코딩의 과제는 초안 모델이 매우 빠르게 실행되어야 한다는 것이다. [207]

초안 모델이 후보를 생성하는 데 걸리는 모든 밀리초는 검증자가 기다리는 시간이다. [208]

기존 GPU 전용 설정에서는 초안 모델과 대상 모델 모두 동일한 하드웨어 리소스를 놓고 경쟁하며, 초안 모델의 속도는 다른 모든 것에 영향을 미치는 동일한 HBM 대역폭 제약에 의해 제한된다. [209]

LPX의 역할 및 이점 [210]

LPX는 이 역할에 매우 적합하다. [210]

결정론적 실행 모델과 LP30의 극단적인 온칩 SRAM 대역폭은 매우 빠르고 예측 가능한 초안 토큰 생성을 가능하게 한다. [211]

더 작은 초안 모델은 단일 LPX 트레이 또는 소수의 트레이 SRAM에 충분히 들어맞으며, 결정론적 스케줄링은 초안 생성이 검증자와 파이프라인을 구성하기 어렵게 만드는 편차 없이 일관되고 예측 가능한 속도로 실행되도록 보장한다. [212]

이 구성에서 시스템은 두 프로세서를 상호 보완적인 역할로 짝지어 사용한다. [213]

LPX는 낮은 지연 시간 아키텍처를 사용하여 초안 토큰을 빠르게 생성한다. [213]

Rubin GPU는 높은 처리량 계산과 대용량 HBM 용량을 사용하여 토큰을 효율적으로 검증하고 확정한다. [213]

이러한 분리는 추측 디코딩이 이기종 프로세서에서 실행되도록 하여, 두 모델이 단일 GPU를 공유해야 하는 것보다 초안 속도와 검증 처리량을 잠재적으로 향상시킨다. [214]

LPX의 가치 제안 [215]

NVIDIA는 AFD와 함께 추측 디코딩을 LPX의 핵심 워크로드로 강조하며, 이를 시스템의 중요한 가치 제안으로 보고 있다. [215]

최첨단 모델이 계속 성장하고 추론 체인이 길어짐에 따라, 특수 하드웨어에서 토큰을 병렬로 생성하고 검증하는 능력은 대화형 응답성을 유지하는 중요한 수단이 될 수 있다. [216]

## 7. 최종 결론: 극단적인 하드웨어/소프트웨어 공동 설계 [217]

NVIDIA Groq 3 LPX는 AI 추론 파이프라인의 병목 현상을 정확히 파악하고, 하드웨어와 소프트웨어를 긴밀하게 통합하여 최적화된 솔루션을 제공하는 극단적인 공동 설계의 결과물이다.

NVIDIA 접근 방식의 특징 [218]

NVIDIA의 Vera Rubin 플랫폼과 LPX에 대한 접근 방식에서 두드러지는 점은 각 구성 요소가 얼마나 정확하게 목표를 설정하고 있는지이다. [218]

NVIDIA의 전략은 추론 파이프라인의 문제를 매우 세분화된 수준으로 이해하고 있으며, 고객이 하드웨어 투자 수익을 극대화할 수 있도록 파이프라인의 모든 부분을 최적화하고 있음을 보여준다. [221]

정확한 최적화 전략 [222]

어텐션/FFN 분리는 마케팅 개념이 아니라, 조 단위 매개변수 MoE 모델 서비스의 측정된 병목 프로필에 대한 직접적인 응답이다. [222]

FFN을 특별히 오프로드하고(어텐션은 아님) CPX 랙을 LPX 랙으로 발전시킨 결정은 어떤 연산이 대역폭 제한적이고 어떤 연산이 용량 제한적인지, 어떤 연산이 정적으로 스케줄링 가능하고 어떤 연산이 동적으로 가변적인지, 그리고 어떤 프로세서 아키텍처가 각 연산에 가장 적합한지에 대한 정확한 이해를 반영한다. [224]

Dynamo 오케스트레이션 레이어, 투명한 CUDA 통합, 케이블 없는 MGX 랙 설계는 전체 배포 수명 주기를 고려한 엔지니어링 조직을 보여준다. [225]

남아있는 질문과 향후 전망 [226]

LPX와 NVIDIA의 새로운 최첨단 제품에는 여전히 많은 미지수가 남아있다. [226]

"패브릭 확장 로직 및 DRAM"의 목적과 사용되는 실리콘 종류, 그리고 x86 소켓에 대한 의문이 남아있다. [227]

LPX 배포는 초기에는 광범위한 가용성보다는 모델 빌더 및 서비스 제공업체에 중점을 둘 것이다. [228]

가변 문맥 길이, 혼합 요청 유형 및 버스트성 동시성을 가진 실제 프로덕션 트래픽에서의 성능과 전력 효율성은 독립적으로 검증되어야 한다. [229]

독립적인 테스트를 위해 이러한 시스템에 접근할 수 있기를 기대한다. [230]
