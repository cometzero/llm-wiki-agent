## 📌 26년 제조 산업에 AI가 적용되면 어떻게 변화하며, LLM 현직자가 제시하는 솔직한 조언은 무엇인가?
LLM은 제조 산업의 <mark>다양한 부서에서 업무 효율을 높이는 데 활용</mark>되며, 특히 문서 작업 시간 단축 및 불량 문서 검색과 같은 과제에 적용됩니다. 현직자는 LLM 에이전트 기술 학습과 프롬프트 엔지니어링, 노코드 기반 개발에 관심을 가질 것을 조언합니다.


## 💡 LLM 에이전트 기술이 제조 산업에서 필요한 주요 이유는?
LLM의 <mark>환각(할루시네이션) 문제, 최신 정보 및 기업 내부 도메인 지식 반영 불가</mark> 등의 한계를 극복하고, 고비용의 파인튜닝 대신 RAG(검색 증강 생성) 기술을 통해 정확하고 효율적인 답변을 얻기 위함입니다.


제조업 현직자가 직접 공개하는 **LLM 기반 RAG(검색 증강 생성) 시스템 구축의 A to Z**를 담고 있습니다. 단순한 이론 설명이 아닌, 8년 차 데이터 사이언티스트가 **제조 대기업의 보안 환경**과 **멀티모달 데이터(이미지, 테이블) 처리**라는 현실적 난제를 어떻게 극복하고 LLM 에이전트를 업무에 적용했는지 구체적인 기술 스택과 노하우를 배울 수 있습니다. 특히, 나이브 RAG의 한계를 뛰어넘는 **어드밴스드 RAG 기법**과 **랭그래프 기반의 에이전트 워크플로우** 설계 방법을 통해, 여러분의 LLM 프로젝트의 성능과 자율성을 극대화할 수 있는 실용적인 통찰을 얻게 될 것입니다.
## 1. 제조 대기업에서의 LLM 및 에이전트 활용 현황 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/0.jpg)
1. **발표자 소개 및 현재 업무** 
  1. 발표자는 현재 제조 대기업에서 8년 차 데이터 사이언티스트로 재직 중이다. 
  2. 현재 LLM 관련 과제를 수행하고 있으며, 작년에는 LLM 프로젝트를 진행했고, 올해부터는 LLM을 활용한 **에이전트 관련 과제**를 진행하고 있다. 

2. **제조업 환경과 LLM 적용의 필요성** 
  1. 발표자의 회사는 IT 회사가 아닌 공장이 있는 **제조업**이며, 제품 생산을 주 업무로 하지만 R&D, 시장 및 경쟁사 동향 파악 등 다양한 업무가 존재한다. 
  2. LLM 기술은 제조업 전반에 걸쳐 활용되고 있으며, 올해부터는 생산 현장, 마케팅(시장 조사), 연구 개발 등 **다양한 부서**에서 LLM 에이전트를 개발하여 업무에 사용하고 있다. 
  3. 내년에는 LLM 에이전트 관련 내용이 전사적으로 확장될 것으로 예상되며, 발표자는 회사 내 여러 부서의 **업무 효율 향상**을 위해 LLM 에이전트 관련 과제를 진행 중이다. 
  4. LLM은 비단 제조뿐만 아니라 IT, 금융권 등 거의 모든 회사에서 생산성 향상을 위해 도입을 검토하고 있다. 
  5. LLM 에이전트의 활용 예시는 다음과 같다. 
  1. **문서 작업 시간 단축**: 회사 업무 중 많은 부분을 차지하는 문서 작업을 LLM 에이전트를 통해 단축한다.
  2. **불량 문서 검색**: 생산 과정에서 불량 파악 시, 기존에는 문서를 일일이 찾아야 했으나, LLM 에이전트를 통해 사내 문서를 기반으로 질문에 답변하는 **챗봇 형태**로 활용한다.

3. **LLM 에이전트의 중요성 및 학습 권고** 
  1. 현재 거의 대부분의 회사에서 LLM 에이전트 적용 업무가 모든 분야에서 쓰이고 있다. 
  2. 데이터 사이언스나 관련 분야에 관심 있는 사람들은 LLM 에이전트를 필연적으로 공부하거나 알아두는 것이 좋다. 
  3. 과거 머신러닝/딥러닝처럼 모든 것을 직접 개발하기보다는, **프롬프트 엔지니어링**을 통해 시중의 LLM을 잘 활용하거나, **노코드 기반**으로도 LLM 에이전트를 개발할 수 있는 환경이 조성되고 있다. 


## 2. LLM의 기본 개념 및 종류 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/285.jpg)
1. **LLM의 정의 및 특징** 
  1. LLM은 방대한 텍스트 데이터를 학습하여 인간의 언어를 이해하고 생성하는 인공지능이다. 
  2. 주요 특징은 다음과 같다. 
  1. **대규모 학습**: 수십억 개의 데이터를 학습한 모델이다.
  2. **다양한 활용**: 정보 검색, 지식 기반 답변, 콘텐츠 생성, 질의응답 등 다양한 분야에 쓰일 수 있다.
  3. **확률 및 통계 기반**: 키워드 매핑이 아닌, 질문에 대해 확률적으로 가장 높은 단어들을 바탕으로 문맥에 맞는 자연스러운 문장을 생성한다.
  3. 일반적인 질의응답 구조는 다음과 같다. 
  1. 사용자 질문이 들어오면, **프롬프트** (예: "너는 유능한 전문가야", "이런 일을 수행할 거야" 등의 지시)와 함께 LLM에 입력된다.
  2. LLM은 입력된 질문과 프롬프트에 따라 답변을 생성한다.

2. **LLM의 종류 및 기업 활용 현황** 
  1. LLM은 크게 **사용 모델**과 **오픈소스 모델**로 나뉜다. 
  1. **사용 모델**: GPT-4, Claude, Gemini, Grok 등 일반적으로 많이 사용되는 모델이다.
  2. **오픈소스 모델**: Llama, Deep Q&A, Qwen, Koala 등 주로 회사에서 많이 사용된다.
  2. 회사에서 오픈소스 모델을 주로 사용하는 이유는 **보안 문제** 때문이다. 
  1. GPT-4나 Claude 같은 사용 모델을 사내에서 사용할 경우, API를 통해 질문과 문서 정보가 외부로 유출될 수 있다.
  2. 따라서 사내에서는 사용 모델 사용을 지양하며, LLM 애플리케이션을 직접 만들 때는 Llama나 Deep Q&A 계열의 오픈소스 모델을 주로 사용한다.


## 3. RAG (검색 증강 생성)의 필요성과 기본 구조 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/459.jpg)
1. **RAG의 정의 및 작동 방식** 
  1. RAG (Retrieval-Augmented Generation)는 기존 LLM이 답변을 생성하는 과정에서 **외부 문서**를 통해 질문과 관련된 정보를 LLM의 컨텍스트에 넣어 답변을 생성하는 구조이다. 
  2. RAG는 단순 프롬프트 외에도, 미리 인덱싱된 **문서 DB (벡터 DB)**를 활용한다. 
  3. 질문이 들어오면, 벡터 DB에서 질문의 의도에 가장 유사한 문맥들을 검색(Retrieval)하여, 이 문맥들을 LLM의 컨텍스트에 함께 넣어 답변을 생성한다. 

2. **RAG가 필요한 이유: LLM의 한계 극복** 
  1. LLM의 가장 큰 단점은 **환각 (Hallucination)** 현상이다. 
  1. LLM은 생성형 모델이자 확률 모델로서, 학습했던 데이터를 바탕으로 질문에 알맞은 답변을 생성한다.
  2. 하지만 사용자의 질문이 LLM이 학습하지 않은 데이터일 경우, 즉 **지식 컷오프(Knowledge Cutoff)** 이슈가 발생한다. 
  2. LLM 단독 사용 시 발생하는 문제점은 다음과 같다. 
  1. **최신 정보 반영 불가**: LLM이 학습한 기간 이후의 최신 정보에 대해 질문하면, 그럴듯하지만 정확하지 않은 답변을 생성한다. 
  2. **내부 도메인 지식 반영 불가**: 회사 내부 지식 같은 정보는 LLM이 알 수 없으므로, 이에 대해 질문하면 정확하지 않은 답변을 한다. 
  3. **실시간 정보 및 최신 이벤트 반영 필요**
  4. **지식의 불분명한 출처**
  3. 이러한 이슈를 해결하기 위해 LLM을 **파인 튜닝(Fine-Tuning)** 할 수 있으나, 이는 비용이 많이 들고 현실적으로 어렵다. 
  1. 파인 튜닝은 GPU 서버 자원이 많이 필요하며, 추론용 GPU보다 학습에 필요한 자원이 더 많다.
  2. 학습을 위해서는 **정제된 데이터**가 매우 많이 필요하다.
  3. GPU 비용이 비싸기 때문에 비용적인 측면에서도 부담이 크다.
  4. 따라서 LLM을 파인 튜닝하는 방법보다는 RAG 기술이 이러한 문제들을 해결하는 데 더 필요하다. 

3. **나이브 RAG (기본 RAG)의 구조 및 프로세스** 

1. **나이브 RAG의 정의**: 단순한 형태의 RAG를 말하며, 바닐라 RAG 또는 베이직 RAG라고도 불린다. 
2. **나이브 RAG의 조건**: 
  1. 검색을 **한 번만** 수행한다.
  2. **벡터 유사도**만 사용한다.
  3. 검색된 청크(Chunk)를 컨텍스트에 넣는다.
  4. RAG 관련 다양한 기법을 사용하지 않는다.
3. **RAG의 프로세스 단계**: 
  1. **문서 로드**: 문서를 불러온다.
  2. **청킹 (Chunking)**: 문서를 작은 조각으로 자른다.
  3. **임베딩 (Embedding)**: 잘린 문서를 임베딩 모델을 통해 벡터화한다.
  4. **벡터 DB 저장**: 벡터화된 문서를 벡터 DB에 저장한다.
  5. **질문 임베딩**: 사용자의 질문도 임베딩 모델을 통해 벡터화한다.
  6. **검색 (Retrieval)**: 질문의 임베딩 벡터와 벡터 DB 내 문서 벡터 간의 **유사도 기반**으로 가장 유사한 문맥을 갖고 온다.
  7. **답변 생성**: 사용자의 질문, 검색된 문맥(컨텍스트), 프롬프트가 LLM에 함께 들어가 답변을 생성한다.


## 4. RAG 구현을 위한 핵심 구성 요소 (인덱싱, 청킹, 임베딩, 벡터 스토어) 


### 4.1. 사전 단계: 인덱싱 (Indexing) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/832.jpg)
1. **인덱싱의 정의**: 선택된 데이터 소스에서 필요한 데이터를 수집하는 작업이다. 
2. **주요 작업 문서 형태**: PDF, 워드, 엑셀, 마크다운, HTML 등 다양한 문서 형태가 있으며, 회사에서는 주로 PDF, 워드, 엑셀을 많이 사용한다. 
3. **문서 처리 방식 (예시)**: 발표자의 회사에서는 PPT 문서를 PDF로 변환한 후, 다시 마크다운 형태로 바꿔 LLM에 넣는 방식을 사용한다. 
4. **로더 (Loader) 활용**: RAG 구현 시 랭체인(LangChain)이나 라마 인덱스(LlamaIndex) 기반의 프레임워크를 사용할 수 있으며, 발표자는 랭체인 기반으로 설명한다. 
  1. 랭체인에는 PDF, CSV, HTML, JSON, 텍스트, 웹 문서 등 다양한 형태의 문서를 다룰 수 있는 **로더 함수**들이 이미 만들어져 있다. 
  2. 이 로더 함수들은 모두 동일하게 랭체인의 **도큐먼트(Document)** 객체로 생성되는 특징이 있다. 


### 4.2. 청킹 (Chunking) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/927.jpg)
1. **청킹의 정의 및 필요성**: 텍스트를 작은 단위로 나누는 과정이며, 효율적인 정보 검색을 위해 필수적이다. 
  1. 문서의 특징이 다르기 때문에, 워드 한 페이지에 있는 수백 개의 문자를 한 번에 넣지 않고 관리하기 편하게 조각으로 분할한다. 
  2. 문맥을 유지하며 텍스트를 처리하고, 특히 LLM이 처리하기 적합한 크기로 문서를 분할한다. 
2. **LLM 컨텍스트 사이즈와의 관계**: 
  1. LLM 모델마다 한 번에 입력할 수 있는 **컨텍스트 사이즈**가 정의되어 있다.
  2. 모델의 크기(예: Llama 8B, 70B)가 클수록 컨텍스트 크기가 커진다.
  3. 너무 많은 양의 컨텍스트를 넣으면 LLM이 감당하지 못해 **맥스 토큰 에러(Max Token Error)**가 발생할 수 있다.
  4. 따라서 LLM이 처리하기 적합한 크기로 문서를 분할해야 한다.
3. **청킹 방법**: 
  1. Recursive Character Text Splitter, Character Text Splitter, Token Text Splitter, Semantic Chunking 등 다양한 방법이 있다.
  2. 일반적으로 **Recursive Character Text Splitter**와 **Semantic Chunking**을 가장 많이 사용한다.
  3. Semantic Chunking은 문맥의 의미론적 내용을 파악하여 청킹하는 방식이다.


### 4.3. 임베딩 (Embedding) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/1055.jpg)
1. **임베딩의 정의**: 문서, 문장, 단어 등 텍스트 데이터를 **고차원의 수치 벡터**로 변환하는 과정이다. 
  1. 우리가 보는 문자열(String)을 숫자로 바꿔야 LLM이 이해할 수 있다.
  2. 임베딩을 통해 텍스트의 **의미와 문맥 정보**를 포함할 수 있다. 
2. **임베딩 모델**: 일반적으로 사전 학습된 임베딩 모델을 사용하며, Open AI Embeddings, Multi-lingual E5 등을 많이 사용한다. 
3. **벡터의 종류**: 
  1. 임베딩은 보통 **댄스 벡터(Dense Vector)**를 의미한다.
  2. **스파스 벡터(Sparse Vector)**는 원-핫 벡터처럼 각 단어의 존재 유무를 0과 1로 표현하는 전통적인 텍스트 수치화 방법이다.
4. **임베딩의 필요성**: 
  1. 텍스트를 수치화로 변환하여 기계가 이해하도록 한다.
  2. 벡터 간의 유사도 계산을 통해 의미론적 내용을 포함하고 문맥적 관계를 파악할 수 있다.


### 4.4. 벡터 스토어 (Vector Store) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/1201.jpg)
1. **벡터 스토어의 정의**: 임베딩된 벡터를 저장하는 특정 데이터베이스 (흔히 **벡터 DB**라고 표현)이다. 
2. **주요 벡터 DB 종류**: Chroma, Faiss, Pinecone, Qdrant, Elasticsearch 등이 있으며, Chroma, Milvus, Pinecone, Faiss 등을 많이 사용한다. 
3. **일반 DB와의 차이점**: 
  1. 일반 데이터베이스는 정확한 키워드 매칭을 통해 데이터를 검색한다.
  2. 벡터 스토어는 임베딩된 벡터들의 **유사성**을 기반으로 데이터를 검색한다.
4. **벡터 스토어의 기능**: 
  1. 벡터 스토어는 유사도 검색을 할 수 있는 메소드를 제공한다.
  2. 이를 통해 사용자의 질문에 대해 벡터 스토어 내 문서/텍스트 중 가장 유사한 것을 확인할 수 있다.


## 5. RAG 파이프라인의 작동 원리 및 검색 기법 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/1298.jpg)
1. **RAG 파이프라인 모식도** 
  1. LLM의 기본 구조와 달리, 질문이 들어오면 바로 LLM으로 가는 것이 아니라 **리트리버(Retriever)**를 거친다.
  2. 리트리버는 벡터 DB (인덱싱, 임베딩을 통해 구축됨)로부터 사용자의 질문에 가장 유사한 내용을 검색하는 역할을 한다.
  3. 검색된 내용(컨텍스트)은 질문 및 LLM에 대한 지침(인스트럭션)이 포함된 프롬프트와 함께 LLM 컨텍스트에 들어간다.
  4. **프롬프트 예시**: "너는 주어진 컨텍스트를 통해 훌륭하게 답변하는 어시스턴트야", "답변 형태는 어떻게 해주고", "모르겠으면 모르겠다 답변해라" 등의 가이드를 줄 수 있다.

2. **리트리버의 구현 및 역할** 
  1. 벡터 스토어를 만들면 as_retriever() 메소드를 통해 바로 리트리버로 변환할 수 있다.
  2. 리트리버의 역할은 사용자의 질문에 대해 유사도 검색을 통해 가장 유사한 문맥을 갖고 오는 것이다.

3. **유사도 검색 방법** 
  1. **MMR (Maximal Marginal Relevance) 방식**: 
  1. 문맥의 유사성과 다양성을 동시에 고려하는 방식으로, 가장 일반적으로 많이 쓰인다.
  2. 예시: 질문에 대해 10개의 문서를 찾은 후, 최종적으로 2개를 반환하는 형태이다. (질문에 대해 무조건적으로 정해진 개수(K)의 컨텍스트를 반환한다.)
  2. **Similarity Score Threshold 방식**: 
  1. 사용자의 질문과 임베딩된 문서 간의 유사성을 판단하여, 특정 **임계치(Threshold)**를 넘는 문서들만 갖고 온다.
  2. 특징: 임계치가 너무 높게 설정되면, 질문에 대해 리트리벌된 결과가 아예 없을 수도 있다.

4. **다양한 리트리버 종류 (Advanced Retrieval)** 
  1. **앙상블 리트리버 (Ensemble Retriever)**: 댄스 벡터(임베딩)와 스파스 벡터(키워드 기반 임베딩, 예: BM25)를 같이 쓰는 하이브리드 검색 방법이다.
  2. **컨텍스트 리오더 (Context Reordering)**: LLM은 컨텍스트가 길어지면 중간 정보를 잘 파악하지 못하는 경향이 있어, 컨텍스트의 순서를 조정하는 방법이다.
  3. **Parent Document Retriever**: 청크들을 작게 검색한 후, 원래 전체 문서를 반환하는 리트리버이다.
  4. **Multi-vector Retriever, Self-query Retriever** 등 다양한 방식이 있으며, 문서 특징과 원하는 작업에 따라 일반적인 벡터 스토어 리트리버의 한계를 극복하기 위해 사용된다.

5. **프롬프트 구성 요소** 
  1. 프롬프트는 LLM에게 지시를 내리는 **인스트럭션**이 핵심이다. 
  2. **구성 요소**: 
  1. **Instruction**: LLM에게 지시를 주는 내용 (예: "QA 작업을 하는 어시스턴트", "답변은 한국어로 해라").
  2. **Question**: 사용자의 질문.
  3. **Context**: RAG의 경우, 리트리버를 통해 검색된 문서 내용.
  4. **Chat History**: 이전 대화 이력.
  5. **Few-shot Prompt**: 프롬프트에 질문과 답변의 예시를 몇 개 넣어주는 방식.
  3. 랭체인에서는 PromptTemplate, ChatPromptTemplate, FewShotPromptTemplate 등의 함수를 통해 프롬프트를 구성할 수 있다. 
  4. 특정 허브에 저장된 태스크별 프롬프트 예시를 가져와 사용할 수도 있다. 

6. **응답 생성 및 모델 선택** 
  1. 프롬프트를 LLM에 넣고 답변을 받는 과정이다. 
  2. 랭체인은 다양한 모델을 지원하지만, 회사에서는 보안 문제로 인해 상용 모델(GPT-4 등) 대신 **허깅 페이스(Hugging Face)의 오픈소스 모델**을 GPU 서버에 띄워 API 호출 방식으로 사용한다. 

7. **RAG 파이프라인 요약** 
  1. **인덱싱 단계**: 문서를 로드하고, 분할(청킹)하며, 임베딩 모델을 통해 벡터 DB를 구축한다.
  2. **RAG 파이프라인 (Retrieval & Generation)**:
  1. **Retrieval**: 벡터 DB를 통해 질문에 가장 유사한 문서를 검색한다.
  2. **Generation**: 검색된 컨텍스트가 프롬프트와 함께 LLM에 들어가 답변을 생성한다.
  3. 이 검색(Retrieval)과 생성(Generation) 과정을 **RAG 파이프라인**이라고 한다.


## 6. 나이브 RAG의 한계와 어드밴스드 RAG 기법 


### 6.1. 나이브 RAG의 주요 한계점 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/1915.jpg)
1. **청크 사이즈 고정으로 인한 문맥 단절**: 
  1. 청크 사이즈가 고정되면 문서 형태가 상이할 때 문맥이 잘리는 경우가 발생한다.
  2. 이로 인해 LLM에게 전달되는 컨텍스트가 불완전할 수 있다.
  3. **해결 방안**: Parent Document Retriever와 같은 방법을 통해 해결할 수 있다.
2. **단일 벡터 검색의 한계**: 
  1. 단순 댄스 벡터(임베딩)만으로는 검색 정확도에 한계가 있다.
  2. 질문의 의도와 다른 과거 데이터가 검색될 수 있다.
  3. **해결 방안**: 댄스 벡터와 BM25(키워드 기반 임베딩, 스파스 벡터)를 같이 고려하는 **하이브리드 검색 (앙상블 리트리버)**을 사용한다.
3. **쿼리-문서 매칭의 한계**: 
  1. 단순 유사도 기반 매칭은 정확도에 한계가 있어, 사용자의 의도와 다른 문서가 검색될 수 있다.
  2. **해결 방안**: **HyDE (Hypothetical Document Embedding)** 기법을 사용한다.
  1. HyDE는 쿼리(질문)와 문서 매칭 대신, **문서와 문서**를 매칭하는 개념이다.
  2. 사용자의 질문에 대해 LLM이 **가상의 문서(Hypothetical Document)**를 생성한 후, 이 가상 문서와 벡터 DB 내의 문서들을 매칭하여 RAG를 수행한다.
4. **사용자 질문의 불충분성 (Query Rewriting 필요)**: 
  1. 사용자들이 질문을 상세하게 하지 않고 단어로만 질문하는 경우가 많아, LLM 에이전트의 목적과 질문 수준이 다를 수 있다.
  2. **해결 방안**: 사용자의 질문을 좀 더 풍부한 표현으로 바꾸는 **Multi-query Retriever**나 **RAG-Fusion** 같은 방법을 사용할 수 있다.
5. **검색된 컨텍스트의 노이즈 문제**: 
  1. MMR 방식 등으로 여러 개의 컨텍스트를 가져와도, 그 안에 질문과 상관없는 노이즈가 섞여 있을 수 있다.
  2. 노이즈가 섞인 컨텍스트는 LLM의 성능 저하를 유발한다.
  3. **해결 방안**: **리랭킹 (Reranking)** 방법을 통해 리트리벌된 컨텍스트를 한 번 더 압축하고 순위를 매겨 노이즈를 제거한다.
6. **로스트 인 더 미들 (Lost in the Middle) 현상**: 
  1. LLM이 긴 컨텍스트를 한 번에 입력받으면, 사람처럼 앞과 뒤만 보고 판단하고 중간에 있는 중요한 정보를 무시하는 현상이다.
  2. **해결 방안**: **Context Compression**을 통해 중요한 내용들을 문서의 앞뒤에 배치해야 한다.
7. **환각 및 근거 부족 문제**: 
  1. 검색된 문서 내용만으로도 LLM이 환각을 생성하거나 근거가 부족한 답변을 할 수 있다.
  2. **해결 방안**: **Self-RAG**나 **RAG-Trieve** 같은 방법을 사용할 수 있다.
8. **멀티모달 데이터 처리 불가**: 
  1. 회사 문서(PDF)에는 텍스트뿐만 아니라 **이미지, 테이블** 등 다양한 형태의 데이터가 섞여 있다.
  2. 텍스트 기반 LLM은 이미지나 테이블 정보를 추출하지 못한다.
  3. **해결 방안**: **멀티모달 RAG**가 필요하며, 비전(Vision) 기능을 포함하는 LLM (예: GPT-4)을 사용하여 한계를 극복할 수 있다.


### 6.2. 어드밴스드 RAG의 3단계 전략 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/2411.jpg)
어드밴스드 RAG는 나이브 RAG의 한계를 극복하기 위해 인덱싱, 프리-리트리벌, 리트리벌, 포스트-리트리벌 단계에서 다양한 기법을 조합하여 사용한다.

1. **프리-리트리벌 (Pre-Retrieval)**: 질문 자체를 변형시키는 단계이다. 
  1. **Query Rewriting (쿼리 리라이트)**: 사용자의 질문을 LLM 파이프라인의 의도에 맞게끔 의미를 보존하면서 변형한다.
  - 예시: "휴가"라는 단어만 입력했을 때, 에이전트가 "휴가 규정에 대해서 찾아줘"와 같은 형태로 질문을 변형한다.
  2. **Query Expansion (쿼리 확장)**: 하나의 쿼리가 아닌, 같은 의미지만 다양한 표현으로 여러 개의 쿼리를 생성하여 벡터 스토어에서 검색한다.
  3. **쿼리의 구조나 형식 변경**

2. **리트리벌 (Retrieval)**: 검색 방식을 개선하는 단계이다. 
  1. 단순 벡터 스토어 리트리버 외에 **앙상블 리트리버 (하이브리드 서치)**, **HyDE**, **Multi-query Retriever** 등 다양한 기법을 사용한다.

3. **포스트-리트리벌 (Post-Retrieval)**: 검색된 컨텍스트를 처리하는 단계이다. 
  1. **리랭커 (Reranker)**: 리트리벌된 컨텍스트에 섞인 노이즈를 제거하고, 질문에 대한 우수한 순위의 문서들을 남기기 위해 한 번 더 압축하고 랭킹을 매긴다.
  2. **컨텍스트 리오더 (Context Reorder)**: 로스트 인 더 미들 현상을 방지하기 위해 문서들의 순위를 바꾼다.


### 6.3. 인덱싱 단계의 개선 기법 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/2559.jpg)
1. **메타데이터 활용**: PDF 내의 메타데이터(페이지, 작성자, 날짜 등) 정보를 활용한다. 
2. **청킹 개선**: 
  1. Recursive Character Splitter 외에 **Semantic Chunking**을 사용한다.
  2. **Parent Document Retriever**: 작은 청크 단위를 임베딩한 후, 리트리벌 단계에서는 그 작은 청크를 포함하는 큰 컨텍스트(Parent Document)를 반환하여 문맥 단절 문제를 해결한다.


### 6.4. 어드밴스드 RAG의 일반적인 구조 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/2602.jpg)
일반적으로 어드밴스드 RAG는 **쿼리 리라이팅**, **하이브리드 서치**, 그리고 **리랭킹**까지 하는 구조를 많이 사용한다.


## 7. 멀티모달 RAG와 에이전트 워크플로우 (LangGraph) 


### 7.1. 멀티모달 RAG의 구현 및 활용 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/2901.jpg)
1. **멀티모달 RAG의 정의**: 텍스트뿐만 아니라 이미지, 표, 오디오, 비디오 등 다양한 데이터 형식을 통합적으로 검색하고 생성하는 시스템이다. 
2. **구현 방식**: 
  1. 멀티모달 임베딩을 사용하거나, OCR 기반으로 PDF 내 테이블과 이미지를 텍스트로 변환하여 사용할 수 있다.
  2. 발표자는 **멀티모달 LLM**을 하나의 파서처럼 사용하는 방식이 성능이 괜찮다고 언급했다.
3. **멀티모달 LLM 활용**: 
  1. 멀티모달 LLM에게 "너는 파싱하는 어시스턴트"라고 인스트럭션을 준다.
  2. 이미지나 테이블을 어떻게 파싱할지 지시하면, LLM이 이미지와 테이블 정보를 텍스트로 잘 추출한다.
  3. 추출된 텍스트 정보를 RAG 파이프라인에 넣어 멀티모달 RAG를 구현할 수 있다.


### 7.2. 모듈러 RAG와 LangGraph 기반 에이전트 워크플로우 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/3004.jpg)
1. **모듈러 RAG의 개념**: 
  1. 랭그래프(LangGraph) 프레임워크를 통해 구현되며, **에이전틱 워크플로우(Agentic Workflow)**라고도 불린다.
  2. 앞에서 설명한 다양한 RAG 기법들을 하나하나 모듈 형태로 만들어, 원하는 태스크에 따라 모듈처럼 띄었다 붙였다 할 수 있는 구조이다.
2. **LangGraph의 필요성 (단방향 RAG의 한계 극복)**: 
  1. 어드밴스드 RAG를 포함한 일반적인 RAG는 **단방향** 구조로, 리트리벌 결과가 만족스럽지 않아도 뒤로 돌아갈 수 없다.
  2. 랭그래프를 사용하면 **양방향**으로 체크가 가능하다.
  3. **자율적 평가 및 재시도**: 리트리벌된 컨텍스트를 LLM에 넣기 전에, "이 결과가 질문에 대해 진짜 맞아?"라고 평가하는 단계를 거친다.
  - 평가가 OK이면 LLM으로 패스하여 답변을 생성한다.
  - 평가가 실패하면 질문을 재작성한 후 다시 리트리벌을 시도할 수 있다.
3. **LangGraph의 특징 및 구조**: 
  1. 질문에 따라 벡터 DB를 여러 개 두거나, 웹 서치 같은 실시간 검색기를 통합하는 등 다양한 내부/외부 지식을 통합할 수 있다.
  2. 질문에 따라 라우팅(Routing)함으로써 프로세스를 그래프 형식으로 자연스럽게 만들 수 있다.
  3. **주요 용어**:
  1. **State (상태)**: 현재 상태값을 저장하고 전이시킨다.
  2. **Node (노드)**: 네모 박스나 세모 박스로 표현되며, 각각의 태스크 역할을 한다 (예: LLM 호출, 리트리벌 수행).
  3. **Edge (엣지)**: 노드들을 연결하며, **Conditional Edge**는 조건에 따라 분기 처리한다.
4. **에이전트 워크플로우의 장점과 단점**: 
  1. **장점**: 단방향이 아닌 양방향으로 갈 수 있으며, **자율성**을 부여한다. 다양한 툴(리트리벌, 웹 검색 등)을 파이프라인에 붙이기 편하다.
  2. **단점**: 일반적인 RAG보다 LLM 호출 횟수가 많아지고, 유지보수나 비용적인 측면에서 어려움이 있다.
5. **결론**: 단순 RAG뿐만 아니라 에이전트 RAG를 구현함에 있어서는 랭그래프 기반의 형태로 구현해야 한다. 


## 8. LLM 및 RAG 실습 코드 개요 


### 8.1. LLM 기본 구조 및 호출 (LangChain) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/3419.jpg)
1. **API 키 설정**: 실습을 위해 OpenAI API 키를 OS 환경 변수나 .env 파일에 설정해야 한다. 
2. **LLM 호출**: ChatOpenAI 함수를 통해 LLM을 호출한다. 
  1. 회사에서는 허깅 페이스의 오픈소스 모델을 GPU 서버에 띄워 API 호출을 사용한다. 
3. **기본 호출 구조**: 
  1. **System Message**: LLM 시스템에 전달하는 메시지로, LLM의 **페르소나(Persona)**나 인스트럭션(지시)을 정의한다.
  2. **Human Message**: 사용자의 질문(User Question)을 넣는다.
  3. LLM은 invoke 메소드를 통해 메시지를 받아 답변을 해준다.
4. **체이닝 (Chaining)**: 프롬프트와 LLM을 파이프 오퍼레이터(|)로 연결하여 체인링할 수 있다. 
  1. PromptTemplate 함수를 통해 템플릿을 정의하고, 변수(예: country)를 지정한다.
  2. 템플릿과 LLM을 연결하면, 키워드만 입력해도 사전 정의된 템플릿 안에서 답변이 생성된다.


### 8.2. 대화형 챗봇 구조 (Chat Prompt Template) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/3632.jpg)
1. **Chat Prompt Template**: 대화형 프롬프트 템플릿으로, 시스템, AI, 휴먼 메시지를 구분하여 정의할 수 있다. 
2. **메시지 포매팅**: 템플릿 안에 메시지를 포매팅할 때, 시스템 메시지, AI 응답 메시지, 사용자 입력 메시지 등으로 역할이 구별된다. 
3. **대화 이력 포함**: MessagesPlaceholder를 사용하여 시스템 메시지와 현재 사용자 입력 사이에 이전 대화 기록(Chat History)을 유연하게 넣을 수 있다. 


### 8.3. 프롬프트 엔지니어링 및 아웃풋 파서 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/3811.jpg)
1. **프롬프트 엔지니어링**: LLM을 잘 활용하기 위해서는 역할을 구조화하여 지침을 주는 것이 중요하다. 
  1. **트릭 활용**: 정답을 잘했을 때 상을 주거나, 답변을 못 할 때 페널티를 주는 내용을 쓸 수 있다. 
  2. **단계별 사고 유도**: Step-by-step 또는 Think step-by-step 같은 문구를 넣어 단계별로 생각하도록 유도한다. 
  3. **COT (Chain of Thought)** 형태도 많이 사용된다. 
2. **아웃풋 파서 (Output Parser)**: LLM의 답변 형태를 원하는 형태로 제한(포매팅)하기 위해 사용된다. 
  1. **Pydantic Output Parser**: Pydantic의 베이스 모델을 상속받아 출력 스키마를 정의한다. 
  - 출력 스키마(예: title, date, attendees)와 각 필드의 형태(예: string) 및 역할(description)을 지정한다.
  - 체이닝 시 프롬프트와 LLM 뒤에 파서를 연결하면, LLM의 답변이 정의된 스키마 형태(예: JSON)로 출력된다. 
  2. **다른 파서 종류**: Comma Separated List Output Parser (쉼표로 구분된 리스트 출력), String Output Parser, JSON Parser 등이 있다. 


## 9. RAG 구현 실습: 프리프로세싱 및 벡터 스토어 구축 


### 9.1. 임베딩 모델 설정 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/4141.jpg)
1. **임베딩의 역할**: 텍스트를 고차원 벡터로 변환하는 기술이다. 
2. **모델 사용**: 허깅 페이스 임베딩 모델을 다운받아 쓰거나, OpenAI Embeddings를 사용할 수 있다. 
  1. 발표자 회사에서는 허깅 페이스 임베딩 모델을 서버에 띄워 API 형태로 사용한다. 
3. **일반적인 모델**: 로컬 환경에서는 Multi-lingual E5 Small을 사용하지만, 리소스가 충분하다면 E5 Large나 BGE M3 같은 모델을 사용하는 것이 일반적이다. 


### 9.2. 도큐먼트 객체 및 로더 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/4212.jpg)
1. **도큐먼트 객체**: 랭체인 내의 객체로, **텍스트 콘텐츠**와 **메타데이터**로 구성된다. 
  1. **Content**: 문서의 텍스트 내용.
  2. **Metadata**: 문서의 소스, 페이지 번호, 작성자, 작성 날짜 등 사용자가 정의하기 나름인 정보.
2. **로더 종류**: PyPDFLoader, CSVLoader, DataFrameLoader, TextLoader, JSONLoader 등 이름이 직관적인 다양한 로더 함수가 존재한다. 
3. **로더 사용**: 특정 경로의 문서를 로더로 불러오면, 해당 문서가 도큐먼트 객체 형태로 로드된다. 


### 9.3. 청킹 (스플리터) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/4364.jpg)
1. **스플리터의 역할**: 긴 텍스트를 관리하기 쉬운 청크로 나누는 것이다. 
2. **Recursive Character Text Splitter**: 일반적으로 많이 사용되며, 시멘틱 청커보다 시간이 덜 걸린다. 
3. **주요 인자**: 
  1. **Chunk Size**: 청크의 길이.
  2. **Chunk Overlap**: 문맥 단절을 방지하기 위해 청크 간에 겹치는 부분을 설정한다 (일반적으로 청크 사이즈의 10~20% 사용).
4. **스플리터 사용**: RecursiveCharacterTextSplitter를 정의하고, 로드된 도큐먼트를 split_documents 메소드를 통해 잘라준다. 
5. **Semantic Chunking**: 임베딩 모델이 필요하며, 문맥의 의미론적 내용을 판단하여 청킹한다. 


### 9.4. 벡터 스토어 구축 및 관리 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/4524.jpg)
1. **벡터 DB 선택**: 로컬에서 사용하기 편한 것은 **Chroma**와 **Faiss**이다. 
  1. Faiss는 인메모리 방식이므로, 계속 사용하려면 반드시 저장을 해줘야 한다. 
2. **Chroma DB 구축**: 
  1. 청킹된 문서(docs)를 from_documents 메소드에 넣고, 임베딩 모델을 정의하며, 저장 경로를 지정하면 자동으로 벡터 DB가 생성 및 저장된다.
  2. similarity_search를 통해 벡터 DB 내에서 유사도 기반 검색을 수행할 수 있다. 
3. **벡터 DB 관리**: 
  1. **삭제**: 문서 ID나 메타데이터 기반으로 문서를 제거할 수 있다.
  2. **필터링**: 메타데이터를 활용하여 where 절과 같은 연산자를 통해 원하는 형태로 필터링하여 제거할 수 있다.
  3. **추가**: add_documents 메소드를 통해 도큐먼트 객체나 텍스트를 추가할 수 있다.
4. **Faiss DB 구축**: 
  1. from_documents로 DB를 만드는 방식은 Chroma와 동일하다.
  2. 다만, save_local()을 통해 지정된 경로에 명시적으로 저장해야 한다.
5. **표준화된 방식**: 벡터 스토어들은 랭체인의 도큐먼트 객체를 따르며, add_documents, add_text, 유사도 검색, 삭제 등의 방식이 표준화되어 있다. 


## 10. RAG 구현 실습: 리트리버 및 파이프라인 구성 


### 10.1. 리트리버 생성 및 검색 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/4791.jpg)
1. **리트리버 생성**: 벡터 스토어 객체에 as_retriever() 메소드를 사용하면 가장 간단하게 리트리버로 변환된다. 
2. **매개 변수**: 
  1. **검색 유형**: similarity (벡터 유사도), MMR (유사도와 다양성 고려), threshold (임계치 기반) 중 선택한다.
  2. **k (반환 문서 수)**: 반환할 문서의 수를 지정한다.
  3. **Threshold**: Similarity Score Threshold 방식 사용 시 임계치 값을 정의하며, 너무 높으면 검색 결과가 반환되지 않을 수 있다.
3. **검색 방식 비교**: 
  1. **Similarity (디폴트)**: 벡터 유사도만으로 검색한다.
  2. **MMR**: 유사도와 다양한 문서 주제를 반환하여 결과의 다양성을 높인다 (가장 많이 사용됨).
  3. **Similarity Score Threshold**: 스코어 기반으로 검색하며, 임계치에 따라 반환되는 문서 개수가 달라진다.


### 10.2. 나이브 RAG 파이프라인 구성 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/4941.jpg)
1. **파이프라인 단계**: 
  1. PDF 로드, 문서 분할(청킹), 임베딩, 벡터 스토어 구축.
  2. 리트리버 생성.
  3. 프롬프트 생성.
2. **체이닝**: 리트리버와 질문을 넣고, 질문에 따라 리트리버에서 검색된 컨텍스트가 프롬프트 템플릿에 들어간다. 
  1. 프롬프트 템플릿에는 컨텍스트와 사용자의 질문이 들어가며, LLM을 거쳐 답변이 생성된다.
  2. 답변 형태를 StringOutputParser로 지정할 수 있다.
3. **결과**: 체이닝된 파이프라인을 invoke하면, 인덱싱된 문서에 대해 가장 유사한 컨텍스트를 갖고 와 답변을 생성한다. 
4. **대안적 구현**: 프롬프트 템플릿을 만들어 체이닝하는 대신, 파이썬의 F-String을 통해 직접 프롬프트를 포매팅한 후 LLM에 넣어줘도 동일하게 답변을 얻을 수 있다. 


## 11. 어드밴스드 RAG 기법 및 멀티모달 RAG 실습 


### 11.1. 어드밴스드 RAG 테크닉 예시 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/5124.jpg)
1. **하이브리드 서치**: 앙상블 리트리버를 사용하여 댄스 벡터와 스파스 벡터를 결합한다. 
2. **멀티 쿼리 (Multi-Query)**: LLM을 통해 질문을 여러 개 생성하게 한 후, 여러 번 리트리벌을 수행하여 더 풍부한 컨텍스트를 얻는다. 
3. **디컴포지션 (Decomposition)**: 복합 질의(연쇄적으로 생각해야 하는 질문)를 분해한 후, 각각에 대해 답변을 하는 테크닉이다. 
4. **HyDE**: LLM이 질문에 대한 가상의 문서를 생성하여, 문서와 문서 간의 관계로서 답변을 생성하는 방식이다. 
5. **라우팅 (Routing)**: 여러 개의 벡터 DB가 있을 때, 쿼리에 따라 적절한 DB로 라우팅하는 기법이다. 
6. **리랭킹 (Reranking)**: 검색된 문서의 순위를 다시 매겨 노이즈를 제거한다. 
7. **모듈러 RAG**: 이러한 기법들을 하나하나 모듈로서 만들어 사용하는 것이다. 


### 11.2. 멀티모달 RAG 실습 (GPT-4 Vision 활용) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/5298.jpg)
1. **문제점**: 일반적인 PDF 로더는 PDF 내 이미지 정보를 가져오기 어렵다. 
2. **해결 방법**: GPT-4와 같은 비전이 가능한 LLM을 활용한다. 
3. **구현 단계**: 
  1. PDF를 이미지로 변환하는 코드를 사용한다.
  2. 변환된 이미지를 **Base64**로 인코딩한다 (LLM에 넣기 위함).
  3. LLM에게 "이미지 내용을 상세하게 설명하고, 테이블이나 다이어그램이 있으면 텍스트로 설명을 해라"고 프롬프트를 준다.
4. **결과**: 페이지별로 캡셔닝(설명)을 할 수 있으며, 멀티모달 LLM이 이미지나 테이블 정보를 텍스트로 잘 파싱하여 추출한다. 
5. **활용**: 파싱된 정보를 벡터 DB에 넣어 멀티모달 RAG를 구현할 수 있다. 


## 12. LangGraph 기반 에이전트 워크플로우 실습 


### 12.1. LangGraph 기본 구조 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/5534.jpg)
1. **LangGraph의 구성 요소**: 상태(State), 노드(Node), 엣지(Edge), 조건부 엣지(Conditional Edge)로 구현된다. 
2. **State 정의**: TypedDict를 상속받아 상태를 클래스로 정의하며, 노드 간에 메시지가 이어 나갈 수 있도록 add_messages 함수를 사용한다. 
3. **Node 정의**: 노드는 특정 태스크(예: LLM 호출)를 수행하며, Chatbot 노드는 스테이트의 메시지를 LLM에 넣어 답변을 받는다. 
4. **Graph 생성**: 
  1. StateGraph를 통해 그래프를 생성한다.
  2. add_node로 노드를 추가한다.
  3. add_edge로 시작(Start)과 끝(End)을 엣지로 연결한다.
  4. compile()하면 그래프가 완성된다.
5. **결과**: 단순 질의응답 구조도 랭그래프 형태로 구현할 수 있으며, 시각화하면 Start → Chatbot → End의 구조를 확인할 수 있다. 


### 12.2. RAG 에이전트 워크플로우 설계 (LangGraph) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/5703.jpg)
1. **RAG State 정의**: 메시지 외에 question, context, tool_calls, routing 등 RAG에 필요한 스키마들을 스테이트에 정의한다. 
2. **Tool 정의**: tool 데코레이터를 사용하여 리트리버 함수를 LLM이 사용할 수 있는 **툴**처럼 만든다 (예: 문서 기반으로 리트리벌 하는 툴). 
3. **노드 및 라우터 정의**: 
  1. 컨텍스트가 있는지 없는지에 따라 분기를 칠 수 있는 노드를 정의한다.
  2. 컨텍스트가 없으면 리트리벌 툴을 호출하여 컨텍스트를 가져오도록 한다.
4. **복잡한 구조 설계**: 
  1. 스테이트를 정의하고 노드를 만든 후, 시작점에서 라우팅을 통해 엣지를 연결한다.
  2. **양방향 구조**: 질문에 따라 리트리벌 툴을 호출하고, 그 결과(컨텍스트)가 충분한지 검증(라우팅)한다.
  - 성공하면 답변 생성으로 끝난다.
  - 불충분하면 질문을 재작성하여 다시 리트리벌 단계로 돌아가는 복잡한 구조를 설계할 수 있다.
5. **중요성**: 에이전틱 워크플로우는 단순히 한 방향이 아닌, **다양한 프로세스를 설계**할 수 있다는 장점이 있다. 


### 12.3. LangChain 에이전트 익스큐터 활용 (대안) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/d2dAe8ZhUXQ/5919.jpg)
1. **LangChain 에이전트**: 랭그래프 외에 랭체인 내의 AgentExecutor와 create_tool_calling_agent를 사용해서도 에이전트를 만들 수 있다. 
2. **툴 정의**: 웹 검색 툴(예: Google News 검색)과 내부 데이터 검색 툴(리트리버)을 정의한다. 
3. **에이전트 생성**: LLM과 툴들, 프롬프트를 create_tool_calling_agent에 넣어 에이전트를 만든다. 
4. **자율적 판단**: 
  1. 이 에이전트는 사용자의 질문에 따라 **자체적으로 판단**하여 어떤 툴을 호출할지 결정한다.
  2. 예시: PDF 기반 질문에는 내부 문서(리트리버)를 사용하고, 최신 동향 같은 질문에는 웹 검색 툴을 사용하여 답변한다.
5. **결론**: 이러한 구조도 랭그래프로 모두 구현 가능하며, 랭그래프를 사용하면 하나의 함수 구조보다는 **직접 워크플로우를 만들어** 핸들링하기 편하다.
