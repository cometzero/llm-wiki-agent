## 1. 하네스 엔지니어링의 이해와 중요성 [1]

하네스 엔지니어링은 AI 에이전트가 자율적으로 작업을 수행하도록 돕는 시스템 설계 방식이다.

### 1.1. 하네스의 정의 및 목적 [1]

하네스는 AI 에이전트의 자율 주행을 위한 장치이다. [1]

AI 에이전트가 한정된 컨텍스트 사이즈로 인해 많은 작업을 할 수 없을 때, 작업을 서브 에이전트 단위로 나누거나 다른 에이전트 페르소나를 만들어 리뷰시키는 등의 방식으로 자율 주행을 돕는다. [40]

사람의 개입 없이 AI 에이전트가 오랫동안 자율 주행하도록 돕는 것이 하네스의 핵심 특징이다. [41]

하네스는 개발 프로세스의 후반 단계에서 특히 강력하다. [41]

개발 프로세스를 네 단계로 나눌 때, 기획 및 구체화와 같은 앞 단계는 사람의 의도가 중요하므로 자율 주행의 의미가 적고 할루시네이션(환각)이 발생하기 쉽다. [42]

반면, 이미 잘 구체화된 기획을 바탕으로 구현하고 검증하는 뒷 단계에서 하네스는 강력한 성능을 발휘한다. [43]

따라서 하네스는 사람이 구체화한 기획을 AI가 틀림없이 구현하도록 돕는 세팅이다. [44]

### 1.2. 기획 구체화의 중요성 [46]

AI 개발의 성패는 기획 구체화에 달려있다. [50]

대부분의 경우, 서비스 기능에 대한 니즈가 충분히 구체적이지 않다. [50]

AI에게 "지금 구체화가 덜 된 포인트가 뭐가 있어?"라고 물어보면, AI가 빠진 부분을 지적해 주어 설계를 구체화하는 데 도움을 받을 수 있다. [51]

무엇을 만들지가 완전히 명확해진 상태가 '구체화가 충분히 되었다'고 볼 수 있다. [54]

'빡센 기획'은 AI의 오작동을 방지하고 효율을 높인다. [57]

기획 PRD 문서와 개발 문서를 자세하게 만드는 과정은 일반 사용자들이 건너뛰기 쉬우나, 이는 좋은 개발로 이어지지 않는다. [60]

AI에게 물어가며 구체화하면 어렵지 않게 기획을 명확히 할 수 있으며, 이는 AI가 정확히 결정된 바 없이 작업을 시작하여 의도와 다르게 결과물이 나오는 것을 방지한다. [63]

구체화가 잘 된 기획을 하네스가 '맛있게 요리'해 주는 역할을 한다. [67]

## 2. 하네스 구축을 통한 개발 및 검증 자동화 사례 [69]

하네스는 개발과 검증 과정을 자동화하여 사람의 개입을 최소화하고 효율성을 극대화한다.

### 2.1. 개발 자동화를 위한 하네스 설계 [70]

문서화를 통한 AI의 프로젝트 이해 및 구체화 [74]

잘 문서화된 기획을 AI에게 제공하여 프로젝트 기획, 디자인, 아키텍처 설계, 의도 등을 정확하게 파악하게 한다. [76]

개발 직전, AI가 구현을 위해 더 구체화해야 할 점을 사용자에게 질문하도록 하여 논의를 진행한다. [78]

사용자가 구현 계획 작성을 지시하면, AI는 여러 페이지로 나뉜 구현 계획을 작성하고 피드백을 요청하며, 이를 확정하면 테스트 및 페이지 파일들을 생성한다. [80]

오케스트레이터 스킬 파일의 활용 [83]

스킬 파일은 전체 흐름을 조율하는 오케스트레이팅 역할을 한다. [83]

스크립트 파일은 전체 페이지 수, 남은 작업, 시작 지점 등을 명시하여 여러 페이즈로 구성된 태스크를 관리한다. [84]

작업 중 멈추거나 오류가 발생하면, 스크립트는 원복 후 재실행할 수 있도록 복구 기능을 포함한다. [86]

스킬을 오케스트레이터로 사용하는 이유는 클로드 코드와의 자연스러운 연동 때문이다. [88]

기획, 디자인, 개발 구체화가 선행된 상태에서 클로드 코드와 대화를 많이 나눈 후 하네스를 호출하게 된다. [91]

스킬을 호출하면 구현 하네스가 바로 발동되므로, 클로드 코드에서 대화하다가 자연스럽게 호출하기 편리하다. [93]

요구 사항 구체화는 하네스화하기 어렵다. [100]

요구 사항 구체화는 변칙적인 일이며, 설계 단계는 정형화하기 어렵다고 느껴진다. [100]

일반 LLM 챗봇도 기획 구체화는 잘 도와주므로, 하네스는 양질의 컨텍스트를 쌓아둔 후 이를 빠짐없이 구현하기 위한 목적이다. [103]

태스크와 페이즈를 통한 작업 관리 [119]

태스크는 전체 작업을, 페이즈는 작업을 마치기 위한 여러 단계를 의미한다. [119]

보통 하나의 태스크에 10개 정도의 페이즈가 만들어지며, 20개 이상이 될 때도 있다. [121]

페이즈 작성 후 AI가 안정성 강화를 위한 테스트 추가 등 논의할 점이 생길 수 있다. [123]

파이썬 스크립트를 사용하여 각 페이즈를 독립적으로 실행한다. [130]

메인 세션의 컨텍스트를 보존하기 위해 구체적인 구현은 하위 일꾼 세션들에게 맡긴다. [131]

서브 에이전트를 사용하면 메인 에이전트가 순차 호출 책임을 담당하게 되므로, 이 책임을 스크립트 안에 넣어 효율화한다. [133]

반복 작업의 스크립트화와 메인 에이전트의 역할 분리 [137]

생각할 필요가 없는 반복 작업은 스크립트로 처리하여 효율을 높인다. [139]

스크립트화를 통해 매뉴얼대로 정석적인 작업이 반복적으로 수행되도록 한다. [142]

메인 에이전트는 사용자의 의도 파악, 변칙적인 대응, 상위 컨텍스트 유지에 집중한다. [143]

이러한 설계는 메인 에이전트의 컨텍스트를 보존하여 효율성을 극대화한다. [145]

버그 발생 시 메인 에이전트가 클리어한 컨텍스트로 최적의 대처 방안을 제시한다. [145]

구현 작업 완료 후에도 메인 에이전트의 컨텍스트 소모가 20% 미만으로 유지된다. [147]

이는 토큰 소모에 대한 문제를 해결하는 데 기여한다. [151]

테스트 케이스도 AI가 스스로 생성하고 계산하도록 설정한다. [153]

구현할 기능에 필요한 테스트 범위를 리스트업하고, 미리 정한 테스트 전략을 바탕으로 필요한 테스트 개수를 결정한다. [154]

AI가 애매하다고 판단하는 부분에 대해서는 사용자가 방향성을 잡아주어 테스트의 퀄리티를 높인다. [157]

### 2.2. 하네스 기반의 자동화된 개발 프로세스 [160]

구체적인 작업 계획 관리 [161]

작업 계획은 JSON 파일로 관리되며, 하위 단계와 상태 정보가 저장된다. [166]

root_index 파일에는 태스크에 대한 하위 단계, 단계 이름, 상태 정보가 저장된다. [168]

각 페이즈별 지침은 같은 폴더 경로에 저장되며, 독립적인 일꾼 세션들이 작업을 온전히 수행할 수 있도록 자기 완결적으로 작성된다. [170]

스펙 문서 참조 및 검증 방법 포함 [174]

스펙 경로에 작성된 문서들을 참조하고, 이전 페이지에서 생성되거나 수정된 내용을 잘 참조하도록 한다. [174]

구체적인 작업 지침과 검증 방법까지 포함된다. [175]

독립 세션에서의 페이즈 실행 [176]

각 페이즈 파일은 독립 세션에서 직렬로 실행된다. [176]

헤드리스 모드로 파이썬 스크립트 안에서 클로드 코드를 프로그램적으로 호출한다. [180]

각 페이지에 대해 서브 프로세스를 띄워 명령어를 호출하며, 페이지에 들어있던 작업 지침이 풀 프롬프트가 된다. [184]

AI 작업 시간 동안의 멀티태스킹 [188]

AI가 구현 작업을 수행하는 동안 사용자는 다른 작업의 구체화에 집중한다. [192]

사용자는 설계 및 코드 레벨까지 구체화하는 데 시간을 투자하고, AI에게 구현 작업을 맡긴다. [194]

여러 프로젝트를 병렬로 돌리기보다는, 구현된 것을 보고 실제로 사용하며 느끼는 점을 반영하기 위해 한 번에 많은 것을 병렬로 구현하지 않는다. [198]

일상에서의 멀티태스킹을 통해 여러 작업 병행이 가능하다. [201]

예를 들어, 30분 설계 후 AI에게 2시간 작업을 시켜놓고 다른 일을 하거나 식사를 한다. [201]

이는 오토파일럿 설계에 시간을 투자하고, AI가 구현하는 동안 다른 일을 처리하는 방식으로, 여러 작업을 병행할 수 있게 한다. [205]

## 3. AI 에이전트 기반의 풀 자동화 개발 및 AX 전략 [208]

### 3.1. GitHub PR 자동 생성 및 코드 리뷰 프로세스 [208]

AI 에이전트의 자동 커밋 및 풀 리퀘스트(PR) 생성 [216]

스크립트 내부에서 AI가 Git으로 커밋을 남기고, 최종적으로 풀 리퀘스트를 생성한다. [216]

PR에 포함된 커밋들은 모두 스크립트로 자동 생성된 것이다. [219]

코드 레빗을 활용한 자동 코드 리뷰 및 반영 [222]

오픈 소스 프로젝트의 경우 코드 레빗을 무료로 사용하여 PR 자동 리뷰를 수행한다. [222]

코드 레빗이 남긴 리뷰를 AI 에이전트가 자동으로 읽고 반영할 만한 리뷰를 반영한다. [227]

에이전트용 GitHub 계정을 만들어 리뷰 반영 후 "반영했습니다"라고 댓글을 달면, 코드 레빗이 "확인했습니다"라고 응답하며 완료 처리하는 시스템이다. [229]

코드 레빗은 다른 개발자의 시각에서 사소한 구현 개선점을 지적할 때가 있으며, 이러한 부분은 AI 에이전트끼리 알아서 처리하도록 한다. [238]

PR의 역할: 인간을 위한 보고서 및 검토 도구 [241]

PR은 풀 자동화된 상황에서 필수적이지 않지만, 인간인 사용자가 보기에 편리하다. [241]

PR은 문서이자 대화 내역을 커멘트 기능으로 보여주어 최종 검수자가 나중에 확인하기 좋다. [246]

AI 에이전트들이 유의미한 대화를 하고 있는지, 반영할 만한 것을 반영했는지 궁금할 때 인간이 검토하기에 편리한 형식이다. [254]

### 3.2. AI 팀 빌딩보다 중요한 인간의 암묵지 이식 [258]

기획 구체화는 인간이 주도해야 한다. [260]

AI 에이전트가 아이디어를 증폭시켜 많은 내용을 생성할 수 있지만, 서비스 오너는 결국 그 내용을 이해해야 한다. [263]

증폭된 내용을 이해하고 깎는 것보다, 구체화 단계에서 인간이 대화를 주도하며 의도에 맞게 미세 조정하는 것이 유리하다. [264]

따라서 구체화 토론은 에이전트에게 맡기지 않는다. [266]

AI 팀 매니지먼트 기능의 한계: 암묵지 전달의 어려움 [269]

클로드의 팀 매니지먼트 기능은 여러 에이전트가 다양한 관점에서 기획을 검토하여 더 좋은 결과를 도출하는 데 유용해 보일 수 있다. [271]

하지만 제품을 만드는 사람만이 아는 '암묵지'가 많다. [274]

예를 들어, 잠재 고객 인터뷰에서 느낀 뉘앙스 등은 AI에게 이식되지 않았지만, 제품 구체화 과정에서 사소한 판단에 큰 영향을 미친다. [274]

암묵지가 전부 전달되지 않은 상태에서는 에이전트 간의 토론이 건전하게 흘러갈 수 없다고 판단한다. [276]

대표의 개입과 암묵지 전달의 중요성 [278]

결국 대표의 개입과 암묵지가 들어가야 완벽하게 의도대로 설계된 제품이 만들어진다. [278]

초기 제품 개발 시 정량적으로 수집된 데이터가 부족하여, 어떤 설계가 좋은지 판단할 기준을 에이전트에게 넘겨주기 어렵다. [281]

암묵지는 살아있는 지식으로 계속 변동되는 컨텍스트이므로, 이를 에이전트에게 잘 넘겨 관리하는 것이 중요하다. [285]

### 3.3. 최종 머지 및 문서 업데이트 원칙 [287]

AI 에이전트의 자동 머지 [288]

PR 리뷰가 완료되면 AI 에이전트가 자동으로 머지(Merge)를 수행한다. [288]

이는 AI 에이전트를 개발자로 고용했다고 생각하고, 개발자가 머지를 직접 하는 것과 같은 맥락이다. [298]

사용자는 AI에게 "왜 필요한지"를 자세하게 설명하는 데 집중하여 이상한 것을 만들지 않도록 한다. [304]

정확도 컨트롤을 위한 문서 업데이트 원칙 [308]

테스크 작성 시 첫 번째 단계는 무조건 문서 업데이트이다. [311]

만들고 싶은 기능으로 인해 기존 문서가 변경되어야 하므로, 문서 업데이트 과정을 작업 시작의 첫 단계에 포함한다. [313]

모든 문서 업데이트 후 docs_diff 파일을 생성하여 변경된 정확한 내용을 스크립트로 취합한다. [315]

이후 페이지들에서 이 docs_diff 파일을 참조하여 작업으로 인해 문서가 어떻게 바뀌었는지를 계속 참조시킨다. [317]

docs_diff 파일은 변경된 내용을 명확히 기록한다. [323]

예를 들어, ADR 문서에서 삭제된 내용은 없고 특정 줄에 어떤 내용이 추가되었는지를 기록한다. [323]

스펙 드리븐 코딩 시 에이전트가 작업 계획을 제멋대로 해석하여 스펙과 어긋나게 구현할 우려가 있으므로, 스펙 변경 내용을 참조하도록 연결한다. [327]

서비스가 커지고 스펙 문서가 많아지고 길어질수록, 단순히 문서가 바뀌었다고 언급하는 것으로는 불충분하므로, 추가된 줄만 명시하여 강조한다. [332]

이는 에이전트가 변경된 기준을 파악하고 설계하는 데 도움을 준다. [338]

하네스는 AI의 길잡이 역할을 한다. [340]

하네스는 AI에게 길잡이 역할을 하며, 변경 사항을 트래킹하여 보여주는 형태는 매우 흥미롭다. [340]

토스에서 PM으로 근무했던 경험이 하네스 구축에 도움이 되었다. [343]

유능한 PM은 작업자들이 무엇을 고민해야 하는지 콤팩트하고 빠르게 알 수 있는 체계를 만드는 데 집중한다. [344]

이는 워커들이 의도와 맞지 않는 작업을 하지 않고, 할 작업을 명확하게 할 수 있도록 만드는 산업 공학적, 조직 관리적 접근이다. [346]

제한된 컨텍스트 리소스에서 필요한 정보만 전달하고, 판단 기준을 문서로 명시하여 길잡이 역할을 하는 것이 하네스에서 가장 중요하다. [349]

### 3.4. 코드 리뷰 하네스 사례 및 AX를 위한 데이터 전략 [350]

코드 리뷰 하네스의 필요성 및 작동 방식 [350]

코드 리뷰는 모든 팀에 필요하며, 가장 큰 병목 현상 중 하나이다. [355]

구현은 완료되었지만 리뷰를 받지 못해 머지하지 못하는 블로킹 이슈가 자주 발생한다. [356]

코드 리뷰를 최적화하면 체감 효용이 크다. [359]

코드 리뷰 하네스 작동 방식 [360]

요구 사항 구체화 및 아키텍처 설계는 여전히 사람이 수행한다. [361]

세션 포크를 통한 설계 의도 문서 및 ADR(Architectural Decision Records) 작성 [363]

충분한 컨텍스트가 쌓이면 동일한 세션을 복제(포크)하여 A, B 세션에서 다른 작업을 수행한다. [363]

포크된 세션에서는 의사 결정 근거를 담은 설계 의도 문서와 ADR 문서를 작성한다. [366]

ADR은 설계 결정 사항을 문서로 남겨 온보딩 개발자들이 조직의 의사 결정 기준을 알 수 있도록 돕는다. [367]

설계 의도 문서는 해당 작업 한정으로 자세히 작성되며, ADR은 공용 자산으로 관리된다. [373]

AI가 작성한 문서가 의도를 명확히 담지 못할 수 있으므로 사람이 검토해야 한다. [376]

문서 작성 세션 폐기 및 평가 기준 수립 [377]

문서 작성 과정에서 컨텍스트가 소모되므로, 포크했던 세션은 문서 작성까지만 하고 폐기하며, 결과물인 문서만 남긴다. [379]

원본 세션에서는 서브 에이전트를 사용하여 코드 리뷰 시 평가 기준을 만든다. [388]

이 서브 에이전트는 방대한 코드 컨벤션이나 ADR 문서에서 해당 작업과 관련된 내용만 골라내어 압축된 암묵지 역할을 한다. [400]

과거 의사 결정 기록 중 이번에 참고해야 할 것만 정리하는 역할을 한다. [414]

평가 기준을 활용한 구현 및 리뷰 퀄리티 향상 [416]

생성된 평가 기준을 구현 단계와 리뷰 단계에 동일하게 적용한다. [416]

코드 컨벤션이나 ADR을 적용하지 않거나 너무 방대하여 포커스가 어려운 문제를 해결한다. [417]

콤팩트한 문서를 만들어 리뷰 시 참고하게 하면 퀄리티가 훨씬 높아진다. [419]

이 서브 에이전트는 유사 RAG(Retrieval Augmented Generation) 역할을 수행한다. [427]

코드 리뷰 하네스 공개 및 AX(AI 전환) 지향점 [439]

마피아 코드 리뷰 하네스는 GitHub 공개 저장소에 공개되어 있다. [439]

클로드 플러그인으로 설치하여 사용할 수 있으며, 구체화가 완료되고 이후 플로우가 자동으로 진행되기를 원할 때 발동시킨다. [443]

PR까지 자동으로 생성해 준다. [448]

기업의 AX(AI 전환)를 위한 데이터 전략 [459]

개발자 교육보다 기업 자체가 유능하고 빠르게 움직이는 것이 더 큰 임팩트를 가진다고 생각하여 AX에 도전하고 있다. [461]

에이전트가 컨텍스트를 잘 구성하면 일을 잘하므로, 기업 내 비정형적으로 남던 데이터를 에이전트가 읽기 쉬운 파일 시스템과 데이터 스토리지로 구축하는 데 집중한다. [466]

데이터만 잘 있으면 복잡한 RAG 없이도 서브 에이전트만으로 웬만한 업무를 잘 수행할 수 있다. [470]
