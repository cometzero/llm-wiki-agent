## 1. LLM 추론 인프라와 토큰 경제학의 중요성 [1]

LLM(대규모 언어 모델)의 추론 인프라와 토큰 경제학은 모델의 효율성과 비용을 결정하는 핵심 요소이며, 특히 최근에는 모델 학습(training)보다 추론(inference)의 중요성이 더욱 커지고 있다.

### 1.1. 추론 인프라의 부상 배경 [8]

추론의 중요성 증대:

Claude Code나 Codex와 같은 모델의 등장으로 추론의 중요성이 훨씬 커졌다 [8].

코드를 실행할 때 긴 컨텍스트(context)를 끊임없이 변경하며 넣는 작업이 많아지고, 추론 토큰(reasoning token)도 많이 사용된다 [9].

GPT-5.5와 같은 모델에 긴 코드를 넣고 작업하는 워크로드가 상당하다 [10].

과거에는 모델 학습에 대한 논의가 많았으나, 이제는 추론이 훨씬 중요해진 시기가 도래했다 [12].

DeepSeek의 효율성 혁신:

DeepSeek은 컨텍스트가 커지더라도 연산(computation)과 메모리 사용을 매우 효율화했다 [18].

연산은 3분의 1, 메모리는 10분의 1로 줄였다 [19].

이러한 효율성은 에이전트(agent) 시대에 큰 의미를 가진다 [19].

하드웨어 발전과의 연관성:

엔비디아(NVIDIA)의 GPU는 모델 구동에 필수적이며, 연산 유닛 속도와 HBM(고대역폭 메모리) 용량이 지속적으로 발전하고 있다 [22].

GPU 간 통신, 랙(rack) 간 통신 등 인프라스트럭처 전반이 발전하고 있다 [24].

블랙웰(Blackwell) NVL72는 GPU 간 통신을 8개에서 72개로 확장했으며, 개별 GPU 메모리 용량도 80~100GB에서 192~288GB로 크게 증가했다 [26].

이러한 하드웨어 발전은 최신 모델 아키텍처에 직접적인 영향을 미치며, 모델의 성능 향상과 직결된다 [29].

GPT-4.5, Claude Opus 4.5/4.6 등 최신 모델들의 성능 변화는 이러한 하드웨어 출시 시기와 맞물려 설명될 수 있다 [30].

과거 1~2T(테라) 모델이 주류였으나, 최근에는 5T, 10T 모델이 등장하는 것도 하드웨어 발전 덕분이다 [34].

토큰 경제학의 복잡성:

입력 토큰(input token)과 출력 토큰(output token)의 가격 차이가 존재하며, 모델마다 가격 정책이 다르다 [51].

캐시(cache) 유지 시간에 따라 가격이 달라지며, 컨텍스트 길이에 따라 다른 가격 티어를 적용하기도 한다 (예: Gemini는 20만 토큰 이상에서 다른 가격 적용) [53].

이러한 가격 정책은 LLM 서빙 아키텍처와 하드웨어 간의 복잡한 관계에서 비롯된다 [54].

### 1.2. LLM 추론 시간 결정 요인: t_compute와 t_memory [57]

두 가지 핵심 요소:

LLM 추론 시간은 연산 시간(t_compute)과 메모리 접근 시간(t_memory) 중 더 오래 걸리는 쪽에 의해 결정된다 [57].

이 두 요소의 조합으로 현대 LLM 추론의 모든 가격이 결정된다 [59].

하드웨어와 모델의 상호작용:

AI 모델은 하드웨어의 그림자이며, 하드웨어 발전이 모델 발전을 이끌고, 모델이 하드웨어를 최대한 활용하기 위해 변화하기도 한다 [60].

MFU(Model FLOPs Utilization)는 GPU가 낼 수 있는 최대 연산 능력을 의미하며, GPU 활용률(utilization)은 실제 GPU가 작동하는 시간을 의미한다 [347].

많은 연산이 메모리 바운드(memory-bound)되는 경우가 많으므로 MFU를 100% 활용하기는 어렵다 [351].

MFU를 최대화하는 지점은 t_compute와 t_memory가 같아지는 지점이라고 가정한다 [353].

## 2. 트랜스포머(Transformer) 아키텍처와 추론 과정 [62]

LLM 추론의 핵심인 트랜스포머 아키텍처는 prefill과 decode 과정을 통해 토큰을 처리하며, 이 과정에서 KV 캐시(KV cache)가 중요한 역할을 한다.

### 2.1. 트랜스포머의 기본 구조 [62]

추론의 복잡성:

트랜스포머의 기본 구조, HBM, 어텐션(attention), 완전 연결 계층(fully connected layer), KV 캐시, prefill과 decode, 포워드 패스(forward pass) 등은 이해하기 어려운 개념들이다 [63].

다행히 추론은 학습(training)보다는 쉽다 [66].

트랜스포머 블록:

트랜스포머는 여러 개의 동일한 블록(예: DeepSeek V4는 61개)으로 구성되어 있으며, 토큰이 이 블록들을 순차적으로 통과하며 연산된다 [96].

각 블록은 어텐션(attention)과 MLP(Multi-Layer Perceptron) 블록으로 구성된다 [191].

최신 모델 아키텍처는 어텐션을 통해 메모리 사용을 줄이고 계산 속도를 높이는 방법과, MLP 블록을 효율화하는 방법에 초점을 맞춘다 [191].

잔차 연결(Residual Connection):

각 블록에서 나온 결과는 자기 자신에게 더해져 의미를 갱신하는 잔차 연결(residual stream)을 통해 흐른다 [181].

이는 정보가 블록을 통과하며 점진적으로 업데이트되는 중요한 메커니즘이다 [186].

### 2.2. Prefill과 Decode 과정 [74]

Prefill (선준비):

사용자가 긴 프롬프트(prompt)를 입력하면, 모델이 다음 토큰을 생성하기 위해 한 번에 병렬로 계산하는 과정이다 [74].

이때 KV 캐시가 생성된다 [75].

긴 입력 토큰(input token)에 대한 처리라고 생각할 수 있다 [87].

예를 들어, Claude Code에 천 줄짜리 코드를 넣는 것이 prefill 과정이다 [81].

Decode (토큰 생성):

prefill 과정 이후, 모델이 생성된 마지막 토큰을 기반으로 다음 토큰을 하나씩 추론하고 생성하는 과정이다 [76].

이 과정은 자기 회귀(autoregressive) 방식으로 진행된다 [106].

생성된 토큰이 다시 입력으로 들어가 다음 토큰을 예측하는 방식으로 반복된다 [120].

prefill과 달리, decode는 한 번에 하나의 토큰만 입력으로 들어간다 [315].

### 2.3. KV 캐시(KV Cache)의 역할 [75]

생성 및 저장:

prefill 과정에서 각 토큰마다 Q(Query), K(Key), V(Value)가 계산되며, Q는 한 번 사용 후 버려지지만 K와 V는 이후 토큰 생성을 위해 저장된다 [92].

트랜스포머의 각 블록마다 KV 캐시가 생성되어 저장된다 [98].

이는 나중에 다시 계산할 필요 없이 재활용될 수 있다 [172].

메모리 효율성 문제:

KV 캐시의 양은 입력 토큰의 길이와 블록 수에 비례하여 어마어마하게 많아질 수 있다 [100].

과거에는 KV 캐시를 모두 저장했지만, 최근에는 이를 압축하는 기법(예: MLA, sparse attention)이 중요해졌다 [153].

KV 캐시가 메모리에서 차지하는 비중이 매우 크다 [478].

QKV의 의미:

QKV는 트랜스포머 저자가 토큰 간의 연관성을 계산하기 위해 구조적으로 만든 일종의 편향(bias)이다 [141].

QKV의 철학적 의미를 깊이 이해하기보다는, 설계자의 의도라고 받아들이는 것이 좋다 [143].

### 2.4. 토큰화(Tokenization)와 임베딩(Embedding) [124]

토큰 ID:

입력된 단어는 토큰 ID(token ID)라는 고유한 일련번호로 변환된다 [124].

예를 들어, "Empowers"는 "em"(795번)과 "powers"(30132번) 두 개의 토큰으로 분리될 수 있다 [126].

어휘 크기(vocabulary size)는 모델이 가지고 있는 단어장의 크기를 의미한다 [128].

벡터화 (임베딩):

토큰 ID는 모델이 이해할 수 있는 벡터(vector) 형태로 변환되는데, 이를 임베딩(embedding) 또는 히든 스테이트(hidden state)라고 부른다 [130].

이 벡터는 모델 내부에서 맥락 정보가 섞여 계속 변화한다 [127].

MLP와 MoE:

어텐션을 통과한 벡터는 MLP(Multi-Layer Perceptron) 또는 FFN(Feed-Forward Network)을 통과한다 [161].

MLP는 벡터에서 정보를 추출하는 데 중요한 역할을 하며, 어텐션보다 더 큰 가중치를 가진다 [162].

MoE(Mixture of Experts)는 이 MLP 부분을 여러 개의 작은 전문가(expert)로 쪼개어 필요한 전문가만 활성화시키는 방식이다 [164].

이는 전체 파라미터 크기를 키우면서도 계산 효율성을 높이는 방법이다 [379].

DeepSeek V4의 경우 384개 전문가 중 6개만 활성화되는 스파스 MoE(sparse MoE) 방식을 사용한다 [166].

MoE의 '전문가'는 특정 지식을 담는 단위가 아니라, 토큰마다 다른 전문가를 지나갈 수 있는 계산 단위이다 [212].

## 3. LLM 서빙 하드웨어 아키텍처 [219]

LLM 서빙은 GPU, HBM, NVLink, NVSwitch 등 최신 하드웨어 기술을 기반으로 하며, 랙(rack) 단위의 통합된 인프라를 통해 효율성을 극대화한다.

### 3.1. 랙(Rack) 기반의 하드웨어 구성 [219]

랙의 중요성:

LLM 서빙은 데이터 서버 랙(rack) 단위로 구성된다 [220].

랙 내부에서는 GPU 간 통신이 NVLink나 NVSwitch를 통해 매우 빠르게 이루어진다 [223].

반면, 랙 외부로 통신할 때는 속도가 느려진다 [225].

따라서 가장 빠른 네트워크 안에서 처리를 완료하는 것이 중요하다 [227].

NVL72 시스템:

엔비디아의 블랙웰(Blackwell) NVL72는 72개의 GPU를 하나의 랙에 통합한 시스템이다 [26].

각 GPU는 192GB 또는 288GB의 HBM 메모리를 탑재하고 있다 [27].

NVL72 랙 하나는 약 20TB의 HBM 메모리를 가지며, CPU용 LPDDR5 메모리까지 합하면 총 40TB의 메모리를 갖출 수 있다 [28].

이러한 대규모 메모리는 5T 이상의 대형 모델을 서빙하는 데 필수적이다 [36].

AI 팩토리 데이터센터:

NVL72와 같은 시스템은 인피니밴드(InfiniBand)와 같은 고대역폭 네트워크를 통해 랙 간 연결되며, 수랭식 냉각 시스템을 갖춘 AI 팩토리 데이터센터를 구성한다 [248].

이는 어마어마한 비용이 들지만, 대규모 LLM 서빙을 위한 필수적인 인프라이다 [253].

### 3.2. GPU와 HBM의 역할 [233]

블랙웰 GPU:

블랙웰 GPU는 두 개의 다이(die)가 합쳐져 만들어지며, 노란색으로 표시된 HBM 메모리가 옆에 붙어 있다 [233].

GPU 두 개와 CPU 하나가 결합된 슈퍼칩(Superchip) 형태로 구성된다 [237].

CPU와 GPU 사이도 매우 빠르게 연결된다 [239].

이러한 구성은 하나의 슬롯을 형성하며, 이를 통해 72개의 GPU를 쌓을 수 있다 [240].

## 4. LLM 추론 시간 분석: Roofline Analysis [271]

LLM 추론 시간은 t_compute(연산 시간)와 t_memory(메모리 접근 시간)에 의해 결정되며, 배치 크기(batch size)에 따라 이 두 요소의 영향이 달라진다.

### 4.1. 추론 시간의 구성 요소 [283]

t_compute (연산 시간):

LLM이 결과를 내는 데 걸리는 시간 중 연산에 소요되는 시간이다 [284].

주로 어텐션 계산과 MLP 블록(또는 FFN) 계산에 걸리는 시간의 합이다 [289].

계산의 편의를 위해 MLP 블록만 고려할 경우, 활성화된 파라미터(active parameters)의 개수와 입력 토큰의 개수(배치 크기)에 비례한다 [298].

t_compute는 (배치 크기 * 활성화된 파라미터 수) / FLOPs(초당 부동소수점 연산 수)로 표현된다 [372].

t_memory (메모리 접근 시간):

LLM이 결과를 내는 데 걸리는 시간 중 메모리 접근에 소요되는 시간이다 [284].

모델의 전체 가중치(total weight)를 메모리에 로딩하는 시간과 KV 캐시를 로딩하는 시간의 합이다 [399].

t_memory는 (전체 파라미터 수 + 배치 크기 <em> 컨텍스트 길이 </em> 토큰당 바이트 수) / 메모리 대역폭으로 표현된다 [409].

HBM이 아무리 빠르더라도 GPU 옆에 있기 때문에 메모리 접근에 시간이 걸린다 [543].

### 4.2. 추론 배치(Batch)의 개념 [300]

학습 배치와의 차이:

학습(training)에서의 배치는 여러 문장을 한 번에 계산하기 위해 사용되며, 시퀀스 길이(sequence length)가 꽉 차 있다 [304].

추론(inference)에서는 사용자의 입력 길이(컨텍스트 길이)가 매우 다양하다 [314].

만약 학습과 동일한 방식으로 처리하면 패딩(padding)으로 인해 메모리 낭비가 심해진다 [319].

추론 배치의 최적화:

추론에서는 패딩을 없애고 여러 사용자의 요청을 이어 붙여 하나의 배치로 처리한다 [322].

이는 vLLM이나 SGLang과 같은 시스템에서 메타 레이어(meta layer)를 통해 각 토큰의 사용자 정보를 매칭하여 처리한다 [327].

사용자의 컨텍스트 길이(KV 캐시 덩어리)가 다양하므로, 이를 효율적으로 관리하는 것이 중요하다 [334].

PagedAttention과 같은 기술은 KV 캐시를 블록 단위로 나누어 포인터로 관리함으로써 메모리 낭비를 줄인다 [442].

GPU 활용률 극대화:

추론 배치를 최적화하는 가장 중요한 이유는 비싼 GPU 자원을 놀리지 않고 최대한 활용하기 위함이다 [341].

GPU 활용률을 70~80% 이상으로 유지해야 경제성을 확보할 수 있다 [346].

하나의 GPU가 수천 명의 사용자를 동시에 서빙할 수 있도록 스케줄러(scheduler)와 오케스트레이션 레이어(orchestration layer)가 작동한다 [330].

이는 마치 하나의 열차에 다양한 승객(사용자)의 워크로드(요청)를 동시에 태워 보내는 것과 같다 [358].

Prefill 요청이 길어지면, decode 요청을 하는 사용자들은 밀려날 수 있으므로, prefill 요청도 잘게 쪼개어(chunked prefill) 처리하는 등 다양한 최적화 기법이 사용된다 [364].

### 4.3. Latency(지연 시간) 그래프 분석 [561]

배치 크기에 따른 Latency:

x축은 배치 크기(batch size), y축은 지연 시간(latency)을 나타낸다 [561].

t_compute는 배치 크기에 비례하여 선형적으로 증가한다 [563].

t_memory는 모델 가중치 로딩 시간(상수)과 KV 캐시 로딩 시간(배치 크기에 비례)의 합으로 구성된다 [564].

배치 크기가 작을 때는 메모리 바운드(memory-bound)되고, 배치 크기가 커지면 연산 바운드(compute-bound)된다 [561].

모델 가중치 로딩 시간은 기본적으로 소요되는 시간이므로 지연 시간 하한선(latency lower bound)을 형성한다 [567].

### 4.4. 토큰당 비용(Cost per Token) 그래프 분석 [574]

배치 크기에 따른 비용:

x축은 배치 크기, y축은 토큰당 비용을 나타낸다 [574].

t_compute와 t_memory를 배치 크기로 나눈 값으로 토큰당 비용을 계산한다 [576].

배치 크기가 작을 때는 토큰당 비용이 매우 높고, 배치 크기가 어느 정도 커지면 연산 바운드에 의해 비용이 결정된다 [596].

이 그래프를 통해 최적의 배치 크기(optimum batch size) 지점을 찾을 수 있다 [601].

경제성 분석:

이러한 분석은 LLM 서비스 제공자들이 토큰당 가격을 책정하고, 인프라의 경제성 및 수율을 개선하는 데 활용된다 [604].

프론티어 랩(frontier lab)들은 이러한 분석을 통해 API 가격을 책정하며, 이는 그들의 토큰 경제학(token economics)을 보여주는 지표가 된다 [776].

## 5. 최적 배치 크기 추정 및 토큰 경제학 [610]

최적의 배치 크기는 연산 시간과 메모리 접근 시간이 균형을 이루는 지점에서 결정되며, 이는 스파시티(sparsity)와 하드웨어 성능에 따라 달라진다.

### 5.1. 최적 배치 크기 계산 [610]

균형점 가정:

처리량(throughput)을 최대화하는 지점은 연산 시간과 메모리 접근 시간이 같아지는 지점이라고 가정한다 [618].

이 가정을 통해 최적의 배치 크기를 계산할 수 있다 [620].

수식 기반 추정:

메모리 대역폭 / FLOPs와 활성화된 파라미터 수 / 전체 파라미터 수를 이용하여 배치 크기를 추정한다 [623].

활성화된 파라미터 수 / 전체 파라미터 수는 스파시티(sparsity)를 의미한다 [636].

하드웨어 발전에도 불구하고 FLOPs / 메모리 대역폭의 비율은 약 300으로 유지된다고 추정한다 [647].

따라서 배치 크기 = 300 * (1 / 스파시티)로 계산할 수 있다 [655].

예를 들어, 스파시티가 1/8인 경우 최적 배치 크기는 300 * 8 = 2400이 된다 [657].

스파시티의 중요성:

스파시티를 높이면 배치 크기를 높게 가져갈 수 있으며, 이는 단위 시간당 더 많은 사용자를 서빙할 수 있음을 의미한다 [677].

GPU 자원과 전기세가 고정되어 있으므로, 더 많은 사용자를 서빙하는 것이 서비스 제공자에게 이익이다 [679].

### 5.2. 20ms 연산 사이클과 Drain Time [687]

연산 사이클:

LLM 추론은 한 번의 연산 사이클(클럭)이 약 20밀리초(ms) 정도 소요되도록 조정된다 [692].

이 시간 동안 배치를 채워 연산을 수행하고 결과를 도출한다 [693].

Drain Time:

드레인 타임(drain time)은 HBM 메모리가 전체 데이터를 한 번 읽어내는 데 걸리는 시간이다 [708].

GB300 기준으로 288GB HBM과 20TB/s 대역폭을 사용하면 약 15ms가 소요되며, 최신 GPU는 15~20ms, 구형 GPU는 40ms 정도이다 [709].

이 드레인 타임을 기준으로 연산 사이클을 20~30ms로 설정한다 [716].

### 5.3. LLM 서빙 최적화 기술 [722]

vLLM과 SGLang:

vLLM과 SGLang과 같은 기술들은 20ms 연산 열차에 최적의 배치(2400~3000)를 꽉 채워 보내기 위한 다양한 최적화 알고리즘을 포함한다 [730].

PagedAttention은 배치별로 다른 KV 캐시 길이를 효율적으로 관리하여 메모리 용량을 줄이고 연산을 최적화한다 [740].

Chunked Prefill은 긴 prefill 요청을 잘게 쪼개어 다른 요청들과 함께 처리함으로써 GPU 활용률을 높인다 [736].

프론티어 랩의 핵심 역량:

이러한 엔지니어링 인프라 기술은 프론티어 랩(frontier lab)들의 핵심 자산이자 경쟁 우위(moat)이다 [753].

하드웨어를 잘 이해하고 사용자 워크로드를 효율적으로 관리하여 서빙 처리량(throughput)을 늘리는 것이 매우 중요하다 [755].

컨텍스트 길이에 따른 비용 차등:

짧은 컨텍스트 길이의 워크로드(예: "안녕하세요")는 더 많은 사용자를 동시에 처리할 수 있어 비용이 저렴하다 [757].

긴 컨텍스트 길이의 워크로드(예: 코딩)는 처리할 수 있는 사용자 수가 줄어들어 비용이 비싸진다 [759].

최적점(optimal point)은 약 200K(20만) 컨텍스트 길이로 추정되며, 이를 넘어서면 GPU 클러스터가 메모리 바운드(memory-bound)되어 사용자 수를 현저히 적게 받아야 한다 [761].

이러한 이유로 Gemini와 같은 모델은 20만 컨텍스트 길이를 기준으로 가격 티어를 다르게 책정한다 [53].

### 5.4. 캐시(Cache) 전략과 비용 구조 [778]

캐시 계층:

사용자의 작업이 진행 중일 때는 KV 캐시가 HBM에 올라가 있어 빠른 처리가 가능하다 [778].

사용자가 잠시 자리를 비울 경우, HBM에서 캐시를 유지하는 것이 이익인 기간(예: 1분)이 존재한다 [781].

일정 시간이 지나면 캐시는 CPU 옆의 DRAM, 플래시 드라이브(flash drive), HDD 등으로 순차적으로 내려가며, 이 과정에서 접근 속도와 비용이 달라진다 [785].

최종적으로는 캐시가 만료되면 완전히 삭제된다 [787].

추론 인프라의 발전:

Claude Code나 Codex와 같은 모델의 등장으로 추론량이 폭발적으로 증가했으며, 컨텍스트 관리(context management)가 핵심 병목(bottleneck)이 되었다 [790].

툴 콜(tool call)을 통해 가져오는 정보도 모두 prefill해야 하는 데이터이므로, 컨텍스트 길이는 더욱 중요해진다 [792].

이러한 인프라 기술은 모델 학습과는 별개로, LLM 기술 발전의 중요한 요소이다 [793].

## 6. Dwarkesh의 학습 방법과 에피소드 마무리 [795]

Dwarkesh는 복잡한 주제를 깊이 있게 탐구하고 쉽게 전달하는 능력을 가지고 있으며, 그의 학습 방법은 플래시카드(flashcard)를 활용한 반복 학습이다.

### 6.1. Dwarkesh의 강연과 학습법 [795]

강연의 가치:

Dwarkesh와 Reiner Pope의 강연은 GPU 서빙 방식과 관련된 복잡한 개념들을 간단한 수식을 통해 이해할 수 있도록 돕는다 [272].

이 강연은 LLM 추론 인프라의 핵심을 파악하는 데 매우 유용하다 [274].

플래시카드 학습:

Dwarkesh는 스스로 플래시카드를 만들어 핵심 개념(예: forward pass 시간 방정식, t_compute 방정식, t_mem 방정식, latency 그래프)을 반복 학습한다 [802].

이는 복잡한 내용을 암기하고 이해하는 데 효과적인 방법이다 [816].

깊이 있는 탐구:

Dwarkesh는 인터뷰이 한 명을 만나기 위해 2주 동안 공부하는 등 깊이 있는 탐구를 통해 다른 누구도 못할 만한 질문을 해낸다 [860].

이러한 학습 태도는 그가 지식의 프론티어를 전진시키고 대중에게 쉽게 전달하는 데 기여한다 [856].

### 6.2. 에피소드 요약 및 시사점 [834]

복잡한 주제의 이해:

이번 에피소드는 LLM 추론 인프라와 토큰 경제학이라는 어렵고 복잡한 주제를 다루었으며, 청취자들에게 깊은 사고를 요구한다 [834].

이는 모델 학습보다 추론과 서빙 인프라의 중요성이 커지는 현 시점에서 매우 의미 있는 내용이다 [8].

하드웨어와 소프트웨어의 상호작용:

GPU, HBM, NVLink 등 하드웨어 발전이 모델 아키텍처와 서빙 효율성에 미치는 영향이 크다 [29].

vLLM, SGLang과 같은 소프트웨어 기술은 하드웨어 자원을 최대한 활용하여 추론 성능을 최적화한다 [732].

경제성의 원리:

토큰당 비용, 캐시 전략, 컨텍스트 길이에 따른 가격 티어 등은 LLM 서비스의 경제성을 결정하는 중요한 요소이다 [51].

서비스 제공자들은 GPU 활용률을 극대화하고 최적의 배치 크기를 찾아 비용 효율성을 높이려 한다 [346].
