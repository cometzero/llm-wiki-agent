## 1. 코딩 AI 모델의 최신 동향 및 주요 모델 분석 [1]

최근 코딩 AI 시장은 GPT-5.5, Claude Opus 4.7, DeepSeek V4 등 주요 모델들의 출시로 경쟁이 심화되고 있으며, 각 모델은 고유한 강점과 약점을 가지고 있다.

### 1.1. GPT-5.5: 복잡한 추론 작업에 강점 [20]

OpenAI의 새로운 선두 주자 [6]

GPT-5.5는 이전 모델인 Opus 4.5가 6개월간 시장을 선도했던 것과 달리, 특정 작업에서 다른 모든 모델보다 훨씬 우수하다고 평가된다. [9]

현재 SemiAnalysis의 일상 업무에 통합되어 사용되고 있다. [11]

가격 및 서비스 계층 [25]

API 가격은 입력 토큰 100만 개당 5달러, 출력 토큰 100만 개당 30달러로, GPT-5.4보다 2배 비싸고 Opus 4.7보다 약간 더 비싸다. [25]

우선순위(priority) 계층은 표준 요금의 2.5배로 제공되며, 이는 빠른 모드(fast mode)와는 다르다. [27]

빠른 모드는 "6배 가격에 2.5배 빠르다"와 같은 모호한 보장을 제공한다. [29]

우선순위는 "> 50 토큰/초 > 99% 시간"과 같은 구체적인 SLA를 제공한다. [30]

Opus 4.6 Fast만이 실제 인기를 얻었다. [31]

GPT-5.5 Pro 및 추론 수준 [34]

GPT-5.5 Pro는 과학 연구나 장기 추론 작업에 적합하며, ChatGPT 및 API를 통해서만 이용 가능하다. [34]

BrowseComp 및 FrontierMath에서 SOTA(State-Of-The-Art) 점수를 획득했으며, GPT-5.4 Pro와 동일한 가격으로 책정되었다. [36]

표준 및 Pro 모델 모두 xhigh, high, medium, low, non-reasoning 등 다양한 추론 수준을 제공하며, 이는 비용과 기능 간의 균형을 이룬다. [38]

토큰 효율성 [40]

GPT-5.5는 GPT-5.4보다 벤치마크 점수가 높으면서도 더 적은 토큰을 사용한다. [40]

이는 "토큰 효율적"이라는 개념으로, 작업당 비용이 토큰당 비용보다 더 중요한 지표가 될 것이다. [42]

Mythos는 토큰당 Opus보다 5배 비싸지만, 동일한 문제를 더 적은 토큰으로 해결할 수 있어 가격 인상이 상쇄된다. [43]

### 1.2. Claude Opus 4.7: 사용자 의도 파악 및 속도에 강점 [45]

Opus 4.7의 개선 사항 [46]

Opus 4.7은 Opus 4.6의 대체 모델로, 벤치마크 점수가 향상되었지만, 획기적인 변화는 아니다. [46]

빠른 모드가 아직 없어, 많은 엔지니어들이 속도를 위해 약간의 품질 저하를 감수하고 있다. [49]

일상적인 작업은 성공적으로 수행되며, 코드 편집이나 PR에 대한 비판은 주로 스타일, 접근 방식, 아키텍처 결정, 토큰 효율성(속도)에 관한 것이다. [52]

모델이 완전히 오작동하는 경우는 드물다. [54]

Opus 4.7의 주요 기능 및 동작 변화 [55]

고해상도 이미지 지원 및 프런트엔드 스타일링을 위한 스크린샷 사용을 포함하는 RL 훈련 목표의 명확한 증가가 있다. [56]

추론 노력 계층에서 "high"와 "max" 사이에 "xhigh" 추론 노력 옵션이 추가되었다. [57]

'사고 내용(Thinking content)'은 기본적으로 생략되지만, 토큰 비용은 여전히 부과된다. [58]

작업 예산(Task budgets) 기능(베타, API 전용)이 도입되어 모델이 작업을 효율적으로 완료하도록 제안받을 수 있다. [59]

새로운 토크나이저를 사용하여 토큰 계산이 업데이트되었으며, 이는 토큰 사용량을 최대 35% 증가시켜 가격 인상으로 이어진다. [60]

도구 사용 및 토큰 효율성 논란 [61]

Opus 4.7은 기본적으로 도구 호출을 덜 사용하고 추론을 더 많이 사용한다. [61]

Anthropic은 복잡한 작업을 위해 추론 노력을 "high"에서 "xhigh" 또는 "max"로 높여 도구 사용을 늘릴 것을 제안한다. [63]

이는 발표에서 주장된 토큰 효율성 절충과는 다르다. [65]

Opus 4.6 성능 저하 논란 [66]

Anthropic은 4.7 출시를 앞두고 4.6 모델의 성능을 의도적으로 저하시켰다는 비난을 받았지만, 이를 부인했다. [66]

그러나 SemiAnalysis의 여러 엔지니어들은 4.6 성능 변화로 인해 "약간 정신분열증을 느끼는" 경험을 했다고 독립적으로 언급했다. [67]

Anthropic은 4.7 출시 일주일 후인 4월 23일, 3월/4월에 발견된 세 가지 버그에 대한 사후 분석을 게시했다. [69]

이 버그들은 몇 주 동안 존재했으며, Claude Code 사용자 대부분에게 영향을 미쳤다. [70]

### 1.3. DeepSeek V4: 오픈소스와 긴 컨텍스트 윈도우 [76]

DeepSeek V4의 특징 [77]

DeepSeek V4는 V3보다 개선되었지만, 시장에 큰 충격을 주지는 않았다. [81]

가중치, 상세 기술 보고서, DeepEP, DeepGEMM, FlashMLA와 같은 업데이트된 라이브러리를 오픈소스화했다. [83]

DeepSeek-V4-Pro(1.6T/49B)와 DeepSeek-V4-Flash(284B/13B) 두 가지 모델이 포함된다. [85]

이 아키텍처들은 총 및 활성 매개변수 수 측면에서 폐쇄형 소스 모델에 비해 여전히 뒤처져 있다. [88]

주요 기술 발전: 1M 컨텍스트 윈도우 [90]

V4는 V3의 128k 컨텍스트 윈도우에서 1M 컨텍스트 윈도우로 확장되었다. [90]

긴 컨텍스트 성능에 중점을 둔 기술 발전은 다음과 같다. [91]

Compressed Sparse Attention (CSA) [93]

Heavily Compressed Attention (HCA) [94]

Manifold-Constrained Hyper-Connections (mHC) [95]

100만 토큰 컨텍스트 설정에서 DeepSeek-V4-Pro는 DeepSeek-V3.2에 비해 단일 토큰 추론 FLOPs의 27%, KV 캐시의 10%만 필요하다. [96]

벤치마크 및 실제 성능 [98]

DeepSeek은 표준 벤치마크가 실제 작업 능력을 잘 포착하지 못한다고 판단하여, 자체적인 에이전트 벤치마크를 도입했다. [98]

V4 Pro는 대부분의 작업에서 최고 모델들과 경쟁할 수 있지만, 특히 어려운 중국어 작문 작업에서는 Claude Opus 4.7에 뒤처진다. [100]

모델 성능 벤치마크에 대한 공개 발표는 실제 성능을 측정하는 데 신뢰할 수 없다. [102]

하드웨어 지원 및 추론 성능 [111]

DeepSeek은 NVIDIA GPU와 Huawei Ascend NPU를 모두 지원하는 Mega-Kernel을 DeepGEMM 내부에 오픈소스화했다. [111]

NPU 지원이 주장되지만, SM90(Hopper) 및 SM100(Blackwell) GPU용 코드만 공개되었다. [112]

매개변수 크기는 FP4에서 8x H20 HGX의 메모리 도메인 내에 들어간다. [114]

H200에서 FP81 성능으로 이 모델은 GPU당 약 150 tok/sec의 처리량을 달성하며, 8k 입력 및 1k 출력에서 20 tok/sec의 상호작용성을 보인다. [121]

V3는 동일한 조건에서 GPU당 약 1.3k~2.3k tok/sec의 처리량을 달성했다. [122]

결론 [126]

DeepSeek은 뛰어난 엔지니어링 성과를 보였으며, SOTA(State-Of-The-Art) 기술에 근접한다. [126]

폐쇄형 소스 모델에 대한 가장 저렴한 대안이 될 것이지만, 기능 면에서는 선두에 미치지 못한다. [127]

## 2. GPT-5.5와 Opus 4.7의 실제 사용 경험 및 벤치마크의 한계 [129]

GPT-5.5와 Opus 4.7은 각각 복잡한 추론과 사용자 의도 파악에서 강점을 보이며, 실제 사용 경험은 벤치마크 결과와 다를 수 있다.

### 2.1. GPT-5.5(Codex) vs Opus 4.7(Claude Code) 사용 경험 [129]

GPT-5.5(Codex)의 강점 [131]

Codex는 코드 변경 전에 많은 컨텍스트를 가져와 비 trivial한 '사고'를 요구하는 변경에 강하다. [135]

PR 검토, 버그 찾기, 기존 코드 설명, 문서 생성/수정 등 코드 구조 이해 및 추론에 뛰어나다. [136]

대시보드 생성 시 Claude보다 훨씬 정확한 데이터를 포함하여, 데이터 구조 및 관계에 대한 강력한 추론 능력을 보여준다. [151]

이는 Codex가 더 "스마트"하고 어렵고 좁은 범위의 작업을 해결하는 데 더 뛰어나다는 전반적인 인상과 일치한다. [154]

GPT-5.5(Codex)의 약점 [138]

Codex는 Claude Code보다 사용자의 진정한 의도를 추론하는 데 여전히 부족하다는 불만이 있다. [138]

사용자가 코딩 에이전트에게 간결하고 잘 정리되지 않은 지침을 제공할 때, Codex는 너무 문자적으로 해석하는 경향이 있다. [139]

코드 변경에 있어 너무 보수적이라는 의견도 있다. [140]

이는 토큰 효율성을 높이지만, 정확성을 희생할 수 있다. [141]

"narrow fix"라는 문구가 출력되면 모델의 작업을 다시 확인해야 하는 신호가 된다. [143]

대시보드 생성 예시에서, Codex는 기존 대시보드의 홈페이지를 완전히 무시했다. [148]

프롬프트에서 홈페이지를 복사하도록 명시적으로 요청했다면 Codex가 그렇게 했을 것이지만, 스스로 의도를 추론하지 못했다. [150]

Claude Code의 강점 [138]

Claude Code는 사용자의 진정한 의도를 추론하는 데 더 뛰어나다. [138]

개방형(open-ended)이고 새로운(greenfield) 문제에 더 적합하다. [154]

하이브리드 워크플로우 [155]

새로운 애플리케이션이나 기능에 대한 초기 계획/스캐폴딩 및 첫 구현/POC 단계는 Claude로 시작한다. [156]

실제 문제 해결이나 버그 수정은 Codex로 전환한다. [157]

GPT-5.5 출시 전에는 SemiAnalysis의 모든 팀원이 이 두 단계를 Claude Code로 수행했다. [158]

Codex의 기능적 한계 [160]

플러그인/CLI 기능이 Codex의 발목을 잡고 있다. [160]

많은 엔지니어들이 1M 컨텍스트를 가진 빠른 모드, 노트북에서 휴대폰으로 세션을 전환하는 원격 제어/샌드박스 플러그인, 대화 중 이미지/스크린샷 업로드를 선호한다. [161]

이 모든 기능은 Claude Code CLI, VSCode 플러그인, 웹 앱, 모바일 앱에서 가능하지만, Codex에서는 현재 불가능하다. [162]

GPT-5.5가 더 나은 모델일지라도, OpenAI는 Anthropic을 따라잡고 채택률을 높이기 위해 더 빠른 속도로 기능을 출시해야 한다. [164]

### 2.2. 벤치마크의 문제점과 활용법 [165]

벤치마크의 본질적인 한계 [165]

모든 새로운 모델 발표에는 다양한 벤치마크 성능을 비교하는 표가 항상 포함된다. [166]

새로운 모델의 "객관적인" 우수성을 증명하기 위해 소수의 숫자를 제시하는 것은 매력적이지만, 많은 AI 커뮤니티 구성원들은 벤치마크가 더 이상 실제 유용성을 측정하는 데 유용하지 않다고 지적한다. [168]

모델의 코딩/금융/추론 능력을 측정한다고 주장하는 것과 실제로 의미 있는 방식으로 측정하는 것 사이에는 큰 차이가 있다. [170]

그러나 모든 연구소는 미래 모델 출시에서 개선된 벤치마크 성능을 계속 강조할 것으로 예상된다. [171]

벤치마크의 구성 요소 [172]

각 벤치마크는 세 가지로 구성된다. [173]

작업(Tasks): 모델이 실제로 수행하도록 요청받는 것 [174]

평가 방법(The evaluation method): 모델이 실제로 점수를 매기는 방법 [175]

하네스(A harness): 작업을 해결하기 위해 모델에 제공되는 도구, 지침, 인터페이스 등 [176]

벤치마크의 품질을 판단하려면 처음 두 가지를 이해하는 것이 중요하다. [177]

MMLU 및 단순 답변 벤치마크 [180]

MMLU (Measuring Massive Multitask Language Understanding) [181]

2020년 학술 연구자들이 발표한 57개 주제에 걸친 15,908개의 객관식 질문 세트이다. [181]

표준화된 시험 및 대학 시험/문제 세트와 같은 온라인 소스에서 대학생들이 수동으로 수집했다. [182]

모든 질문은 정확히 4개의 보기를 가지며 공개적으로 이용 가능하며, 난이도는 "초급"부터 "고급 전문가"까지 다양하다. [183]

MMLU의 한계 및 해결 [185]

MMLU는 웹 검색과 같은 도구가 포함되지 않은 최소한의 하네스를 사용한다. [185]

객관식 형식은 채점을 쉽게 만든다. [187]

GPT-4가 2023년 3월 86.4%를 기록하며 사실상 "포화"되었다. [188]

벤치마크의 실제 최대 점수는 일부 작업이 모호하거나, 잘못 작성되었거나, 단순히 부정확하기 때문에 일반적으로 100%보다 낮다. [189]

한 논문은 MMLU 질문의 6.49%에 오류가 포함되어 있다고 추정한다. [190]

다른 유사 벤치마크 [191]

GSM8K: STEM 학위 계약자들이 만든 다단계 수학 문제로, 평가를 단순화하기 위해 모든 답변은 단일 숫자이다. [192]

HellaSwag: 일상 시나리오의 가장 가능성 있는 연속을 예측하도록 AI에게 요청하는 객관식 질문이다. [193]

MMMU: MMLU와 동일하지만 질문에 이미지가 포함되어 모델에 시각 능력이 필요하다. [194]

GPQA: 61명의 박사급 계약자들이 만든 "Google-proof" 객관식 과학 질문이다. [195]

벤치마크의 진화 [196]

각 벤치마크가 포화됨에 따라, 제작자들은 이전 버전에서 쉬운 질문을 필터링하거나, LLM을 사용하여 보기를 4개에서 10개로 늘리거나, 계약자에게 더 어려운 질문을 만들도록 비용을 지불하는 등의 전술을 사용하여 더 어려운 버전을 만들었다. [196]

Humanity’s Last Exam (HLE) [199]

2025년 1월 Scale AI가 발표한 가장 관련성 높은 단순 답변 벤치마크이다. [199]

대수 기하학부터 고전 발레에 이르기까지 2500개의 질문을 만들기 위해 전 세계 1000명 이상의 전문가를 고용했다. [200]

질문의 80%는 정확히 일치하는 짧은 답변을 요구하고 20%는 객관식이다. [201]

하네스의 경우, 웹 검색 및 코드 실행과 같은 도구를 사용하거나 사용하지 않고 모델을 실행할 수 있다. [202]

HLE의 문제점 및 활용 [205]

HLE 질문은 실제 LLM 사용을 대표하지 않으며, 문제점도 많다. [205]

한 연구에 따르면 HLE 화학/생물학 질문의 30%는 동료 검토 문헌과 직접적으로 상충되는 답변을 가지고 있었다. [206]

그러나 연구소들은 훈련의 RL 단계에서 이러한 벤치마크를 적극적으로 활용한다. [207]

Google은 2025년에 HLE 스타일 STEM 질문에만 9자리 예산을 책정했으며, 이는 Gemini 3 Pro가 벤치마크에서 획기적인 개선을 이룬 것과 무관하지 않다. [208]

HLE와 같은 난해한 객관식 질문을 해결하여 얻은 지식이 다른 사용 사례로 전이될 것이라는 긍정적인 설명과, 기업 VP들이 자신의 업무를 증명하기 위해 단일 숫자를 제시하려는 냉소적인 설명이 있다. [211]

SWE-bench 및 코딩 벤치마크 [213]

SWE-bench (2023년 출시) [214]

코딩은 가장 중요한 AI 기능이며, SWE-bench는 최초의 대규모 코딩 벤치마크이다. [214]

Django, scikit-learn, seaborn을 포함한 12개의 Python 저장소에서 자동으로 작업을 스크랩했다. [215]

작업 생성 과정은 3단계 필터링을 거쳤다. [216]

평가는 저장소의 모든 기존 테스트와 PR에 포함된 새로운 테스트를 사용한다. [221]

AI는 기존 테스트를 깨뜨리지 않고(pass-to-pass) 모든 새로운 테스트를 통과하면(fail-to-pass) 성공으로 간주된다. [222]

모델은 작업을 시도하는 동안 새로운 테스트를 볼 수 없다. [223]

하네스의 경우, 모델은 코드베이스를 검사할 수 있지만 실제 코드를 실행할 수는 없다. [224]

SWE-bench의 문제점 [225]

작업 생성 과정에서 사람의 검증이 없었다. [225]

GitHub 이슈는 종종 모호하고 불분명하게 지정된다. [226]

개발자들이 PR에 포함하는 테스트는 일반적으로 포괄적이지 않고 특정 구현 세부 사항에 맞춰져 있다. [227]

이로 인해 두 가지 큰 문제가 발생한다. [228]

문제 설명이 여러 솔루션을 허용하지만 테스트가 단일 올바른 솔루션에 맞춰져 있으면 일부 올바른 답변이 잘못 거부된다. [229]

테스트가 포괄적이지 않으면 AI가 요구 사항의 일부만 완료했더라도 잘못 통과시킨다. [230]

SWE-bench 작업 중 상당수가 고장 나 있었다. [231]

예를 들어, 한 작업은 문제 설명에 전혀 언급되지 않은 19단어 오류 메시지를 평가에서 완벽하게 일치시켜야 했다. [232]

SWE-bench Verified 및 Pro [234]

OpenAI는 2024년 8월 SWE-bench Verified를 출시하여 이러한 문제를 해결하려고 시도했다. [234]

93명의 Python 개발자를 고용하여 모든 작업 설명과 평가를 모호성/불공정성에 대해 수동으로 검토했다. [234]

문제가 있는 작업을 필터링한 후, 원래 2294개의 문제 중 500개의 "검증된" 작업만 남았다. [235]

OpenAI는 또한 AI가 코드를 실행할 수 있도록 하네스에 bash 도구를 추가하고, 각 작업을 Docker 컨테이너로 패키징하여 인프라 안정성을 개선했다. [236]

2026년 2월, OpenAI는 SWE-bench Verified에 대한 결과를 더 이상 보고하지 않겠다고 발표했다. [237]

o3가 지속적으로 실패한 138개 문제 중 절반 이상이 여전히 작업 설명에 언급되지 않은 특정 구현 세부 사항에 맞춰진 불공정한 평가 또는 작업 설명에 언급되지 않은 기능을 확인하는 추가 테스트를 가지고 있었다. [238]

모든 PR이 모든 모델의 훈련 데이터에 포함된 인기 있는 오픈소스 저장소의 일부였기 때문에, GPT-5.2, Opus 4.5, Gemini 3 Flash가 일부 답변을 암기했다는 증거를 발견했다("오염"). [239]

대신 모델 제작자들에게 SWE-bench Pro 결과를 보고하도록 권장했다. [240]

SWE-bench Pro는 Scale이 만든 또 다른 벤치마크로, 오염을 피하기 위해 덜 허용적인 라이선스를 가진 공개 저장소와 비공개 저장소를 사용했다. [242]

또한 계약자를 고용하여 커밋에 대한 평가 및 문제 설명을 작성했으며, GitHub 이슈 및 기존 PR에만 의존하지 않았다. [243]

이러한 모든 조치는 좋은 단계이지만, SWE-bench Verified에서 확인된 두 가지 문제를 완전히 해결하지는 못한다. [244]

어떤 벤치마크도 완벽하지 않다. [245]

다른 인기 코딩 벤치마크 [246]

SWE-bench Multilingual: SWE-bench Verified와 기본적으로 동일하지만 Python 외에 9개 언어를 포함한다. [247]

Terminal-bench: 터미널에서 가능한 모든 작업을 다루며, 작업과 평가는 크라우드소싱된다. [248]

NL2Repo: 인간 주석자들이 104개의 오픈소스 Python 저장소를 자연어 요구 사항 문서로 역설계했으며, AI의 작업은 문서를 기반으로 저장소를 재현하는 것이다. [249]

GDPval 및 비코딩 에이전트 벤치마크 [250]

GDPval (2025년 9월 OpenAI 출시) [252]

에이전트 AI는 오늘날 코딩을 훨씬 넘어 확장되며, 에이전트 벤치마크도 마찬가지이다. [251]

금융 분석가부터 간호사까지 44가지 직업에 걸쳐 실제 경제적으로 가치 있는 작업을 AI가 완료하는 능력을 측정하는 것을 목표로 한다. [253]

OpenAI는 각 직업의 전문가 계약자를 고용하여 작업당 세 가지를 제공하도록 요청했다. [254]

일반 텍스트와 함께 참조 파일을 포함할 수 있는 문제 설명 [256]

PDF, 스프레드시트, 비디오 등 다양한 형식의 결과물을 포함하는 문제에 대한 예시 솔루션 [257]

주어진 솔루션을 채점하는 방법을 설명하는 루브릭 [258]

GDPval의 하네스 및 평가 [259]

하네스는 코딩 벤치마크보다 한 단계 더 발전했다. [259]

에이전트는 표준 웹 검색 및 코드 실행 도구와 함께 LibreOffice(Microsoft Office 클론) 및 CAD 소프트웨어와 같은 앱에 액세스할 수 있다. [260]

최신 에이전트 벤치마크는 AI가 작업을 성공적으로 완료하기 위해 탐색해야 하는 가짜 캘린더, 이메일, Slack 메시지, Google Drive 등도 포함한다. [261]

각 작업을 평가하기 위해 OpenAI는 추가 전문가 계약자를 고용하여 AI 출력을 인간이 제공한 솔루션과 비교했다. [263]

루브릭을 사용하여 솔루션 순위를 매기는 AI 채점기도 만들었지만, 여전히 인간 전문가만큼 신뢰할 수 없다고 인정했다. [264]

이 때문에 더 느리고 비용이 많이 들더라도 공식 결과에는 여전히 인간 전문가를 사용한다. [265]

GDPval의 한계 [267]

"LLM-as-a-judge"는 객관적으로 검증할 수 없는 작업에 대한 다른 에이전트 벤치마크에서 인기 있는 기술이다. [267]

루브릭은 스타일과 같은 중요한 질적 특성을 측정할 수 있지만, 계약자나 AI가 작성한 루브릭의 품질을 보장하기 어렵다는 명백한 한계가 있다. [269]

LLM을 사용하여 품질을 평가하는 것도 본질적으로 의심스러우며, 특히 최종 결정을 내리는 인간이 없을 때 더욱 그렇다. [271]

GDPval의 또 다른 큰 한계는 명확하게 정의되고 부자연스럽게 지정된 프롬프트이다. [272]

실제 작업에는 일반적으로 이 벤치마크에는 없는 모호성 요소가 포함된다. [273]

인간의 작업은 피드백을 기반으로 한 반복을 포함하지만, GDPval은 엄격하게 단일 턴이다. [274]

다른 인기 에이전트 벤치마크 [275]

Apex Agents: Mercor 벤치마크로, 은행, 컨설팅, 법률에만 초점을 맞춘다. [276]

Finance Agent: 인간 전문가가 생성한 작업으로, 최근 SEC 서류 분석을 포함한다. [277]

BrowseComp: 계약자들이 만든 Google 검색이 어려운 질문들이다. [278]

OSWorld: LibreOffice, GIMP, VLC와 같은 앱을 사용하는 AI의 능력을 테스트하는 컴퓨터 사용 벤치마크이다. [279]

Tau-bench: 주문 취소 및 항공편 변경과 같은 작업을 수행하는 AI의 능력을 테스트하는 고객 서비스 벤치마크이다. [280]

OpenAI의 벤치마크 보고 방식 [281]

벤치마크는 측정하려는 능력을 광범위하게 대표하지 않는 경우가 많지만, 완전히 쓸모없는 것은 아니다. [282]

기업들이 보고하지 않는 벤치마크를 살펴보는 것도 의미 있는 정보를 제공할 수 있다. [284]

예를 들어, OpenAI는 GPT-5.4 발표에서 벤치마크를 거의 포함하지 않았고 Anthropic 모델과 비교하지도 않았다. [285]

이는 GPT-5.4가 한 달 전에 출시된 Opus 4.6에 비해 크게 뒤처졌을 것이기 때문으로 추정된다. [286]

GPT-5.5를 통해 OpenAI는 다시 선두에 올랐으며, 이 때문에 Claude와 Gemini가 벤치마크 표에 다시 포함되었다. [290]

그러나 여전히 의심스럽게 누락된 벤치마크가 있다. [292]

OpenAI는 2월에 SWE-bench Pro가 업계의 새로운 사실상 벤치마크가 되어야 한다고 주장하는 블로그 게시물을 작성했지만, 대신 "Expert-SWE" 벤치마크를 사용했다. [293]

블로그 게시물 하단에 따르면, GPT-5.5는 Opus 4.7에 뒤처졌다(Mythos는 77.8%를 기록). [295]

이는 GPT-5.5가 일부 코딩 작업에서 Opus 4.7보다 낫지만, 전반적으로 결정적으로 낫지는 않다는 질적 인상을 뒷받침한다. [299]

동일한 하네스를 사용한 비교의 문제점 [301]

SemiAnalysis는 GPT-5.5, 5.4, Opus 4.6에 대한 벤치마크를 자체적으로 실행했다. [302]

SemiAnalysis의 수치는 OpenAI 및 Anthropic보다 일반적으로 낮은데, 이는 두 연구소 모두 성능 향상을 위해 맞춤형 폐쇄형 하네스를 사용하고, SemiAnalysis는 비용 절감을 위해 대부분의 벤치마크에서 작업의 일부만 실행했기 때문이다. [304]

동일한 하네스를 사용하여 더 공정한 비교를 했다고 주장할 수 있지만, 하네스는 이제 제품의 일부이다. [307]

사람들이 실제로 관심을 갖는 것은 GPT-5.5 대 Opus 4.7이 아니라 Codex 대 Claude Code의 성능이다. [309]

하네스는 작업당 최종 비용에 큰 영향을 미친다. [310]

프롬프트 캐싱, 입력/출력 비율, 도구 사용 패턴은 모두 하네스에 의해 크게 결정된다. [311]

예비 분석에 따르면 Codex는 Claude Code보다 토큰 효율성이 더 높으며, 평균 입력/출력 비율이 80:1 대 100:1이다. [314]

입력/출력 비율이 높을수록 Mtok당 가격은 낮아지지만, Codex는 전체적으로 더 적은 입력 토큰을 소비하므로 여전히 더 저렴하다. [314]
