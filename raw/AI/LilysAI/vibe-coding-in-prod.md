## 1. 책임감 있는 프로덕션 환경에서의 바이브 코딩 [1]

바이브 코딩은 AI가 코드를 생성하는 것을 넘어, 개발자가 코드가 존재한다는 사실조차 잊고 제품 자체에 집중하는 개발 방식이며, 이를 프로덕션 환경에서 책임감 있게 활용하는 방법을 설명한다.

### 1.1. 바이브 코딩의 정의와 중요성 [12]

바이브 코딩은 AI를 활용해 코드를 생성하는 것을 넘어, 코드가 존재한다는 사실 자체를 잊고 제품에 집중하는 것을 의미한다 [12]

많은 사람이 바이브 코딩을 AI를 통한 코드 생성과 혼동하지만, 이는 AI와 긴밀하게 상호작용하며 코드를 검토하는 수준에 머무는 것을 의미한다 [13]

진정한 바이브 코딩은 Andre Carpathy의 정의처럼 "분위기에 완전히 몰입하고, 기하급수적인 발전을 받아들이며, 코드가 존재한다는 사실조차 잊는 것"이다 [18]

바이브 코딩은 비전문가도 앱을 개발할 수 있게 하여 코드 생성에 대한 관심을 높였다 [20]

코딩 지식이 없는 사람도 바이브 코딩을 통해 전체 앱을 직접 코딩할 수 있게 되었다 [22]

하지만 이는 API 키 사용량 초과, 구독 우회, 데이터베이스에 무작위 데이터 생성 등 예상치 못한 문제점을 야기하기도 했다 [25]

바이브 코딩의 성공 사례는 주로 버그가 발생해도 큰 문제가 없는 저위험 프로젝트(예: 비디오 게임, 재미있는 사이드 프로젝트)에 국한되었다 [26]

바이브 코딩에 주목해야 하는 이유는 AI의 발전 속도가 기하급수적이기 때문이다 [29]

AI가 수행할 수 있는 작업의 길이는 7개월마다 두 배로 증가하고 있으며, 현재는 약 1시간 분량의 작업을 처리할 수 있다 [30]

미래에는 AI가 하루 또는 일주일 분량의 작업을 생성할 수 있게 되므로, 개발자가 모든 코드를 일일이 검토하는 방식으로는 AI의 발전 속도를 따라갈 수 없다 [37]

따라서 이러한 기하급수적인 발전을 활용하기 위해서는 바이브 코딩을 책임감 있게 수용할 방법을 찾아야 한다 [39]

컴파일러의 발전 과정처럼, 개발자는 AI가 생성한 코드를 신뢰하는 방법을 배워야 한다 [40]

과거 개발자들이 컴파일러가 생성한 어셈블리 코드를 직접 확인했던 것처럼, 초기에는 AI가 생성한 코드를 모두 검토하려 할 수 있다 [41]

그러나 시스템이 복잡해지면 모든 코드를 검토하는 것은 불가능해지므로, 시스템을 신뢰해야 하는 시점이 온다 [43]

앞으로 소프트웨어 산업의 과제는 프로덕션 환경에서 바이브 코딩을 안전하게 수행하는 방법을 찾는 것이다 [45]

### 1.2. 코드는 잊되, 제품은 잊지 않는 바이브 코딩 [45]

코드는 잊어도 제품은 잊지 않는 것이 바이브 코딩의 핵심이다 [45]

컴파일러 비유처럼, 개발자는 어셈블리 코드를 직접 이해하지 못해도 좋은 소프트웨어를 만들 수 있다 [46]

이처럼 AI가 생성한 코드를 모두 이해하지 못해도 제품의 품질을 보장할 수 있는 수준에 도달해야 한다 [48]

관리자가 전문가의 작업을 검토하는 방식에서 바이브 코딩의 해답을 찾을 수 있다 [49]

CTO가 자신이 전문가가 아닌 분야의 전문가를 관리하거나, PM이 모든 코드를 읽지 않고도 엔지니어링 기능을 검토하거나, CEO가 회계사의 작업을 확인하는 것과 유사하다 [50]

이러한 문제들은 수백 년간 존재해 왔으며, 이미 해결책이 있다 [50]

CTO는 구현을 이해하지 못해도 인수 테스트를 작성하여 작업의 품질을 확인할 수 있다 [51]

PM은 코드를 직접 작성하지 않아도 제품이 예상대로 작동하는지 확인할 수 있다 [53]

CEO는 데이터의 핵심 부분을 스팟 체크하여 전체 재무 모델에 대한 신뢰를 구축할 수 있다 [54]

즉, 자신이 이해하지 못하는 구현을 관리하는 것은 문명만큼 오래된 문제이며, 모든 관리자가 이미 다루고 있는 문제이다 [55]

소프트웨어 엔지니어는 스택의 모든 깊이를 이해하는 데 익숙하지만, 생산성을 높이기 위해서는 이러한 세부 사항을 놓아줄 필요가 있다 [57]

안전하고 책임감 있는 바이브 코딩을 위해서는 구현을 알지 못해도 검증할 수 있는 추상화 계층을 찾아야 한다 [61]

현재로서는 기술 부채(Tech Debt)를 코드 검토 없이 측정하거나 검증할 좋은 방법이 없다는 한계가 있다 [62]

코드베이스의 리프 노드(Leaf Nodes)에 집중하여 바이브 코딩을 적용해야 한다 [69]

리프 노드는 다른 어떤 것도 의존하지 않는 코드의 최종 기능 부분을 의미한다 [70]

리프 노드에 기술 부채가 있더라도 다른 부분에 영향을 미치지 않으므로 큰 문제가 되지 않는다 [74]

반면, 시스템의 핵심 아키텍처나 기본 브랜치(트렁크)는 엔지니어가 깊이 이해하고 보호해야 할 부분이다 [75]

AI 모델의 발전으로 인해 미래에는 더 많은 스택 영역에서 바이브 코딩이 가능해질 것이다 [77]

## 2. 바이브 코딩 성공 전략: AI의 PM이 되고 검증 가능성을 확보하라 [80]

바이브 코딩을 성공적으로 수행하려면 AI의 제품 관리자(PM) 역할을 하고, 코드베이스의 리프 노드에 집중하며, 시스템의 검증 가능성을 확보해야 한다.

### 2.1. AI의 제품 관리자(PM) 역할 수행 [81]

AI(Claude)의 PM이 되어 AI가 성공할 수 있도록 필요한 지침과 맥락을 제공해야 한다 [81]

AI에게 "이 기능 만들어줘" 또는 "이 버그 고쳐줘"와 같은 간단한 요청만 하는 것은 신입 직원에게 충분한 정보를 주지 않고 작업을 맡기는 것과 같다 [83]

코드베이스에 대한 설명, 요구사항, 사양, 제약 조건 등 AI가 성공하는 데 필요한 모든 정보를 제공하는 것이 중요하다 [84]

AI와 함께 계획을 수립하고 충분한 정보를 담은 프롬프트를 작성해야 한다 [88]

발표자는 Claude와 기능 작업을 할 때 15~20분 동안 지침을 모아 하나의 프롬프트로 만든다 [88]

이 과정은 Claude와 대화하며 코드베이스를 탐색하고, 변경될 파일, 따라야 할 코드 패턴 등을 함께 계획하는 것을 포함한다 [90]

이렇게 충분한 정보를 제공하면 Claude의 성공률이 매우 높아진다 [94]

비기술적인 사람은 바이브 코딩을 통해 비즈니스를 구축하는 것이 위험할 수 있다 [96]

이는 AI의 효과적인 PM 역할을 할 수 없기 때문에 올바른 질문을 할 수 없기 때문이다 [98]

### 2.2. 실제 프로덕션 코드베이스에 바이브 코딩 적용 사례 [100]

Anthropic은 Claude가 작성한 22,000줄의 코드를 프로덕션 강화 학습 코드베이스에 성공적으로 병합했다 [100]

이 작업은 단순히 하나의 프롬프트로 이루어진 것이 아니라, 요구사항 도출, Claude 안내, 시스템 설계 등 며칠간의 사람의 노력이 투입되었다 [103]

개발팀은 Claude의 PM 역할을 충실히 수행했다 [105]

변경 사항은 주로 리프 노드에 집중되었으며, 핵심 부분은 사람의 철저한 검토를 거쳤다 [106]

변경 사항은 주로 가까운 미래에 변경될 가능성이 적은 리프 노드에 집중되어 기술 부채가 발생해도 문제가 없도록 했다 [106]

확장성이 중요하다고 판단된 핵심 부분은 사람의 집중적인 검토를 거쳤다 [107]

시스템의 검증 가능성을 확보하기 위해 스트레스 테스트를 설계하고 입출력을 명확히 했다 [108]

안정성을 위한 스트레스 테스트를 신중하게 설계했다 [108]

시스템이 사람이 쉽게 검증할 수 있는 입출력을 갖도록 설계했다 [109]

이를 통해 전체 구현을 이해하거나 읽지 않고도 정확성을 확인할 수 있는 검증 가능한 체크포인트를 만들었다 [110]

이러한 접근 방식을 통해 코드베이스의 다른 변경 사항과 동일한 수준의 신뢰를 얻으면서도, 시간과 노력을 크게 절약할 수 있었다 [114]

이 경험은 엔지니어링 방식에 대한 사고방식을 변화시켰고, 더 크고 많은 기능을 더 적은 비용으로 개발할 수 있게 했다 [115]

### 2.3. 책임감 있는 바이브 코딩을 위한 핵심 원칙 [121]

AI의 PM 역할 수행: AI가 성공할 수 있도록 필요한 모든 지침과 맥락을 제공해야 한다 [122]

리프 노드에 집중: 바이브 코딩은 핵심 아키텍처가 아닌 리프 노드에 적용하여 기술 부채가 발생해도 중요한 영역에 영향을 미치지 않도록 한다 [124]

검증 가능성 확보: 코드를 직접 읽지 않고도 변경 사항의 정확성을 확인할 수 있는 방법을 고민해야 한다 [125]

기하급수적 발전 수용: 현재는 바이브 코딩을 하지 않아도 괜찮지만, 1~2년 후에는 모든 코드를 직접 읽거나 작성하려 한다면 큰 불이익이 될 것이다 [126]

AI 모델이 대규모 작업을 생성할 수 있게 되므로, 이를 활용하지 못하면 병목 현상이 발생할 수 있다 [128]

## 3. 바이브 코딩 시대의 개발자 학습 및 생산성 [134]

바이브 코딩 시대에는 개발자가 AI의 PM 역할을 효과적으로 수행하고, AI 도구를 활용하여 빠르게 학습하며, 테스트 주도 개발 방식을 적용하여 생산성을 높이는 것이 중요하다.

### 3.1. 바이브 코딩 시대의 학습 방법 [134]

과거에는 구문 문제나 라이브러리 연결 등을 직접 해결하며 코딩을 배웠지만, 이제는 AI를 통해 학습 방식이 변화하고 있다 [134]

AI 도구를 사용하면 훨씬 빠르게 새로운 것을 학습할 수 있다 [139]

Claude와 코딩할 때, 모르는 라이브러리가 나오면 Claude에게 설명을 요청하고, 왜 그 라이브러리를 선택했는지 물어보며 학습할 수 있다 [140]

게으른 사람은 학습하지 못하겠지만, 배우고자 하는 의지가 있다면 AI는 훌륭한 학습 자원이 될 것이다 [143]

AI는 개발자가 더 많은 시도를 통해 고수준의 학습을 할 수 있도록 돕는다 [145]

시스템 엔지니어는 큰 아키텍처 변경의 결과를 파악하는 데 2년이 걸릴 수 있지만, AI를 통해 이 시간을 6개월로 단축하면 같은 기간 동안 4배 더 많은 교훈을 얻을 수 있다 [146]

### 3.2. AI에 정보 제공의 균형과 테스트 주도 개발 [147]

AI에 정보를 제공할 때, 너무 많거나 적지 않게 균형을 맞추는 것이 중요하다 [147]

구현 방식에 크게 신경 쓰지 않는 경우, 최종 요구사항만 전달한다 [150]

코드베이스를 잘 아는 경우, 사용할 클래스나 유사 기능 예시 등 구현 세부 사항을 더 깊이 설명한다 [151]

AI 모델은 과도하게 제약하지 않을 때 가장 잘 작동하므로, 엄격한 형식보다는 주니어 엔지니어에게 제공할 정보 수준으로 생각하는 것이 좋다 [154]

바이브 코딩 시 사이버 보안과 효과성의 균형을 맞추는 것이 중요하다 [158]

바이브 코딩으로 인해 취약한 앱이 만들어질 수 있다는 보고가 있었는데, 이는 코딩에 대한 지식이 없는 사람들이 프로덕션 시스템에 바이브 코딩을 적용했기 때문이다 [158]

발표자의 사례에서는 완전히 오프라인 시스템이었기 때문에 보안 문제가 발생할 가능성이 없었다 [167]

중요한 시스템에 바이브 코딩을 적용할 때는 위험한 부분을 파악하고, Claude를 올바른 방향으로 안내할 수 있는 충분한 지식이 필요하다 [160]

미래에는 비전문가도 안전하게 소프트웨어를 개발할 수 있도록 검증 가능한 제품 및 프레임워크가 필요하다 [173]

백엔드 시스템의 중요한 인증 및 결제 부분이 미리 구축되어 있고, 사용자는 UI 레이어만 채우면 되는 방식의 제품이 나올 수 있다 [176]

Claude Artifacts처럼 프런트엔드 전용으로 제한되어 안전한 환경에서 코드를 작성하고 호스팅할 수 있는 도구가 좋은 예시이다 [180]

테스트 주도 개발(TDD)은 바이브 코딩에서 매우 유용하다 [187]

Claude가 구현 코드를 먼저 작성하고 테스트 케이스를 나중에 작성하는 경향이 있지만, 테스트 케이스를 먼저 작성하도록 유도할 수 있다 [187]

Claude가 구현에 너무 특화된 테스트를 작성하는 것을 피하기 위해, 세 가지 엔드투엔드 테스트(성공 경로, 에러 케이스 2가지)를 작성하도록 구체적으로 지시하는 것이 좋다 [191]

바이브 코딩 시 코드의 첫 번째 검토 부분은 테스트가 될 수 있으며, 테스트가 통과하면 코드에 대한 신뢰를 가질 수 있다 [196]

## 4. 기하급수적 발전의 의미와 바이브 코딩 워크플로우 [198]

기하급수적 발전은 AI 기술이 상상 이상으로 빠르게 발전할 것임을 의미하며, 개발자는 이러한 변화에 맞춰 AI와 협력하는 바이브 코딩 워크플로우를 최적화해야 한다.

### 4.1. 기하급수적 발전의 진정한 의미 [198]

기하급수적 발전을 받아들인다는 것은 AI 모델이 단순히 계속해서 나아지는 것을 넘어, 우리가 상상할 수 없을 정도로 빠르게 발전할 것이라고 가정하는 것을 의미한다 [204]

이는 마치 1990년대 컴퓨터의 RAM이 킬로바이트 단위에서 현재 테라바이트 단위로 발전한 것처럼, 단순히 두 배가 아닌 수백만 배의 발전이 일어날 수 있음을 뜻한다 [211]

따라서 20년 후 AI 모델이 단순히 두 배 좋아지는 것이 아니라, 현재보다 수백만 배 더 똑똑하고 빨라질 것이라고 생각해야 한다 [216]

이러한 변화는 우리가 현재 상상할 수 없는 수준의 파급력을 가질 것이다 [218]

### 4.2. 바이브 코딩 워크플로우 최적화 [223]

바이브 코딩 시 터미널과 VS Code/Cursor를 모두 활용하며, AI 세션을 적절히 압축(compact)해야 한다 [226]

발표자는 Claude Code를 터미널과 VS Code에서 모두 사용하며, Claude Code가 대부분의 편집을 하고 자신은 코드를 검토한다 [234]

Claude 세션을 압축하는 시점은 인간 프로그래머가 작업을 멈추고 휴식을 취할 만한 좋은 지점이다 [238]

예를 들어, Claude가 관련 파일을 찾고 계획을 세운 후, 그 내용을 문서로 작성하게 한 다음 세션을 압축하여 토큰 수를 줄일 수 있다 [240]

Claude Code와 Cursor 같은 다른 도구들을 함께 사용하여 생산성을 높일 수 있다 [243]

발표자는 Claude Code로 작업을 시작하고 Cursor로 세부 사항을 수정하거나, 특정 파일에 대한 명확한 변경 사항이 있을 때는 Cursor를 직접 사용한다 [244]

익숙하지 않은 코드베이스에서 빠르게 작업할 때는 Claude Code를 활용하여 코드베이스를 탐색하고 이해해야 한다 [247]

기능을 작성하기 전에 Claude Code에게 코드베이스에서 인증이나 특정 기능이 어디서 발생하는지, 유사한 기능은 무엇인지 등을 물어본다 [249]

이를 통해 파일 이름이나 클래스 정보를 얻어 코드베이스에 대한 정신적 그림을 구축하고, 바이브 코딩을 하면서도 상황을 잘 파악할 수 있도록 돕는다 [251]
