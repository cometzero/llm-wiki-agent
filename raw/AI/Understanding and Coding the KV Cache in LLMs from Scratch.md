
대규모 언어 모델(LLM)의 **추론 속도(Inference Speed)**를 비약적으로 높이는 핵심 기술인 **kv 캐시****(KV Cache)**의 개념과 동작 원리를 밑바닥부터 이해하고 코드로 구현하는 방법을 배울 수 있습니다. 이 콘텐츠는 LLM이 텍스트를 생성할 때 발생하는 **불필요한 중복 계산(Key와 Value 벡터의 재계산)** 문제를 어떻게 해결하여 생산 환경에서 필수적인 **선형적 복잡도(O(n))**를 달성하는지 명확히 보여줍니다. 코드의 가독성을 최우선으로 한 **실제 Python 구현 예시**를 통해 이론을 실무에 바로 적용하고, 메모리 관리와 성능 최적화 팁(Pre-allocation, Sliding Window)까지 익힐 수 있어 LLM 엔지니어링 역량을 크게 향상시켜 줄 실용적인 가이드입니다.
## 1. LLM 추론 효율성을 위한 KV 캐시의 개요 
1. **KV 캐시****의 핵심 역할**: KV 캐시는 프로덕션 환경에서 **LLM 추론****(Inference)의 효율성**을 높이는 가장 중요한 기술 중 하나이다. 
2. **KV 캐시****의 정의 및 목적**: KV 캐시는 학습 이후 텍스트 생성 중 재사용할 수 있도록 **중간 키(K)와 ****값(V) 벡터****의 계산 결과**를 저장하는 메커니즘이다. 
3. **효과**: 이 캐싱 덕분에 텍스트 생성 시 상당한 **속도 향상**이 발생한다. 
4. **단점 및 상쇄**:
  1. KV 캐시는 코드 복잡성을 증가시키고 메모리 요구 사항을 높이며 (처음 책에 포함하지 않은 주된 이유), 학습 중에는 사용할 수 없다. 
  2. 하지만 프로덕션 환경에서는 추론 속도 향상이 코드 복잡성과 메모리 증가라는 **트레이드오프를 상쇄하고도 남는다.** 


## 2. KV 캐시가 해결하는 LLM의 중복 계산 문제 


### 2.1. KV 캐시 없는 텍스트 생성 과정의 비효율성 
1. **LLM의 ****토큰**** 생성 방식**: LLM은 일반적으로 한 번에 하나의 토큰을 생성한다. 
2. **반복적인 전체 시퀀스 재처리 (비효율성)**:
  1. 프롬프트 "Time"이 주어졌을 때, 첫 번째 단계에서 "flies"를 생성한다. 
  2. 다음 단계에서 "fast"를 생성하기 위해, LLM은 **전체 시퀀스("Time flies")**를 다시 처리한다. 
  3. 이 과정에서 이전에 처리했던 컨텍스트("Time flies")가 **매 생성 단계마다 반복적으로 재처리**되는 비효율성이 발생한다. 
3. **어텐션 메커니즘****에서의 중복**:
  1. 어텐션 메커니즘의 핵심은 입력 토큰(예: "Time", "flies")을 가중치 행렬 W를 사용하여 **키(K), 값(V), 쿼리(Q) 벡터**로 변환하는 것이다. 
  2. LLM이 세 번째 토큰("fast")을 생성할 때, 이전에 이미 계산했던 **첫 두 ****토큰****("Time", "flies")의 키와 값 벡터(k(1)/v(1) 및 k(2)/v(2))를 다시 계산**한다. 
  3. 비교 결과, 이전 단계와 현재 단계에서 계산된 첫 두 토큰의 키 및 값 벡터는 **정확히 동일**하며, 매 라운드마다 재계산하는 것은 낭비이다. 


### 2.2. KV 캐시를 통한 비효율성 해결 
1. **KV 캐시****의 개념**: KV 캐시는 이 불필요한 재계산을 피하기 위해 **이전에 생성된 키와 값 벡터를 저장하고 재사용**하는 캐싱 메커니즘을 구현하는 아이디어이다. 
2. **KV 캐시**** 적용 시의 동작 순서**:
  1. **초기 단계**: 모델은 입력 토큰에 대한 키 및 값 벡터를 계산하고 이를 캐시에 저장한다. 
  2. **새 ****토큰**** 생성 단계**: 모델은 **해당 특정 새 ****토큰**에 대해서만 키와 값 벡터를 계산한다. 
  3. **재사용**: 이전에 계산된 벡터는 캐시에서 검색되어 중복 계산을 방지한다. 
3. **재사용 이점**: 텍스트가 길어질수록 이미 계산된 키와 값을 재사용할 기회가 많아져 **생성 속도가 증가**한다. 
  1. 예시: "Time"은 한 번 계산되어 두 번 재사용되고, "flies"는 한 번 계산되어 한 번 재사용된다. 
4. **결론**: KV 캐시가 적용되면, 다음 라운드에서는 이전에 계산된 키와 값 벡터를 **캐시에서 검색하여 재사용**함으로써 더 빠른 생성이 가능해진다. 


## 3. KV 캐시의 실제 Python 코드 구현 (가독성 위주) 
kv 캐시를 구현하는 핵심은 새로운 토큰에 대해서만 키와 값 텐서를 계산하고, 이를 저장하여 다음 라운드에서 검색해 사용하는 것이다. 


### 3.1. MultiHeadAttention 클래스 수정: 캐시 등록 및 저장/검색 
1. **캐시 버퍼 등록**: MultiHeadAttention 생성자 내부에 단계를 거쳐 연결될 키와 값들을 담을 두 버퍼(cache_k, cache_v)를 추가한다. 
  - 코드: self.register_buffer("cache_k", None) / self.register_buffer("cache_v", None)
2. forward 메소드 확장: forward 메소드에 use_cache=False 인수를 추가한다. 
3. **캐시 저장 및 검색 로직 (핵심)**:
  1. **저장 (Storing)**: use_cache=True일 때, 캐시가 초기화되지 않은 경우(self.cache_k is None) 새로운 키(keys_new)와 값(values_new)으로 캐시를 초기화한다. 
  2. **갱신 (Concatenation)**: 이미 캐시가 초기화되어 있는 경우, 새로 생성된 키와 값을 기존 캐시에 torch.cat을 이용해 **차원 1(****토큰**** 길이 차원)**을 따라 연결하여 추가한다. 
  3. **검색 (Retrieving)**: 연결된 self.cache_k와 self.cache_v를 최종적으로 사용될 keys와 values로 지정한다. 
  4. **캐시 미사용 시**: use_cache=False인 경우, 새로 계산된 keys_new와 values_new를 그대로 사용한다. 


### 3.2. GPTModel 클래스 수정: 캐시 관리 및 위치 추적 
1. **캐시 초기화 (Clearing the Cache)**:
  1. **필요성**: 두 번의 독립적인 텍스트 생성 호출 사이에 캐시를 재설정해야 한다. 
  2. **미재설정 문제**: 재설정하지 않으면 새로운 프롬프트의 쿼리가 이전 시퀀스에서 남은 **오래된 키(stale keys)**에 어텐션하여 관련 없는 컨텍스트에 의존하고 **일관성 없는 출력**을 생성한다. 
  3. **메소드 추가**: MultiHeadAttention 클래스에 reset_cache 메소드를 추가하여 cache_k와 cache_v를 None으로 재설정한다. 
2. **모델 전체에 **use_cache 전파: GPTModel 클래스 내부의 변경 사항이다. 
  1. **위치 추적 변수 추가**: 생성자(Instructor)에 모델이 이미 캐시한 토큰 수를 기억하는 간단한 카운터 self.current_pos = 0를 추가한다. 
  2. forward 메소드 수정: use_cache=True일 때, pos_ids (위치 ID)를 self.current_pos부터 시작하여 seq_len만큼 계산하도록 한다. 
  3. **카운터 갱신**: 계산 후 self.current_pos에 seq_len을 더해 카운터를 증가시킨다. 
  4. **위치 추적의 중요성**: 새로운 쿼리가 이미 저장된 키와 값 바로 뒤에 **정렬(line up)되어야** 하기 때문에 위치(self.current_pos)를 추적해야 한다. 
  5. **블록 반복**: 명시적 루프를 통해 use_cache 인수를 각 트랜스포머 블록에 전달한다. 
  6. **모델 레벨 캐시 리셋**: GPTModel 클래스에 reset_kv_cache 메소드를 추가하여 모든 블록 캐시와 self.current_pos를 한 번에 지운다. 
3. **TransformerBlock 수정**: forward 메소드가 use_cache 인수를 받아 이를 내부 어텐션(self.att)에 전달하도록 수정한다. 


### 3.3. 캐시를 활용한 텍스트 생성 함수 
1. generate_text_simple_cached 함수 구현: use_cache=True를 설정하여 캐시를 활용한 텍스트 생성 함수를 구현한다. 
2. **캐시 사용 시**:
  1. 전체 프롬프트로 캐시를 초기화한다 (model.reset_kv_cache() 호출 후, model(idx[:, -ctx_len:], use_cache=True) 호출). 
  2. 다음 토큰을 생성할 때, **새로운 ****토큰****(**next_idx)만을 모델에 입력하여(logits = model(next_idx, use_cache=True)) 키와 값을 계산하도록 한다. 
3. **캐시 미사용 시**: 매번 **전체 입력 시퀀스**(logits = model(idx[:, -ctx_len:], use_cache=False))를 모델에 공급한다.

## 5. KV 캐시의 장단점 및 최적화 기법 


### 5.1. 시퀀스 길이에 따른 장단점 
1. **장점: ****계산 효율성**** 증가 (선형 복잡도 달성)**: 
  1. 캐시가 없을 경우: 단계 $t$에서 새로운 쿼리는 $t$개의 이전 키와 비교해야 하므로 누적 작업량이 **2차 복잡도($O(n^2)$)**로 증가한다.
  2. 캐시 사용 시: 각 키와 값은 한 번만 계산되고 재사용되므로, 총 단계별 복잡도가 **선형 복잡도($O(n)$)**로 감소한다.
2. **단점: ****메모리 사용량**** 선형 증가**: 
  1. 각 새 토큰이 KV 캐시에 추가되어 시퀀스가 길어질수록 캐시 크기가 누적되며, 이는 상당하거나 감당할 수 없는 수준의 (GPU) 메모리를 소비할 수 있다.
  2. **해결책**: KV 캐시를 잘라내는 방법(Sliding Window)이 있지만, 이는 복잡성을 더욱 증가시킨다.


### 5.2. KV 캐시 구현 최적화 기법 
<em>이전에 제시된 구현은 교육적 목적으로 가독성을 높인 것이며, 실제 배포 시에는 최적화가 필요하다.</em> 

1. **일반적인 확장 문제**: 
  1. **메모리 단편화**** 및 반복 할당**: torch.cat을 사용하여 텐서를 지속적으로 연결하면 빈번한 메모리 재할당으로 인해 성능 병목 현상이 발생한다.
  2. **메모리 선형 증가**: 적절한 처리 없이는 매우 긴 시퀀스에 대해 KV 캐시 크기가 비실용적이 된다.
2. **Tip 1: 메모리 ****사전 할당**** (Pre-allocate Memory)**: 
  1. 텐서를 반복적으로 연결하는 대신, 예상되는 **최대 시퀀스 길이**를 기반으로 충분히 큰 텐서를 **사전 할당**한다.
  2. 이는 일관된 메모리 사용을 보장하고 오버헤드를 줄인다.
  3. 추론 중에는 이 사전 할당된 텐서의 슬라이스에 쓰기만 한다.
3. **Tip 2: ****슬라이딩 윈도우****를 통한 캐시 절단 (Truncate Cache via Sliding Window)**: 
  1. GPU 메모리 폭증을 막기 위해 **동적 절단(dynamic truncation)** 기능이 있는 슬라이딩 윈도우 접근 방식을 구현한다.
  2. **작동 방식**: 캐시에 window_size 만큼의 **가장 최근 ****토큰**만 유지한다.
  3. 코드 예시: cache_k = cache_k[:, :, -window_size:, :]


## 6. 최적화된 구현 성능 비교 및 보너스 연구 결과 
1. **최적화된 구현 ****성능 비교**: 최적화된 구현(gpt_with_kv_cache_optimized.py)은 CPU 환경에서 200토큰 생성 시 가독성 중심 구현에 비해 <em>큰 속도 차이를 보이지는 않았다</em>. 
  - <em>참고</em>: 이 작은 모델에서는 디바이스 전송 및 통신 오버헤드가 KV 캐시의 이점을 상쇄하기 때문에, CUDA 환경에서는 속도 이점이 사라진다. 
2. **결론**: 캐싱은 복잡성과 메모리 고려 사항을 추가하지만, 효율성 측면의 이점이 **생산 환경에서는 일반적으로 단점을 능가**한다. 
  - 실용적인 구현은 메모리 사전 할당이나 슬라이딩 윈도우 캐시 적용과 같은 **사려 깊은 최적화**가 필요하다. 


### 6.1. 보너스: Qwen3 및 Llama 3에서의 KV 캐시 성능 
1. **대규모 모델 적용**: Qwen3 (0.6 B) 및 Llama 3 (1 B) 구현에 KV 캐시를 추가하여 추가 실험을 진행했다. 
2. **구현 방식 선택**:
  1. 메모리 오버헤드 문제로 인해 **사전 할당**** 방식** 대신, torch.cat 접근 방식을 채택했다. 
  2. Llama 3와 Qwen3의 지원 컨텍스트 크기(각각 131k, 41k)가 매우 커서 사전 할당된 텐서는 **약 8GB의 추가 메모리**를 소비하기 때문이다. 
3. **컴파일러 최적화**: 메모리 효율적인 torch.cat 방식을 사용하되, 연산 효율을 높이기 위해 KV 캐시를 모델 외부로 옮겨 torch.compile로 모델을 컴파일했다. 
4. **성능 결과**: 
  1. **CPU**** 환경**: KV 캐시는 **가장 실질적인 속도 향상**을 가져왔으며, 컴파일이 이 성능을 더욱 증폭시켰다.
  2. **GPU**** 환경**: KV 캐시가 없는 일반 컴파일 모델이 최고의 성능을 달성했다. 이는 텐서가 GPU에 사전 할당되지 않았고 모델 크기가 비교적 작기 때문인 것으로 추정된다.
