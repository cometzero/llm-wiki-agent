## 1. AI 시대의 전환점과 소프트웨어 패러다임의 변화 [1]

안드레이 카파시는 2025년 12월을 AI 코딩의 중요한 분기점으로 제시하며, 소프트웨어 개발 패러다임이 1.0에서 3.0으로 변화하고 있음을 강조한다.

### 1.1. 2025년 12월: AI 코딩의 분기점 [9]

에이전트의 실제 작동 시작 [11]

카파시는 에이전트가 실제로 작동하기 시작한 시점을 2025년 12월로 명확히 지적한다 [11].

이전에는 코드 덩어리를 던져주면 가끔 맞고 직접 고쳐야 하는 수준이었으나, 12월 이후에는 코드가 자동으로 생성되는 수준으로 발전했다 [17].

AI 코딩의 새로운 경험 [14]

AI 코딩의 발전이 곡선이 아닌 계단처럼 끊어진 분기점으로 나타났다고 설명한다 [14].

2025년 12월부터는 에이전트가 리서치, 계획, 코딩, 테스트, 디버깅을 일관된 흐름으로 처리하는 에이전트적이고 일관성 있는 워크플로가 가능해졌다 [27].

과거 경험에 대한 재평가 필요 [26]

작년 GPT 수준에서 AI를 경험했다면 12월부터는 다시 평가해야 한다고 강조한다 [26].

작년 11월쯤 AI 코딩이 별로라고 결론 내렸다면, 지금은 다시 시도해 볼 필요가 있다 [32].

### 1.2. 소프트웨어 1.0, 2.0, 3.0의 시대적 변화 [34]

소프트웨어 패러다임의 정의 [36]

소프트웨어 1.0: 사람이 직접 코드를 작성하는 방식이다 [37].

소프트웨어 2.0: 신경망을 훈련시키는 방식으로, 데이터셋 구축, 모델 아키텍처 설계, 학습 자체가 프로그래밍이 된다 [39].

소프트웨어 3.0: 프롬프트를 작성하는 것이 프로그래밍이며, 컨텍스트 윈도우에 무엇을 넣느냐가 핵심 레버가 된다 [41].

소프트웨어 3.0의 실제 사례 [43]

오픈클로 설치 사례: OS별 복잡한 배시 스크립트(소프트웨어 1.0) 대신, 텍스트 한 덩어리를 에이전트에 붙여 넣으면 에이전트가 알아서 환경을 보고 디버깅하며 설치를 완료한다 [44].

메뉴젠 사례: 식당 메뉴판 사진을 찍으면 OCR로 항목을 추출하고 이미지 생성기로 음식 사진을 만들어 보여주는 앱(소프트웨어 1.0)이 있었다 [56]. 그러나 소프트웨어 3.0에서는 메뉴 사진을 LLM에 주고 "나노바나 이미지 생성 모델로 메뉴 위에 음식 사진을 오버레이해 줘" 한 줄이면 모든 과정이 처리되어 기존 앱 자체가 불필요해진다 [63].

패러다임 변화의 의미 [72]

이는 기존 패러다임의 속도 향상이 아니라, 이전에는 불가능했던 것이 가능해진 변화이다 [72].

코드가 빨라진 것이 아니라, 일반적 정보 처리 자체가 자동화되고 코드가 사라진 자리에 신경망이 직접 들어가는 것이다 [74].

현재 만들고 있거나 만들 계획이 있는 앱이 신경망 호출 한 번으로 가능한지 질문해 봐야 하며, 가능하다면 만들 필요가 없어진다 [77].

### 1.3. 미래의 '당연한' 카테고리: 신경 컴퓨터 [79]

신경 컴퓨터의 개념 [80]

카파시는 미래에 신경 컴퓨터(뉴럴 컴퓨터)가 등장할 것이라고 예측한다 [80].

이는 코드가 거의 사라지고 신경망이 모든 일을 처리하며, 기기가 원시 비디오/오디오 신호를 신경망에 직접 넣어 고유한 UI를 디퓨전으로 렌더링하는 그림이다 [81].

컴퓨터 역사와 신경망의 역할 변화 [84]

50~60년대에는 컴퓨터가 계산기형이 될지 신경망형이 될지 불분명했으나, 결국 계산기 경로를 택했다 [84].

현재 신경망은 계산기형 컴퓨터 위에서 가상화되어 돌아가지만, 카파시는 미래에 신경망이 호스트 프로세스가 되고 CPU는 코프로세서로 격하될 수 있다고 본다 [87].

이는 신경망이 메인이 되고 결정론적 계산이 필요할 때만 CPU를 호출하는 방식으로, 현재와 정반대의 그림이다 [91].

코드의 신경망 흡수 가능성 [93]

이러한 변화는 점진적으로 일어날 것이며, 5~10년 안에 현재 짜는 코드의 상당 부분이 신경망으로 흡수될 수 있음을 시사한다 [94].

## 2. AI의 능력과 한계, 그리고 인간의 역할 [97]

AI는 채점 가능한 영역에서 천재성을 보이지만, 일상적 상식에서는 들쭉날쭉한 제기드 인텔리전스를 가지므로, 인간은 AI를 감독하고 이해하는 역할을 수행해야 한다.

### 2.1. AI의 능력: 채점 가능한 영역에서의 천재성 [97]

검증 가능성의 법칙 [98]

AI는 답이 맞는지 채점할 수 있는 영역에서 강력한 능력을 발휘한다 [107].

강화 학습(RL): 에이전트가 행동에 대한 점수를 받고 점수를 최대화하는 방향으로 학습하는 방식이다 [101].

LLM은 답이 맞으면 플러스 점, 틀리면 마이너스 점을 주는 거대한 RL 환경에서 훈련된다 [105].

AI가 천재적인 영역 [109]

수학: 답이 정해져 있어 채점 가능하다 [109].

코드: 컴파일 여부나 테스트 통과 여부로 채점 가능하다 [111].

AI의 한계: 들쭉날쭉한 지능 (Jagged Intelligence) [113]

채점 불가능한 영역에서는 AI의 능력이 들쭉날쭉하며, 어떤 곳에서는 천재처럼, 다른 곳에서는 바보처럼 행동한다 [113].

스트로베리 사례: 과거 GPT가 '스트로베리'의 'R' 개수를 틀리게 답한 적이 있다 [116].

세차장 사례: 최신 모델이 50m 앞 세차장에 차로 갈지 걸어갈지 물었을 때 "걸어가라"고 답하는 유명한 사례가 있다 [120].

카파시는 10만 줄 코드 베이스를 리팩토링하고 제로데이 취약점을 찾아내는 모델이 세차장에 차로 가야 한다는 것을 모르는 것이 미친 일이라고 표현하며, 이것이 제기드 인텔리전스의 실체라고 설명한다 [125].

이러한 들쭉날쭉함이 남아있는 한, 인간이 루프 안에 있어야 하며 LLM에 결정권을 통째로 넘기면 안 된다 [128].

데이터 분포의 중요성 [130]

GPT 3.5에서 GPT-4로 갈 때 체스 능력이 향상된 것은 일반 능력 진보가 아니라, 오픈AI가 체스 데이터를 프리트레이닝에 잔뜩 넣었기 때문이다 [131].

LLM의 능력은 랩이 어떤 데이터를 넣고 어떤 RL 환경을 만드느냐에 따라 좌우되므로, 사용자가 직접 탐험하여 모델의 회로와 강점, 약점을 알아내야 한다 [134].

### 2.2. 파운더와 엔지니어링의 기회 [136]

파운더를 위한 기회 [137]

검증 가능한 RL 환경이 있는 영역이면서도, 아직 랩들이 만들지 않은 환경에 기회가 있다 [139].

가치는 크지만 아무도 RL 환경을 만들지 않은 영역에서 직접 RL 환경 예시를 만들고 파인튜닝하면 잘 작동하는 시스템을 만들 수 있다 [142].

자동화가 풀릴 영역 [148]

거의 모든 것이 어느 정도는 검증 가능하게 만들 수 있다는 것이 카파시의 답변이다 [148].

글쓰기처럼 애매한 영역도 LLM 저지 위원회(여러 LLM이 채점단으로 들어가는 구조)를 두면 어느 정도 채점 가능해진다 [149].

이는 쉬움과 어려움의 차이일 뿐이다 [150].

바이브 코딩과 에이전틱 엔지니어링 [151]

바이브 코딩: "모두를 위한 바닥을 높이는 것"으로, 코딩을 못 하던 사람도 아이디어만으로 앱을 만들 수 있게 하는 것이다 [154].

에이전틱 엔지니어링: "천장을 확장하는 것"으로, 기존 프로페셔널 소프트웨어의 품질 기준을 유지하면서 더 빠르게 개발하는 것이다 [160].

바이브 코딩으로 만들었더라도 보안 취약점 등 책임 있는 엔지니어링 절차는 따라야 하며, 이것이 에이전틱 엔지니어링의 핵심이다 [163].

카파시는 에이전트를 잘 다루는 사람은 기존의 '10배 엔지니어'보다 훨씬 높은 생산성(1000배 이상)을 낼 수 있다고 본다 [173].

### 2.3. AI 네이티브 시대의 사용자 및 채용 변화 [178]

평범한 사용자 vs AI 네이티브 사용자 [178]

AI 네이티브 사용자는 쓸 수 있는 도구에서 최대한을 뽑아내고 모든 기능을 활용하며 본인 셋업에 투자하는 사람이다 [180].

이는 과거 빔(Vim) 사용자, VS Code 단축키/확장 프로그램 사용자처럼 도구를 얼마나 잘 활용하느냐에 따라 결과물 차이가 크게 벌어지는 것과 유사하다 [181].

클로드 코드, 코덱스, 오픈클로 같은 도구에서도 이러한 격차가 벌어지고 있다 [185].

채용 패러다임의 변화 [188]

대부분의 회사는 아직 에이전트 시대의 채용 방식을 반영하지 못하고 있으며, 퍼즐 풀기나 알고리즘 문제 풀이 같은 인터뷰는 옛날 패러다임이다 [189].

카파시는 새로운 채용 방식으로 트위터 클론을 안전하게 만들고, 10개의 에이전트(예: 코덱스 5.4xi)가 해킹을 시도해도 뚫리지 않도록 하는 세팅에서 사람의 작동을 관찰하는 것을 제안한다 [192].

이는 손으로 알고리즘을 푸는 능력보다, 에이전트와 협업하여 큰 시스템을 안전하게 구축할 수 있는 능력이 중요해졌음을 의미한다 [199].

### 2.4. 인간이 더 잘해야 하는 것: 미학, 판단, 감독 [203]

인턴 수준의 에이전트와 인간의 역할 [205]

현재 에이전트는 놀랍지만 인턴 수준이므로, 인간에게는 미학(좋아 보이는가/나빠 보이는가), 판단(옳은 결정인가), 취향(어떤 것이 더 우아한가), 감독(헛소리 하는 건 아닌가)이 남는다 [205].

에이전트의 황당한 실수 사례 [207]

카파시의 메뉴젠 앱에서 에이전트가 구글 로그인 이메일과 스트라이프 결제 이메일을 매칭하여 크레딧을 배정한 사례가 있다 [208].

이는 고유 식별자를 사용하지 않아 결제용/로그인용 이메일이 다른 경우 크레딧 매칭이 안 되거나, 보안상 위험한 상황(다른 사람 이메일로 결제 시 크레딧이 들어가는)을 초래할 수 있다 [212].

에이전트는 동작은 하지만 시스템적으로 이상한 결정을 내리며, 인간은 "유저 아이디는 고유해야 하고 모든 것을 거기에 묶어야 한다"는 결정을 1초 만에 내릴 수 있지만 에이전트는 그렇지 못한다 [216].

인간의 스펙 명세 설계와 시스템 모델 이해 [220]

인간이 상세한 스펙 명세를 설계하고 에이전트가 그 안을 채우는 방식이 핵심이다 [220].

파이토치와 넘파이 비유: API 디테일(예: keepdims vs axis, reshape, permute, transpose)은 에이전트(인턴)가 잘 외워주므로 사람이 외울 필요가 없다 [225].

그러나 텐서 아래의 스토리지, 뷰와 같은 스토리지 공유, 별도 스토리지의 비효율성과 같은 시스템 모델에 대한 이해는 여전히 사람의 몫이다 [232].

미학의 자동화 가능성 [235]

미학의 자동화 가능성은 있지만, 현재는 RL의 미약 보상이 부족하여 잘 안 된다 [235].

카파시는 동작은 하지만 블로티하고 복부투성이이며 어색한 코드를 "심장마비"라고 표현하며, 모델이 "더 단순하게"라는 프롬프트에도 이를 구현하지 못했다고 언급한다 [240].

근본적으로 불가능한 것은 아니며, 랩들이 아직 시도하지 않았을 뿐이라는 것이 카파시의 결론이다 [242].

### 2.5. AI는 동물이 아닌 유령 [243]

동물 지능과 LLM의 차이 [244]

카파시는 "우리는 동물이 아니라 유령을 소환하고 있다"는 비유를 사용한다 [244].

동물 지능은 진화의 산물로 본질적인 동기(배고픔, 두려움, 호기심) 위에 학습이 얹어진 것이다 [250].

LLM은 동물 지능이 아니며, 진화의 산물이 아니라 데이터와 보상 함수로 빚어진 들쭉날쭉한 통계적 시뮬레이션이다 [252].

LLM의 기반층은 프리트레이닝(통계)이며, 그 위에 RL이 붙어 능력을 늘리는 구조이다 [255].

LLM 다루는 방식 [259]

동물에게 통하는 "소리 지르거나 사정하거나 협박하는" 방식은 LLM에게 통하지 않는다 [259].

우리는 무의식적으로 "제발 제대로 해 봐", "이번엔 정말 중요해" 같은 프롬프트를 사용하며 동물 지능에 대한 직관을 적용하고 있지만, 이는 효과가 없다 [264].

LLM을 어떻게 다뤄야 할지에 대한 명확한 답은 없으며, 의심을 유지하면서 모델의 회로, 강점, 약점을 직접 탐험하여 알아내는 것이 현재 할 수 있는 일이다 [273].

'하지 마'의 중요성 [276]

유령(LLM)은 '하지 마'라고 강하게 말하는 부분에 대해서는 잘 듣는 경향이 있다 [276].

클로드닷MD에서도 '하지 마'라고 하는 부분의 중요성을 강조한다 [279].

### 2.6. 에이전트 네이티브 세계의 모습 [280]

인프라, 문서, API의 변화 필요성 [282]

카파시는 프레임워크 문서가 인간에게 "뭘 하라고 시키는 것"에 짜증을 느낀다 [282].

인프라, 문서, API를 에이전트 네이티브로 다시 작성해야 한다 [288].

사람이 단계별로 따라할 것이 아니라, 에이전트가 한 번에 흡수하여 실행할 수 있는 형태로 바뀌어야 한다 [289].

에이전트 네이티브의 리트머스 테스트: 메뉴젠 배포 [289]

카파시는 메뉴젠 앱을 만들 때 코드 작성보다 버셀(Vercel) 배포(서비스 연결, 설정, DNS 구성, 환경 변수 세팅 등)가 더 어려웠다고 말한다 [290].

이상적인 에이전트 네이티브 환경에서는 "메뉴젠 빌드해서 배포해 줘" 한 줄로 끝나야 한다 [294].

인간이 아무것도 건드리지 않아도 인터넷에 올라가는 것이 인프라가 에이전트 네이티브가 되었는지의 좋은 이정표이다 [296].

현재 AWS, GCP, Azure, Vercel 등 클라우드 콘솔은 대부분 사람이 클릭하도록 만들어져 있지만, 이는 클릭이 아닌 텍스트로 묘사 가능한 인터페이스로 바뀌어야 한다 [298].

미래의 에이전트 상호작용 [303]

카파시는 미래에 "제 에이전트가 당신 에이전트랑 미팅 디테일 잡게 하겠습니다"와 같이 사람 조직마다 에이전트 대리인이 붙는 세상을 그린다 [303].

캘린더 조율, 스케줄링, 사전 자료 조사 등이 에이전트끼리 처리되는 그림이다 [305].

### 2.7. 핵심 통찰: Thinking은 아웃소싱 가능, Understanding은 불가 [309]

싱킹(Thinking)과 언더스탠딩(Understanding)의 차이 [310]

카파시는 "싱킹은 아웃소싱할 수 있지만, 언더스탠딩은 아웃소싱할 수 없다"는 트윗을 인용하며, 이것이 인터뷰 전체를 관통하는 핵심 메시지라고 강조한다 [312].

싱킹(사유): 정보를 받아서 분석하고 단계 밟아 결론에 도달하는 일종의 처리 작업으로, LLM이 잘하므로 아웃소싱 가능하다 [318].

언더스탠딩(이해): 정보가 자기 뇌에 들어와 자리 잡고 다른 정보와 연결되어 '아, 이게 이런 거였구나'라는 깨달음으로 변환되는 것으로, 본인이 직접 해야 한다 [321].

인간의 마지막 병목 [324]

카파시는 무엇을 빌드할지, 왜 할 가치가 있는지, 에이전트를 어떻게 지휘할지는 여전히 인간의 병목이라고 말한다 [325].

싱킹과 프로세싱을 지휘하는 것은 결국 언더스탠딩에 의해 제약된다 [327].

AI에게 많은 것을 위임하면서 자신이 무엇을 만들고 있는지에 대한 이해가 흐려질 수 있으며, 코드는 돌아가지만 그 안을 모르는 상황이 발생할 수 있다 [329].

코드를 치는 능력은 중요하지 않지만, 이것을 왜 만들고 있고 어떻게 검증할지는 본인의 언더스탠딩 위에서 결정해야 하며, 이를 못 하면 에이전트에게 방향을 줄 수 없다 [336].

LLM과 언더스탠딩 [340]

카파시는 LLM 지식 베이스 같은 도구에 흥미를 느끼는데, 이는 정보를 처리하는 방법이고 다른 투영(projection)을 볼 때마다 인사이트가 생기기 때문이다 [340].

카파시 본인은 기사를 읽으면 위키에 쌓고 거기에 질문하면서 언더스탠딩을 키워가는 방식으로 사용한다 [341].

LLM은 언더스탠딩이 뛰어나지 않으며, 이는 여전히 고유하게 인간의 영역이다 [343].

### 2.8. 핵심 메시지 요약 [345]

2025년 12월 분기점: AI 코딩은 단순한 도구에서 에이전트가 코드를 제대로 짜는 수준으로 발전했다 [348].

소프트웨어 3.0 시대: 프로그래밍은 프롬프팅이며, 컨텍스트 윈도우에 무엇을 넣느냐가 핵심이고, 앱 자체가 불필요해지는 영역이 늘어난다 [351].

AI의 제기드 인텔리전스: AI는 채점 가능한 영역에서만 천재이며, 그렇지 않은 곳은 들쭉날쭉한 능력을 보인다 [355].

바이브 코딩과 에이전틱 엔지니어링: 바이브 코딩은 바닥을 높이고 에이전틱 엔지니어링은 천장을 확장하지만, 책임 있는 소프트웨어를 위해서는 후자가 핵심이다 [358].

인간의 역할: 취향, 판단, 미학, 스펙 설계가 인간에게 남으며, API 디테일은 에이전트의 몫이고 시스템 모델 이해는 사람의 몫이다 [361].

AI는 유령: LLM은 동물이 아닌 유령이므로, 소리 지르거나 사정해도 통하지 않으며, 동물 지능에 대한 직관을 버려야 한다 [364].

언더스탠딩의 중요성: 싱킹은 아웃소싱할 수 있어도 언더스탠딩은 아웃소싱할 수 없으며, 코드 치는 능력보다 이해하는 능력이 인간의 마지막 병목이다 [368].
