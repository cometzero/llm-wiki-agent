## 📌 SDV(소프트웨어 정의 차량) 시대의 차세대 차량 진단 기술 SOVD(Service-Oriented Vehicle Diagnostics)는 무엇인가?
SOVD는 SDV 시대에 필요한 유연하고 동적인 차량 데이터 교환을 위해 <mark>기존 이진 기반 진단 프로토콜을 대체하여 HTTP REST 프로토콜로 정의된 차세대 차량 진단 인터페이스</mark>입니다.


SDV(소프트웨어 정의 차량) 시대를 맞아 차량 진단의 패러다임을 바꿀 **SOVD(Service-Oriented Vehicle Diagnostics)**의 핵심과 실질적인 활용 방안을 도요타 엔지니어의 시각에서 소개합니다. 기존의 복잡하고 비표준화된 바이너리 기반 진단 방식(UDS/DoIP)이 아닌, HTTP REST API를 기반으로 유연성과 확장성을 극대화한 SOVD를 통해 **소프트웨어 및 하드웨어 구성 요소를 동적으로 진단하고 원격에서 관리**하는 방법을 구체적인 POC 시스템 구성과 데모를 통해 배울 수 있습니다. 특히, 차량의 사설 IP 문제로 인한 외부 접근의 어려움을 해소하기 위해 Proxy Agent를 활용하여 **실시간 원격 진단 시나리오를 구현**하는 기술적 통찰을 얻고, ACC(Automotive Edge Computing Consortium)에서의 협력 사례를 통해 차세대 차량 데이터 활용의 방향성을 명확히 파악할 수 있습니다.
## 타임라인 노트: SDV 시대의 차세대 차량 진단(SOVD) 및 가상 피드를 활용한 SDV 중심 사용 사례


## 1. 발표 소개 및 배경: SDV와 차량 진단의 중요성 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/AYiNXp_uvbs/25.jpg)
1. **발표 목표 및 내용 구성** 
  1. 본 세션의 주제는 **SDV(소프트웨어 정의 차량) 중심 사용 사례**이며, 차세대 차량 진단 기술인 **SOVD(Service-Oriented Vehicle Diagnostics)**와 가상 피드(Virtual Read) 활용에 초점을 맞추고 있다. 
  2. 다만, 발표자는 시간 부족으로 가상 피드 데모 시스템 구축을 완료하지 못하여, 현재는 차량 1대 관련 내용만 다룬다. 
  3. 발표의 주된 내용은 SDV 시대를 대비하는 관점에서 **차세대 차량 진단 기술**에 중점을 둘 것이며, 작은 데모를 통해 이를 보여줄 예정이다. 

2. **발표자 소개 및 ACC 활동** 
  1. 발표자는 토요타(Toyota)에서 커넥티드 차량 시스템 R&D를 담당하며, 주요 기술 분야는 엔드 투 엔드(end-to-end) 관측성(observability), 표준화, 차량 진단이다. 
  2. 현재는 **ACC(Automotive Edge Computing Consortium)**를 대표하여 발표하며, ACC 내 여러 워킹 그룹 중 주로 **데이터 퍼스트(Data First)** 분야에 집중하고 있다. 
  3. 참고로 발표자는 약 30년 전 운영체제(OS) 분야에서 경력을 시작하여 클라우드 인프라 등으로 전문 분야를 전환했다. 

3. **SDV 시대의 데이터 처리 개요** 
  1. SDV 이전에는 Connected, Autonomous, Shared/Service, Electric을 의미하는 **CASE**라는 키워드가 있었으나, 이제 자동차 산업에서는 거의 모두 **SDV(Software-Defined Vehicle)**를 논한다. 
  2. SDV 시대의 핵심은 차량 측에서 생성되는 데이터를 **유연하게 활용**하는 것과 차량과의 **연결성(Connectivity)**을 확보하는 것이다. 
  3. 연결성 확보 후에는 "어떤 종류의 차량 데이터를 얻을 수 있는가"가 중요해지며, 차량 대 차량(V2V) 또는 차량 대 센터(V2C) 간의 데이터 교환의 **유연성과 신속성**이 매우 중요하다. 


## 2. 기존 차량 데이터 및 진단 방식의 문제점 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/AYiNXp_uvbs/246.jpg)
1. **저수준(Raw) CAN 데이터의 문제점** 
  1. 과거에는 낮은 수준의 CAN(Controller Area Network) 데이터(예: K, L, F 등 형식)가 오랫동안 차량에 사용되었고, 잘 표준화되어 널리 채택되었다. 
  2. **문제점**: 이 Raw 데이터는 OEM(제조사)뿐만 아니라, 동일 OEM 내에서도 **모델마다 종속적**이다. 
  3. 유효한 데이터를 추출하기 위해서는 **NDA(기밀유지협약)**가 필요하며, **베타 사인 테이블(beta sign table)**이 요구된다. 

2. **기존 진단 방식 (UDS/DoIP)의 한계** 
  1. 표준화된 진단 방식으로는 **UDS(Universal Diagnostic Service)**와 **DoIP(Diagnostics over IP)**가 있다. 
  2. **장점**: 이 진단 데이터는 규제 때문에 정부가 표준화된 진단 데이터 지원을 요구했기 때문에 Raw CAN 데이터보다 **더 유용하고 균일하게 채택**된다. 
  3. **한계**: UDS 또는 DoIP는 기본적으로 **바이너리 기반** 포맷이며, 데이터 ID가 단순한 숫자로 되어 있어 **유연성이 낮다**. 
  4. OEM 관점에서 UDS나 DoIP에 새로운 정보 항목을 추가하는 작업이 매우 어렵고 고통스러우며, 여전히 Raw 데이터보다는 낫지만 **일부 OEM 종속성**이 남아있다. 

3. **KOB (Keyword-Oriented Bus)의 현실** 
  1. KOB는 좋은 추상화(abstraction) 방식이지만, 불행히도 **실제 양산(production)에서는 거의 지원되지 않는** 현실이다. 


## 3. 차세대 진단 프로토콜 SOVD (Service-Oriented Vehicle Diagnostics) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/AYiNXp_uvbs/407.jpg)
1. **SOVD의 정의 및 특징** 
  1. SOVD는 차세대 진단 방식인 **Service-Oriented Vehicle Diagnostics**의 약어이다. 
  2. 기존 진단 프로토콜이 바이너리 기반인 것과 달리, SOVD는 **HTTP REST 프로토콜**로 정의된다는 점에서 큰 차이가 있다. 
  3. SOVD는 ASAM에 의해 처음 표준화되었고, 버전 1.0은 약 2년 전 출시되었다. 
  4. 현재는 ISO에서 SOVD 1.1 표준화가 진행 중이며, 12월에 최종 초안 국제 표준(FDS) 문서가 발표되고, 2월경 국제 표준이 출시될 것으로 예상된다. 

2. **SOVD의 주요 목표 및 사용 사례** 
  1. ASAM 관계자들이 밝힌 것처럼, SOVD는 처음부터 **SDV 시대 지원**을 목표로 표준화 범위에 포함되었다. 
  2. SOVD 1.1 초안에는 17가지 사용 사례가 제시되었으며, 기존 UDS와 호환성을 위한 **레거시 기능**도 포함되어 있다. 
  3. **새롭게 추가된 핵심 기능 (Red ones)**:
  1. **엔티티 발견 (Discover Entities) (Use Case #2)**: 소프트웨어를 포함한 **동적 발견(Dynamic Discovery)**이 가능하다. 
  2. SDV 시대에는 새로운 기능이 **하드웨어(ECU) 박스**가 아닌 **소프트웨어** 형태로 제공되며 OTA(Over-The-Air) 업데이트를 통해 이루어진다. 
  3. 진단 시스템의 **대상**이 판매 후 동적으로 추가되거나, 제거되거나, 업데이트될 수 있는데, 이는 레거시 UDS 시스템으로는 지원하기 매우 어렵다. 
  4. **소프트웨어 업데이트 지원**: SOVD는 소프트웨어 업데이트 기능도 지원한다. 
  5. **스크립트 관리 및 실행 (Manage and Execute Script) (Use Case #14)**: 스크립트 런타임은 OEM마다 다를 수 있지만, 판매 후 스크립트 기반 테스트를 사용할 수 있다. 

3. **HTTP REST API 프로토콜 예시** 
  1. SOVD의 진단 대상은 레거시 하드웨어 구성 요소뿐만 아니라 **소프트웨어 구성 요소**까지 포함한다. 
  2. **예시 1: 하드웨어 정보 검색 (GET)** 
  - SOVD는 REST API 프로토콜로 정의되어 차량 내부 구성 요소를 **REST API 경로 요소**로 표현한다 (예: /components/power_steering과 같이 하드웨어 유닛을 나타냄).
  3. **예시 2: 소프트웨어 정보 검색 (GET)** 
  - 소프트웨어의 정보를 가져오는 경우 (예: /apps/advanced_rain_keeping) /apps 경로를 사용하여 애플리케이션 목록을 얻을 수 있다.
  - SOVD는 이처럼 하드웨어 및 소프트웨어 구성 요소 정보를 모두 처리할 수 있다. 
  4. **예시 3: 스크립트 실행 (POST)** 
  - HTTP POST 메소드를 사용하여 운전 컴퓨터에 correct_upmetrics라는 스크립트 실행을 요청한다.
  - 스크립트의 매개변수는 HTTP 요청의 본문(body) 부분에 명시된다.
  5. **핵심 요약**: SOVD의 기본 개념은 레거시 바이너리 UDS 같은 프로토콜이 아닌, **HTTP REST API 프로토콜**로 정의된다. 


## 4. ACC 협업을 통한 SOVD 활용 POC (Proof of Concept) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/AYiNXp_uvbs/827.jpg)
1. **ACC (Automotive Edge Computing Consortium) 소개** 
  1. 발표자는 SOVD의 유용성을 입증하기 위해 ACC에서 다른 회사들과 협력하고 있다. 
  2. ACC는 **이슈 중심(issue-driven)의 협업 공간**으로, 문제와 사용 사례에서 출발하는 것이 중요하다. 
  3. ACC는 정기적으로 화이트 페이퍼를 발표하고 있으며 (현재 약 20개), POC 목록도 웹사이트에서 확인할 수 있다. 
  4. 올해부터 특정 솔루션 영역에 기반한 SIG(Special Interest Group)가 결성되었으며, 발표자의 작업은 **첫 번째 SIG인 Data Fast**에 속한다. 
  - **Data Fast 목적**: V2V 통신에서 시작하여, 더 유연하고 신뢰할 수 있는 차량 데이터 활용을 가능하게 하는 것이다. 

2. **ACC 내 다른 SIG 활동** 
  1. **Vertical API**: GSMP32 프로토콜을 통한 원격 SIM 프로비저닝(remote SIM provisioning) 기술을 사용하여 다중 통신사(multiple men) 간 연결성을 유지하는 것을 목표로 한다. 구현은 Linux Foundation Ref Networking 프로젝트에서 진행 중이다. 
  2. **Green Computing**: 차량 데이터 회수 후 탄소 중립 문제를 해결하는 것을 주요 목적으로 한다. 

3. **POC 협력사 및 SDV 스택** 
  1. 발표자가 현재 진행 중인 POC를 위해 중국 회사와 협력 중이다. 
  2. 협력사는 자동차 분야를 위한 두 가지 주요 제품 라인을 가지고 있다.
  1. **ACOS (AC OS)**: 도메인 컨트롤러, 중앙 처리 시스템 또는 SDV의 존 아키텍처를 위한 운영 체제 역할을 한다. 
  - 이 발표 관점에서 중요한 것은 **SDV 소프트웨어 스택**이다. 
  - 협력사는 AGL(Automotive Grade Linux)을 대상으로 하는 SDV 소프트웨어 스택을 제공했으며, 이를 이용한 데모를 후술할 예정이다. 
  2. **Auto-Gy**: 생성형 AI를 활용한 차량 소프트웨어 개발 지원 시스템이다. 
  - 이 제품을 사용하여 ACOS에 대한 AC 인증을 자체적으로 수행하고 상당한 노동력을 절감했다고 한다. 


## 5. 원격 진단 시나리오 및 기술적 난제 극복 (Proxy Agent) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/AYiNXp_uvbs/1166.jpg)
1. **POC의 큰 그림과 단순화된 시나리오** 
  1. **큰 그림**: 차량 내부에는 SOVD, AI 에이전트, 비즈니스 로직 서비스가 있으며, 이 에이전트들이 SOVD를 통해 차량 내부 또는 근처 차량으로부터 데이터를 수집한다. 이 구조는 네트워크 위치를 포함하여 계층적으로 형성되며, 최종적으로 클라우드 내 중앙 제어 포인트로 연결된다. 
  2. **오늘의 공유 내용 (첫 번째 단계)**: 현재는 이 큰 그림 중 **원격 진단 시나리오(Remote Diagnostic Scenario)**라는 단순화된 사용 사례를 공유한다. 
  3. **원격 진단의 장점**:
  - 기존 UDS/DoIP 방식은 정비소에서 OBD2 커넥터를 사용해 유선으로 PC나 테스터를 연결해야 했다. 
  - SOVD를 활용한 원격 진단 시나리오에서는 OEM 엔지니어나 정비사들이 셀룰러 네트워크를 통해 인터넷을 경유하여 차량에 접근할 수 있다. 
  - 이는 **온라인 및 실시간 원격 진단**을 가능하게 하며, OEM이 제품을 지원하는 관점에서 매우 중요하고 유용한 기능이다. 

2. **POC 시스템 구성 및 네트워크 에뮬레이션** 
  1. POC 시스템은 에뮬레이션된 **5G 네트워크**를 포함하여 구축되었다. 
  2. 모바일 네트워킹 세계의 오픈소스 구현체를 사용했다.
  - **코어 네트워크(Core Network)**: Free 5GC 사용 
  - **RAN(Radio Access Network)**: U-Lancing을 사용하여 UDP 기반으로 RAN을 에뮬레이션했다. 
  3. 이를 통해 발표자의 데이터 센터에서 이더넷 연결만으로 POC 시스템을 구축할 수 있었다. 

3. **기술적 문제: 차량의 사설 IP 주소 문제** 
  1. **문제 제기**: 인터넷에서 차량 내부의 서버(SOVD 서버 등)로 직접 접근하는 것에 기술적인 문제가 없는가? 
  2. **원인**: 차량은 큰 스마트폰과 같으며, 기본적으로 **사설(Private) IP 주소**를 사용한다. 따라서 인터넷에서 이 스마트폰(차량)으로 직접 접근할 수 없다. 이는 TCU(Telematics Communication Unit)에서도 마찬가지이다. 
  3. **연결 패턴 분류 및 비용 문제**:
  1. **옵션 1: VPN 없는 사설 IP**: 이 경우 인터넷 측에서 차량에 직접 접근이 불가능하다. 
  2. **옵션 2: VPN 사용**: VPN을 도입하면 인터넷에서 차량에 연결할 수 있다. 
  - **단점**: VPN은 추가적인 비용을 발생시킨다. 토요타와 같이 연간 약 1,000만 대의 차량을 생산하는 경우, 대당 추가 비용이 작더라도 총액은 막대해진다. 
  3. **옵션 3: 글로벌 IP 사용 (IPv6)**: 높은 보안 기능을 갖춘 글로벌 IP를 사용하는 방안도 있으나, 발표자의 의견으로는 토요타 같은 레거시 대형 OEM들은 이 선택지를 택하지 않을 가능성이 높다. 
  4. **결론**: 대부분의 OEM이 VPN을 사용하고 있지 않기 때문에, 토요타는 옵션 1을 고수하면서 액세스를 돕기 위한 **추가 구성 요소**가 필요하다. 

4. **해결책: Proxy Agent 도입** 
  1. **Toyota의 제안**: 지난달 ASAM 회의(SOVD 1.2 표준화를 위한)에서 토요타는 **프록시 에이전트(Proxy Agent)** 박스를 추가하는 방안을 제안했다. 
  2. **작동 방식**:
  - 이 프록시 에이전트는 **차량 측(사설 네트워크)에서 인터넷(OEM 서버)**으로 능동적인 TCP/IP 연결을 먼저 시작한다. 
  - OEM 서버는 이 연결을 통해 규제 기관 등의 SOVD 접근을 위임(Delegate)한다. 
  - 프록시 에이전트는 인터넷 사용자(규제 기관 등)의 REST API 접근을 차량으로 **프록시**해준다. 
  3. **난점**: 차량 개발 엔지니어들은 이러한 네트워크 문제를 잘 이해하지 못하는 경우가 많아, 프록시 에이전트의 필요성을 이해시키는 데 시간이 걸렸다. 
  4. **POC 시스템 구현**: 발표자는 이 아키텍처(프록시 에이전트 활용)를 따라 POC 시스템을 구축하여, 에뮬레이션된 5G 네트워크와 AGL 기반의 에뮬레이션된 차량 OS를 사용하여 인터넷에서 차량 측으로 접근하는 것이 가능함을 입증하고자 했다. 
  5. **Proxy Agent 구현**:
  - 처음에는 직접 코드를 작성하려고 했으나, Python Proxy(P proxy)라는 흥미로운 컴포넌트를 발견하여 POC에 사용하기로 결정했다. 
  - POC 구성 요소 중 클라우드(센터) 측과 엣지(차량) 측 모두에 Python Proxy를 설치했다. 
  - **핵심**: TCP 연결은 **차량 측에서 센터 측으로** 시작된다. 


## 6. 데모 시연 및 결과, 그리고 향후 계획 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/AYiNXp_uvbs/1915.jpg)
1. **데모 환경 구성 상세** 
  1. 발표자는 POC 시스템에 Trout을 사용했으며, AGL(Automotive Grade Linux) 통합 및 5G UE 통합 외에도 일부 수정을 가했다. 
  2. 발표자는 AGL 커뮤니티에서 발표된 SDV 레퍼런스 플랫폼인 'So Dev'에 Vioan 드라이버를 통합했으며, 이 드라이버는 OpenSynergy로부터 통합된 것이다. 
  3. 이 시스템은 발표자가 구축한 시스템과 거의 1:1로 대응되는 상세 다이어그램을 기반으로 한다. 

2. **원격 접속 데모 시연** 
  1. 발표자는 인터넷 측에서 curl 명령어를 사용하여 SOVD 서버에 접속하는 것을 시연했다. 
  2. HTTP 프록시를 통해 Python Proxy 서버 측으로 요청을 보내서 차량 내부의 SOVD 서버에 접속하는 데 성공했다. 
  3. 이를 통해 사설 IP 공간 내에서 실행되는 차량 내부 서버로 **Python Proxy 터널**을 통해 인터넷 측에서 접근하는 것이 가능함을 입증했다. 

3. **SOVD 리소스 계층 구조 및 게이트웨이** 
  1. **대시보드 시연**: 발표자가 실행하려고 했던 대시보드 화면을 통해 SOVD의 특성을 설명했다. 
  2. SOVD가 REST API로 정의되어 있으므로, 컴포넌트, 소프트웨어, 기능 등 **차량 리소스의 계층적 구조**를 가지고 있다. 
  3. **SOVD-to-UDS 구성**: SOVD 구현은 여러 구성 요소로 이루어져 있으며, 특히 **SOVD to UDS** 구성 요소가 존재한다. 
  - 버튼을 눌러 성공적으로 연결되면, SOVD 게이트웨이는 SOVD to UDS 서비스를 통해 **고전적인 UDS 기반 정보**를 검색한다. 

4. **요약 및 향후 계획** 
  1. **ACC**: 이슈 중심의 협업 작업 공간이다. 
  2. **SOVD**: SDV 시대에 필요한 일반적인 데이터 교환에 적합한 차세대 차량 진단 인터페이스이며, 그 이상이다. 
  3. **POC 계획**: 현재 ACC에서 AGL을 사용하여 POC 작업을 진행 중이며, 상세 보고서는 **내년 4월 스웨덴 예테보리**에서 열리는 다음 ACCM에서 공개될 예정이다. 
  4. 또한, 내년 5월 일본에서 열릴 다음 AGL AMM에서도 발표할 기회가 있을 것으로 예상된다. 


## 7. 질의응답 (Q&A) 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/AYiNXp_uvbs/2449.jpg)
1. **통신 시작 주체 (Initiator) 및 발견(Discovery) 관련 질문** 
  1. **통신 시작 주체**: SOVD 서비스의 사용자(통신 시작 주체)는 **정비사, OEM 엔지니어, 규제 기관의 검사관** 등이다. 
  2. **발견 프로세스**: 차량 내부에서도 발견 프로세스가 존재하며, 특히 소프트웨어에 대한 동적 발견이 중요하다. 
  - 하드웨어의 경우 ODX 등을 사용할 수 있는데, 이는 하드웨어 구성 요소가 자주 추가되지 않기 때문이다. 
  - **OTA(Over-The-Air)를 통한 신기능 추가**에 발맞추기 위해 차량 내부에서도 발견 프로세스가 수행될 것이다. 
  3. **발견 기술**: 어떤 발견 기술을 사용할지는 현재 논의 중이다. 

2. **API 보안 및 개인 정보 보호(Privacy) 관련 질문** 
  1. **표준화 관점**: 발표자는 ASAM과 ISO의 표준화 활동에 참여하고 있으며, 이 관점에서 프라이버시 문제는 **'Extended Vehicle'**이라는 다른 ISO 사양에 속한다고 본다. 
  2. **OEM 관점**: OEM 입장에서는 고객 보안이 매우 중요하며, SDV 도입 이전에도 내부 규정과 규칙을 통해 고객 정보를 보호하고 있다. 
  3. 이러한 기존 규제들이 SDV에도 적용될 것이며, 이로 인해 SOVD의 풍부한 기능 일부가 제한될 수 있다. 

3. **장기 연결 프로토콜 사용 가능성 질문 (MQTT, gRPC 등)** 
  1. **질문 요지**: 사설 IP 주소 침투 문제(NAT issue) 해결을 위해 Python Proxy 대신 **MQTT, gRPC(HTTP/3.0 포함)**와 같은 장기 연결(Long-standing connection) 프로토콜을 사용하는 것을 고려했는가? 
  2. **답변**: Python Proxy를 사용한 것은 **POC를 위해 시간을 절약**하기 위함이었으며, MQTT, gRPC, 또는 다른 프로토콜 등 다른 옵션들이 분명히 존재한다.
