## 📌 Linux 장치 드라이버 모델에서 다양한 소프트웨어 노드 유형을 이해하는 방법은 무엇인가요?
Linux 커널의 장치 드라이버 모델에서 OF-노드, FW-노드, SW-노드, Device Link 및 속성 같은 다양한 소프트웨어 노드<mark> 유형과 이들의 역사적 발전, 상호 관계</mark>를 이해하는 것이 중요합니다.


## 💡 이 노드들이 필요한 주된 이유는 무엇인가요?
장치가 시스템마다 다르게 연결되어 있더라도 <mark>동일한 장치 드라이버를 재사용하고 구성</mark>하기 위해 펌웨어(장치 트리, acpi)를 통해 장치 설정을 전달해야 하기 때문입니다.


리눅스 커널 드라이버 개발자들을 위한 **펌웨어 노드****(Firmware Node)와 ****장치 링크****(Device Links)**에 대한 혼란을 명쾌하게 해소하는 가이드입니다. 이 강연은 리눅스 드라이버 모델의 작동 원리와, 과거 platform data와 board files의 한계를 극복하고 등장한 Device Tree, 그리고 이를 일반화한 FW node (OF node, ACPI node, SW node 포함)의 복잡한 진화 과정을 흥미롭게 설명합니다. 특히, **새로운 드라이버 작성 시 최적의 API 선택(Device Property Accessors, FW node API, Low-level API)** 기준을 명확히 제시하므로, 리눅스 커널 개발의 깊은 지식을 실무에 적용하고자 하는 분들에게 실질적인 **코드 포팅 및 설계 통찰**을 제공합니다.
## 1. 리눅스 커널 드라이버 모델 개요 및 작동 원리 


### 1.1. 드라이버 모델의 구성 요소 
![image]()
1. **드라이버 모델의 목적**: 모든 유형의 장치에서 공통 코드를 공유할 수 있도록 추상화 계층을 제공하는 것이다. 
2. **세 가지 주요 행위자**: 리눅스 드라이버 모델에는 장치(Devices), 드라이버(Drivers), 버스(Buses) 세 가지 주요 구성 요소가 있다. 
3. **장치 (Device)**:
  1. struct device로 표현되며, 하드웨어 구성 요소의 소프트웨어적 논리 표현이다. 
  2. 실제 하드웨어 구성 요소 하나가 여러 struct device로 표현될 수도 있고, 하드웨어 없이 논리적으로만 존재하는 struct device도 생성 가능하다. 
4. **드라이버 (Driver)**:
  1. struct device_driver로 표현되며, 특정 장치를 처리하는 방법을 운영체제에 알려주는 일종의 레시피이다. 
5. **버스 (Bus)**:
  1. struct bus_type으로 표현되는 논리적 개체이다. 
  2. 주요 역할은 **드라이버와 장치를 서로 매칭시키고 연결**하여 그 기능을 수행하게 하는 것이다. 
  3. 드라이버는 항상 특정 버스 유형을 가지며, 버스 자체도 장치(Device)가 될 수 있다 (예: USB 컨트롤러는 USB 장치를 관리하는 버스이지만 그 자체로 장치이다). 


### 1.2. 장치와 드라이버 매칭 및 프로빙 과정 
![image]()
1. **초기 상태**: 모든 버스는 장치 목록(List of devices)과 드라이버 목록(List of drivers)을 가지고 있다. 
2. **드라이버 등록**: 동적 모듈 로딩이나 빌트인 모듈 초기화를 통해 새로운 드라이버가 버스에 등록된다. 
3. **매칭 시작 (장치 등장 시)**: 새로운 장치가 장치 목록에 나타나면, 버스는 이 장치에 연결되지 않은 드라이버 목록을 순회한다. 
  1. 버스는 드라이버 목록을 순서대로 순회하며, 장치와 드라이버를 매칭시키기 위해 콜백 함수(C 함수)를 호출한다. 
  2. **매치 콜백**: 이 콜백 함수의 역할은 장치와 드라이버가 함께 작동할 수 있는지 확인하는 것이다. 
  3. 매칭이 되지 않으면 다음 드라이버로 이동한다. 
4. **프로빙 (Probing)**: 매칭이 성공하면, 드라이버를 장치에 부착(attaching)하는 절차를 시작하기 위해 probe 콜백을 호출한다. 
  1. **프로빙의 목적**: 장치와 드라이버가 올바르게 매칭되었음을 확인한 후, 실제로 함께 작동할 수 있는지를 확인하는 과정이다. 
  2. **성공적인 부착**: probe 함수가 0을 반환하면 프로빙이 성공한 것이며, 장치는 드라이버에 **바운드(bound)** 상태로 등록되어 함께 작동하게 된다. 
5. **프로브**** 지연 (Probe Deferral)**:
  1. 새로운 장치가 나타나 매칭에 성공했으나 probe 함수가 E_PROBE_DEFER 오류를 반환할 수 있다. 
  2. **지연의 의미**: 이는 장치와 드라이버가 호환되지만, 장치 기능 활성화에 **일부 리소스가 누락**되어 있음을 의미한다. 
  3. 커널 드라이버 모델은 해당 장치를 **지연된 장치 목록 (list of deferred devices)**에 넣어 리소스가 준비될 때까지 프로빙을 기다리게 한다. 
6. **지연된 장치의 처리**:
  1. 이후 다른 장치(Device 2)가 나타나 성공적으로 프로브되어 시스템에 부착되면, 이 장치 2가 이전에 Device 1이 필요로 하던 누락된 리소스를 제공했을 가능성이 있다. 
  2. 커널은 지연된 장치 목록으로 돌아가 이전에 매칭되었던 드라이버로 다시 프로빙을 시도하며, 이번에 프로브가 성공하면 장치 1도 부착된다. 
7. **역방향 매칭 (Reverse Matching)**:
  1. 새로운 드라이버가 시스템에 등록될 경우 (이미 장치가 등록된 상태), 시스템은 드라이버 목록 대신 장치 목록을 순회하여 새 드라이버와 매칭을 시도한다. 
  2. 이러한 과정을 통해 모든 장치와 드라이버가 리눅스 커널에서 작동하게 된다. 


## 2. 정적 장치 (Non-Discoverable Devices)와 플랫폼 버스 
![image]()
1. **장치 분류**: 장치는 동적으로 발견될 수 있는 장치(예: USB 장치)와 동적으로 발견될 수 없는 장치(정적으로 정의되어야 하는 장치, 예: USB 컨트롤러)의 두 가지 주요 범주로 나뉜다. 
2. **플랫폼 버스****의 중요성**:
  1. 동적으로 발견될 수 없는 장치를 시스템에 등록할 수 있게 해주는 버스를 **플랫폼 버스****(Platform Bus)**라고 한다. 
  2. 플랫폼 버스는 리눅스에서 매우 중요한 버스로 간주되는데, 대부분의 동적 버스(Dynamic bus)는 결국 플랫폼 버스 상의 부모를 가지기 때문이다. 
3. **펌웨어에 의한 장치 설명의 필요성**:
  1. 동일한 foo라는 추상적 장치가 시스템 A와 시스템 B에서 다르게 배선되어 있다고 가정한다 (예: 다른 레귤레이터, 다른 클럭 사용). 
  2. 심지어 동일한 SOC의 IP라도 다른 레지스터 범위에 매핑될 수 있다. 
  3. **목표**: 드라이버가 동일하더라도 시스템에 따라 다르게 구성되어야 하며 (예: 올바른 레지스터 범위 매핑, 특정 레귤레이터 활성화), 이러한 구성 정보를 드라이버에 전달해야 이식성이 보장된다. 
4. **핵심 문제**: 동일한 장치에 대해 배선 방식이 다를 때 동일한 플랫폼 드라이버를 재사용하려면, 장치와 함께 **어떤 종류의 설정 정보**를 드라이버에 전달해야 한다. 


## 3. 설정 전달의 역사: Platform Data와 Board Files의 한계 
![image]()
1. **과거의 설정 전달 방식 (2010년 이전): ****보드 파일**** (Board Files)**:
  1. Device Tree가 널리 채택되기 이전에 ARM 시스템 등에서는 **보드 파일**을 사용하여 플랫폼 장치를 등록했다. 
  2. 보드 파일은 하드웨어를 C 언어 구조체로 정의하고, 부팅 시퀀스 중 특정 함수를 호출하여 장치를 시스템에 등록했다. 
  3. **주요 문제점**:
  1. **C 코드와 하드웨어 설명의 혼합**: 하드웨어를 기술하는 C 코드는 절차적 언어이므로 엄격한 순서가 요구되었고, 장치 초기화의 병렬화가 불가능했다. 
  2. **기능 논리와 하드웨어 설명 혼재**: 하드웨어 설명이 기능 논리와 뒤섞였다. 
  3. **수동적인 의존성 관리**: 의존성을 수작업으로 처리해야 했으며, 아키텍처 코드(보드 파일)와 드라이버 코드 사이에 C 콜백이 혼재되어 복잡했다. 
2. **하드웨어 설명의 주요 구조**: 보드 파일에는 resources와 platform data 두 가지 주요 구조체가 있었다. 
  1. **Struct Resource**:
  1. 매우 오래된 구조로, Git이 사용되기 훨씬 전부터 존재했다. 
  2. 레지스터 범위, 주소, 인터럽트 정보를 설명하는 트리 형태의 구조이며, 부모-자식 관계를 가진다. 
  3. 현재까지도 사용되고 있으며, 일부 Device Tree 속성(Properties)은 리소스로 변환되어 드라이버에서 사용된다. 
  2. **Platform Data**:
  1. struct resource로 전달될 수 없는 구성을 드라이버에 전달하기 위해 사용되었다. 
  2. 각 드라이버는 자체 구성 정보를 담는 C 구조체를 헤더 파일에 정의했다. 
  3. **문제점**: 문자열, 정수, 다양한 유형의 속성을 전달하기 위해 구조체가 반복적으로 정의되었고, GPIO 설정 등을 위한 콜백 함수들이 아키텍처 코드로 돌아갔다. 
  4. **폭발적인 증가**: 각 플랫폼마다 자체 platform data 구조를 정의하면서 구조체의 수가 폭발적으로 증가하여 일관성 문제가 심각해졌고, 리누스 토르발스는 ARM 개발자들에게 일관성을 갖출 것을 요구했다. 
3. **결론**: 드라이버에 구성을 제공하기 위한 더 나은 방법이 필요했다. 


## 4. Device Tree (DT)의 등장과 구조 
![image]()
1. **Device Tree (DT)**: 하드웨어를 설명하는 데이터 구조로 도입되었다. 
  1. Device Tree는 사실 트리 구조보다는 **비순환 방향성 그래프(acyclic directed graph)**에 가깝지만, 'Device Tree'라는 이름으로 채택되었다. 
  2. 텍스트 및 바이너리 형식을 모두 정의하며, DTC(Device Tree Compiler)를 사용하여 상호 변환할 수 있다. 
2. **DT의 주요 구성 요소**:
  1. **노드**** (Nodes)**: Device Tree의 기본 단위이며, 부모-자식 관계를 가진다. 
  2. **P 핸들**** (P handles)**: 노드들이 서로를 참조할 수 있도록 하는 메커니즘이다. 
  3. **속성 (****Properties****)**: 노드가 가지는 데이터로, 문자열, 배열, 정수 등 다양한 유형이 있다. 
3. **DT 구성 예시**:
  1. foo와 bar가 노드이며, bar의 자식 노드가 존재한다. 
  2. fu 노드가 bar 노드를 P 핸들로 참조하는 방식이 사용된다. 
  3. Device Tree에는 그래프, 포인트, 엔드포인트 등의 복잡한 개념들도 포함된다. 
4. **바인딩**** (Bindings)**:
  1. Device Tree 소스를 업스트림하려면 Device Tree 바인딩(Bindings)에 따라야 한다. 
  2. 바인딩은 특정 장치 리소스가 따라야 하는 속성과 형식(Schema documents)을 정의한다. 
5. **리눅스에서의 DT 처리**:
  1. 리눅스는 부팅 시 전달된 Device Tree의 바이너리 형식을 파싱하고, 메모리에서 device_node라는 구조체의 비순환 방향성 그래프로 표현한다. 
  2. **OF 인터페이스**: 리눅스 드라이버는 Device Tree를 순회하고 속성을 추출하며, 노드를 참조하는 등의 작업을 수행하는 라이브러리 함수들을 제공하며, 이 함수들은 **OF (Open Firmware)** 접두사를 공유한다. 
  3. **OF 함수 예시**: 문자열 속성은 of_property_read_string으로, 노드 주소는 parse_p_handle로, 자식 노드는 반복자를 통해 접근할 수 있다. 


## 5. 펌웨어 노드 (FW Node)의 일반화와 진화 
1. **펌웨어 설명의 다양성**: Device Tree 외에도 ACPI가 하드웨어를 펌웨어로 설명하는 방식이다. 
2. **ACPI**** ****노드**: ACPI 역시 C 구조체의 집합으로 번역될 수 있으며, 부모-자식 관계와 노드 참조, 속성을 가진다. 
3. **소프트웨어 노드**** (Software Node)**:
  1. Device Tree 및 ACPI 외에 **C 기반**으로 장치를 설명하는 또 다른 개념으로, platform data보다 개선된 방식이다. 
  2. 소프트웨어 노드는 Device Tree 노드(OF node), ACPI 노드와 유사한 역할을 수행한다. 
4. **FW Node (****펌웨어 노드****)의 탄생**:
  1. Device Node, ACPI Node, Software Node가 모두 비슷한 역할을 수행함에 따라, 이들을 동일한 인터페이스로 접근할 수 있도록 일반화하는 노력이 이루어졌으며, 그 결과 **펌웨어 노드**가 탄생했다. 
  2. **FW Node 구조**: struct fwnode_handle을 사용하여 Device Node 등을 감싸는 프론트엔드 역할을 한다. 
  3. Device Tree의 P 핸들은 펌웨어 노드에서는 **참조(references)**로 일반화되었다. 
5. **FW Node API의 사용**:
  1. 기존의 OF 인터페이스를 사용하던 Device Node를 of_fwnode_handle 함수를 사용하여 펌웨어 노드로 형 변환하면, 드라이버는 FW node 인터페이스를 사용하여 모든 노드에 접근할 수 있다. 
  2. 이로써 드라이버는 내부적으로 ACPI 노드, Device Node, Software Node 중 무엇이 사용되는지 신경 쓰지 않고 동일한 인터페이스를 사용하게 된다. 


### 5.1. 소프트웨어 노드의 역할과 Platform Data와의 차이 
![image]()
1. **소프트웨어 노드****의 필요성**:
  1. 일부 장치에 펌웨어 노드가 아예 없거나 (예: ACPI에서 누락), 펌웨어 설명에 런타임에 읽어야 하는 정보가 부족한 경우 (부트로더에서 Device Tree를 업데이트할 수 없을 때), 소프트웨어 노드가 생성된다. 
2. **특징**:
  1. 정적으로 정의되어 런타임에 등록되거나, 완전히 동적으로 등록될 수 있다. 
  2. Device Tree와 동일한 속성을 공유하며, 부모-자식 관계를 가지고 다른 소프트웨어 노드를 참조할 수 있다. 
3. **Platform Data와의 유사성**:
  1. C로 작성된 소프트웨어 노드의 정의 부분은 platform data와 매우 유사해 보인다. 
  2. **장점**: 소프트웨어 노드는 firmware node 인터페이스를 공유하므로, 드라이버는 특별한 헤더를 포함하거나 특정 구조체를 파싱할 필요 없이 장치의 펌웨어 노드를 가져와 사용하면 된다. 


### 5.2. Secondary Firmware Node (보조 펌웨어 노드) 
![image]()
1. **개념**: 장치에 **주요 ****펌웨어 노드****(Primary firmware node)** 외에 **보조 ****펌웨어 노드****(Secondary firmware node)**를 하나 더 연결할 수 있다. 
2. **사용 목적**: 주요 노드에 속성(Properties)이 누락되었을 경우, 소프트웨어적으로 해당 속성들을 정의하여 보조 노드로 부착하고 주요 노드를 보완하는 데 사용된다. 
3. **속성 검색 순서**: 펌웨어 노드 인터페이스를 사용하여 속성을 읽으면, 시스템은 먼저 **주요 ****펌웨어 노드**에서 찾고, 해당 속성이 없으면 **보조 ****펌웨어 노드**에서 검색한다. 
4. **실제 적용 사례**: ACPI 시스템에서 속성이 누락되거나 잘못된 경우, x86 드라이버들은 소프트웨어 노드를 정의하고 이를 ACPI 노드의 보조 노드로 할당하여 문제를 해결하는 것이 일반적이다. 
5. **DT에서의 사용**: Device Tree에서는 부트로더에서 업데이트가 가능하므로 보조 노드가 많이 사용되지 않지만, OF(DT) 장치 노드에도 누락된 속성을 가진 보조 소프트웨어 노드를 할당하여 리눅스 커널 내에서 수정하는 것이 가능하다. 


## 6. 장치 링크 (Device Links) 및 진화적 설계 
![image]()
1. **장치 링크****의 필요성**:
  1. 펌웨어 노드가 주로 부모-자식 관계에 초점을 맞추는 반면, 장치 링크는 **수평적 관계** (형제 관계, 리소스 공급자-소비자 관계 등)를 다룰 때 사용된다. 
  2. 특히 **리소스 공급자(Suppliers)와 소비자(Consumers)** 간의 관계를 정의하는 데 유용하다. 
2. **작동 원리 (순서 강제)**:
  1. **예시**: SOC의 MAC 장치가 클럭과 외부 PHY(FI)를 필요로 한다. 클럭과 PHY는 MAC의 공급자이다. 
  2. 리눅스는 MAC을 프로빙하기 전에 클럭과 PHY가 준비되어야 한다고 판단한다. 
  3. **효율성**: 공급자가 없으면 MAC 드라이버는 프로브를 지연시킬 것이고, 이는 자원 할당 등 시간 낭비로 이어지므로, Device Link는 드라이버가 불필요하게 프로브 지연을 하지 않도록 순서를 강제하는 데 사용된다. 
3. **다른 용도 (Suspend/Resume 및 Unbind)**:
  1. 장치 링크는 **Suspend (일시 정지) 및 Resume (재개) 계층 구조**를 설정하는 데도 사용된다. 소비자가 사용 중인 리소스 공급자를 소비자가 정지되기 전에 정지할 수 없기 때문이다. 
  2. 드라이버 바인딩 해제 시에도, 리소스 공급자를 제거하기 전에 **모든 소비자를 먼저 ****바인딩**** 해제**해야 한다. 
4. **리눅스 커널**** 설계의 은유 (반회후두신경)**:
  1. 연설자는 리눅스 커널의 복잡한 구조를 **반회후두신경(Recurrent laryngeal nerve)**에 비유한다. 
  2. 이 신경은 뇌에서 후두를 거쳐 심장까지 내려갔다가 대동맥을 감고 다시 후두로 돌아오는 비효율적인 경로를 가진다. 
  3. 이는 해양 생물이었던 조상들이 아가미로 신경이 직진하던 구조에서 진화했으나, 대동맥 뒤에 신경이 그대로 남게 된 진화적 결과이다. 
  4. **리눅스의 진화**: 리눅스 커널도 수많은 세월 동안 지능적인 설계가 아닌, **점진적인 변화(Evolution)**를 겪어왔다. 새로운 프레임워크가 등장해도 기존 인터페이스를 사용하는 코드가 남아있기 때문에 완벽한 설계가 불가능하며, **충분히 좋은(good enough)** 구조를 만들어 시스템에 통합해왔다. 
  5. 이것이 바로 리눅스에 다양한 유형의 펌웨어 노드가 존재하는 이유이다. 


## 7. 새로운 드라이버 작성 시 API 선택 가이드라인 


### 7.1. 최우선 권장: Device Property Accessors (상위 레벨 API) 
![image]()
1. **대상**: 플랫폼 드라이버나 보조 드라이버를 작성하며 속성을 검색해야 할 때. 
2. **사용 API**: struct device를 사용하여 최상위의 **Generic Device Property Accessors**를 사용해야 한다. 
  1. **가장 일반적**: 이 API는 가장 일반적이며, **펌웨어 노드**** 경로(firmware node path)**를 사용하여 속성을 찾는다. 
  2. **Secondary FW Node 지원**: 이들은 OF(Open Firmware) 인터페이스와 달리 **보조 ****펌웨어 노드**까지 하강하여 속성을 찾을 수 있다. 
3. **함수 형태**: 기존의 OF 및 FW Node 인터페이스는 device_property_read_something 형태의 함수로 대체된다. 


### 7.2. FW Node API (중간 레벨 API) 사용 시점 
![image]()
1. **제한된 상황**: Device Property Accessors는 다소 제한적이어서 모든 상황을 커버하지 못한다. 
2. **주요 사용 사례**:
  1. **Device와 연결되지 않은 ****노드**** 처리**: 단일 장치와 연결된 펌웨어 노드가 자식 노드(children)를 가질 때, 이 자식 노드들은 장치(Device)와 연결되어 있지 않을 수 있다. 
  2. **자식 ****노드**** 순회**: 장치에 연결되지 않은 자식 노드를 순회하려면, device_for_each_child_node를 사용하고 반환된 FW node 핸들을 FW node 인터페이스에 전달해야 한다. 
  3. **장치에 부착되지 않은 ****노드**** 정보 추출**: 아직 장치에 부착되지 않은 노드로부터 정보를 추출해야 할 때 FW node API를 사용할 수 있다. 


### 7.3. Low-level API (OF, SW, ACPI Node API) 사용 시점 
![image]()
1. **FW Node API의 한계**: 펌웨어 노드 API에는 펌웨어 노드의 **모든 속성을 순회**할 수 있는 방법이 없다. 
  1. **속성 순회 필요 시**: 어떤 이유로든 노드의 모든 속성을 순회해야 한다면, 해당 노드를 Device Node로 형 변환하고 속성 항목(property entries)을 직접 순회해야 한다. 
2. **소프트웨어 노드**** 등록 이전**: 소프트웨어 노드는 실제로 등록(Register)되어야 펌웨어 노드가 되며, 등록 함수가 호출되기 전까지는 **소프트웨어 노드**** 인터페이스**를 직접 사용해야 한다. 


### 7.4. 최종 권장 사항 (우선순위) 
![image]()
1. **새로운 드라이버 작성 시 API 우선순위**:
  1. **1순위**: **Device Property Accessors**
  2. **2순위**: Device Property Accessors를 사용할 수 없는 경우 **Firmware Node API**
  3. **3순위**: 위 두 가지 모두 사용할 수 없는 경우 **OF, SW Node 또는 ****ACPI**** Node API** (Low-level API)
2. **결론**: Device Tree만 사용하는 플랫폼용 드라이버를 작성하더라도, 더 추상적이고 일반적인 **Firmware Node API**를 사용하는 것이 권장된다. 


## 8. Q&A 및 기술적 문제 논의 
![image]()
1. **FW Node API의 속성 순회 기능 부재 (기술적 난제)**: 
  1. 연설자는 모든 펌웨어 노드의 속성을 순회하는 기능을 구현하고 싶지만, **기술적인 어려움**이 있다. 
  2. **이유**: 노드 유형별로 속성을 저장하는 방식이 다르다 (OF 노드는 OF 고유 구조체의 배열 사용, 소프트웨어 노드는 property_entry 사용). 
  3. property_entry는 다양한 유형의 데이터를 저장하는 일종의 가변체(variant) 형태로, 파싱하기가 매우 까다롭다. 
  4. 모든 속성에 대한 공통 반환 타입을 정의하기 위해 또 다른 추상화 계층을 도입해야 하는 문제가 있다. 
2. **FW Node API의 호환성 (****ACPI**** ****바인딩****)**: 
  1. **질문**: FW Node API를 사용하는 것이 권장된다면, ACPI도 Device Tree와 정확히 동일한 바인딩(예: XYZ 속성)을 구현한다고 가정해야 하는가? 
  2. **답변**: **일반적으로 그렇다**. ACPI 표준(예: PRP00001)에 의해 ACPI가 Device Tree 전용 드라이버를 사용할 수 있도록 호환성 매칭을 지원하는 경우가 있다. 
  3. Device Tree 바인딩이 매우 영향력이 커서, 일부 ACPI 속성은 코드 내에서 Device Tree 바인딩에 대응하도록 번역되기도 한다. 
  4. **역문제**: ACPI는 전원 관리 등 Device Tree 바인딩이 표현할 수 없는 훨씬 많은 기능을 수행하는 경우가 있으며, 이 경우 드라이버를 Device Tree 바인딩에 맞추어 작성할 수 없는 문제가 있다. 
  5. **해결책**: 이 경우, ACPI 노드에 **소프트웨어 노드**를 생성하여 누락된 정보를 채우는 **Secondary Firmware Node** 개념이 도움이 될 수 있다. 
3. **Device Tree의 메타데이터 비효율성 (Config 필터링 부재)**: 
  1. **문제 제기**: Device Tree는 Board Files보다 좋지만, Device Tree를 지원하는 드라이버들이 커널 구성(Kernel Config)에 따라 필터링되지 않는 방대한 호환성(Compatible) 목록을 가지고 있다는 큰 문제가 있다. 
  2. 예를 들어, CPU 유휴 드라이버 등은 실제로 사용되지 않는 시스템의 호환성 목록까지 모두 포함하여 컴파일되므로, 쓸모없는 데이터가 커널에 남아 비효율적이다. 
  3. **연설자의 답변**: 이것은 Device Node 자체의 문제가 아니라, 드라이버가 여러 개의 호환성 문자열을 포함하도록 작성된 **드라이버 문제**이며, 하드웨어 표현 방식과는 무관하다. 
  4. **해결책**: ifdef를 사용하여 아키텍처 활성화 여부에 따라 호환성 목록을 조건부 컴파일하는 방식으로 해결할 수 있을 것으로 보인다. 
4. **ACPI****와 DT 동시 지원 드라이버의 비효율성**: 
  1. **문제 제기**: ACPI와 Device Tree를 모두 지원하는 드라이버는 데이터를 다른 방식으로 가져오는데, ACPI가 없는 플랫폼에서도 Device Node 내에 ACPI 관련 정보가 남아있을 수 있다. 
  2. **마무리**: 발표자가 이 부분은 추가 논의가 필요하다고 판단하며 발표가 마무리된다.
