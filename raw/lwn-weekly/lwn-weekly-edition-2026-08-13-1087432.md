## 전체 기술 요약

- Linux 실행 형식 처리에 BPF를 연결해, 재배치 가능한 바이너리와 컨테이너 환경의 인터프리터 선택을 더 유연하게 만들려는 작업이 진행 중이다.[^1]
- KVM planes는 CPU 공급사별 confidential-computing 격리 모델을 하나의 Linux/KVM 추상화로 다루려는 시도다.[^2]
- BPF 안전성 논의는 커널 충돌 방지를 넘어, 스케줄링 지연과 XDP 트래픽 손실 같은 서비스 수준의 불변식까지 확장되고 있다.[^3]
- shadow-utils는 주기적 비밀번호 교체를 기본 보안 관행에서 제거하고, 침해 대응과 강한 인증 수단에 초점을 옮기고 있다.[^4]
- 블록 계층 오류 주입은 실제 장치별 I/O 실패를 재현해 파일시스템·스토리지 복구 경로를 테스트하기 쉽게 만든다.[^5]
- ESP32 기반 소형 e-reader의 CrossPoint 펌웨어는 제한된 메모리와 전력 예산에서 EPUB 렌더링·전송·글꼴 처리를 최적화하는 사례다.[^6]

### [BPF를 binfmt_misc로 가져오기](https://lwn.net/Articles/1086947/)

- `binfmt_misc`의 BPF `struct_ops`가 `match()`와 `load()` 콜백으로 실행 파일에 맞는 인터프리터를 선택하도록 한다.[^1]
- 재배치 가능한 Nix 바이너리에서는 BPF가 동적 링커를 결정해, 절대 `PT_INTERP` 경로의 제약을 줄이는 방향이다.[^7]
- 투명 디스패치와 로더 대체 모드는 `argv` 및 프로세스 이름을 원래 실행 파일 기준으로 유지하려 한다.[^8]
- setuid와 컨테이너 네임스페이스에서의 로더 주입을 막기 위해, 미리 연 허용 인터프리터 집합과 사용자별 리소스 제한을 둔다.[^9]

### [CrossPoint e-reader 펌웨어 살펴보기](https://lwn.net/Articles/1087635/)

- CrossPoint 1.5.0은 대형 EPUB 열기, 오프라인 사전, 레이아웃·글꼴 설정, RTL/CJK 렌더링을 개선했다.[^6]
- ESP32-C3/S3 기반 기기의 적은 RAM과 느린 CPU를 전제로, PDF·RSS·작성 도구보다 읽기 성능과 배터리 수명을 우선한다.[^10]
- 내장 웹 서버로 Wi-Fi 파일 전송과 설정을 제공하지만 HTTP이므로 공용 Wi-Fi에서는 민감한 사용을 피해야 한다.[^11]
- Calibre 플러그인은 이미지 축소·내장 글꼴 제거·큰 장 분할로 기기 메모리 사용량을 낮춘다.[^12]

### [KVM planes가 이륙을 준비하다](https://lwn.net/Articles/1087590/)

- KVM planes는 SEV-SNP, TDX, Hyper-V VTL, Arm Realm Plane처럼 서로 다른 보안 도메인을 공통 모델로 표현한다.[^2]
- plane은 주소 공간은 공유하되 CPU 레지스터 상태와 일부 자원을 분리하고, plane 전환은 하이퍼바이저를 통해 수행한다.[^13]
- `KVM_CREATE_PLANE`은 새 plane용 파일 디스크립터를 돌려주며, 각 plane은 유용하려면 적어도 하나의 vCPU를 가져야 한다.[^14]
- 권한이 낮은 plane은 자신이 가진 권한보다 더 큰 메모리·인터럽트 권한을 얻을 수 없도록 설계된다.[^15]

### [BPF에 대한 더욱 공식적인 검증](https://lwn.net/Articles/1087069/)

- 현재 BPF verifier는 커널 불변식을 보호하지만, 서비스가 계속 유용한지까지 보장하지는 않는다.[^3]
- `sched_ext`는 실행 가능한 태스크를 방치하지 않는 성질, XDP는 패킷을 반드시 어떤 목적지로 전달하는 성질이 후보 불변식이다.[^16]
- Verus 같은 도구로 단순한 Rust 래퍼의 `push()`·`pop()` 불변식을 컴파일 시 증명하고, 이후 일반 BPF verifier를 통과시키는 구상이 제시됐다.[^17]
- 성능 저하도 사용 맥락에 따라 안전성의 일부가 될 수 있으므로, 배포 전 워크로드별 검증이 중요하다.[^18]

### [shadow-utils 비밀번호 만료 기능의 변경 사항](https://lwn.net/Articles/1086949/)

- 주기적 비밀번호 교체는 예측 가능한 작은 변경을 유도할 수 있어, 현대 지침은 이를 강제하지 않는 방향이다.[^4]
- 최소 비밀번호 수명은 침해 의심 시 즉시 변경을 막을 수 있으므로 제거 대상이 된다.[^19]
- `chage`, `usermod`, `/etc/shadow`의 노화 관련 필드·옵션은 단계적으로 축소 또는 폐기될 예정이며, 조직 정책은 그 영향을 점검해야 한다.[^20]
- 이는 비밀번호 회전 자체를 금지하기보다, MFA·침해 감지·신속한 재설정 같은 더 효과적인 통제로 보완해야 한다는 운영상 함의를 갖는다.[^21]

### [블록 계층 오류 주입](https://lwn.net/Articles/1086344/)

- `CONFIG_BLK_ERROR_INJECTION`과 디스크별 `debugfs` 규칙은 지정한 블록 I/O에 전송·미디어 오류 등을 의도적으로 발생시킨다.[^5]
- 대상 섹터·길이·연산·발생 확률을 정해 정상 요청은 그대로 두고 특정 실패 경로만 재현할 수 있다.[^22]
- 이는 드라이버·파일시스템·애플리케이션의 재시도와 데이터 무결성 처리를 실제 장애 전에 검증하는 데 유용하다.[^23]
- 테스트는 격리된 장치 또는 `scsi_debug` 같은 시험 환경에서 수행하고, 운영 디스크의 `debugfs` 설정은 피해야 한다.[^24]

## 각주

[^1]: `binfmt_misc`는 파일 매직이나 확장자에 맞춰 실행기를 고르는 Linux 커널 메커니즘이다.
[^2]: confidential computing은 VM 내부도 여러 신뢰 경계로 나눠 민감 구성 요소를 보호하려는 접근이다.
[^3]: BPF verifier는 메모리·형·호출 규칙을 검사하지만 업무 수준의 성능·가용성 정책은 별도 검증이 필요하다.
[^4]: 비밀번호 만료는 유출 증거가 없을 때의 일괄 교체보다 강한 비밀번호·MFA·침해 대응을 중시하는 지침과 충돌할 수 있다.
[^5]: 오류 주입은 정상 경로만으로는 검증하기 어려운 I/O 실패 복구 코드를 의도적으로 실행하는 테스트 기법이다.
[^6]: e-ink 기기는 갱신 속도, RAM, 전력 제약이 커서 데스크톱용 기능 선택을 그대로 적용하기 어렵다.
[^7]: `PT_INTERP`는 ELF 동적 실행 파일이 사용할 로더 경로를 담는 세그먼트다.
[^8]: `argv`와 프로세스 이름 보존은 `ps`, `top`, 감사 로그에서 실제 실행 대상을 알아보기 쉽게 한다.
[^9]: 미리 연 파일을 쓰면 마운트 네임스페이스가 바뀌어도 공격자가 다른 로더 경로로 바꾸기 어렵다.
[^10]: 기능 범위 제한은 임베디드 펌웨어에서 메모리 단편화와 배터리 소모를 통제하는 설계 선택이다.
[^11]: HTTP 관리 화면은 같은 네트워크의 도청·변조 위험이 있으므로 신뢰 가능한 LAN에서만 쓰는 것이 안전하다.
[^12]: EPUB 내부 자원을 줄이면 작은 RAM에서 파싱·렌더링 시 실패하거나 느려질 위험을 낮춘다.
[^13]: 하이퍼바이저는 VM보다 낮은 계층에서 plane 전환과 격리 규칙을 강제한다.
[^14]: 파일 디스크립터 기반 KVM API는 생성한 가상화 객체의 수명·설정을 사용자 공간에서 제어하게 한다.
[^15]: 권한 상승을 금지하는 단조성은 낮은 신뢰 도메인이 더 높은 도메인을 침범하지 못하게 하는 핵심 속성이다.
[^16]: 런타임 watchdog은 정적 증명이 없는 경우 비정상 BPF 프로그램을 퇴출하는 최후의 방어선이다.
[^17]: 단순화된 API는 증명해야 할 상태 공간을 줄여 형식 검증을 실용화하는 일반적 방법이다.
[^18]: 저부하 성능 회귀도 운영 환경에서는 장애처럼 보일 수 있어 대표 워크로드 시험이 필요하다.
[^19]: 최소 변경 주기는 계정 탈취 직후 비밀번호 교체를 지연시킬 수 있다.
[^20]: `/etc/shadow`의 노화 필드는 배포판 도구·감사 스크립트와 결합될 수 있으므로 호환성 검토가 필요하다.
[^21]: MFA는 비밀번호 하나가 유출돼도 추가 인증 요소로 계정 탈취 위험을 줄인다.
[^22]: 블록 I/O 규칙의 범위화는 실패 주입이 다른 시험 데이터나 운영 워크로드에 퍼지는 것을 막는다.
[^23]: 재시도 정책은 오류 유형에 따라 데이터 손상·중복 쓰기 위험이 달라져, 실제와 가까운 실패 시험이 중요하다.
[^24]: `debugfs`는 주로 진단·개발용 인터페이스이므로 운영 시스템에서의 변경은 위험할 수 있다.

[실행 가능 및 연결 가능 형식(ELF)](https://en.wikipedia.org/wiki/Executable_and_Linkable_Format)에 대한 지원은 1993년 0.99.13 릴리스에 추가되었으며, 배포 지원(업그레이드가 너무 고통스러워 수년이 지난 후에도 여전히 외상 후 스트레스를 유발할 수 있음)이 1995년경에 도착했습니다. 그러나 초창기부터 다양한 형식으로 프로그램을 실행하는 데 관심이 있었습니다. 예를 들어, x86 시스템에 사용할 수 있는 Unix 변형은 다양했습니다. 각 변형은 고유한 바이너리 형식을 가지고 있습니다. 자체 가상 머신으로 컴파일되고 별도의 인터프리터가 필요한 Java와 같은 언어가 있습니다. 커널은 이러한 모든 형식을 *지원할 수* 있지만 좀 더 일반적인 솔루션이 필요하다는 것이 일찍부터 이해되었습니다.
해당 솔루션은 1997년 2.1.43pre1 개발 릴리스에 추가된 binfmt_misc입니다. 현재 형식에서 binfmt_misc는 /proc/sys/fs/binfmt_misc 아래에 Register라는 파일이 포함된 디렉터리를 제공합니다. 해당 파일에 문자열을 쓰면 새로운 형식이 등록되고 해당 형식의 실행 파일을 인식하는 방법을 커널에 알려줍니다. 인식은 파일 자체의 처음 256바이트에 있는 패턴이나 파일 이름 확장자를 기반으로 할 수 있습니다. 예를 들어, 문서에는 이 문자열을 레지스터 파일에 기록하여 압축된 DOS 응용 프로그램에 대한 지원을 가질 수 있다고 나와 있습니다.::DEXE:M::\x0eDEX::/usr/bin/dosexec: 이 행은 커널이 파일 시작 부분의 4바이트 시퀀스 \x0eDEX로 압축된 DOS 실행 파일을 인식하도록 합니다. 해당 실행 파일을 실행하기 위해 /usr/bin/dosexec를 호출합니다. 또 다른 예로, 확장자가 a.py이고 실행 권한이 있는 모든 파일은 다음을 사용하여 직접 실행할 수 있습니다::python:E::py::/usr/bin/python3: 이 작업이 완료되면 .py 파일은 #! 포함 여부에 관계없이 Python 인터프리터에 의해 실행됩니다. 선. 여러 binfmt_misc 항목을 만들 수 있습니다. 프로그램에 대한 통역사를 찾아야 할 때마다 첫 번째 일치 항목이 선택됩니다. 특이한 점은 항목이 예상한 반대 순서로 확인된다는 점입니다. 가장 최근에 추가된 항목이 먼저 확인됩니다. binfmt_misc를 사용하여 커널 개발자는 사용자 공간이 고유한 특수 실행 파일 형식에 필요한 모든 정책을 설정할 수 있도록 허용했습니다. 더 이상 커널에 전용 지원을 추가할 필요가 없었습니다. 이 기능은 수년에 걸쳐 천천히 개선되었지만 거의 30년 전에 도입된 이후 근본적인 변화는 많지 않았습니다.
밀폐형 바이너리 binfmt_misc로 정의된 형식에는 모두 프로그램의 실제 실행을 처리하는 인터프리터가 포함됩니다. 대신 네이티브 바이너리는 CPU에서 직접 실행되지만 (정적으로 링크되지 않는 한) 여전히 인터프리터가 필요합니다. 이 경우 인터프리터는 바이너리 코드를 메모리에 로드하고, 라이브러리를 로드하고, 참조를 해결하는 동적 링커입니다. 해당 인터프리터의 위치는 ELF 파일의 경우 ELF 바이너리 자체의 PT_INTERP 세그먼트에 있습니다. 이는 일반적으로 /lib64/ld-linux-x86-64.so.2.와 같습니다. 커널은 인터프리터를 로드한 다음 사용자 공간에서 나머지 작업을 수행하도록 합니다. 이 계획은 수년 동안 잘 작동했지만 항상 뭔가 다른 것을 원하는 사람이 있습니다. 지난 6월에 Farid Zakaria는 Nix 배포판에 재배치 가능한 바이너리가 필요하다는 [사례를 만들었습니다](https://fzakaria.com/2026/06/21/nix-needs-relocatable-binaries). 이는 완전히 독립적이고(밀폐적) 파일 시스템 계층 구조의 위치에 관계없이 실행될 수 있는 바이너리 프로그램입니다. 밀폐형 바이너리에는 무엇보다도 특정 버전의 동적 링커가 필요합니다. 이는 바이너리가 실행될 것으로 예상되는 시스템에 설치된 기본 버전이 아닐 수도 있습니다. PT_INTERP 메커니즘을 사용하면 다른 동적 링커를 지정할 수 있지만 해당 링커에 대한 절대 경로가 필요합니다. 이로 인해 실행 파일을 패치하거나 [chroot()](https://man7.org/linux/man-pages/man2/chroot.2.html) 또는 네임스페이스를 사용하여 트릭을 사용할 필요 없이 임의의 위치에 프로그램(및 해당 링커)을 설치하기가 어렵습니다. 결과적으로 이러한 유형의 시스템을 구축하는 것은 생각보다 어렵습니다. 이 문제에 대한 Zakaria의 [제안된 솔루션](https://lwn.net/ml/all/20260622043934.179879-1-farid.m.zakaria@gmail.com/)은 PT_INTERP가 실행 파일이 저장된 위치에 상대적인 경로를 지정하도록 허용하는 것이었습니다.
커널 커뮤니티는 최종 목표(밀폐형 바이너리 실행)를 지지했지만 이 접근 방식은 많은 우려를 불러일으켰습니다. Kees Cook은 커널 경로 조작으로 인해 발생하는 보안 문제에 대해 [걱정](https://lwn.net/ml/all/202606231236.325C882A78@keescook/)했습니다. Christian Brauner는 [더 강력하게 부정적](https://lwn.net/ml/all/20260625-atomkraftgegner-hunger-kursbuch-b452ff2becab@brauner/)으로 Zakaria의 접근 방식이 "악성 로더 주입 공격에 적합"하며 문제를 다른 방식으로 해결해야 한다고 말했습니다. 특히 그는 BPF 프로그램 설치가 프로그램에 적합한 인터프리터를 선택할 수 있도록 binfmt_misc를 늘리는 것이 올바른 접근 방식이라고 생각했습니다(https://lwn.net/ml/all/20260703-meditation-ratsuchende-moratorium-9ecdf1f3f8bb@brauner/). binfmt_misc용 BPF 2주도 채 지나지 않아 Brauner는 해당 기능을 구현하는 [패치 세트](https://lwn.net/ml/all/20260707-work-bpf-binfmt_misc-v1-0-74b995c84ec1@kernel.org)를 가지고 돌아왔습니다. 당시 그는 그 시점에서 일에서 물러나 자카리아가 일을 끝내도록 할 생각이었다고 말했다. Zakaria는 며칠 후 [자신만의 패치](https://lwn.net/ml/all/20260711-binfmt-misc-bpf-v2-v2-0-d6591ceaf207@gmail.com)로 정식으로 응답했습니다. 휴가 중 진정으로 휴식하는 방법을 보여주는 Brauner는 그동안 스스로 아이디어를 계속 개발했지만 결국 솔루션이 취할 형태로 보이는 [업데이트된 패치 세트](https://lwn.net/ml/all/20260714-work-bpf-binfmt_misc-v2-0-57b7529c002c@kernel.org)를 7월 14일에 가지고 돌아왔습니다. 이 작업에는 BPF 인터페이스와 binfmt_misc에 대한 추가라는 두 가지 구성 요소가 있습니다. BPF 측에는 프로그램이 인터프리터를 관리하도록 스스로 설정할 수 있는 새로운 [struct_ops](https://lwn.net/Articles/974848/) 인터페이스가 있습니다. 프로그램은 두 개의 콜백을 사용하여 새로운 작업 구조를 등록합니다.
struct binfmt_misc_ops { bool (*match)(struct linux_binprm *bprm); int (*load)(struct linux_binprm *bprm); 문자 이름[BINFMT_MISC_OPS_NAME_MAX]; }; match() 콜백은 실행 중인 프로그램을 설명하는 [linux_binprm](https://elixir.bootlin.com/linux/v7.1.5/source/include/linux/binfmts.h#L15) 구조에 대한 포인터를 받습니다. 이 작업은 BPF 프로그램이 이 경우 인터프리터를 관리하는 데 올바른 프로그램인지 결정하는 것입니다. 이는 현재 binfmt_misc 구현에서 특정 바이트 또는 파일 확장자에 대한 테스트와 동일한 기능을 제공합니다. 이 프로그램은 잠자기 가능하며 실행 파일의 모든 부분을 읽을 수 있습니다. 기존 binfmt_misc 테스트와 달리 처음 256바이트로 제한되지 않습니다. match() 콜백이 참 값을 반환하면 load() 콜백이 호출되어 이 프로그램을 실행하는 데 사용할 인터프리터를 선택합니다. 인터프리터를 프로그램과 연결하는 데 사용되는 새로운 kfunc인 bpf_binprm_set_interp()가 있습니다. match()가 true를 반환한 경우 load()는 성공해야 합니다. 그렇지 않으면 프로그램 실행이 실패합니다. 이름 필드는 binfmt_misc를 구성할 때 이 프로그램을 식별하는 데 사용됩니다. 해당 구성은::name:B::::bpf-handler-name:과 같은 문자열을 레지스터 파일에 작성하여 수행됩니다. 여기서 name은 binfmt_misc 항목이 알려진 이름이고(/proc/sys/fs/binfmt_misc 아래에 해당 이름으로 하위 디렉터리가 생성됨) bpf-handler-name은 BPF 프로그램을 등록할 때 사용되는 이름입니다. 등록이 완료되면 커널이 실행 가능한 프로그램을 실행하는 방법을 알아내려고 할 때마다 식별된 BPF 프로그램이 호출됩니다.
이 기능은 Nix 사용 사례를 만족시키기에 충분한 것 같습니다. Zakaria는 재배치 가능한 바이너리를 작동시키는 데 필요한 일종의 간단한 BPF 프로그램의 예를 포함하는 [만족스러운 블로그 게시물](https://fzakaria.com/2026/07/20/linux-kernel-will-support-origin-sort-of)을 게시했습니다. 그는 이 기능을 #! 라인 재배치가 가능하여 스크립트 케이스의 문제도 해결됩니다. 추가 단계 겉보기에 만족스러운 해결책을 통해 Brauner는 이전보다 더 즐거운 마음으로 휴가를 다시 보낼 것이라고 생각할 수도 있지만 그렇지 않았습니다. Zakaria는 새로운 binfmt_misc에 대한 한 가지 작은 문제를 지적했습니다. 인터프리터는 실행되는 프로그램이 *되지만* 사용자가 실행 중이라고 *생각*한 프로그램은 결국 인터프리터에 전달되는 인수가 됩니다. 이는 현재 시스템의 스크립트에서 볼 수 있는 것과 동일한 효과입니다. ps와 같은 도구는 인터프리터를 스크립트가 아닌 실행 중인 프로그램으로 표시합니다. ps 또는 top이 동적 링커를 실행하는 모든 프로세스로 가득 찬 시스템을 표시하면 사용자로부터 한두 가지 불만이 발생할 수 있습니다. 이에 대한 Brauner의 대답은 더 많은 binfmt_misc 기능을 추가하는 [21개 부분으로 구성된 패치 시리즈](https://lwn.net/ml/all/20260721-work-bpf-binfmt_misc-ptinterp-v2-0-e57866e4ae0f@kernel.org)였습니다. 그 중 하나는 binfmt_misc 항목의 플래그( T )를 사용하여 요청하거나 일치하는 BPF 프로그램에서 지정할 수 있는 새로운 "투명 디스패치" 모드입니다. 이 모드를 선택하면 커널은 바이너리를 직접 실행하는 것처럼 동작하지만 뒤에서 인터프리터를 대체합니다. 인수 벡터("argv") 및 작업 명령 문자열은 원래 [execve()](https://man7.org/linux/man-pages/man2/execve.2.html)에 전달된 대로 유지됩니다. 인터프리터는 필요한 특별한 방법으로 프로그램을 로드하고 실행하는 데 사용할 수 있는 열린 파일 설명자(AT_EXECFD [보조 벡터](https://www.man7.org/linux/man-pages/man3/getauxval.3.html) 항목에 지정됨)를 수신합니다.
실행할 프로그램이 실제로 대상 시스템의 기본 바이너리일 때 선택할 수 있는 더 간단한 모드도 있습니다. 이 경우 L 플래그로 선택된 "로더 대체" 모드는 BPF 프로그램에서 반환된 인터프리터가 실행 파일에 저장된 모든 PT_INTERP를 재정의하도록 합니다. 따라서 BPF 프로그램이 수행해야 하는 유일한 작업이 동적 링커를 찾을 수 있는 위치를 파악하는 것(예: Nix의 경우)인 경우 로더 대체 모드만 있으면 됩니다. 두 모드 중 하나를 사용하면 Zakaria가 지적한 문제가 해결되어 실행된 프로그램이 인터프리터의 이름이 아닌 자체 이름으로 표시됩니다. 하지만 이야기는 아직 끝나지 않았습니다. BPF 프로그램은 주어진 프로그램을 실행해야 하는 인터프리터의 경로 이름을 제어할 수 있지만 해당 경로 이름이 어떻게 해결되는지에 대해서는 언급하지 않습니다. 해당 해결은 프로그램이 호출된 네임스페이스에서 발생합니다. 해당 네임스페이스에 대한 권한을 가진 누군가가 새 파일 시스템을 마운트하여 자신만의 특별한 "해석기"를 향해 해결 방법을 지시할 수 있다면 문제가 발생할 수 있습니다. 이 문제는 setuid 프로그램이 실행되는 경우 특히 심각합니다. 잠재적인 공격자에게 자신의 통역사를 제공할 수 있는 기능을 제공하는 것은 만족스러운 결과를 얻는 방법처럼 보이지 않습니다. 인터프리터가 항목 자체에 지정되어 있는 일반적인 binfmt_misc 항목의 경우 커널은 인터프리터가 포함된 파일을 열고 모든 후속 호출에 이를 사용하도록 지시할 수 있습니다. 이는 프로그램이 실행되는 환경에 관계없이 의도한 인터프리터가 항상 사용되도록 보장합니다.
이 기능은 호스트의 파일 시스템에서 격리된 컨테이너 내에서 인터프리터를 사용할 수 있게 만드는 방법으로 [2016년에 추가](https://lwn.net/Articles/679308/)되었습니다. 그러나 BPF 프로그램은 인터프리터 경로를 원하는 대로 설정할 수 있으므로 커널이 특정 인터프리터를 미리 여는 것이 어렵습니다. Brauner에는 당연히 해당 문제에 대한 [패치 시리즈](https://lwn.net/ml/all/20260730-work-binfmt_misc-preopen-v1-0-4a0b0da71f16@kernel.org)도 있습니다. 이는 binfmt_misc 구성이 구성 시 커널에 의해 열릴 알려진 인터프리터 세트를 포함하도록 허용합니다. 그러면 BPF 프로그램은 특정 프로그램이 실행될 때마다 이들 중에서 선택할 수 있습니다. 하지만 이 모드를 활성화하려면 극복해야 할 몇 가지 어려움이 있었습니다. 현재 커널에서는 레지스터 파일에 대한 단일 쓰기로 binfmt_misc 항목을 완전히 지정해야 합니다. 해당 항목은 쓰기가 완료된 직후 전역적으로 표시되므로 절반만 지정된 상태로 둘 수 없습니다. 특히 경로 이름이 긴 경우에는 지정할 수 있는 인터프리터의 수를 제한할 수 있는 레지스터에 기록된 행의 길이 제한도 있습니다. 두 문제에 대한 해결책은 binfmt_misc 항목이 즉시 활성화되지 않고 생성될 수 있도록 하는 새로운 "비활성화" 모드를 만드는 것이었습니다. 그런 다음 여러 줄을 사용하여 해당 항목을 활성화하기 전에 조정할 수 있습니다. 사용 예는 커버레터에 나와 있습니다: cd /proc/sys/fs/binfmt_misc echo ':qemu:B::::qemu_user:D' >register echo '+aarch64 /usr/bin/qemu-aarch64' > qemu echo '+arm /usr/bin/qemu-arm' > qemu echo 1 > qemu 이 시퀀스는 qemu라는 새 항목을 생성하여 시작됩니다. 이 항목은 다음과 같은 BPF 프로그램을 호출합니다. qemu_user; 이 항목은 제어 디렉터리에 있는 파일(qemu라고도 함)로 표시됩니다. 첫 번째 echo 명령 끝에 있는 D는 항목이 처음에 비활성화됨을 나타냅니다.
다음 두 줄은 aarch64와 arm이라는 두 가지 인터프리터 선택 사항을 추가하며, 각각 커널에 의해 열려 있는 자체 프로그램이 있습니다. 끝에 echo 1이 있으면 항목이 활성화됩니다. BPF 프로그램의 load() 콜백이 일치하는 프로그램에서 실행되면 더 이상 인터프리터에 대한 전체 경로를 제공할 필요가 없습니다. 대신, 미리 구성된 인터프리터 중 하나의 이름만 제공합니다. 그런 다음 프로그램은 프로그램이 호출된 네임스페이스에 관계없이 동일한 파일을 사용하여 지정된 인터프리터로 실행됩니다. 마지막 (지금까지) 단계로 Brauner는 [짧은 시리즈](https://lwn.net/ml/all/20260803-work-binfmt_misc-interplimit-v1-0-4a2435500bd9@kernel.org)에서 특정 사용자가 열어 둘 수 있는 인터프리터 파일 수를 제한하는 손잡이를 설정했습니다. 이러한 제한이 없으면 사용자 네임스페이스에서 실행되는 적대적인 사용자는 시스템 리소스를 고갈시킬 만큼 충분한 "통역사" 파일을 열 수 있습니다. 최종 리소스 제한 시리즈를 제외하고 이 모든 작업은 현재 linux-next에 있으므로 7.3 병합 기간 동안 메인라인에 포함될 것으로 예상됩니다. 궁금하신 분들을 위해 [문서/admin-guide/binfmt_misc.rst](https://docs.kernel.org/next/admin-guide/binfmt-misc.html)에 새로운 기능에 대한 문서가 있습니다. 이국적인 형식의 바이너리를 투명하게 호출하는 커널의 기능이 훨씬 더 유연해질 예정입니다. 어떤 사람들은 의심할 여지없이 그것으로 흥미로운 일을 할 것입니다. CrossPoint 순식간에 저는 6월에 [Xteink 4](https://www.xteink.com/products/xteink-x4)를 구입했는데, 배송된 그대로 사용하고 기본 펌웨어가 만족스럽지 않으면 CrossPoint를 설치할 계획이었습니다. Xteink는 내장 스토리지가 아닌 SD 카드를 스토리지로 사용합니다. 배터리는 최대 2주간 책을 읽을 수 있을 것으로 예상됩니다. 확인할 수는 없지만 며칠 동안 무료로 많이 사용하는 데는 확실히 좋습니다. 기본 펌웨어는 EPUB, [Mobipocket](https://en.wikipedia.org/wiki/Mobipocket), 일반 텍스트 파일, PDF는 물론 PNG 및 JPEG 이미지도 지원합니다. Xteink 4의 기본 펌웨어는 나쁘지 않지만 약간 아쉬운 부분이 있습니다. 예를 들어, EPUB 책의 렌더링은 느리고 별로 매력적이지 않았습니다. 내비게이션이 약간 투박하다는 것을 알았습니다. 버튼에는 라벨이 붙어 있지 않으며, 어떤 버튼이 "확인"인지 "뒤로"인지 구분하는 것은 약간 실망스러웠습니다. 글꼴 설정이나 정렬을 조정하는 기능도 거의 없습니다. 펌웨어는 작업을 완료하기에 충분할 만큼 기능적이지만 읽는 동안 특별히 기분이 좋지는 않습니다. Xteink의 표준 펌웨어가 포함된 전자책의 몇 장을 읽은 후 전환할 준비가 되었습니다. 그러나 공평하게 말하면 Xteink는 더 많은 기능과 향상된 기능을 추가하기 위해 계속해서 기본 펌웨어를 업데이트한다는 점에 유의해야 합니다. 어느 시점에서는 CrossPoint가 제공하는 기능을 따라잡거나 심지어 능가할 수도 있습니다.
CrossPoint 설치에 권장되는 방법은 장치가 USB-C를 통해 연결된 동안 [웹 기반 플래시 도구](https://crosspointreader.com/#flash-tools)를 사용하는 것입니다. 그러나 [일부 Xteink 장치는 USB 플래시가 비활성화되어 있습니다](https://github.com/crosspoint-reader/crosspoint-reader#usb-locked-devices-xteink-unlocker). 이 경우에도 [SD 카드에서 새 펌웨어를 업데이트](https://crosspointreader.com/unlock)하여 CrossPoint를 설치할 수 있습니다. 두 경우 모두 CrossPoint 펌웨어를 장치에 플래시하는 것은 어렵지 않으며 몇 분 밖에 걸리지 않습니다. CrossPoint 관리 비즈니스의 첫 번째 순서는 일부 독서 자료를 독자에게 복사하는 것입니다. 펌웨어가 잠겨 있는 장치는 USB를 통한 리더의 저장소 연결을 허용하지 않을 수 있습니다. Xtenink 3와 같이 CrossPoint가 지원하는 일부 장치에는 USB-C 커넥터가 전혀 없습니다. 따라서 대부분의 경우 USB-C를 통해 파일을 복사하는 것이 불가능할 수 있습니다. 한 가지 방법은 리더의 SD 카드를 꺼내 컴퓨터에 연결하고 파일을 복사하는 것입니다. 더 간단한 방법은 WiFi를 통해 장치에 파일을 복사하는 것입니다. Xteink의 기본 펌웨어를 사용하면 사용자는 장치에서 실행되는 핫스팟에만 연결할 수 있습니다. 사용자는 현재 WiFi 네트워크 연결을 끊고 장치에 연결하여 파일을 복사해야 합니다. 반면 CrossPoint에는 파일 전송 및 장치 구성을 위한 [내장 웹 서버](https://github.com/crosspoint-reader/crosspoint-reader/blob/develop/docs/webserver.md)가 있습니다. CrossPoint 장치는 로컬 2.4GHz WiFi 네트워크에 연결하고 DHCP를 사용하여 IP 주소를 얻을 수 있습니다. 그러면 사용자는 브라우저에서 "crosspoint.local"을 방문하거나 DHCP에서 할당한 IP 주소를 사용하여 장치에 연결할 수 있습니다. CrossPoint는 보안 연결을 설정하지 않습니다. 모든 것이 HTTP를 통해 제공되므로 장치를 공용 Wi-Fi에 연결하는 것은 좋지 않은 생각일 수 있습니다. 사용 가능한 로컬 네트워크가 없는 경우 CrossPoint는 장치에 직접 연결할 수 있는 핫스팟 설정도 지원합니다.
웹 기반 인터페이스(아래 표시)를 통해 사용자는 파일 업로드, 디렉터리 생성, 파일 이름 바꾸기 또는 삭제 등을 수행할 수 있습니다. EPUB를 업로드할 때 기기에 맞게 최적화하도록 제안합니다. 또한 사용자는 웹 인터페이스에서 모든 장치 설정을 관리할 수 있는데, 이는 장치의 설정 인터페이스를 일일이 살펴보는 것보다 훨씬 편리합니다. 사용자는 버튼 할당 변경, 디스플레이 설정 수정, 사용자 인터페이스 설정 조정, CrossPoint 테마 변경, 책 레이아웃 사용자 정의, 글꼴 선택 등을 수행할 수 있습니다. [사용자 가이드](https://github.com/crosspoint-reader/crosspoint-reader/blob/develop/USER_GUIDE.md)에는 사용 가능한 다양한 설정에 대한 좋은 개요가 있으며 CrossPoint의 최신 릴리스에 맞춰 업데이트되어야 합니다.![[CrossPoint 웹 기반 파일 관리자]](https://static.lwn.net/images/2026/cp-web-interface.png) 글꼴 다운로드와 같은 웹 인터페이스에는 몇 가지 기능이 없습니다. CrossPoint의 펌웨어에는 두 가지 글꼴이 포함되어 있지만 [많은 추가 글꼴](https://github.com/crosspoint-reader/crosspoint-fonts/blob/main/README.md)이 있습니다. 장치의 리더 설정 메뉴에서 다운로드할 수 있지만 웹 메뉴를 통해서는 다운로드할 수 없습니다. CrossPoint에서 제공하는 글꼴 중 만족스러운 글꼴이 없으면 약간의 추가 작업을 통해 [사용자 정의 글꼴을 업로드](https://github.com/crosspoint-reader/crosspoint-reader/blob/develop/USER_GUIDE.md#38-custom-fonts-sd-card)할 수 있습니다. CrossPoint는 Xteink에서 사용하는 BIN 형식이 아닌 자체 글꼴 형식인 cpfont를 사용합니다. OpenType 또는 TrueType 형식을 직접 지원하지는 않지만 프로젝트에서는 이러한 형식을 cpfont로 변환할 수 있는 [웹 기반 글꼴 빌더](https://crosspointreader.com/fonts)를 제공합니다. 그런 다음 사용자는 웹 관리자를 통해 또는 파일을 SD 카드에 복사하여 장치에 파일을 복사할 수 있습니다. [Calibre](https://lwn.net/Articles/1015226/)로 전자책 라이브러리를 관리하는 사용자를 위한 [CrossPoint 플러그인 for Calibre](https://github.com/crosspoint-reader/calibre-plugins/blob/master/crosspoint_reader/README.md)가 있습니다.
전자책을 독자에게 복사하는 기능만 관리하는 것이 아닙니다. 또한 CrossPoint를 실행하는 장치에 대해 EPUB를 최적화하여 메모리 사용량을 줄일 수도 있습니다. 플러그인의 최적화 프로그램은 EPUB의 이미지를 작은 화면에 더 적합한 크기로 변환하고, 포함된 글꼴을 제거하며, 메모리 사용량을 줄이기 위해 큰 장을 분할할 수 있습니다. 읽기![[CrossPoint 인터페이스]](https://static.lwn.net/images/2026/crosspoint-nav.png)
