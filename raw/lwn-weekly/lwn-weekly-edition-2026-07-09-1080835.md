어딘가에 있는 영구 매체에 저장된 일련의 바이트를 표현합니다.
파일 시스템 작업의 대부분은 작업 구현으로 귀결됩니다.
메모리와 메모리 사이에서 데이터를 이동하여 파일 및 오프셋으로 표현됩니다.
그 영구 미디어.  이 작업의 핵심 부분은 매핑을 관리하는 것입니다.
두 도메인 사이에 있습니다.

Linux 초기에는 이 매핑이 [buffer heads](https://lwn.net/Articles/930173/)으로 표시되었지만 여러 가지 문제로 인해 어려움을 겪었습니다.
문제.  디스크 블록과 동일한 크기의 블록 간의 직접 매핑으로
메모리 영역, 버퍼 헤드는 오늘날의 대용량 파일용으로 설계되지 않았으며
익스텐트 기반 파일 시스템.  크고 효율적으로 생성하기가 어렵습니다.
관련된 데이터가 다음과 같은 경우의 I/O 작업
버퍼 헤드로 표시됩니다.  디스크의 단일 연속 범위는 다음과 같습니다.
수백 개의 버퍼 헤드가 필요하며 각각은 단일 블록을 관리해야 합니다.
소수의 I/O로 재조립 가능
운영.

iomap을 사용하면 많은 수의 버퍼가 포함될 수 있는 매핑
대신 머리는 단일 [`iomap`
structure](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/iomap.h#L117)으로 표현될 수 있습니다.


```

구조체 iomap {
	u64 주소; 		/* 매핑의 디스크 오프셋, 바이트 */
	loff_t 오프셋;		/* 매핑의 파일 오프셋, 바이트 */
	u64 길이;		/* 매핑 길이, 바이트 */
	u16 유형;		/* 매핑 유형 */
	u16 플래그;		/* 매핑을 위한 플래그 */
	구조체 block_device *bdev;		/* I/O용 블록 장치 */
	구조체 dax_device *dax_dev; 	/* dax 작업을 위한 dax_dev */
	무효 *inline_data;
	무효 *비공개;	/* 파일 시스템 프라이빗 */
	u64 유효성_쿠키; /* .iomap_valid()와 함께 사용됨 */
    };
````

일을 조금 단순화하기 위해 이 구조의 인스턴스에서는 범위가 다음과 같이 표시됩니다.
`offset` 바이트에서 시작하여 계속되는 파일
`length` 바이트는 기본 장치의 `addr`에 저장됩니다.
이는 `bdev`(일반 블록 장치의 경우)으로 식별됩니다.
`dax_dev`(영구 메모리 DAX 장치의 경우) 또는 메모리 범위
`inline_data`.  `type` 필드는 어떤 종류의
매핑은 실제로 다음과 같이 표현됩니다.

- `IOMAP_MAPPED`은 파일에서 영구 저장 장치의 공간으로의 정상적인 매핑을 나타냅니다.
- 대신 `IOMAP_INLINE`은 파일과 `inline_data`가 가리키는 메모리 간의 매핑입니다. 이러한 종류의 매핑은 파일 데이터가 파일 inode 자체에 저장될 수 있는 작은 파일에 사용될 수 있습니다.
- `IOMAP_HOLE`은 기본 스토리지가 할당되지 않았으며 매핑이 전혀 없음을 의미합니다. 이는 읽기 작업에만 유효하며 결과적으로 이 범위에서 읽으면 0이 반환됩니다.
- `IOMAP_DELALLOC`도 매핑이 존재하지 않지만 나중에 생성될 것이라고 말합니다.
- `IOMAP_UNWRITTEN`에서는 매핑이 존재하지만 백업 저장소가 작성되지 않았으며 임의(또는 민감한) 데이터가 포함될 수 있다고 말합니다. 이 범위에서 읽으면 백업 저장소로 이동하지 않고 0이 반환됩니다.

파일 시스템에서 다음과 같이 설정할 수 있는 [an
extensive set of `flags`](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/iomap.h#L36)이 있습니다.
I/O 수행 방법에 영향을 미치려면 공유를 표시하십시오.
쓰기 시 복사해야 하는 매핑 등.

이러한 `iomap` 구조는 파일 시스템에서 채워져야 합니다.
iomap 계층의 요청에 대한 응답으로 구현됩니다.  그
요청은 다음에서 제공하는 몇 가지 콜백을 통해 수신됩니다.
파일 시스템:


```

구조체 iomap_ops {
	/*
	 * pos에서 기존 매핑을 반환하거나 다음에서 시작하는 공간을 예약합니다.
	 * 단일 매핑으로 수행할 수 있는 한 최대 길이에 대한 위치입니다.
	 * 실제 길이는 iomap->length에 반환됩니다.
	 */
	int (*iomap_begin)(struct inode *inode, loff_t pos, loff_t 길이,
			서명되지 않은 플래그, struct iomap *iomap,
			구조체 iomap *srcmap);
	/*
	 * iomap_begin을 사용하여 이전에 할당된 공간을 커밋 및/또는 예약 취소합니다.
	 * Written은 성공적인 쓰기 작업의 길이를 나타냅니다.
	 *는 커밋해야 하고 나머지는 예약되지 않은 상태로 유지해야 합니다.
	 * 데이터가 기록되지 않은 경우 기록된 값은 0일 수 있습니다.
	 */
	int (*iomap_end)(struct inode *inode, loff_t pos, loff_t 길이,
			ssize_t 작성, 서명되지 않은 플래그, struct iomap *iomap);
    };
````

작업이 시작되기 전에 `iomap_begin()`이 호출되어 이를 알려줍니다.
파일의 표시된 영역을 읽으려는 파일 시스템 또는
작성되었습니다.  관련된 파일은 `inode`로 식별됩니다.
`pos` 및 `length`는 해당 파일의 범위를 나타냅니다.
작동에 영향을 미칠 것입니다.  `flags` 매개변수에는 다음을 포함하여 앞으로 일어날 일을 설명하는 [a
number of options](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/iomap.h#L194)이 있습니다.

- `IOMAP_WRITE`: 지정된 범위가 기록되므로 공간을 할당해야 합니다(아직 없는 경우). 이 플래그가 없으면 읽기 작업을 의미합니다.
- `IOMAP_ZERO`: 파일 범위를 0으로 만듭니다.
- `IOMAP_DIRECT`: 페이지 캐시를 피하는 직접 I/O 작업이 필요합니다.

`iomap_begin()` 함수는 제공된 값을 채워야 합니다.
적어도 첫 번째에 대해 적합한 매핑이 있는 `iomap` 구조
요청된 작업의 바이트 물론 지도를 많이 그리는 것이 더 낫습니다.
단일 매핑으로 수행할 수 있는 경우 더 큰 범위입니다.  는
작업에 대한 데이터가 있는 경우에는 `srcmap` 매개변수가 존재합니다.
(블록을 쓰기 전에 블록을 읽어야 하는 작은 쓰기를 상상해 보십시오.
부분)은 다른 장치에서 읽어야 합니다.

`iomap_end()` 함수는 작업이 수행될 때 호출됩니다.
완료; `written` 매개변수에는 바이트 수가 포함됩니다.
실제로 쓴 것입니다.  이 콜백은 파일 시스템을 정리할 수 있도록 하기 위한 것입니다.
작업 후 할당된 블록을 계산하고 모든 블록을 해제합니다.
실제로 작성되지 않은 것입니다.


#### 파일 시스템 I/O

위에서 설명한 매핑은 커널이 사용할 수 있는 경우에만 유용합니다.
실제로 I/O를 수행하고 일반적으로 파일 시스템 기능을 구현합니다.
Iomap은 이와 관련하여 도움이 될 수 있는 많은 기능을 제공합니다. 그들은,
일반적으로 완벽하게 문서화되지 않았으며 파일 시스템이 필요합니다.
개발자는 소스를 파헤쳐 소스를 발견하고 방법을 알아냅니다.
그들을 사용하십시오.  이러한 상황으로 인해 iomap이 느려졌을 수도 있는지 여부
변환은 독자가 결론을 내리도록 남겨둡니다.

해당 문서를 모두 작성하는 것은 업무 범위를 넘어서는 일입니다.
이 기사에서는 달성할 수 있지만 예를 들어 설명할 수 있습니다.  다음을 고려하십시오.
버퍼링된 읽기의 경우.  애플리케이션이 [`read()`](https://man7.org/linux/man-pages/man2/read.2.html)을 호출하는 경우
파일에는 다음을 포함하여 발생해야 하는 여러 가지 작업이 있습니다.
페이지 캐시에 공간 할당, 디스크에서 데이터 찾기, 읽기
데이터를 페이지 캐시에 저장하고 이를 사용자 공간 버퍼에 복사합니다.  는
커널의 가상 파일 시스템 계층은 이러한 세부 사항 중 많은 부분을 처리하지만
파일 시스템이 구현해야 하는 부분입니다.

버퍼링된 I/O의 경우 파일 시스템은 구현할 여러 콜백과 함께 [`struct
address_space_operations`](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/fs.h#L401)을 제공해야 합니다.
특정 작업.  읽기 작업에 사용되는 것 중 하나는 다음과 같습니다.
`read_folio()`:


```

int (*read_folio)(struct file *file, struct folio *folio);
````

`folio` 구조는 데이터가 저장되는 메모리를 설명합니다.
읽어야 한다; 여기에는 Folio가 저장하는 파일의 세부 정보도 포함되어 있습니다.
지도, 파일 내의 Folio 오프셋 및 길이.  파일 시스템
실제 읽기를 수행하고 Folio를 다음과 같은 것으로 표시하여 응답해야 합니다.
현재.  Folio가 다음과 같은 경우 여러 I/O 작업을 수행해야 할 수 있습니다.
백업 장치의 여러 비연속 블록에 걸쳐 있습니다.

파일 시스템 구현은 대부분의 작업을 구현할 수 있습니다.
`read_folio()`과 [`iomap_read_folio()`](https://elixir.bootlin.com/linux/v7.1.1/source/fs/iomap/buffered-io.c#L585) 호출,
하지만 그렇게 간단하지는 않습니다. 접착제가 일정량 들어있어
먼저 파일 시스템의 `read_folio()` 콜백에 적용되어야 합니다.
여기에는 `iomap_read_ops` 구조의 정의가 포함됩니다.


```

구조체 iomap_read_ops {
	int (*read_folio_range)(const struct iomap_iter *iter,
				struct iomap_read_folio_ctx *ctx, size_t len);
	무효 (*submit_read)(const struct iomap_iter *iter,
			    struct iomap_read_folio_ctx *ctx);
        /* ... */
    };
````

`read_folio_range()` 작업은 다음을 생성하는 작업을 수행합니다.
단일 읽기 작업, 아마도 더 큰 요청의 일부만 다룰 수도 있습니다.
`read_folio_range()`가 동기식이면
`submit_read()` 콜백; 그렇지 않으면 해당 기능을 제공해야 합니다.
실제로 읽기 작업을 시작합니다. 두 함수에 대한 인수는 다음과 같습니다.
[`iomap_iter`](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/iomap.h#L233)
무엇보다도 현재 읽기 위치를 포함하는 구조
이 구조 유형의 인스턴스인 `ctx` 인수:


```

구조체 iomap_read_folio_ctx {
	const struct iomap_read_ops *ops;
	구조체 폴리오 *cur_folio;
	구조체 readahead_control *rac;
	무효 *read_ctx;
	loff_t read_ctx_file_offset;
    };
````

이 구조는 파일 시스템의 `read_folio()`에서 생성되어야 합니다.
구현; `cur_folio`는 `folio`으로 설정되어야 합니다.
인수가 전달되고 `ops`가 파일 시스템에 전달됩니다.
`iomap_read_ops` 구조.  다행히도 많은 파일 시스템은 그렇지 않습니다.
실제로 자체 `iomap_read_ops`을 생성해야 합니다. 아이오맵 레이어
일반적인 경우에 대한 자체 구현이 있습니다.  예를 들어,
디스크 기반 파일 시스템은 [`iomap_bio_read_ops`](https://elixir.bootlin.com/linux/v7.1.1/source/fs/iomap/bio.c#L152)을 사용할 수 있습니다.
자체적으로 공급하는 것이 아니라

적절한 구조가 갖춰지면 `read_folio()`
구현은 `iomap_read_folio()`에 대한 호출로 귀결됩니다.


```

void iomap_read_folio(const struct iomap_ops *ops,
			  구조체 iomap_read_folio_ctx *ctx,
			  무효 *비공개);
````

여기서 `ops` 구조는 마지막으로 매핑 작업 집합입니다.
얼마 전에 설명했던 것입니다.  iomap 레이어는 이를 사용합니다.
파일 백업의 하나 이상의 범위에 읽기를 매핑하는 작업
저장한 다음 제공된 읽기 작업을 사용하여 해당 범위를
폴리오 제공.

위의 호출 순서는 다음과 같습니다.

> ![[호출 순서도]](https://static.lwn.net/images/2026/iomap-sequence.png)

iomap 레이어는 구현에 따른 많은 복잡성을 숨깁니다.
파일 시스템이지만 여전히 상당한 양이 누출됩니다. 그것의 대부분은되었습니다
여기에 교묘하게 광택을 냈습니다.  예를 들어, `struct iomap_read_folio_ctx`의 [`readahead_control`
structure](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/pagemap.h#L1331)은 다음을 제공합니다.
블록 세트를 가져올 수 있는 미리 읽기 작업용 매개변수
미래의 읽기 속도를 높이기 위해 추측적으로.

버퍼링된 쓰기 작업은 `struct
address_space_operations`에서 `writepages()` 콜백에 의해 구현됩니다.
여기서도 비슷한 임피던스 매칭 작업을 수행할 수 있습니다.  [`iomap_writeback_ops`
structure](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/iomap.h#L438)은 쓰기를 구현하기 위한 하위 수준 콜백 세트를 제공합니다.
이는 [`iomap_writepage_ctx`
structure](https://elixir.bootlin.com/linux/v7.1.1/source/include/linux/iomap.h#L469)에 저장된 다음 [`iomap_writepages()`](https://elixir.bootlin.com/linux/v7.1.1/source/fs/iomap/buffered-io.c#L1944)에 전달되어야 합니다.

다른 많은 파일 시스템 작업에는 iomap이 지원됩니다. 여기에는 직접 포함
I/O, DAX I/O,
파일 내 검색, 페이지 오류 처리, 파일 잘림, 파일 스왑
활성화 등.  위의 비웃음 댓글에도 불구하고
[some
documentation for iomap](https://docs.kernel.org/filesystems/iomap/index.html)은 커널에 포함되어 있습니다. 그것은 여러 작품을 그린 Darrick Wong의 [added to the 6.11
release](https://git.kernel.org/linus/a7ca193bc9b6)이었습니다.
개발자.


#### 결론적으로

iomap 하위 시스템은 아직 완성되지 않았으며 새로운 작업이 병합되었습니다.
거의 모든 개발 주기.  최근 변경 사항에는 파일 지원이 포함됩니다.
[fs-verity](https://docs.kernel.org/filesystems/fsverity.html) 사용
무결성 보호, [T10

#### 안정적인 1GB 할당

Linux 시스템이 실행되면 메모리가 조각화되는 경향이 있습니다.
크고 물리적으로 인접한 메모리 덩어리를 할당하는 것은 어렵습니다.
이러한 상황을 개선하기 위해 수년에 걸쳐 많은 작업이 수행되었습니다. 는
커널은 조각화를 방지하고 적극적으로 메모리 조각 모음을 수행하기 위해 열심히 노력합니다.
필요에 따라.  더 큰 할당은 이전보다 더 안정적입니다.
그럼에도 불구하고 할당 문제는 예를 들어 다음과 같은 상황을 더 어렵게 만들 수 있습니다.
이상적인 것보다 2MB PMD 수준의 거대한 페이지를 제공하는 시스템입니다.

이러한 어려움을 고려하면 PUD 수준의 안정적인 할당이 불가능해 보일 수 있습니다.
(1GB) 거대한 페이지는 불가능한 목표입니다.  그러나 Rik van Riel이 말했듯이
[cover
letter](https://lwn.net/ml/all/20260520150018.2491267-1-riel@surriel.com)부터 40개 부분으로 구성된 패치 시리즈까지, 얻을 수 있는 워크로드가 있습니다.
가능한 경우 1GB 대용량 페이지를 사용하면 상당한 성능 이점을 얻을 수 있습니다.
획득에 성공합니다.  영역을 안정적으로 할당하는 유일한 방법
현재 커널의 해당 크기는 [hugetlbfs](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html)을 사용하는 것입니다.
부팅 시 이러한 목적으로 메모리를 예약하는 하위 시스템입니다.  거대한lbfs
하지만 융통성이 없습니다. 예약된 페이지는 다른 용도로 사용할 수 없습니다.
작업 부하에 필요한 경우 추가 페이지를 예약할 수 없습니다.
그들.  시스템 관리자는 예약이 설정되기를 바랄 뿐입니다.
부팅 시 시스템이 이후에 실행될 수 있는 모든 작업 부하에 적합합니다.

Van Riel의 패치 세트는 1GB 할당을 더 안정적으로 만들려고 시도합니다.
hugetlbfs 예약이 필요합니다.  이를 위해서는 여러 가지 접근 방식이 필요합니다.
그 목표를 달성하지만 핵심 아이디어는 메모리를 단위로 관리하는 것입니다.
"슈퍼 페이지 블록"으로 알려져 있습니다.  커널은 메모리를 페이지 블록으로 나눕니다.
이제는 단편화를 방지하기 위해 설계된 방식으로 이를 관리합니다.  다음 중 하나
핵심 기술은 이동할 수 있는 할당을 분리하는 것입니다.
그건 할 수 없습니다.  예를 들어, 대부분의 사용자 공간 메모리는 이동 가능합니다.
관련된 모든 페이지 테이블 항목을 일치하도록 변경하는 문제입니다.  에
반면에 커널 자체 사용을 위한 할당은 일반적으로 이동할 수 없습니다.
두 가지 유형을 분리하여 유지함으로써 커널은 다음과 같은 가능성을 극대화합니다.
페이지를 다른 곳으로 이동하여 전체 무료 페이지 블록을 생성합니다.

페이지 블록은 페이지를 돕는 데 있어서 합리적으로 잘 작동합니다.
할당자는 PMD 수준의 거대한 페이지를 제공합니다.  하지만 그것들은 생각보다 훨씬 작습니다.
Van Riel이 맞추려고 하는 1GB 목표; 이 글을 쓰는 데 사용된 시스템에서
기사의 페이지 블록 크기는 4MB로 구성됩니다.  전형적인
시스템에서 일부 페이지 블록은 이동 가능한 할당에 사용되고 다른 페이지 블록은
이동할 수 없는 할당을 보유합니다.  이동식 블록은 필요에 따라
더 많은 PMD 수준의 거대한 페이지를 생성하기 위해 비워졌습니다.  그러나 그것은 단지
1GB의 거대한 페이지를 포함하는 전체 페이지를 렌더링하는 이동 불가능한 단일 페이지 블록
움직일 수 없으며 결과적으로 영구적으로 조각화됩니다.

슈퍼 페이지 블록을 추가하면 페이지 할당자에게 또 다른 수준의
메모리 사용에 대한 가시성.  할당 요청이 들어오면
이동할 수 없는 페이지인 경우 할당자는 이동할 수 없는 페이지에서 할당을 시도합니다.
이전과 마찬가지로 페이지 블록.  여유 메모리가 있는 페이지 블록이 없는 경우
하지만 할당자는 새 페이지 블록을 선택해야 합니다.
에서 할당합니다.  Van Riel의 패치 세트는 할당자가 다음을 시도하도록 합니다.
이미 다른 페이지 블록을 보유하고 있는 슈퍼 페이지 블록에서 해당 페이지 블록을 선택합니다.
움직일 수 없는 할당.  즉, 이동성과 이동성을 분리하는 것입니다.
이제 이동할 수 없는 할당이 1GB 규모로 수행되어 가능성이 높아졌습니다.
필요에 따라 1GB의 대용량 페이지를 생성하고 할당할 수 있습니다.

이를 돕기 위해 사용되는 다른 기술도 많이 있습니다.
전반적인 정책이 성공했습니다.  예를 들어 가상으로 매핑된
커널 공간 할당(`kvmalloc()`으로 얻을 수 있음)
여러 페이지가 필요합니다.  이 할당은 이동할 수 없으므로
이동할 수 없는 슈퍼 페이지 블록에 배치됩니다.  그런 블록이 없다면
이렇게 많은 연속 페이지를 사용할 수 있으므로 할당자는 자연스럽게
새로운 슈퍼 페이지 블록을 선택하여 "오염"시키고 이동할 수 없게 만듭니다.
그러나 기존의 이동 불가능한 슈퍼에서 할당을 충족할 수 있는 경우
페이지 블록을 더 작은 덩어리로 분할하면 할당자가 이를 수행합니다.
그.

이 시리즈의 패치에는 다음을 나타내는 Assisted-by 태그가 있습니다.
Claude Opus LLM이 창작에 사용되었습니다.  위에서도 언급했지만 밴은
Riel은 LLM 지원이 필요한 새로운 개발자가 아닙니다.

— 1998년; 그는 [proposed](https://web.archive.org/web/20000521171334/http://www.surriel.com/zone-alloc.html)
이후에 존(zoned) 메모리 할당자가 추가되었습니다.
그는 의심의 이익을 얻을 가능성이 있는 일종의 개발자입니다.

#### 가상 머신 게스트 메모리에 대한 작업 세트 추적

VM(가상 머신)에는 두 가지 수준의 메모리 관리가 적용됩니다.
내부적으로 자체 메모리를 처리하지만 호스트 수준도 있습니다.
시스템의 물리적 메모리가 사용되는지 확인하는 관리
실행 중인 모든 VM에서 효율적으로 수행됩니다.  다음과 같은 경우 호스트 수준 작업이 더 쉽습니다.
VM 관리자(하이퍼바이저)는 특정 VM이 어떤 페이지에 있는지 볼 수 있습니다.
실제로 사용 중입니다. 해당 정보는 더 차가운 페이지를 회수하는 데 사용될 수 있습니다.
(또는 느린 메모리로 이동).  하지만 그 정보는 대개
VM 자체 내부에 잠겨 있습니다.

Kiryl Shutsemau의 [This patch
series](https://lwn.net/ml/all/20260629120749.566063-1-kirill@shutemov.name)은 해당 사용 정보를 만들기 위한 것입니다.
VM 관리자가 더 쉽게 사용할 수 있습니다.  새로운 등록 모드를 추가합니다.
[`userfaultfd()`](https://man7.org/linux/man-pages/man2/userfaultfd.2.html)
(호스트 수준에서) 보호를 발생시키는 시스템 호출
"액세스 불가"로 표시할 페이지 범위를 나타냅니다.  등록시
시간이 지나면 무슨 일이 일어날지에 대해 두 가지 대안 중에서 선택할 수 있습니다.
가상 머신이 해당 페이지 중 하나에 액세스할 때.  동기식인 경우
모드가 선택되면 VM 관리자는 다음으로부터 메시지를 받습니다.
커널에서 오류를 확인한 후 다른 커널로 문제를 해결할 수 있습니다.
커널에 다시 요청합니다.  비동기 모드에서는 커널이 재설정됩니다.
VM 관리자에게 알리지 않고 권한을 부여합니다.  나중에,
관리자는 페이지 범위를 스캔하여 어떤 페이지에 액세스했는지 확인할 수 있습니다.
[This
documentation patch](https://lwn.net/ml/all/20260629120749.566063-16-kirill@shutemov.name)는 이 기능을 더 자세히 설명합니다.

이 패치에도 Claude Opus라는 이름의 Assisted-by 태그가 포함되어 있습니다.
Shutsemau는 커널 커뮤니티에서 Van Riel만큼 오래 활동하지 않습니다. 데
2008년에 [his
first contribution](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=e621e69137b2)을 2.6.25 커널로 만들었고, 그는 친척입니다.
신인.  그럼에도 불구하고 그의 이력은 다음과 같은 점을 분명히 할 만큼 충분히 길다.
다시 한 번, 그는 자신이 하는 일을 완전히 이해할 수 있게 되었습니다.
커뮤니티에 제출합니다.

이 시리즈는 일곱 번의 개정과 중요한 변화를 거쳤습니다.
받은 리뷰로 인해 발생합니다.  Van과 달리
Riel의 작업이 접수되었지만 그 리뷰 중 어느 것도 LLM의 역할이 아니었습니다.
작품 창작에 대한 우려가 제기되었습니다.  두 번째에 대한 응답으로
그러나 LLM 사용 방법에 대한 정보는 Andrew Morton [did
ask](https://lwn.net/ml/all/20260508103220.aa46427b6f4c5d0247d2afb0@linux-foundation.org) 개정판을 참조하세요. 슈체마우 [responded in detail](https://lwn.net/ml/all/af5eALk9yO8pPcHv@thinkstation).  많이
도구의 역할 중 하나는 아이디어를 검증하는 것이었습니다.

> 이 특정 프로젝트에서는 길을 찾는 데 상당한 노력이 필요했습니다.
> 저는 Claude의 아이디어를 튕겨내는 단계를 가졌습니다. 그것은 나에게 도움이 되었다
> 문제 공간을 더 잘 이해하고 가능한 공식화
> 솔루션.  스테로이드에 고무 더킹.
> _무엇을_ 해야 할지 명확해지면 _어떻게_할지에 대한 계획을 세웁니다. 그것은 또한
> 앞뒤로 움직입니다.
> 계획이 완성되면 실행에 나섰습니다.

그는 이 과정에서 가장 시간이 많이 걸리는 부분은 검토하는 것이라고 말했다.
결과 코드; 프로세스를 처음부터 다시 시작하는 것과 관련이 있습니다.
한 번 이상.  '어쩌면 8~10' 라운드 정도 걸렸습니다.
그가 만족한 코드를 얻은 다음 전체 시리즈를 공급하기 전에
다양한 프롬프트 세트와 함께 LLM에 검토를 요청합니다.

이 워크플로는 겉으로는 다음과 같은 실행 가능한 패치 세트를 생성한 것 같습니다.
핵심 메모리 관리 코드가 크게 변경되었습니다.  핵심은
위에서 설명한 작업과 관련하여 성공은 다음과 같이 나타날 수 있습니다.
도구를 얻기 위해 상당한 양의 인간 시간을 투자해야 합니다.
일을 제대로 수행하고 남은 문제는 나중에 처리하십시오.
패치가 다음 수준에 도달했는지 확인하기 위해 겉보기에 주의를 기울인 것 같습니다.
커뮤니티가 메일링 리스트에 등록될 때 기대하는 품질
모든 변화를 가져온 것 같습니다.

Shutsemau는 그 전체 과정이 다른 것보다 더 효율적인지 여부를 밝히지 않았습니다.
LLM의 도움 없이 단순히 일을 하고 있지만 그는

## 기술 각주

[^lwn1080835-kernel-cryptography]: 커널 암호화 코드는 오래된 알고리즘 호환성, FIPS·컴플라이언스 요구, 하드웨어 가속, API 안정성이 얽혀 있어 정리 작업이 느리지만 보안과 유지보수성에 직접 영향을 줍니다.
[^lwn1080835-iomap]: iomap은 파일시스템이 파일 offset을 block device의 extent와 매핑하는 공통 계층입니다. XFS, ext4, btrfs 같은 파일시스템의 buffered/direct I/O, page cache, writeback 경로 단순화와 성능에 중요합니다.
[^lwn1080835-llm-assisted-kernel-development]: LLM 보조 커널 패치는 코드 작성 속도를 높일 가능성이 있지만, 메모리 관리처럼 불변식이 복잡한 영역에서는 리뷰 가능성, 테스트 증거, 환각으로 인한 subtle bug가 핵심 리스크입니다.
[^lwn1080835-security-updates]: 배포판 보안 업데이트 표는 CVE 자체보다 패키지 버전, advisory ID, 배포판별 backport 여부를 함께 추적해야 실제 패치 상태를 판단할 수 있습니다.
[^lwn1080835-filesystems]: 파일시스템 변경은 데이터 무결성, page cache, writeback, block layer와 직접 연결되므로 기능 개선과 regression 위험을 함께 봐야 합니다.
[^lwn1080835-negative-dentries]: dentry cache는 pathname lookup 성능의 핵심입니다. 긍정/부정 dentry 보존 정책은 메모리 사용량과 파일시스템 latency 사이의 trade-off를 결정합니다.
[^lwn1080835-rcu]: RCU(Read-Copy-Update)는 Linux 커널의 핵심 lockless 동기화 기법입니다. grace period와 callback 처리 지연은 대규모 CPU 시스템의 tail latency와 메모리 회수 성능에 영향을 줍니다.
[^lwn1080835-memory-management]: Linux 메모리 관리는 allocator, page cache, reclaim, NUMA, filesystem I/O가 맞물리는 영역이라 작은 패치도 워크로드별 성능과 안정성에 큰 차이를 만들 수 있습니다.
[^lwn1080835-guix-security]: Guix는 재현 가능한 빌드와 functional package management를 지향하지만, 빌드·배포 파이프라인의 취약점은 공급망 보안 모델 전체에 영향을 줄 수 있습니다.
[^lwn1080835-openssh]: OpenSSH 릴리스는 원격 접속 인프라의 사실상 표준 구현을 바꾸므로, 프로토콜 기본값·암호 알고리즘·호환성 변화가 운영 환경에 직접 영향을 줍니다.
[^lwn1080835-distro-sabotage]: 배포판 sabotage나 protestware 논란은 코드 변경 자체보다 maintainer 권한, review 정책, 사용자 동의, 복구 절차가 공급망 신뢰의 핵심임을 보여 줍니다.
