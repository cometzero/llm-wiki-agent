## 📌 EROFS는 컨테이너 환경에서 어떤 이점을 제공하는가?
EROFS는 컨테이너 OS의 시작 속도를 높이고 이미지 크기를 줄이며, OCI 이미지 풀링을 가속화하고, 루트 파일 시스템의 무결성을 보장하여 전반적인 <mark>컨테이너 운영 효율성을 크게 향상</mark>시킵니다.


## 💡 EROFS의 핵심 기술적 특징은 무엇인가?

- 블록 기반의 불변(immutable) 파일 시스템
- 고정 파일 시스템 블록 크기를 사용한 데이터 정렬
- 내장된 청크 기반 중복 제거 및 투명 압축 기능

EROFS(Enhanced Read-Only File System)가 **컨테이너 환경의 성능과 보안**을 어떻게 혁신하고 있는지 심도 있게 다룹니다. EROFS의 **불변성과 단순한 디스크 포맷**이 OCI 이미지 처리 속도를 최대 3배까지 가속하고, 이미지 무결성을 보장하며, 복잡한 루프백 장치 없이 컨테이너를 구동하게 만드는 실질적인 이점을 확인할 수 있습니다. 특히, VM 기반 컨테이너에서의 오버헤드 최소화 방안과 함께, EROFS의 설계적 안전성이 어떻게 사용자 네임스페이스 마운팅 같은 커널 보안 논쟁의 새로운 해법이 될 수 있는지에 대한 핵심 개발자들의 토론까지 놓치지 않고 다루므로, 차세대 컨테이너 인프라를 구축하려는 엔지니어에게 **당장 적용 가능한 아키텍처 통찰**을 제공합니다.
## 1. EROFS (Enhanced Read-Only File System) 개요 및 특징 


### 1.1. EROFS 기본 정보 및 설계 이점 
![image]()
1. **EROFS의 정의 및 역사**: EROFS는 'Enhanced Read-Only File System'의 약자로, 2017년 말에 시작되어 리눅스 커널 5.4 버전부터 사용 가능한 블록 기반의 <em>불변(immutable) 파일 시스템</em>이다. 
  1. EROFS는 tar, zip, CPIO와 같은 아카이브 형식과 유사하지만, 다른 일반 디스크 파일 시스템과 유사한 고급 기능을 제공한다. 

2. **핵심 설계 특징**: EROFS는 고정된 파일 시스템 블록 크기를 사용하며, 디스크 내 데이터가 파일 시스템 블록 내에서 엄격하게 정렬(aligned)된다. 
  1. **극한의 성능**: 이러한 정렬 덕분에 DMA(Direct Memory Access) 등을 활용하여 극한의 성능을 얻을 수 있다. 
  2. **FS-DAX(File System Direct Access)**: 호스트 페이지 캐시(host page cache)를 사용하여 게스트 페이지 캐시(guest page cache)를 피하고 호스트와 게스트 간에 이미지를 공유할 수 있게 한다. 
  3. **Direct IO 활용**: 대규모 언어 모델(LLM)과 같이 큰 파일의 경우, 페이지 캐시와 버퍼 I/O를 사용할 때 필요한 페이지 캐시 공간을 줄여 Direct IO를 통해 이점을 얻을 수 있다. 

3. **데이터 중복 제거 및 마운트 기능**: 
  1. **청크 기반 중복 제거 (Chunk-based Deduplication)**: EROFS는 파일 내 또는 서로 다른 파일 간에 데이터를 공유할 수 있는 내장된 청크 기반 중복 제거 기능을 제공한다. 
  2. **저장 스택 전반의 중복 활용**: 데이터가 파일 시스템 블록 내에서 엄격하게 정렬되어 있으므로, ref link와 같은 기술을 사용하여 다른 파일 시스템 간에도 중복 제거를 활용할 수 있다. 
  3. **파일백 마운트 (Fileback Mount)**: 비교적 새로운 기능으로, 루프백(loopback) 블록 장치와 같은 가상 블록 장치 없이도 EROFS를 마운트할 수 있게 해준다 (리눅스 5.5 버전부터 사용 가능). 

4. **보안 및 안정성**: 
  1. **악성 데이터 저항성**: EROFS는 설계상 악의적인 신뢰할 수 없는 데이터에 저항할 수 있는 구조적 보장을 제공한다. 
  2. **퍼징(Fuzzing) 상태**: 악의적으로 제작된 이미지에 대한 매우 우수한 퍼징 테스트(fuzz) 상태를 유지하고 있으며, 현재 발생하는 무작위 이슈는 대부분 새로운 기능이나 복잡한 압축 데이터로 인해 발생한다. 


### 1.2. EROFS의 응용 분야 및 부가 기능 
![image]()
1. **주요 응용 분야**: EROFS는 이미 Composé, font, containerd, gvisor와 같은 다양한 프로젝트에 적용되고 있다. 
  1. 컨테이너 분야의 새로운 서브 프로젝트인 nerd books (Kata VM 기반 컨테이너)에서도 사용된다. 

2. **투명 압축 (Transparent Compression)**: EROFS의 투명 압축 기능은 다른 대안과 달리 개별 파일에 적용할 수 있다. 
  1. 성능이 중요한 시나리오에서는 LD4와 같은 빠른 알고리즘을 사용할 수 있다. 
  2. 성능이 중요하지 않은 아카이브 용도의 파일(예: man page)에는 LDMA나 deflate, STD 같은 알고리즘을 사용할 수 있다. 

3. **기타 기술적 특징**: 
  1. **테일 엔드 데이터 패킹 (Fragments)**: 파일의 끝부분(tail end data)을 특수한 I/O 영역에 묶어서 압축할 수 있는데, 이를 프래그먼트(fragments)라고 한다. 
  2. **CDC (Content Defined Chunking) 변형**: EROFS는 유연한 컷 포인트(cut point)를 가지지만, 데이터가 파일 시스템 블록에 엄격하게 정렬되어야 하므로 컷 포인트 역시 데이터 블록에 맞춰야 한다. 
  3. **메타데이터 압축**: 선택적으로 메타데이터 압축 기능도 제공한다. 


## 2. EROFS의 컨테이너 환경 적용 사례 및 성능 개선 


### 2.1. 불변 운영체제(Immutable OS) 적용 사례 
![image]()
1. **AWS Bottle Rocket**: AWS의 컨테이너 OS인 Bottle Rocket은 기존 ext4에서 EROFS로 전환했다. 
  1. 이를 통해 컨테이너 OS 시작 시간이 <mark>더 빨라졌으며</mark>, 이미지 크기도 <mark>더 작아졌다</mark>. 

2. **기타 사용 사례**: 
  1. **DDI 이미지**: EROFS를 이러한 종류의 이미지에 사용하도록 권장된다. 
  2. **Amazon Linux**: 이 불변 OS는 EROFS와 DM-verity 보호를 사용하여 루트 파일 시스템이 수정되지 않도록 보장한다. 


### 2.2. 컨테이너 이미지 처리 개선 (containerd 통합) 
![image]()
1. **containerd 통합**: containerd는 1.1 버전 릴리스부터 EROFS 통합 기능이 내장되어 있다. 

2. **OCI 이미지 경험 개선**: 현재 EROFS는 OCI 이미지 처리 속도를 개선하는 데 중점을 두고 있다. 
  1. **메타데이터 오버헤드 감소**: 언더레이(underlay) 파일 시스템에 파일을 직접 언팩(unpack)하는 것을 피하여 메타데이터 오버헤드와 I/O 트래픽(예: GBD2)을 줄인다. 
  2. **성능 향상**: 측정 결과, EROFS를 사용하는 방식이 언팩 방식보다 최소 <mark>20% 더 빠르다</mark>. 
  3. **데이터 무결성 보장**: 이미지를 하나의 파일로 변환하여 FS-verity를 적용할 수 있으므로 런타임 데이터의 무결성을 보장하며 이미지 레이어가 변경되지 않도록 한다. 
  4. **루프백 장치 불필요**: EROFS의 파일백 마운트 지원 덕분에 최신 커널에서는 루프백 장치가 필요하지 않다. 

3. **추가 최신 기능 및 성능 향상**: 
  1. **병렬 언패킹 (Parallel Unpacking)**: 디스크 스냅샷 방식처럼 레이어를 순차적으로 적용할 필요 없이, OCI 변환 단계에서 언패킹 단계를 병렬로 수행할 수 있어 이미지 풀링 속도가 훨씬 빨라진다. 
  2. **Netflix 피드백**: Netflix는 EROFS 실험 적용 후 런치 타임(launch time)이 <mark>2~3배 빨라졌다</mark>고 보고했다. 
  3. **기타 기능**: 화이트보드 레이어(whiteboard layer) 및 쿼터(quota)와 같은 기능도 포함된다. 


### 2.3. VM 기반 컨테이너에서의 오버헤드 최소화 (EROFS Merge Feature) 
![image]()
1. **VM 기반 컨테이너의 문제**: VM 기반 컨테이너에 컨테이너 이미지 루트 파일 시스템을 전달할 때 전통적인 방법인 VirtFS를 사용하면 호스트에 파일 디스크립터(FD)를 열어야 하는데, AI 학습용 데이터셋처럼 수백만 개의 파일이 있을 경우 오버헤드가 커진다. 

2. **블록 장치 방식의 한계**: EROFS를 블록 장치와 함께 사용하면 메타데이터 성능 문제를 해결할 수 있지만, EROFS 레이어를 하나씩 마운트하면 너무 많은 블록 장치가 필요해진다. 

3. **EROFS 머지 기능 (Merge Feature)**: EROFS는 여러 레이어를 하나의 블록 장치로 병합하고 한 번에 마운트하는 기능을 제공한다. 
  1. **VMM 요구사항**: 이 기능은 VMM(Virtual Machine Monitor)에서 단일 블록 장치에 대해 멀티 어태치(multi-attach)를 지원해야 하지만, 대부분의 VM이 이 기능을 가지고 있지 않다. 
  2. **VMDK 활용**: 이에 대한 대안으로 VMDK 표준 형식을 도입했으며, 현재 libkrun 및 QEMU가 VMDK와 EROFS를 사용하여 컨테이너 이미지용 블록 장치를 병합하는 것을 지원한다. 


### 2.4. 기타 활용 사례 및 향후 커널 기능 
![image]()
1. **Composé FS 활용**: Composé FS는 EROFS를 사용하여 OS3 인프라를 개선한다. 
  1. **하드 링크 문제 극복**: 기존 OS3는 하드 링크를 사용하여 다른 이미지 간 블롭(blob)을 공유했지만, EROFS와 오버레이 FS(Overlay FS)를 사용하여 하드 링크의 장점을 유지하면서 별도의 메타데이터를 분산한다. 
  2. **데이터 검증**: <mark>오버레이 신뢰 리다이렉트(overlay trusted redirect)</mark> 기능을 사용하여 메타데이터 내의 파일을 OS3 컨테이너 주소 저장소 블롭으로 리다이렉션한다. 
  3. **무결성 보장**: 데이터 블록 검증은 비교적 새로운 FS-verity 다이제스트를 오버레이 FS 메타데이터에 보관하여 데이터 무결성을 보장한다. 

2. **FS-DAX를 통한 게스트 페이지 캐시 회피**: EROFS는 FS-DAX를 활용하여 게스트 페이지 캐시를 피하고 호스트에서 게스트로 컨테이너 이미지를 공유할 수 있게 한다. 
  1. **레이어 식별 가능**: 기존 방식은 각 레이어를 독립적인 파일 시스템으로 처리하여 서로 다른 레이어를 구분할 수 없었으나, EROFS의 네이티브 레이어링 기술은 호스트에 여러 장치나 블롭을 사용하고 유니온 마운트(Union Mount) VMM을 통해 레이어를 전달할 수 있어 <mark>고유한 호스트 페이지 캐시 점유율</mark>을 갖는다. 

3. **런타임 페이지 캐시 공유 (Upcoming Feature)**: 
  1. **문제점**: 기존 파일 시스템에서는 마운트마다 고유한 페이지 캐시를 가지지만, 컨테이너 환경에서는 레이어링이나 중복 제거 기술로 인해 동일한 파일이 많을 수 있다. 
  2. **해결책**: EROFS는 익명 아이노드(anonymous inode)를 사용하는 새로운 페이지 캐싱 기술을 통해 사용자의 경로(user path)와 아이노드(user inode)를 올바르게 표시하는 <mark>백킹 파일 인프라</mark>를 사용한다. 
  3. **상태**: 이 기능은 다음 커널 릴리스에 거의 준비되었지만, mmap 또는 기타 인프라 수정이 필요한 경우 추가 검토가 필요하다. 


## 3. 사용자 네임스페이스 마운팅에 대한 커널 개발자 논의 


### 3.1. 사용자 네임스페이스 마운팅의 요구사항 및 문제점 
![image]()
1. **강력한 요구사항**: 컨테이너 커뮤니티에서는 사용자 네임스페이스(user namespace) 내에서 마운트하는 것에 대한 매우 강력한 요구사항이 있다. 
2. **보안적 관점**: 사용자 네임스페이스는 이미 격리되어 있지만, 보안 요구 사항(온-디스크 포맷)은 호스트 자동 마운트(automount)와 거의 동일하다. 
3. **일반 파일 시스템의 반대 이유 (Ext4, XFS)**: 
  1. **확인 어려움**: Ext4, XFS와 같은 가장 인기 있는 리눅스 디스크 파일 시스템은 이 기능을 거부하는데, 그 이유는 온-디스크 포맷에 중복된 메타데이터가 포함되어 있어 검증하기 어렵기 때문이다. 
  2. **일관성 검증의 어려움**: 추가적인 파일 시스템 메타데이터(예: 할당 트리, 비트맵, 아이노드 익스텐트, 역매핑 트리 등)가 일관성이 있는지 성능 저하 없이 확인하는 것은 어렵다. 
  3. **저널링 문제**: 대부분의 일반 파일 시스템이 저널링(journaling)을 사용하기 때문에 문제가 더욱 복잡해진다. 
  4. **성능 중심 구현**: 최대 성능을 달성하려는 런타임 구현 방식이 실시간 일관성 검사를 느슨하게 만들 수 있다. 
  5. **리소스 부족**: 보안 문제를 적극적으로 해결할 개발 리소스가 부족하다는 점도 주요 우려 사항이다. 

4. **단순 파일 시스템의 주장 (EROFS)**: 
  1. **단순한 포맷**: 불변 파일 시스템과 같은 단순한 파일 시스템을 지지하는 사람들은 온-디스크 포맷 파싱이 매우 단순하며 VFS(Virtual File System)에 기본 정보(아이노드, 디렉터리 등)만 제공한다고 주장한다. 
  2. **FUSE보다 단순**: EROFS는 현재 FUSE 프로토콜보다도 더 간단할 수 있는데, FUSE는 최근 IO ring 등 복잡해져 잠재적인 취약점의 원인이 될 수 있다. 
  3. **개발 자원의 낭비**: EROFS는 이미 충분히 단순함에도 불구하고, 사용자 네임스페이스 마운트 요구사항을 위해 새로운 단순 FS 시도가 계속되는 것은 개발 자원의 낭비이며 커뮤니티에 혼란을 야기한다고 지적한다. 


### 3.2. 보안 문제와 커널 정책 논쟁 
![image]()
1. **Automount vs. User Namespace Mount**: 한 참석자(브랜든)는 자동 마운트와 사용자 네임스페이스 마운트가 근본적으로 다르지 않다고 주장한다. 
  1. **호스트 마운트의 제어**: 호스트에 마운트할 경우, 실행 파일이나 특수 장치 파일(SUID/SGID) 접근을 no SWID 및 no dev 옵션으로 막을 수 있다. 
  2. **핵심 문제**: 사람들이 우려하는 핵심은 <mark>커널 내 익스플로잇(in-kernel block)</mark> 문제이며, 이는 두 경우 모두 동일하다. 

2. **EROFS에 대한 커널 개발자의 입장**: 레너드 등 커널 개발자들은 EROFS를 네임스페이스에서 사용하고 싶어 하지만, 권한 없는(unprivileged) 네임스페이스에서 발생한 수많은 문제들 때문에 많은 우려가 발생하고 있다고 말한다. 
  1. EROFS와 같은 파일 시스템은 저널링이나 재기록 가능한 파일 시스템보다 문제가 적을 것으로 보이지만, 사람들이 여전히 불안해하는 이유이다. 

3. **위협 모델 및 익스플로잇 위험**: 
  1. **위협 모델**: 권한 없는 사용자가 악의적으로 퍼징된(fuzzed) 이미지를 사용하여 커널 패닉, 버퍼 오버런, 심지어 컨테이너 탈출(container escape)을 유발할 수 있다는 것이 위협 모델이다. 
  2. **정책 문제**: 이러한 위험 때문에 사용자 네임스페이스 마운트를 허용하는 것에 대해 우려하며, 이는 <mark>유저랜드(userland) 정책 문제</mark>로 보인다고 주장한다. 
  3. **대안 제안**: systemd-mountd와 같은 메커니즘이 더 나은 해결책으로 제시된다. 

4. **보안 보증과 서비스 거부 공격(DOS)**: 
  1. **커널 보증의 부재**: EROFS 개발자(샹 가오)는 커널에서 안전하다는 보증을 하지 않기 때문에 유저 스페이스에서 이 기능을 사용할 수 없다고 주장한다. 
  2. **알고리즘 보안 우려**: 레너드 등은 단순히 크래시뿐만 아니라, 데이터 구조의 복잡성이 악의적인 파일 시스템 이미지에 의해 선형적으로 증가하여 <mark>서비스 거부(DOS) 공격</mark>이 발생할 수 있는지 여부를 커널이 보장할 수 있는지에 대해 우려한다. 
  3. **신뢰 구축 방안**: systemd의 mountd는 서명 확인을 통해 신뢰를 구축한다. 
  4. **DM-verity의 페널티**: 서명과 DM-verity는 성능 저하(performance penalty)를 유발하지만, 신뢰는 데이터 구조 자체가 아닌 <mark>서명</mark>에서 오는 것이 더 편안하다는 의견이 제시된다. 

5. **네트워크 스택과의 비교**: EROFS 개발자는 네트워크 스택도 신뢰할 수 없는 데이터를 처리하며, 이 또한 퍼징 테스트가 필요하다는 점에서 파일 시스템과 유사하다고 주장한다. 
  1. **차이점**: 그러나 네트워크 프로토콜의 대부분은 유저 스페이스에서 해석되며, 커널이 네트워크 프로토콜을 통해 익스플로잇되는 경우가 잦다는 점이 반론으로 제시된다.
