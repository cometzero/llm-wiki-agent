

## 📌 KernelSBOM은 무엇을 하는 프로젝트인가?
 kernelsbom은 리눅스 커널 빌드를 재구성하여 <mark>신뢰할 수 있는 </mark>spdx<mark> 소프트웨어 자재 명세서(SBOM)를 생성</mark>하는 파이썬 기반 도구입니다. 


## 💡 KernelSBOM이 SBOM을 생성하는 방식은?
 성공적인 커널 빌드로부터 bzImage나 커널 모듈 파일 같은 최종 배포 아티팩트를 역추적하여, cmd 파일과 추가적인 휴리스틱(예: .s 파일 내 incbin 구문, 하드코딩된 메이크파일 의존성)을 분석해 빌드 과정을 재구성합니다. 


linux 커널 빌드의 내부 작동 방식을 **spdx**** 소프트웨어 명세서(SBOM)**로 완벽하게 재구성하는 심층 기술 분석을 제공합니다. 단순히 빌드 산출물을 나열하는 것을 넘어, 비결정적인 빌드 환경에서도 소스 파일부터 중간 단계, 최종 아티팩트까지 **빌드 그래프(Build Graph)**를 어떻게 99% 이상 추적하고 **재현 가능한 SBOM**을 생성하는지 그 핵심 논리를 배울 수 있습니다. 특히 cmd 파일의 불완전성을 보완하는 커널 빌드 분석 기법과 SBOM을 활용한 라이선스 컴플라이언스 체크의 가능성을 제시하여, 소프트웨어 공급망 보안 전문가와 커널 개발자에게 **실질적인 보안 및 규제 대응 통찰**을 제공합니다.
## 1. KernelSBOM 프로젝트 개요 및 빌드 분석 접근 방식 
![image]()
1. **프로젝트 소개 및 목표** 
  1. 이 프로젝트의 핵심 임무는 **Linux 커널 빌드**를 위한 **SBOM(Software Bill of Materials)**을 생성하는 것이다. 
  2. 생성된 SBOM은 현재 GitHub URL에 위치하며, **SPDX**** 재단 저장소**로 이동하거나 프로젝트 이름이 변경될 수 있으며, 현재 활발히 개발 중이다. 
  3. KernelSBOM은 성공적인 커널 빌드(소스 디렉터리와 출력 디렉터리로 구성됨)가 주어졌을 때, 빌드가 완료된 <em>후에</em> 실제로 무슨 일이 일어났는지 **재구성**하는 Python 도구이다. 
  4. 목표는 최종 배포 아티팩트(예: **BZ 이미지** 또는 커널 모듈 파일)와 같은 루트(Roots)에서 시작하여 해당 아티팩트들이 **어떻게 생성되었는지** 또는 **어떤 요소들이 포함되었는지**를 파악하는 것이다. 

2. **빌드 분석을 위한 ****CMD 파일**** 활용** 
  1. 커널 빌드 시스템(KU)은 각 빌드 단계에서 **CMD 파일**을 생성하며, 이 파일은 해당 빌드 단계에서 발생한 작업을 설명하는 **Ground truth** 역할을 한다. 
  2. **CMD 파일****의 내용 구조**:
  1. 일부 CMD 파일은 saved command_target name 변수에 해당 **make 명령어**를 단일 행으로 저장한다. 
  2. 일부 CMD 파일은 make 명령어 외에 **소스(Sources)** 및 **의존성(Dependencies)** 정보를 추가로 명시한다. 
  3. **CMD 파일**** 분석 예시 (명령어 파싱)** 
  1. BZ 이미지 타겟의 예시에서는 저장된 명령어가 DD와 cat이며, 이 명령어를 파싱하여 입력 파일(예: setup.bin 및 VM Linux.bin)을 종속성으로 유추할 수 있다. 
  2. LD 명령어를 사용하는 다른 예시에서는 긴 단일 행의 명령어를 분석하여 해당 빌드에 포함된 **모든 오브젝트 파일** 목록을 추출할 수 있다. 
  4. **CMD 파일**** 분석 예시 (명시적 종속성)** 
  1. 소스와 종속성이 파일에 명시적으로 표현된 경우, 상단에는 여전히 **GCC**** 명령어**가 저장되어 있지만, 추가적으로 **소스와 종속성**이 명시적으로 나열된다. 
  2. 종속성 내부에 있는 **와일드카드 항목**은 설정 플래그(config flags)를 인코딩하는 데 사용되며, 실제 파일 목록에서는 빈 집합으로 평가되어 무시된다. 

3. **불완전한 ****CMD 파일**** 보완 전략** 
  1. CMD 파일은 빌드 그래프를 구성하는 데 **완벽하거나 충분하지 않은** 경우가 있으므로, 프로젝트는 두 가지 추가적인 논리(휴리스틱)를 도입하여 빌드 그래프를 완성한다. 
  2. **S 파일 파싱 (inkbin)** 
  1. 일부 .S 파일에는 ink bin 또는 include binary 형태의 포함(include) 구문이 있으며, 이는 CMD 파일에서 누락되는 경우가 있다. 
  2. 프로젝트는 이 구문을 파싱하여 빌드 그래프에 추가하며, 이 바이너리들은 다시 CMD 파일을 가지므로 빌드 트리를 계속 따라갈 수 있다. 
  3. **하드 코딩된 의존성** 
  1. 일부 make 파일과 kit 파일은 의존성을 직접 포함하며, 이를 파싱하기가 매우 어렵다. 
  2. 현재는 **하드 코딩된 의존성** 목록으로 이 부족한 부분을 채우고 있으며, 장기적으로는 파서를 추가하거나 목록을 완성하여 해결할 계획이다. 
  4. **빌드 그래프 계산 과정** 
  1. BZ 이미지와 같은 루트에서 시작하여 CMD 파일, 하드 코딩된 의존성, S 파일의 inkbin 구문에서 추출한 정보를 따라 **트리를 거슬러 올라가며** 빌드 그래프를 구성한다. 
  2. 생성된 빌드 트리는 각 엣지(Edge)에 대해 **어떤 명령어**나 **어떤 빌드 유형**이 사용되었는지 파악하게 해준다. 


## 2. 빌드 그래프의 완전성 검증 및 S-trace 비교 
![image]()
1. **빌드 그래프의 완전성 검증** 
  1. 생성된 빌드 그래프의 완전성을 분석하기 위해 두 가지 검증 방법을 사용했다. 
  2. **소스 트리 재빌드 테스트**: 그래프에서 참조된 **모든 소스 파일**을 파악하고, 참조되지 않은 파일을 제거한 후 다시 빌드를 시도했을 때 빌드가 성공했다. 
  3. **S-trace 기반 비교**:
  1. 빌드를 S-trace로 실행하여 빌드 과정에서 실제로 **접근된 파일**을 추적했다. 
  2. 현재 S-trace 결과와 빌드 그래프에서 파악한 파일 목록 간의 **일치율은 ****99.49%**이다. 
  3. 아직 100% 완전하지는 않으며, 일부 엣지 케이스는 계속 조사 중이지만, 그래프는 거의 완성된 상태이다. 

2. **S-trace 사용 방식에 대한 질의응답** 
  1. **질문**: 모든 이 과정 대신 S-trace만 사용하여 100% 완전성을 달성하는 것이 가능하지 않은가? 
  2. **답변**:
  1. S-trace 덤프를 사용하여 빌드 트리를 재구성하는 프로젝트가 실제로 존재한다. 
  2. 이 프로젝트의 목표는 **make 타겟**으로서 빌드 자체에 통합되는 것이며, S-trace는 일반적으로 빌드를 추적하기 위해 **권한(privileges)**이 필요하다. 
  3. 목표는 가능한 한 **통합하기 쉽게** 만드는 것이었으며, 현재의 분석 접근 방식이 이를 달성했다고 판단한다. 

3. **CMD 파일****의 불완전성에 대한 질의응답** 
  1. **질문**: .S 파일이 ink bin 지시어로 참조하는 파일을 왜 명시적인 의존성으로 만들지 않는가? 
  2. **답변**:
  1. 이는 CMD 파일에 누락된 부분으로 보이며, 버그이거나 의도된 범위 밖의 일일 수 있다. 
  2. 중장기 목표는 이 발견 내용을 CMD 파일 로직에 기여하여 **CMD 파일****의 격차를 메우는 것**이다. 
  3. 문제의 원인은, 참조되는 .S 파일이 소스 트리에 존재하며 빌드 출력물이 아니므로, 그 옆에 의존성을 인코딩할 CMD 파일이 없기 때문이다. 


## 3. SPDX 기반의 소프트웨어 명세서(SBOM) 생성 
![image]()
1. **SBOM 생성 목표 및 형식** 
  1. 빌드 분석 데이터를 사용하여 **SPDX** 형식의 SBOM을 생성하는 것이 목표이다. 
  2. SPDX는 널리 사용되는 선호 SBOM 형식 중 하나이며, Linux Foundation 프로젝트이고, <mark>JSON LD</mark>를 직렬화 형식으로 사용한다. 
  3. 프로젝트는 **세 가지 상호 연결된 파일** 형태의 SBOM을 생성한다. 

2. **세 가지 상호 연결된 SBOM의 역할** 
  1. **Output SBOM**: 배포 가능한 아티팩트(패키지)와 메타데이터(예: 커널 및 커널 모듈)를 설명한다. 
  2. **Source SBOM**: 사용된 소스 파일과 라이선스, 파일 해시 등의 메타데이터를 설명한다. 
  3. **Build SBOM**: 소스를 빌드에 연결하고 중간 단계를 설명하는 역할을 한다. 

3. **아웃 오브 트리 빌드(Out-of-tree build)의 구분** 
  1. 파일이 소스 파일인지 빌드 파일인지 구분하기 위해 파일이 존재하는 디렉터리(소스 디렉터리 또는 빌드 디렉터리)를 기반으로 구분한다. 
  2. **인-트리 빌드(In-tree build)**일 경우, 소스 및 빌드 디렉터리를 구분할 수 없으므로 **Source SBOM과 Build SBOM을 하나로 병합**한다. 


## 4. SPDX SBOM의 상세 구조 및 요소 


### 4.1. Source SBOM의 상세 구조 
![image]()
1. **소스 파일 정보 포함**: Source SBOM은 빌드에 포함된 소스 파일의 라이선스 등의 정보를 설명한다. 
2. **정보 추출 방법**:
  1. 정적 분석을 통해 파일 내의 **SPDX**** ****라이선스 식별자**를 찾아 라이선스를 추출한다. 
  2. 확장자와 위치를 기반으로 파일 유형(예: 소스 파일)을 추측한다. 
  3. 파일 해시와 콘텐츠를 식별하기 위한 잠재적 식별자(<mark>gethoid content identifier</mark>)를 계산한다. 
3. **SPDX**** 직렬화 예시 (init/main.c)** 
  1. 파일에는 유형, 내부 ID(글로벌 고유 ID의 약어), 파일 해시, 기본 목적(source), 파일 이름(init/main.c)이 포함된다. 
4. **라이선스 정보 인코딩** 
  1. SPDX에서 라이선스 정보는 실제 파일 정보와 분리되어 저장된다. 
  2. 파일은 has declared license 관계를 통해 라이선스 요소에 연결되며, 이 요소는 해당 라이선스(예: GPL2.0)를 설명한다. 


### 4.2. Output SBOM의 상세 구조 
![image]()
1. **패키지 요소 포함**: Output SBOM은 생성된 빌드 아티팩트(패키지)를 설명한다. 
2. **커널 패키지 예시 (bzImage)** 
  1. Linux 커널 패키지(bzImage)는 아키텍처를 설명하는 주석, 기본 목적(Primary Purpose: Application), 버전 정보를 포함한다. 
  2. 커널 모듈 또한 별도의 항목으로 참조된다. 
3. **배포 관계 및 ****빌드 환경** 
  1. 추상적인 패키지는 has distribution artifact 관계를 통해 빌드된 실제 파일에 연결된다. 
  2. SPDX는 빌드 환경을 인코딩하며, **빌드 요소(Build elements)**를 사용하여 빌드 단계를 설명한다. 
  3. Output SBOM에는 모든 작은 단계를 포괄하는 **고수준 빌드(High Level Build)** 요소가 포함되어 있으며, 이는 출력물이 Linux 커널 빌드임을 나타낸다. 
4. **Output SBOM의 역할**: 이 SBOM 자체로 사용 가능하며, 아티팩트에 대한 고수준 정보, 빌드 방식, 포함된 요소를 설명한다. 


### 4.3. Build SBOM의 상세 구조 
![image]()
1. **상세 연결 역할**: Build SBOM은 소스를 출력물과 상세한 방식으로 연결하는 역할을 한다. 
2. **빌드 단계 저장**:
  1. 이 구조에는 사용된 모든 **make 명령어**가 저장된다. 
  2. 모든 작은 빌드 단계는 이전 슬라이드에서 언급된 고수준 빌드에 ancestor of 관계를 통해 연결된다. 
3. **빌드 단계 요소 예시** 
  1. 중간 빌드 단계 요소에는 해당 빌드에 사용된 **실제 명령어**가 주석(comment)으로 포함된다. 
  2. has input 관계는 빌드 단계의 입력이 무엇이었는지 설명하며, has output 관계는 출력물을 설명한다. 
  3. 이 요소들이 소스 파일, 빌드 단계, 중간 단계, 최종 출력물을 연결하여 **빌드 트리**를 표현하는 객체들이다. 


## 5. SBOM 생성의 재현성 및 향후 계획 
![image]()
1. **재현 가능성 (Reproducibility)** 
  1. 생성된 SBOM은 **재현 가능**해야 하며, 이를 위해 SPDX에서 요구하는 특정 매개변수(예: **UUID**나 **빌드 시간**)를 외부에서 전달받아 사용한다. 
  2. 외부 데이터를 전달함으로써 전체 SBOM 생성 과정의 **결정론적**이고 **재현 가능**함을 보장할 수 있다. 

2. **향후 통합 계획 및 PoC** 
  1. **커널 소스 통합**: 프로젝트의 핵심 기능(저장소 내 sbom 폴더)만을 추출하여 **커널 소스의 **tools/sbom 경로에 기여하는 것이 목표이다. 
  2. **자동화**: 이 기능을 활성화하는 **설정 옵션**을 추가하여 make build 시 커널 빌드가 SBOM을 자동으로 생성하도록 할 계획이다. 
  3. **PoC (Proof of Concept)**: 이미 PoC가 구현되어 있으며, 명령어를 호출하면 빌드 출력 폴더에 세 개의 JSON 파일이 생성되어 기능이 작동함을 증명했다. 
  4. **확장 계획**: 현재 x86<mark>과 </mark>ARM<mark> 아키텍처</mark>로 제한되어 있으나, 이를 확장하고자 한다. 
  5. **제한 요소**: 지원 확장의 제한 요인은 초기 make 파일의 명령어 파서에 있으며, 이 부분의 격차를 메우는 작업이 진행 중이다. 

3. **외부 도구와의 통합 및 지식 그래프** 
  1. **Yocto 빌드 통합**: Yocto 빌드가 SPDX 파일을 생성할 때, 해당 파일이 커널을 참조한다면, KernelSBOM이 생성한 상세한 SBOM을 참조하도록 하여 **하나의 큰 지식 그래프**를 구성할 수 있다. 

4. **추가 질의응답 (라이선스 호환성 및 도구 체인)** 
  1. **라이선스 호환성 강제 여부**:
  1. 현재 계획은 소스 코드의 **라이선스 정보가 완전해야 한다**는 기본 동작을 설정하고, 누락된 정보를 명시적으로 허용해야만 진행되도록 하는 것이다. 
  2. 라이선스 호환성 검사는 이 코어 툴링에 포함하지 않으며, 이 SBOM을 소비하는 **외부 도구**에서 분석하도록 하는 것이 더 적절하다(툴이 의견을 가질 수 있고 사용 사례에 따라 달라지기 때문). 
  3. 빌드 트리를 통해 출력물에 어떤 소스 라이선스가 포함되었는지 추론할 수는 있지만, 커널 모듈 자체의 선언된 라이선스 메타데이터는 아직 부족하다. 
  2. **도구 체인 스냅샷 캡처**:
  1. 빌드에 사용된 컴파일러의 **버전 정보**를 문서화할 계획이다. 
  2. 빌드 요소는 이를 인코딩할 수 있도록 지원하며, 현재는 환경 정보만 캡처하고 있지만 버전을 포함하는 것이 목표이다. 

5. **Git 커밋 해시****와 식별자 문제** 
  1. **질문**: 커널 빌드의 식별자는 항상 Git 리포지토리와 커밋 해시였는데, 이것이 충분하지 않은 이유는 무엇인가? 
  2. **답변**:
  1. Git 커밋 해시는 소스의 상태를 식별하는 데 좋지만, **동일한 커밋 해시**라도 다른 환경이나 설정으로 다르게 컴파일될 수 있다. 
  2. <em>불완전한 작업 트리(unclean G tree)</em>로 빌드하면 정보가 불충분할 수 있으므로, 프로젝트는 **파일 해시**를 기반으로 식별하며, SPDX 또한 파일 해시를 요구한다. 
  3. Git 커밋 해시는 최종 문서에 추가할 수 있는 **귀중한 식별자**이지만, **빌드 설정(config)** 정보를 제공하지 못한다. 
  4. 빌드 요소는 config source URI를 통해 **빌드에 사용된 설정**을 설명하는 다른 SPDX 요소를 참조하여 이 정보를 인코딩할 수 있다.
