

## 📌 CPU 격리(CPU Isolation) 시 발생하는 IPI(Inter-Processor Interrupt) 간섭 문제의 원인과 해결 방안은 무엇인가?
CPU를 격리해도 커널 텍스트 업데이트(정적 키) 및 tlb 플러시 등으로 인해 ipi 간섭이 발생하며, 이를 해결하기 위해 커널 진입 시 작업을 지연 처리하거나 하드웨어 지원을 활용하는 방안을 논의 중입니다.


고성능 컴퓨팅 환경에서 **cpu 격리****(Isolation)**의 실질적인 문제점과 그 해결 방안을 심도 있게 다룹니다. 격리된 CPU를 사용하는 dpdk 같은 사용자 공간(User Space) 애플리케이션에 커널이 원치 않는 간섭을 일으키는 주범인 **IPI (Inter-Processor Interrupts)**의 메커니즘을 상세히 분석하고, 정적 키(Static Keys) 업데이트와 tlb 플러시 같은 주요 간섭 요소를 커널 진입 시점으로 **지연 처리(Deferral Approach)**하는 혁신적인 방법을 제안합니다. 이 논의를 통해 하드웨어 제약이 있는 x86 환경에서 **지연 시간이 극도로 중요한(Hard Real-time)** 시스템의 안정성을 확보하고, 커널 간섭을 최소화하는 리눅스 커널 개발의 최전선 인사이트를 얻을 수 있습니다.
## 1. CPU 격리 환경의 문제점 및 IPI 간섭의 주범 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/6YMhfpQUUFI/0.jpg)
1. **CPU 격리****의 목적**: 사용자가 지정한 CPU(들)를 **완벽하게 격리**하여, 해당 CPU에서 실행되는 DPDK와 같은 순수 사용자 공간 애플리케이션에 커널 간섭이 발생하지 않도록 하는 것이 목적이다. 
  1. 목표하는 환경: 스케줄러를 포함한 모든 성가신 커널의 방해가 격리된 CPU에서는 발생하지 않아야 한다. 

2. **현재 x86 환경의 간섭 현상**: 현재 x86 머신에서 CPU 격리를 설정하고, 격리되지 않은 CPU(하우스키핑 CPU)에서 작업을 기록하면, 격리된 CPU에도 간섭이 발생한다. 
  1. 주요 간섭 원인: 관찰되는 간섭은 대부분 **IPI(Inter-Processor Interrupts, 프로세서 간 ****인터럽트****)**에 의해 발생한다. 
  2. IPI 발생 원인 1: 커널 텍스트 업데이트(주로 **정적 키****, Static Keys** 업데이트) 시 IPI가 발생한다. 
  1. 정적 키: 커널 소스에서 많이 사용되며 매우 유용하지만, 정적 키 하나를 변경할 때마다 시스템의 모든 CPU에 IPI를 발생시킨다 (x86 아키텍처의 특징). 
  3. IPI 발생 원인 2: **TLB 플러시****(TB flushes)**가 발생한다. 
  1. 재현 테스트 사례: 커널 컴파일(LT val)과 핵벤치(hackbench)를 하우스키핑 CPU에서 실행하면 TLB 플러시가 발생하고, 이것이 격리된 CPU에 간섭을 일으킨다. 


## 2. 커널 진입 시점 지연(Deferral) 처리 방식 제안 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/6YMhfpQUUFI/139.jpg)
1. **지연 처리 방식의 기본 아이디어**: 격리된 CPU로 전송되는 작업이 **커널 공간**에만 관련된 것이라면, 사용자 공간 태스크를 즉시 인터럽트할 필요가 없다. 
  1. 해결책: "이 작업을 수행해야 한다"고 기억해 두고, **다음에 커널에 진입할 때** 해당 작업을 실행하도록 연기할 수 있다. 
  2. 정적 키 적용의 용이성: 정적 키 업데이트는 커널 코드를 업데이트하는 것이므로, 사용자 공간 코드를 실행 중인 프로세스는 커널에 진입하기 전까지는 해당 커널 명령에 도달하지 않기 때문에 커널 진입 시점까지 연기하는 것이 합리적이다. 

2. **지연 처리 구현 시의 기술적 난제**: 연기된 작업을 '커널 진입 직후'에 실행하는 것이 핵심인데, 실제로 <em>진입 직후</em>라는 시점을 정의하기 어렵다. 
  1. 초기 커널 진입 과정: 커널에 진입하자마자 임의의 코드를 실행할 수 없다. KPTI(Kernel Page Table Isolation)가 적용된 경우 커널 페이지 테이블로 전환하고 스택을 설정하는 등 사전 작업이 필요하다. 

3. **기존 방식(IPI)과 지연 방식의 비교**: 
  1. 기존 IPI 방식 (커널 텍스트 업데이트): 커널 진입 후 커널 페이지 테이블로 전환하고 컨텍스트 트래킹 등을 거쳐 **동기적(synchronous)으로** 콜백을 실행한다. 
  2. 지연 처리 방식: 수행해야 할 정보를 저장한 후, 다른 이유로 커널에 진입할 때까지 **비동기적(asynchronous)으로** 처리한다. 커널 진입까지 몇 시간이 걸릴 수도 있다. 
  3. 주의사항: 특히 오른쪽(지연 방식의 코드)에서 코드 실행 시점을 신중하게 처리해야 한다. 

4. **IPI 발생 원인 목록과 Slow Path 개념 논의**: 
  1. IPI 원인 종류: TLB 플러시, sync cores (메모리 배리어), 텍스트 업데이트 등이 있으며, IPI를 발생시키는 행위는 유한한 세트로 존재한다. 
  2. 원인 수량: 드라이버별로 다양하게 존재하여 정확한 숫자를 특정하기 어렵다. 
  3. **Slow Path 제안**: 격리된 CPU가 사용자 공간으로 진입할 때(혹은 나오면서) 해당 CPU를 IPI 전송 대상에서 제외하여, 사용자 공간에서 IPI를 전혀 받지 않도록 한다. 
  1. 커널 재진입 시 처리: 사용자 공간에서 나올 때, 저장해 두었던 모든 동기화 작업을 수행하며 이는 매우 느릴 수 있지만, 격리 CPU의 목적상 느려지는 것은 중요하지 않다. 
  4. **저자의 두 가지 접근법**: 저자는 이러한 문제를 해결하기 위해 두 가지 다른 접근법을 가지고 있었다. 


## 3. 지연 처리를 위한 구체적인 방법론 논의 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/6YMhfpQUUFI/374.jpg)
1. **컨텍스트 트래킹 기반 텍스트 업데이트 처리**: 
  1. 텍스트 업데이트 방식: 컨텍스트 트래킹을 활용하여 처리하며, 정적 키나 정적 호출 접근 시 위험 구역(danger zone) 문제가 발생하지 않도록 계측(instrumentation)이 잘 되어 있다. 

2. **TLB 플러시**** 처리의 어려움과 Dave Hansen의 제안**: 
  1. TLB 플러시 문제: TLB 플러시 처리는 구현하기가 **매우 어려웠다**. 
  2. Dave Hansen의 제안: 커널 페이지 테이블로 전환한 직후, **무조건적인(unconditional) ****TLB 플러시**를 수행하는 것이다. 
  3. 제안의 장점: 이 경우 매핑되지 않은 페이지에 접근할 위험이 없으므로 문제가 해결된다. 
  4. 제안의 단점: 이 코드는 <mark>극도로 끔찍하며</mark>, 시스템을 느리게 만든다. 

3. **No-HZ 및 ****CPU 격리**** 환경의 철학**: 
  1. 철학적 결론: No-HZ 및 CPU 격리 환경에서 커널에 진입하는 순간, <mark>이미 패배한 것</mark>이나 마찬가지다. (You lose) 
  2. Slow Path 허용: 커널에 진입했을 때, 지금까지 방해받지 않았던 모든 작업을 처리해야 하므로, 이 경로가 느려지는 것은 문제가 아니다. 
  3. 기술적 문제: 하지만 커널 초기에 진입하는 코드(super early entry code)에서 영향을 주지 않는 작업을 무조건 실행하는 것은 원치 않는다. 

4. **애플리케이션 주도 격리 설정의 필요성**: 
  1. 요구사항: 단순히 ISO CPUs로 지정된 CPU에서 실행되는 모든 애플리케이션이 이 처리 과정을 거치는 것이 아니라, **애플리케이션 스스로** "커널에 의해 방해받고 싶지 않다"고 선언할 수 있는 시스템 콜이나 PR control 같은 메커니즘이 필요하다. 
  2. 배경: 이렇게 해야 해당 애플리케이션이 커널로 진입했을 때 완전히 그 영향(느려짐)을 받게 된다. 

5. **하드 실시간 환경에서의 시간 지연 문제**: 
  1. 기존 방식 채택: 발표자는 이미 그러한 방식(애플리케이션 선언)을 수년 동안 사용해 왔지만, 지금은 그 방식을 껐다. 
  2. 메모리 매핑 문제: 커널로 진입하기 위해 메모리 매핑을 바꾸는 순간, 모든 것을 잃게 된다. 
  3. 하드 실시간 문제: 단순한 Soft GPS가 아니라 **하드 실시간(Hard Real-time)** 환경에서는 틱을 놓쳐 Phase Lock Loop를 업데이트하지 못하면 시스템 전체가 망가진다. 
  4. 지연 처리의 실효성 의문: IPI를 캐싱했다가 나중에 (몇 시간 후) 실행하면, 원래 IPI를 요청했던 태스크가 그때 실행되는 것을 정말로 신경 쓸지 의문이다. (실효성이 없다) 

6. **Errata(하드웨어 버그) 처리에 대한 고려**: 
  1. 새로운 간섭원: IPI가 하드웨어 버그(errata) 처리를 위해 사용되는 경우가 많다. 
  2. 복잡성 증가: 이러한 errata 관련 IPI를 안전하게 지연 처리할 수 있는지 여부가 시스템 복잡성을 증가시킬 수 있다. 
  3. 다른 아키텍처 (ARM 64): ARM 64의 경우, 텍스트 업데이트 시 아키텍처 자체가 올바른 동작을 보장하고, TLB 무효화를 위해 IPI 대신 TBI 명령어를 사용하므로 해당 문제가 발생하지 않는다. 
  4. x86의 errata: 일부 errata는 캐시 플러싱 등을 강제하기 위해 IPI를 중앙 CPU로 보내도록 요구하는 경우가 있으며, 이는 x86의 고유한 문제로 보인다. 


## 4. 하드웨어 개선의 기대와 인터페이스 논의 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/6YMhfpQUUFI/636.jpg)
1. **x86 하드웨어의 개선 방향**: TLB 플러시 문제에 대해 x86 하드웨어에서 지원이 이루어질 조짐이 있다. 
  1. AMD: 이미 <mark>invalidate broadcast</mark> 기능을 지원하고 있다 (커널 6.15?). 
  2. Intel: RAR (Remote Action Request)을 개발 중이며 아직 지원되지는 않지만 작업이 진행 중이다. 

2. **무조건적인 초반 진입 코드에 대한 회의론**: 
  1. 문제점: 현재 무조건적인 초반 진입 코드(super early entry unconditional stuff)는 코드가 깨끗하지 않고, 작성한 본인도 싫어하는 방식이다. 
  2. 개발 방향의 불확실성: 이 방식을 계속 밀고 나가야 할지, 아니면 고객에게 새 하드웨어로 교체하도록 권유해야 할지 명확한 방향이 필요하다. 

3. **격리 모드를 위한 API/인터페이스 논의**: 
  1. 격리 설정 단계:
  1. **No-HZ Full**이 필요하다. 
  2. 현재 확실하게 작동하는 방식은 커널 명령줄에 ISO CPUs를 지정하여 해당 CPU를 격리(shutdown)하는 것이다. 
  3. **CPU sets**가 동일한 기능을 수행하도록 개발 중이며, 완료되면 이를 사용하여 CPU를 격리할 것이다. 
  2. 애플리케이션 선언: CPU 격리 이후, **새로운 ****시스템 콜**** 또는 PR control**을 통해 애플리케이션이 "나는 방해받고 싶지 않다(I don't want to be bothered)"고 선언해야 한다. 
  3. 대상 애플리케이션: 이 기능은 CPU에 있는 모든 애플리케이션이 아니라, <mark>하드 실시간</mark>이 필요한 안전 필수(safety critical) 인프라나 고주파 매매(high-frequency trading)와 같은 곳에서 필요하다. 

4. **커널 진입 시점에서의 플래그 확인 메커니즘**: 
  1. 인터페이스 사용의 어려움: PR control 같은 인터페이스를 커널 초반 진입 어셈블리 코드(super-entry assembly code)에서 소비해야 하므로 C 언어의 편리함을 사용할 수 없다. 
  2. 플래그 기반 처리 제안: 커널 진입 시 **태스크 구조체(task struct)를 확인**하여 플래그가 설정되어 있다면, 커널에서 다른 어떤 작업을 하기 전에 <mark>완벽한 동기화</mark> 작업을 수행해야 한다. 
  1. 처리 시점: 이 플래그 확인 및 처리는 **모든 ****인터럽트**** 발생 시**에도 적용되어야 한다. 
  3. 정적 키 활용: 프레데릭의 제안에 따라, 이 초반 진입 코드에서 정적 키를 사용할 수 있도록 약간의 어셈블리 코드가 존재한다. 
  1. 활성화 조건: PRTL을 사용하여 **첫 번째 사용자**가 있을 때만 정적 키를 활성화할 수 있다. 


## 5. 비-IPI 간섭 요인 및 시스템 설계 문제 
![image](https://resource-release.s3.ap-northeast-2.amazonaws.com/thumbnails/6YMhfpQUUFI/969.jpg)
1. **주요 간섭 요인 1: 자원 누적 문제 (Per-CPU 페이지)**: 
  1. 문제: 격리된 코어가 커널에 전혀 진입하지 않고 계속 실행되면, 일반 목적 태스크(예: 로그 읽기)가 사용하던 **CPU당 페이지(per-CPU pages)**를 해제할 기회가 없게 된다. 
  2. 결과: 결국 시스템 전체가 락업(lock up)될 수 있다. 
  3. 요구사항: API는 IPI 문제 외에도, 할당된 슬라이스를 포기하지 않아 시스템을 블로킹하는 문제를 포괄적으로 다룰 수 있어야 한다. 
  4. 현재 상황: 일부 서브시스템에서는 No-HZ 애플리케이션에서 페이지 할당 관련 문제를 해결하기 위한 임시 방편(Ad hoc solution)이 존재하지만, 이는 일반적인 해결책이 아니다. 

2. **주요 간섭 요인 2: 버스 락업 (Bus Lockup)**: 
  1. 문제: IPI나 CPU 사용량 외에도, 다른 CPU가 메모리 버스(memory bus)를 락업하여 격리된 CPU의 작업이 갑자기 멈출 수 있다. 
  2. 위험성: 대형 머신에서는 다른 CPU에서 발생하는 현상이 다른 애플리케이션에 큰 영향을 미칠 수 있다. 
  3. 시스템 설계의 중요성: 이러한 문제는 시스템 설계의 일부이며, NUMA 환경에서 하나의 노드만을 사용하여 버스 문제를 최소화해야 한다. 

3. **CR3 전환과 ****TLB 플러시****의 관계**: 
  1. 질문: 커널 CR3(컨트롤 레지스터 3)을 전환하는 것만으로는 TLB 플러시가 자동으로 되지 않는가? 
  2. 답변: 메모리 관리 전문가의 의견으로는 모든 경우에 자동 플러시가 되는 것은 아니다. 
  3. KPTI 사용 시: KPTI를 사용하면 글로벌 비트(Global bit)를 이미 비활성화하고 있기 때문에 CR3 전환만으로 해결되지 않는 문제가 있다.
