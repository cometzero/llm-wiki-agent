## 📌 KUnit 테스팅의 주요 문제점과 한계는 무엇인가?
KUnit은 커널 내에서 유닛 테스트를 수행하는 데 유용하지만, <mark>의존성 관리의 어려움, 느린 빌드 및 실행 시간, 복잡한 테스트 작성 및 유지보수 부담</mark> 등 기존 유닛 테스팅 프레임워크에 비해 여러 가지 부족한 점과 한계가 있습니다.


## 💡 KUnit의 한계로 인해 발생하는 구체적인 문제들은?

- **의존성 관리**: 패치 도입 및 유지보수로 인한 복잡성 증가, 수동적인 기능 스터빙/모킹 필요.
- **개발 주기**: 커널 전체 빌드 및 부팅으로 인해 테스트 작성-실행-관찰 주기가 느림.
- **확장성**: 많은 수의 정교한 테스트 시 여러 커널 빌드 필요 및 테스트 충실도 문제 발생.
- **실행 환경**: 시스템 상태에 대한 높은 의존성, 에뮬레이션 또는 실제 하드웨어 필요.

KUnit의 **본질적인 테스트 한계**를 실제 개발자 경험을 통해 심층적으로 분석하는 발표입니다. 특히 작은 **격리된 단위 코드**에 대한 상세 테스트(TDD, 안전 기능 검증)를 진행할 때, KUnit이 기존 유닛 테스트 도구들(Mocking, Faking)처럼 **의존성을 효율적으로 관리**하지 못해 발생하는 비효율성(패치 유지보수, 느린 write-execute-observe 주기)을 구체적인 코드 예시와 함께 지적합니다. 리눅스 커널 개발 환경에서 보다 빠르고 신뢰성 높은 **고립된 유닛 테스트**를 구축하고자 하는 개발자라면, KUnit 프레임워크의 구조적 제약을 명확히 이해하고 대안을 모색하는 데 실질적인 통찰을 얻을 수 있습니다.
## 1. KUnit의 테스트 한계 및 비효율성 분석 
![image]()
발표자(Matt Whitehead, The Boeing Company)는 KUnit의 본질적인 테스트 한계, 특히 **작은 고립된 단위 코드**를 테스트할 때 발생하는 비효율성을 논의한다. 

1. **테스트 시나리오 및 목표**: 
  1. KUnit의 한계는 **고도의 상세 테스트(highly detailed tests)**나 **작고 고립된 단위(small, isolated units)**를 테스트할 때 명확해진다. 
  2. 이는 기능적 안전성 검증(functional safety verification)이나 형식 검증(formal verification)처럼, 의존성이 최소화된 작은 환경에서 사양을 테스트하려는 시나리오와 연관된다. 
  3. 목표는 **의도된 기능(intended function)**, 기능적 안전성(functional safety), 지속적인 기능, 보안 등을 검증하는 것이다. 
  4. 논의를 위해 **의존성을 최소화**하려고 시도한 <em>단단히 결합된(tightly coupled)</em> 테스트의 데모 예시를 활용한다. 

2. **KUnit 테스트 과정의 비효율성**: 
  1. 일반적인 테스트 과정은 '테스트 작성(Write tests)', '테스트 빌드(Build tests)', '테스트 실행(Execute tests)' 순서로 진행된다. 
  2. KUnit은 커널 컨텍스트 내에서 실행되어야 하므로, **전통적인 유닛 테스트 도구(Mocking, Faking)**가 제공하는 **의존성 관리 및 디커플링** 도구들이 결여되어 있다. 
  3. **코드 고립 및 의존성 관리 문제**: 
  1. KUnit으로 코드 고립과 의존성 관리를 달성하려면, 커널 내부에 **패치(patches)**를 도입해야 한다. 
  2. 이 패치들은 유지보수(maintenance) 부담을 발생시키며, 특히 **작은 고립된 단위 코드에 대한 상세 테스트**를 많이 작성할 경우 이 유지보수 부담이 빠르게 증가한다. 

3. **느린 **write-execute-observe 주기: 
  1. KUnit 테스트는 커널을 부팅하고 실행해야 하므로, **작성-실행-관찰(write-execute-observe) 주기**가 느려진다. 


## 2. KUnit에서 의존성 최소화를 위한 수동 작업 및 복잡성 
![image]()
발표자는 의존성을 최소화하여 작은 단위 코드를 테스트하려 할 때 KUnit에서 요구되는 구체적인 수동 작업들을 제시한다. 

1. **테스트를 위한 수동 코드 변경 목록**: 
  1. **Config 항목 추가**: 테스트를 활성화/비활성화하고, 도입된 모킹(mocking) 기능을 켜고 끌 수 있도록 설정 항목을 추가해야 한다. 
  2. **수동적인 Mock/Stub 구현**: 실제 스텁(stub)이나 목(mock)을 도입할 수 없으므로, 테스트 프레임워크의 일부로서 수동으로 코드를 조작해야 한다. 
  3. **Define 주입**: 테스트의 일부로 특정 기능 항목을 켜고 끌 수 있도록 코드에 **Define**을 주입해야 한다. 
  4. **데이터 구조 코드 중복 및 수동 설정**: 
  1. 다양한 데이터 구조에 대해 코드를 중복(duplicate code)해야 한다. 
  2. 이벤트 시퀀스를 확인하기 위한 **테스트 데이터**를 추가해야 한다. 
  3. 테스트의 **전제 조건(preconditions)**을 설정해야 하며, 이는 KUnit의 일반적인 상황처럼 시스템을 부팅하고 해당 조건이 발생하기를 기다리는 대신 **인위적으로 조건**을 도입하기 위해 수동 코드를 작성하고 유지보수해야 함을 의미한다. 
  5. **데이터 구조 설정을 위한 추가 호출**: 모킹 기능의 부재로 인해 데이터 구조를 설정하기 위한 광범위한 추가 호출이 필요하다. 

2. **코드 예시를 통한 복잡성 시연**: 
  1. 발표자는 GPIO 라인 레코드 기능 테스트 예시를 보여주며, 이 테스트를 위해 많은 **추가 코드 중복(duplicates)**이 필요함을 시연한다. 
  2. 테스트 코드 자체 내에서도 모든 설정을 위해 여러 단계를 거쳐야 한다. 
  3. 이는 일반적인 KUnit 테스트(시스템이 정상적인 흐름으로 설정되기를 기다리는 인-컨텍스트 테스트)와 달리, 기능을 주입하여 **컨텍스트 외부에서 테스트**를 시도하는 방식이므로 복잡성을 증가시킨다. 
  4. 원하는 방식으로 작동하도록 하기 위해(특정 함수가 특정 방식으로 호출되었는지 확인하기 위해) <mark>config 조각</mark>과 <mark>#ifdef</mark>를 다수 주입해야 했다. 


## 3. 빌드 및 실행 단계에서의 한계와 높은 비용 
![image]()
테스트 작성 후 빌드 및 실행 과정에서도 상세한 유닛 테스트가 많을 경우 KUnit의 구조적 한계로 인해 비용과 복잡성이 증가한다. 

1. **빌드 단계의 비효율성**: 
  1. 테스트가 커널에 빌드되기 때문에, 매번 **커널 전체를 빌드**해야 한다. 
  2. 테스트가 1,000개가 넘어가기 시작하면 커널 바이너리 크기 때문에 **여러 개의 커널**이 필요하게 된다. 
  3. 여러 커널을 유지보수하는 부담이 발생하며, 이는 **테스트의 충실도(fidelity)** 문제로 이어진다. 즉, 테스트에 사용된 커널이 실제 커널과 다를 수 있다. 
  4. 빌드가 여러 번 필요하여 시간 소모가 크며, 패치를 직접 유지보수해야 하는 경우 유지보수 부담이 매우 높다. 

2. **실행 단계의 비효율성**: 
  1. **시스템 상태에 대한 높은 의존성(heavy dependency on system state)**이 문제의 핵심이며, 앞서 작성한 테스트는 이 의존성을 제거하려는 시도였다. 
  2. 테스트가 많으면 **많은 빌드와 많은 부팅**이 요구된다. 
  3. **충돌하는 시스템 상태(conflicting system states)**를 테스트해야 하는 경우, 테스트 개수보다 훨씬 더 많은 부팅이 필요할 수 있다. 예를 들어, 10개의 커널 빌드가 있어도 10회 이상 부팅해야 할 수 있다. 
  4. **긴 실행 시간**: 특정 시스템 상태가 안정화되기를 기다려야 테스트를 수행할 수 있으므로 실행 시간이 길어진다. 이는 유닛 테스트가 해당 유닛만 빌드하고 실행하는 방식과 대조된다. 
  5. 테스트 실행을 위해 최소한 **에뮬레이션(QEMU 등)** 또는 실제 하드웨어가 요구된다. 
  6. 이러한 모든 이유로 인해, 빌드 파이프라인의 **자동화가 자원 집약적**이며 비용과 시간을 증가시킨다. 


## 4. 실제 테스트 실행 결과 및 코드 커버리지 문제 
![image]()
의존성을 제거한 작은 예제 테스트를 실행한 결과, 실행 속도가 매우 느린 것으로 나타났으며, 이러한 복잡한 테스트 방식이 코드 커버리지를 위해 필요할 수 있다는 점이 지적된다. 

1. **테스트 실행 시간 측정**: 
  1. 의존성을 제거한 매우 작고 제약적인 예제 테스트를 실행한 결과, <mark>총 경과 시간은 143초</mark>가 소요되었다. 
  2. 이는 **단 하나의 매우 작은 테스트**에 대해서는 상당한 시간이다. 

2. **코드 커버리지와의 관계**: 
  1. 커널에 **코드 커버리지 계측(instrumentation)**을 추가하면 테스트를 위한 공간이 더욱 부족해져 상황이 악화된다. 
  2. **특정 의존성을 제거하며 KUnit 테스트를 작성해야 하는 한 가지 이유**는 바로 **코드 커버리지**를 위해서이다. 


## 5. Q&A 및 KUnit 한계에 대한 논쟁 
![image]()
청중과의 Q&A를 통해 KUnit의 구조적 한계와 커널 테스트의 본질적인 어려움에 대한 논의가 진행된다. 

1. **Google CHOS 커널 팀의 경험 (Tomas)**: 
  1. CHOS 커널 팀은 KUnit을 사용하여 업스트림과 내부 테스트 인프라 간에 공유 가능한 테스트를 만들려고 시도했다. 
  2. 그들이 발견한 한계는 스텁(stub)을 **명시적으로 코드 내부에 지정**해야 한다는 것이었다. 
  3. Capro 같은 도구를 사용하여 이 문제를 해결하려는 접근 방식이 있었으나, 이는 모킹이나 페이킹과는 거리가 멀고 **우회책(workarounds)**에 가깝다고 언급된다. 

2. **커널 테스트의 본질적 문제 vs KUnit의 문제**: 
  1. 청중은 제시된 문제 중 일부(예: 하드웨어 의존성, 전제 조건 설정의 어려움)는 **KUnit의 문제가 아니라 커널을 테스트하는 것 자체의 문제**라고 주장한다. 
  2. 발표자는 이에 대해 반박하며, **전통적인 유닛 테스트 프레임워크**는 의존적인 코드를 실행할 필요 없이 **전제 조건을 설정할 수 있는 도구 상자(toolbox)**를 제공하며, 커널 컨텍스트에서도 유사한 작업을 수행할 수 있다면 해당 문제를 우회할 수 있다고 주장한다. 
  3. 발표자는 **타사 유닛 테스트 도구**를 사용하여 동일한 기능을 테스트한 프로토타입을 언급한다. 
  4. 이 프로토타입에서는 해당 코드 섹션을 커널에서 분리하여 **사용자 공간(user space)** 또는 네이티브 환경에서 빌드하고 실행할 수 있었다. 
  5. 외부 도구의 툴박스를 사용하면 **커널 코드를 모두 실행할 필요 없이** 의존성과 시스템 상태 정보를 원하는 대로 설정할 수 있었다. 
  6. 발표자는 하드웨어 의존적인 시나리오 외에도 **작은 섹션의 코드 고립 및 테스트**에 대해서는 KUnit이 제공하지 않는 도구들이 도움이 된다고 강조한다. 

3. **기존 Mocking 기능 및 UML 모드 질문 (David)**: 
  1. 청중(David)은 기존의 정적 스텁 및 Tomas가 언급한 기능들(static stubs, Capro 등)이 어느 정도 도움이 될 수 있음을 언급한다. 
  2. 또한, **UML(User-Mode Linux) 모드**를 사용해 보았는지 질문한다. UML 모드는 빌드 및 실행 속도가 훨씬 빠르다. 
  3. 발표자는 UML 모드가 **빌드와 실행을 더 빠르게** 하지만, 패치 관리, 많은 테스트 유지보수 등 자신이 제기한 **다른 문제들을 해결해 주지는 못한다**고 답한다. 

4. **KUnit vs 타사 도구의 비교 장점**: 
  1. 발표자는 안전 기능 검증, 코드 커버리지 등의 시나리오에서 일반 유닛 테스트 프레임워크가 제공하는 도구가 KUnit보다 우수하다고 재차 주장한다. 
  2. 타사 테스트 프레임워크를 사용했을 때, 테스트하려는 코드를 **더 쉽게 고립**시키고 의존성과 시스템 상태를 **모킹(mock out)**할 수 있었으며, 실행 시간도 훨씬 좋았다. 
  3. 타사 도구와 방법론을 적용하기 어려운 이유는 커널이 **모놀리식(monolithic)이고 복잡하여** 설정을 시작하는 단계의 어려움 때문일 수 있다. 
  4. 발표자가 사용한 특정 도구(CMock 포함)는 **자동 의존성 모킹** 기능을 제공하여 수동으로 62개의 헤더 파일을 모킹할 필요가 없어 큰 도움이 되었다. 

5. **과거의 경험과 KUnit의 상대적 우위**: 
  1. 청중 중 한 명은 약 20년 전 넷필터(net filter) 코드를 사용자 공간으로 분리하여 테스트하려 했을 때, 모킹 작업이 테스트 자체를 작성하는 것보다 **훨씬 더 어려웠다**고 언급한다. 
  2. 이 청중은 KUnit 접근 방식이 당시의 경험보다 훨씬 **더 실현 가능한(feasible)** 접근법이었다고 평가한다. 
  3. 발표자는 시간이 많이 지났기 때문에 상황이 변했을 수 있음을 인정하지만, 자신이 사용한 프레임워크(CMock)가 **의존성 모킹을 자동으로 처리**해주어 초기 프로토타입 설정이 어려웠음에도 확장성이 있었다고 설명한다. 

6. **KUnit과 외부 모킹의 난이도 차이**: 
  1. 발표자는 외부 모킹 프레임워크를 사용할 경우, 대부분의 모킹 대상은 빌드 시 발생하는 **간접적인 의존성**이며, 실제로 로직을 주입해야 하는 부분은 소수에 불과하다고 말한다. 
  2. 반면 KUnit은 정적 함수처럼 **함수 내부에 있는 매우 구체적인 부분**을 테스트하려면, 필요한 정보에 훅(hook)을 걸기 위해 커널의 여러 지점에 **많은 추가 코드를 삽입**해야 한다. 

7. **사용자 공간 테스트 활용 사례 및 QEMU 개선**: 
  1. 청중은 비교적 고립된 코드에 큰 변경 사항을 적용할 때 사용자 공간 테스트 기법을 사용하기도 한다고 언급한다. 
  2. 또한, 지난 20~25년간 QEMU와 KVM의 부팅 속도가 크게 개선되어 커널을 부팅하는 오버헤드가 과거보다 훨씬 줄었다고 지적한다. (단, 디바이스 드라이버에는 해당되지 않는다.)
