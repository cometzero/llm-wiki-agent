

## 📌 멀티커널 아키텍처는 무엇이며, 어떤 핵심적인 이점을 제공하는가?
멀티커널 아키텍처는 가상화나 하이퍼바이저 없이 <mark>하나의 머신에서 여러 Linux 커널을 동시에 실행</mark>하여 커널 간 격리와 탄력적인 리소스 관리를 제공하는 새로운 접근 방식입니다.


## 💡 기존 클라우드 컴퓨팅 기술(컨테이너, VM)과 비교했을 때 어떤 이점이 있는가?

| **항목** | **컨테이너** | **VM** | **멀티커널** |
| --- | --- | --- | --- |
| 격리 수준 | 리소스 레벨 | 하이퍼바이저 기반 | 커널 레벨 (더 강력) |
| 오버헤드 | 낮음 | 존재 | 낮음 (가상화 없음) |
| 단일 실패 지점 | 커널 공유 (존재) | 하이퍼바이저 (존재) | 없음 |
| 복잡성 | 보통 | 높음 | 낮음 |

리눅스 커널의 **고전적인 '단일 커널' 모델**에 도전하여, 하이퍼바이저나 가상화 없이 **단일 머신에서 여러 ****리눅스 커널****을 동시 실행**하는 멀티커널(Multikernel) 아키텍처를 소개합니다. 이 콘텐츠를 통해 독자들은 커널 수준의 강력한 격리(Isolation)와 동적 자원 관리를 실현하는 혁신적인 접근법을 이해하고, 기존 컨테이너 및 VM의 한계를 넘어 **노이즈 이웃 문제 제거** 및 **공격 표면 축소**를 달성하는 방법을 배울 수 있습니다. 특히, kexec, Device Tree Overlay와 같은 기존 리눅스 요소를 재활용하여 **무중단 ****라이브 커널 업데이트**나 **커널 크래시 자동 복구**를 구현하는 구체적인 청사진과 실질적인 코드를 확인할 수 있어 시스템 엔지니어와 개발자에게 깊은 통찰을 제공합니다.
## 1. 멀티커널 아키텍처 소개 및 기존 싱글 커널 모델의 한계 
![image]()
1. **발표자 및 배경 소개** 
  1. 발표자는 Tong Wang이며, 리눅스 커널 개발자이자 마이크로넬 테크놀로지(Micronel Technology)의 창업자 겸 CEO이다. 
  2. 발표 주제는 **멀티커널 아키텍처**이며, 이 아키텍처는 커널 간 격리(kernel-to-kernel isolation)와 탄력적 자원 관리(elastic resource management)를 제공한다. 

2. **고전적인 싱글 커널 모델에 대한 도전** 
  1. 오랫동안 하나의 머신에서는 하나의 리눅스 커널만 실행될 수 있다는 가정이 존재했다. 
  2. 여러 커널을 실행하려면 KVM이나 Xen과 같은 **가상화****(Virtualization)** 기술 또는 AM과 같은 **특정 하드웨어**가 필요하다는 가정이 지배적이었다. 
  3. 이러한 가정은 SMP(Symmetric Multiprocessing) 설계에 뿌리를 두고 있으며, SMP에서는 모든 CPU가 대칭적으로 관리된다는 특징이 있다. 
  4. 그러나 이 싱글 커널 모델은 하드웨어 요구사항이 아니며, 멀티커널 아키텍처는 이 가정을 완전히 무효화한다. 

3. **멀티커널 아키텍처의 특징** 
  1. 멀티커널은 **가상화****, ****하이퍼바이저****, 전문 하드웨어 없이** 동일한 머신에서 여러 리눅스 커널을 동시에 실행한다. 
  2. 각 커널은 자체 하드웨어 파티션을 제어하며, 서로 다른 커널들은 명시적인 메시징(explicit messaging)을 통해 통신한다. 
  3. 멀티커널(Multikernel) 개념 자체는 새로운 것이 아니며, 학계에서는 **코-커널(Co-kernel)**, **코-커널 분리 커널(Co-kernel separation kernel)**, 또는 **중첩 커널(Nested kernel)** 등으로 불리기도 했다. 


## 2. 기존 멀티커널 연구 검토 및 설계 철학 
![image]()
1. **선행 멀티커널 연구 사례** 
  1. **Barce (2009년)**: 멀티커널 연구의 선구자로, 복제(replica)를 기반으로 하며 전체 시스템이 **단일 시스템 이미지(Single System Image)**를 형성한다. 다만, 이 운영체제는 리눅스가 아니다. 
  2. **Popcorn Linux (2013년)**: 멀티커널 개념을 리눅스에 도입한 최초의 사례로, 커널 간 프로세스 마이그레이션(process migration)을 구현했지만, 여전히 단일 시스템 이미지를 유지했으며 이기종 CPU(heterogeneous CPUs)에 초점을 맞추었다. 
  3. **MegaKernel (2015년)**: **투-티어(Two-tier) 설계**를 사용했으며, 리눅스 기반의 서비스 커널(Service kernel)과 맞춤형 경량 커널(Customized lightweight kernel, 리눅스가 아님)인 성능 커널(Performance kernel)로 구성되었다. 

2. **발표자가 제시하는 멀티커널의 설계 철학** 
  1. 발표자의 설계는 MegaKernel로부터 많은 영감을 받았으며, 복제(replication) 대신 **격리(isolation)** 접근 방식을 채택한다. 
  2. 서로 다른 커널들은 **피어(Peer)로서 공존**하며, 호스트 커널(Host kernel)이 스폰 커널(Spawned kernels)의 라이프사이클을 관리하는 등의 관리적 역할에서만 차이를 둔다. 
  3. 각 커널은 전용이지만 **탄력적인(elastic) 하드웨어 자원**을 가지고 실행되며, 격리되어 있기 때문에 각 애플리케이션은 해당 커널 인스턴스 내에서 맞춤 제작된(tailored) 리눅스 커널을 실행할 수 있다. 


## 3. 멀티커널 OS의 구조 및 기존 리눅스 요소 재사용 전략 


### 3.1. 멀티커널 OS의 고수준 설계 및 통신 방식 
![image]()
1. **호스트 커널**** (Host Kernel)** 
  1. 부팅 커널(Booting kernel)로서 모든 관리 책임을 맡는다. 
  2. 모든 하드웨어 자원을 관리하고, 스폰 커널의 라이프사이클을 관리한다. 
  3. 동일 호스트 내 다른 커널들 간의 자원 관리를 조정한다. 

2. **스폰 커널**** (Spawned Kernels)** 
  1. 호스트 커널에 의해 시작되며, 더 나은 성능과 경량화를 위해 **맞춤 제작된 ****리눅스 커널****(tailored Linux kernel)**을 실행해야 한다. 
  2. 실제 애플리케이션은 스폰 커널 내에서 실행되며, 각 스폰 커널은 격리된 하드웨어 자원을 갖는다. 

3. **커널 간 통신 (Inter-Kernel Communication)** 
  1. 커널들은 **프로세서 간 인터럽트(IPI, Interprocessor Interrupt)**와 **공유 메모리****(Shared Memory)**를 사용하여 통신한다. 

4. **MegaKernel 대비 차별점 및 Linux 재사용 강조** 
  1. MegaKernel이 맞춤형 커널을 사용한 것과 달리, 발표자의 접근 방식은 **표준 ****리눅스 커널****(Linux kernel as it is)**을 사용한다. 
  2. 리눅스 커널을 사용하는 이유는 그 **기능(capability)** 때문이며, MegaKernel이 구현한 시스템 콜 200여 개는 리눅스 지원 시스템 콜의 절반도 되지 않는다. 
  3. 리눅스는 오늘날 시스템 콜 그 이상(예: eBPF)이므로, 전체 리눅스 생태계와 호환되는 새로운 OS를 바닥부터 구현하는 것은 불가능에 가깝다. 


### 3.2. 기존 리눅스 인프라 재사용 전략 
![image]()
1. **커널 이미지 관리 및 부팅 재사용: ****kexec** 
  1. 멀티커널 지원을 리눅스 커널에 추가하고, 경량 커널을 얻기 위해 리눅스 커널을 맞춤 제작(tailor)하는 방식을 사용한다. 
  2. 커널 이미지 로드 및 언로드를 위한 기존 리눅스 메커니즘인 **kexec**를 재사용한다. 
  3. kexec 재사용을 통해 **커널 서명**** 인프라(kernel signing infrastructure)**와 최근 커뮤니티에서 지원하는 **kexec**** 핸드오버(****kexec**** handover)**를 추가적인 노력 없이 얻을 수 있다. 
  4. kexec 핸드오버는 커널 간 다른 정보(예: Device Tree)를 전달하는 데 사용된다. 
  5. 발표자의 설계 철학은 "새로운 것을 발명하지 않고(don't reinvent anything), 모든 것을 재사용하는 것"이다. 

2. **추가 재사용되는 리눅스 컴포넌트** 
  1. **프로세서 간 인터럽트 (IPI)**: 이미 리눅스 커널에서 흔히 사용되는 IPI를 재사용한다. 
  2. **물리 메모리 관리**: 물리 메모리 할당자를 새로 구현하는 대신 **jpool allocator**를 재사용하며, 이는 잘 작동한다. 
  3. **커널 일시 중지/재개**: 기존 커널 일시 중지 및 재개 인프라를 재사용하며, 향후 최대 절전 모드(hibernation) 인프라를 활용하여 **체크포인팅(checkpointing)**과 **커널 컨텍스트 스위칭(kernel context switching)**을 지원할 계획이다. 
  4. **커널 간 통신 (Inter-Kernel Communication)**: **v-shock 인프라**를 활용하여 프로토콜을 구현한다. 
  5. 이러한 접근 방식은 리눅스 커널 서브시스템과의 심층적인 통합을 통해 리눅스를 포용하려는 철학을 반영한다. 


## 4. 동적 자원 관리: Device Tree 및 Hot Plug 활용 
![image]()
1. **자원 관리**** 접근 방식 결정: 동적 할당의 필요성** 
  1. 커뮤니티에서 자주 묻는 질문은 정적 파티셔닝(Static partitioning)을 할 것인가, 동적 할당(Dynamic allocation)을 할 것인가이다. 
  2. 정적 파티셔닝은 너무 쉽고 동적 할당의 기본 상태일 뿐이며, 동적 할당은 훨씬 유연하다. 
  3. 클라우드 컴퓨팅 및 고성능 컴퓨팅(HPC) 시나리오에서는 자원 활용도를 높이기 위해 **동적 ****자원 관리**가 필수적이다. 
  4. 동적 자원 관리는 격리를 유지하면서 구현하기 어렵지만, 발표자는 장기적으로 유연성이 승리할 것이라 믿으며 동적 할당을 선호한다. 

2. **Device Tree와 Overlay를 통한 동적 ****자원 관리**** 인터페이스** 
  1. 자원 관리 구현을 위해 기존 리눅스 인프라인 **Device Tree**를 재사용한다. 
  2. Device Tree는 임베디드 시스템에서 하드웨어 자원을 기술하는 데 사용되는 잘 확립된 표준이다. 
  3. Device Tree는 **Device Tree Overlay** 기능을 제공하는데, 이는 임베디드 시스템에서 런타임에 동적 하드웨어 구성을 변경할 수 있게 한다. 
  4. 이는 멀티커널에서 동적 자원 변경을 가능하게 하는 완벽한 인터페이스가 된다. 
  5. Device Tree를 사용하면 취약한 **커널 명령줄 조작(kernel command line manipulation)**을 피할 수 있는 추가적인 이점이 있다. 
  6. **Device Tree Overlay 예시**: 테스트에 사용된 실제 예시를 통해 특정 커널 인스턴스('웹 서버')에 메모리 (1GB 또는 0.5GB), 물리적 ID 1번 CPU, PCI 장치(네트워크 인터페이스) 등을 할당하는 것을 보여주었다. 
  7. Device Overlay를 사용하여 CPU 2번을 웹 서버 커널 인스턴스에 추가할 수 있으며, 적용 후 해당 인스턴스는 CPU 1과 CPU 2를 모두 갖게 된다. 

3. **자원 변경의 실제 구현: Hot Plug 재사용** 
  1. Device Tree는 인터페이스일 뿐이며, 실제 변경을 적용하기 위해 하드웨어 자원을 업데이트하는 구체적인 작업이 필요하다. 
  2. 발표자는 새로운 것을 발명하지 않고 리눅스에서 잘 지원되는 **Hot Plug(핫플러깅) 메커니즘**을 활용한다. 
  3. CPU, 메모리, PCI 장치에 대한 핫플러깅은 매우 잘 작동한다. 

4. **동적 자원 업데이트 프로세스 순서** 
  1. **사용자 공간 요청**: 사용자 공간이 변경을 원할 때, 변경 사항을 기술하는 Device Tree Overlay를 생성한다. 
  2. **호스트 커널**** 처리**: 호스트 커널은 이 오버레이를 자원 업데이트 메시지로 변환한다. 
  3. **메시지 전송**: 메시지는 IPI와 공유 메모리를 통해 대상 커널(target kernel)로 전송된다. 
  4. **대상 커널 적용**: 대상 커널은 메시지를 수신하면 실제 핫플러그 작업을 사용하여 변경 사항을 적용하고, 자원 업데이트가 완료된다. 


## 5. IO 장치 격리 및 공유 (하드웨어 큐 활용) 
![image]()
1. **IO 장치**** 자원 할당의 어려움** 
  1. 앞서 언급된 프로세스는 충분한 하드웨어 자원이 있다고 가정하지만, IO 장치의 경우 항상 그렇지 않다. 
  2. 서버는 수백 개의 CPU 코어를 가질 수 있지만, IO 장치는 소수에 불과하기 때문이다. 

2. **가상화****의 SR-IOV 해결책과 그 한계** 
  1. 가상화는 SR-IOV(Single Root I/O Virtualization)라는 하드웨어 수준 격리 솔루션을 사용하여 IO 장치 문제를 해결한다. 
  2. SR-IOV는 각 가상 머신(VM)에 장치에 대한 추가 추상화를 제공한다. 
  3. 하지만 SR-IOV는 검증이 제한적이고 유연성이 떨어지며, 결정적으로 SR-IOV를 사용하려면 MMU(메모리 관리 장치)를 건드려야 하는 등 가상화 스택 전체를 건드려야 한다. 

3. **멀티커널의 ****IO 장치**** 공유 솔루션: ****하드웨어 큐** 
  1. 발표자의 솔루션은 **하드웨어 큐****(hardware queue)**를 사용하는 것이다. 
  2. 최신 IO 장치는 이미 많은 하드웨어 큐를 지원하며, 이를 활용하여 서로 다른 커널 인스턴스에 다른 하드웨어 큐를 할당하고 격리할 수 있다. 

4. **네트워킹 큐 공유 (AF\_****XDP**** 및 I/O Uring)** 
  1. **AF\_****XDP**는 네트워크 인터페이스 큐와 연결되어 있으며, **IO\_Uring**을 활용할 수 있다. 
  2. 이들은 링 버퍼를 사용하고 **제로 카피(zero copy) 지원**을 제공하며, 이는 멀티커널 사례에 완벽하게 적합하다. 
  3. XDP와 IOURing은 사용자 공간 API 호환성을 제공하므로 커널 간 호환성 유지에 도움이 된다. 
  4. 동적 큐 할당은 일반적인 자원 할당보다 훨씬 빠르다. 
  5. **네트워킹 큐 공유 개념**:
  1. 호스트 커널은 XDP 인프라로 링 버퍼를 설정하고 각 큐와 연결한 다음, 이 링 버퍼를 스폰 커널과 매핑한다. 
  2. 스폰 커널 내부에는 이 공유 링 버퍼에서 데이터를 검색하는 간단한 **소프트웨어 네트워킹 장치**를 구현해야 한다. 
  3. IPI는 TX/RX 인터럽트를 시뮬레이션하기 위한 **도어벨(doorbell)** 역할을 한다. 

5. **스토리지 큐 공유 (UBRK 및 LVM)** 
  1. 스토리지는 IO Uring을 기반으로 하는 UBRK를 사용하며, 이는 네트워킹 개념과 유사하다. 
  2. 그러나 스토리지는 데이터를 저장할 백엔드 스토리지가 필요하므로 더 어렵고, **데이터 자체의 격리**가 필요하다. 
  3. **논리 볼륨 관리자(LVM, Logical Volume Manager)**를 활용하여 디스크 격리를 관리할 수 있다. 
  4. 호스트 커널에 UBRK 서버를 구축하고, 각 스폰 커널 내에 UBRK 클라이언트 역할을 하는 **소프트웨어 블록 장치(software block device)**를 구현한다. 
  5. 클라이언트는 공유 링 버퍼를 사용하여 UBRK 서버와 통신한다. (이는 아직 개념 단계이며 구현된 코드는 없다.) 


## 6. 멀티커널의 네 가지 주요 사용 사례 


### 6.1. 클라우드 컴퓨팅에서의 장점 
![image]()
1. **컨테이너****와의 비교** 
  1. 컨테이너 격리: 커널이 제공하는 **자원 수준 격리(resource-level isolation)**이다. 
  2. 멀티커널 격리: **커널 수준 격리(kernel-level isolation)**로, 더 강력한 격리를 제공하며 성능이 더 잘 격리된다. 
  3. 이를 통해 컨테이너의 **노이즈 이웃 문제(noisy neighbor issue)**를 제거할 수 있다. 
  4. 컨테이너는 동일 커널을 공유하여 애플리케이션에 맞춘 경량 커널 구축이 불가능하지만, 멀티커널에서는 가능하다. 
  5. 결과적으로 OS 노이즈를 줄이고, 각 애플리케이션에 대해 더 잘 조정되고 최적화된 **고도로 맞춤화된 ****리눅스 커널**을 얻을 수 있다. 

2. **VM(****가상 머신****)과의 비교** 
  1. 멀티커널은 **하이퍼바이저****가 없으며** 가상화 오버헤드가 발생하지 않는다. 
  2. VM은 호스트 커널이 단일 실패 지점(single point of failure)이지만, 멀티커널 아키텍처는 단일 실패 지점이 없다. 
  3. 전체 기술 스택이 훨씬 단순하며, 보안 측면에서 **공격 표면(attack surface)이 상당히 줄어든다**. 
  4. 하이퍼바이저 계층이 없으므로 자원 관리가 VM보다 훨씬 탄력적이다. 
  5. 부팅 시간이 빠르다 (init 프로세스로 직접 부팅하고 다른 모든 것을 제거). 


### 6.2. 무중단 라이브 커널 업데이트 
![image]()
1. **기존 커널 업데이트 방식의 한계** 
  1. 현재 대부분은 커널 재부팅을 통해 업데이트하며, 이는 모든 애플리케이션의 중단을 초래한다. 
  2. 대규모 클러스터 관리 시 커널 업데이트 일정을 잡아야 하고, 이를 위해 이중화(redundancy)가 필요하다. 
  3. 최근 리눅스 커널 커뮤니티에서 제안된 라이브 업데이트 옵션은 kexec 빠른 재부팅을 기반으로 하며, 다운타임을 줄이지만 완전히 제거하지는 못한다. 
  4. kexec 트랜잭션 동안 모든 프로세스가 일시 중지되어야 하며, 이 트랜잭션은 '전부 아니면 전무(either all or nothing)' 방식이다. 

2. **멀티커널 방식의 라이브 업데이트** 
  1. 멀티커널은 여러 커널을 동시에 실행할 수 있다. 
  2. 새로운 업데이트 커널을 기존 커널과 함께 구동하고, 프로세스를 기존 커널에서 새 커널로 점진적으로 마이그레이션한다. 
  3. 모든 프로세스가 마이그레이션되면 기존 커널은 은퇴하고, 새 커널이 모든 자원을 인수하여 업데이트가 완료된다. 
  4. 이 과정에서 **롤백(rollback)을 지원**할 수 있어 매우 편리하다. 
  5. 목표는 **다운타임 제로 커널 업데이트**를 달성하는 것이다. 


### 6.3. 커널 크래시 복구 (Kernel Crash Healing) 
![image]()
1. **기존 커널 크래시 복구 방식의 문제점** 
  1. 커널 크래시 발생 시 kexec 기반의 KVM 덤프 커널(Kdump kernel)이 머신을 인수하여 크래시된 커널의 VM 코어를 캡처한다. 
  2. Kdump 커널은 최소화되어 있어 프로덕션 서비스를 실행하기에 불충분하므로, 정상 커널로 돌아가기 위해 **두 번 재부팅**해야 한다. 
  3. 이는 수 분의 다운타임을 의미할 수 있다. 

2. **멀티커널 방식의 크래시 복구** 
  1. 백업 커널을 시작하여 일반 커널과 병렬로 실행한다. 
  2. 백업 커널은 하트 비트(hard beating) 메커니즘을 통해 일반 커널의 정상 작동 여부를 주기적으로 감지한다. 
  3. 타임아웃이 감지되면 백업 커널은 즉시 모든 하드웨어 자원을 인수한다. 
  4. 원하는 경우 보존된 메모리에서 프로세스 데이터를 복원할 수도 있다. 
  5. 이 방식으로 서비스를 **수 초 내에 재개**할 수 있다. 


### 6.4. 커널 라이브 디버깅 
![image]()
1. **기존 ****커널 디버깅**** 방식** 
  1. 크래시 후 디버깅(post-crash debugging)에는 주로 Kdump가 사용된다. 
  2. 라이브 커널 디버깅(live kernel debugging)은 실행 중인 커널에 대해 KCore에 의존하며, 외부 디버거 없이는 커널을 일시 중지하는 것이 불가능하다. 

2. **멀티커널 방식의 라이브 디버깅** 
  1. 멀티커널은 복잡한 외부 디버거 없이 **호스트 커널****과 ****스폰 커널****만**으로 디버깅이 가능하다. 
  2. 호스트 커널을 사용하여 스폰 커널을 검사할 수 있다. 
  3. 호스트 커널은 실행 중인 스폰 커널의 KCore(마이크로커널 파일 시스템)을 직접 얻을 수 있다. 
  4. 호스트 커널은 스폰 커널의 실행을 언제든지 일시 중지(pause)하고 재개(resume)할 수 있다. 


## 7. 보안 모델의 단점 및 하드웨어 개선 요청 
![image]()
1. **보안 모델의 주요 단점 및 트레이드오프** 
  1. 멀티커널의 주요 단점은 **보안 모델**이다. 
  2. 각 커널은 최소한 자체 자원 경계를 존중하도록 **신뢰(trusted)**되어야 한다. 
  3. 현재 모델은 퍼블릭 클라우드 서비스 제공과 같은 사례에는 여전히 적합하지 않다. 
  4. 멀티커널은 격리(isolation)보다는 **성능(performance)**에 중점을 둔 트레이드오프를 가진다. 

2. **CPU 벤더에게 요구되는 하드웨어 지원 개선** 
  1. **메모리 보호**: 메모리 포인터에 경계를 적용하거나 메모리 태그 지정을 통해 메모리 격리를 강화할 수 있도록 하드웨어 지원이 필요하다. 
  2. **IPI 필터링**: 현재는 어떤 CPU든 동일 노드의 다른 CPU에 IPI를 보낼 수 있는데, 오버헤드가 없는 하드웨어 필터링된 IPI 지원이 필요하다. 
  3. **기밀 컴퓨팅 (Confidential Computing)**: VM과의 경쟁력 확보를 위해 기밀 컴퓨팅 지원이 필요하지만, 멀티커널 아키텍처에 대한 하드웨어 지원은 아직 미비하다. 

3. **IO 장치**** 벤더에게 요구되는 개선** 
  1. 스토리지 및 네트워킹 장치 벤더는 하드웨어 큐를 개선해야 한다. 
  2. NVMe 장치는 이미 네임스페이스(namespaces)를 지원하여 스토리지 격리에 유용하지만, 그 위에 **큐 격리(Q isolation)**도 필요하다. 
  3. **컨트롤러 파티셔닝**과 같은 개념이 제안된다. 


## 8. 구현 코드 공개 및 관련 프로젝트 소개 
![image]()
1. **구현 코드 공개** 
  1. 발표된 내용은 깃허브에 공유된 리눅스 커널 코드를 기반으로 하며, 이 코드는 리눅스 커널 메일링 리스트에도 게시되었다. 

2. **사용자 공간 및 관련 프로젝트** 
  1. curve: 사용자 공간에서 운영 및 관리를 위한 툴이다. 
  2. Kor: 커널 크래시 자동 복구 및 커널 라이브 업데이트를 위한 프로젝트로, 재부팅 없이 커널 변환을 목표로 한다. 
  3. KernelScript: eBPF 개발을 단순화하고 eBPF를 통한 커널 맞춤 제작을 크게 간소화하기 위한 프로그래밍 언어이다. 

3. **향후 협업 제안** 
  1. 발표자는 이 토크가 청중에게 영감을 주기를 바라며, 더 많은 질문을 가지고 있으므로 답변을 구하거나 협업을 제안한다. 
  2. 관심 있는 연구자들의 협업 참여를 환영한다. 
  3. 문의 사항, 피드백, 협력 제안은 이메일, Discord 및 메일링 리스트를 통해 가능하다. 
  4. 유튜브 채널에는 발표자가 시간 관계상 보여주지 못한 비디오 데모들이 있다. 


## 9. 질의응답 및 토론 (순서별 정리) 
![image]()
1. **LKL에서의 논쟁 및 Paravirtualization 비판 (원격 참석자)** 
  1. 발표 내용이 **Paravirtualization(준****가상화****)을 잘못된 수준에서 재발명**하는 것과 같다는 비판이 제기되었다. 
  2. 발표자가 제시한 관리 커널은 Xen의 DOM 0와 직접적으로 동일하며, 기저의 하이퍼바이저가 없기 때문에 **커널 대 ****커널 격리**가 부족하다는 점이 지적되었다. 
  3. Paravirtualization은 막대한 유지보수 부담을 리눅스 개발 커뮤니티에 전가하기 때문에 20년 동안 지양되어 온 방식이라는 점이 언급되었다. 
  4. (발표 진행자가 시간 관계상 오프라인 토론을 제안하며 마무리되었다.) 

2. **멀티커널의 크래시 격리 및 방식 (원격 참석자)** 
  1. **질문**: 멀티커널이 한 인스턴스의 크래시를 다른 인스턴스로부터 격리하는가? 
  2. **답변**: 그렇다. 커널 크래시 격리 데모가 유튜브에 있으며, 이는 **리부트 벡터(reboot vectors)를 격리**함으로써 커널 크래시가 다른 커널에 영향을 미치지 않도록 한다. 

3. **CPU 스케줄링 및 과잉 할당 (Overcommitment) (원격 참석자)** 
  1. **질문**: 물리적 CPU가 멀티커널의 가상 CPU에 어떻게 스케줄링되는가? 
  2. **답변**: CPU는 스케줄링되지 않으며, **완전히 격리**되어 있다. 
  3. 따라서 아직 CPU 과잉 할당(overcommitment)을 구현하지 않았다. 
  4. 커널 스위칭을 구현할 수 있다면 CPU 스케줄링도 가능할 것으로 보인다. 

4. **kexec**** Handover를 통한 정보 전달 (Jason, ****kexec**** 개발자)** 
  1. **배경**: kexec 핸드오버의 목적은 두 번째 커널이 부팅 시 특정 메모리 조각을 건드리지 않도록 메모리 조각을 전달하는 것인데, 멀티커널은 메모리가 이미 라이브 상태이다. 
  2. **질문**: 호스트 커널에서 스폰 커널로 kexec 핸드오버를 통해 어떤 종류의 정보를 전달하는가? 
  3. **답변**: 전달하는 정보는 주로 **Device Tree**이다. 리소스를 기술하는 데 Device Tree를 사용하기 때문에 스폰 커널 시작 시 모든 자원 정보를 전달해야 한다. 

5. **기존 Device Tree 활용 가능성 (Petush 및 청중)** 
  1. **질문**: 커널은 이미 베이스 Device Tree를 갖고 있는데, 그 정보를 활용할 수는 없는가? (ARM 64에서는 KO Device Tree가 그 안에 있다.) 
  2. **답변**: 발표자는 아직 x86 아키텍처만 구현했으며 ARM 부분은 구현하지 않았다. 

6. **클라우드 사용 사례 및 Live Update의 어려움 (청중)** 
  1. **클라우드 사용 사례에 대한 비판**: 하드웨어 가상화 없이는 격리 문제가 심각하여 클라우드 사용 사례는 불가능해 보이며, 최적화된 VM은 오버헤드가 1% 이하로 매우 낮으므로 클라우드 사용 사례는 불필요하다. 
  2. **디버깅 사용 사례**: 디버깅은 좋은 예이지만, 이를 위해 전체 시스템을 구현할 가치가 있는지 의문이다. (Solaris의 MDB와 유사한 개념) 
  3. **Live Update의 어려움**: 라이브 업데이트 시 두 커널이 병렬로 실행되는 동안 **APIC(Advanced Programmable Interrupt Controller)와 같은 전역 머신 상태**를 안전하게 공유하기가 매우 어렵다. 

7. **Live Update 간소화 방안 (청중)**
