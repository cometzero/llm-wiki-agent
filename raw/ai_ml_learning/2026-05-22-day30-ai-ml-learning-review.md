## 1. 평가와 벤치마크

### 한 줄 직관

모델 평가는 “이 모델이 진짜 쓸 만한가?”를 확인하는 시험이고, benchmark는 여러 모델을 같은 시험지로 비교하는 공통 기준입니다.

### 개념 정의

평가(evaluation 또는 eval)는 모델이 어떤 일을 얼마나 잘하는지 측정하는 과정입니다. 예를 들어 분류 모델이 고양이 사진과 강아지 사진을 구분한다면, 새 사진 100장을 보여 주고 몇 장을 맞혔는지 확인합니다.

벤치마크(benchmark)는 모델들을 같은 조건에서 비교하기 위해 미리 정해 둔 데이터셋과 문제 모음입니다. 사람마다 다른 문제를 내면 공정하게 비교하기 어렵습니다. 그래서 “모든 모델에게 같은 1,000문제를 풀게 하자”라는 식으로 기준을 만듭니다.

LLM에서는 eval이라는 말을 매우 자주 씁니다. 예를 들어 “이 챗봇이 수학 문제를 잘 푸는가?”, “코드를 잘 작성하는가?”, “사용자 지시를 잘 따르는가?”, “거짓말을 덜 하는가?”를 각각 다른 eval로 측정합니다.

### 왜 이런 개념이 필요한가

AI 모델은 학습할 때 loss를 줄이는 방향으로 훈련됩니다. loss는 모델의 예측이 정답과 얼마나 다른지를 나타내는 숫자입니다. 그런데 loss가 낮다고 해서 실제 사용자가 만족한다는 뜻은 아닙니다.

예를 들어 번역 모델이 학습 데이터에서는 loss가 낮아도, 실제 사용자가 입력한 긴 문장을 어색하게 번역할 수 있습니다. LLM도 마찬가지입니다. 다음 단어를 잘 예측하도록 학습된 모델이 항상 정확하고 안전한 답을 주는 것은 아닙니다.

그래서 모델을 만들 때는 “학습 중 숫자”와 “실제 사용 성능”을 따로 봐야 합니다. benchmark와 eval은 이 둘 사이의 차이를 확인하는 도구입니다.

실무에서는 모델을 바꿀 때마다 eval을 돌립니다. 새 모델이 이전 모델보다 더 좋은지, 특정 기능이 좋아졌지만 다른 기능이 나빠지지는 않았는지 확인해야 하기 때문입니다. 이것을 하지 않으면 모델 업데이트가 실제 서비스 품질을 떨어뜨릴 수 있습니다.

### 아주 쉬운 예시

작은 스팸 메일 분류 모델을 생각해 봅시다. 테스트 메일 10개가 있고, 실제 정답은 다음과 같다고 합시다.

- 스팸 5개
- 정상 메일 5개

모델이 10개 중 8개를 맞혔다면 정확도(accuracy)는 8/10 = 80%입니다.

하지만 여기서 끝내면 위험할 수 있습니다. 만약 모델이 정상 메일 5개 중 3개를 스팸으로 잘못 판단했다면 사용자는 중요한 메일을 놓칠 수 있습니다. 이 경우 단순 accuracy만 보면 80%라 괜찮아 보이지만, 실제 서비스에서는 큰 문제가 될 수 있습니다.

LLM 예시도 비슷합니다. 수학 문제 10개 중 8개를 맞히는 모델 A와, 10개 중 7개를 맞히지만 틀렸을 때 “잘 모르겠습니다”라고 솔직하게 말하는 모델 B가 있다고 합시다. 어떤 서비스에서는 A가 좋을 수 있지만, 의료나 법률 상담처럼 위험한 영역에서는 B가 더 안전할 수 있습니다.

### 개념 구조와 핵심 포인트

평가는 보통 다음 흐름으로 진행됩니다.

1. 평가할 task를 정합니다. 예를 들어 번역, 요약, 수학 풀이, 코드 생성, 질의응답 중 무엇을 볼지 정합니다.
2. 평가 데이터를 준비합니다. 모델이 학습 때 보지 않은 데이터여야 공정합니다.
3. metric을 정합니다. 즉, 무엇을 기준으로 잘했다고 판단할지 정합니다.
4. 모델 출력을 얻습니다. 같은 입력을 여러 모델에 넣어 봅니다.
5. 결과를 숫자 또는 사람 평가로 비교합니다.

여기서 task metric이 중요합니다. task metric은 특정 작업에 맞춘 성능 측정 기준입니다. 예를 들어 이미지 분류에서는 accuracy가 자연스럽지만, 검색 시스템에서는 “상위 5개 결과 안에 정답이 있는가” 같은 metric이 더 중요할 수 있습니다.

LLM에서는 자동 metric만으로 충분하지 않은 경우가 많습니다. 답변이 자연스러운지, 친절한지, 사용자의 의도를 잘 이해했는지 같은 것은 숫자로 완벽히 재기 어렵습니다. 그래서 human evaluation도 사용합니다. 사람이 직접 모델 답변을 비교하고 더 좋은 답을 고르는 방식입니다.

또한 benchmark는 절대적인 진실이 아닙니다. benchmark 점수가 높아도 실제 서비스에서 나쁠 수 있습니다. 이유는 benchmark 문제가 실제 사용자 질문과 다를 수 있고, 모델이 유명 benchmark 문제를 이미 학습했을 수도 있기 때문입니다.

### 핵심 수학 포인트

평가 metric은 대부분 “여러 사례의 결과를 하나의 숫자로 요약”하는 방식입니다.

가장 쉬운 예는 accuracy입니다.

- 전체 문제 수: 10개
- 맞힌 문제 수: 8개
- accuracy = 8 / 10 = 0.8 = 80%

분류에서는 정답/오답이 비교적 명확합니다. 하지만 LLM 답변은 정답이 하나가 아닐 수 있습니다. “좋은 요약”은 여러 형태가 가능하기 때문입니다.

그래서 LLM 평가에서는 다음처럼 여러 관점의 점수를 함께 봅니다.

- 정확성: 사실이 맞는가?
- 완전성: 필요한 내용을 빠뜨리지 않았는가?
- 지시 준수: 사용자가 요구한 형식과 조건을 지켰는가?
- 안전성: 위험하거나 부적절한 답을 하지 않았는가?
- 유용성: 실제 사용자가 도움을 받을 수 있는가?

수학적으로는 하나의 scalar score로 요약할 때가 많지만, 실제로는 여러 metric이 trade-off 관계에 있습니다. 예를 들어 답변을 짧게 만들면 latency는 줄어들 수 있지만, 완전성 점수는 낮아질 수 있습니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- benchmark: 여러 모델을 같은 기준으로 비교하기 위한 문제 세트와 평가 방식입니다.
- eval: 모델 성능을 측정하는 평가 절차입니다. LLM 개발에서는 “eval을 돌린다”는 표현이 흔합니다.
- human evaluation: 사람이 직접 모델 출력을 보고 품질을 판단하는 평가입니다.
- task metric: 특정 task에 맞는 측정 기준입니다. 예를 들어 accuracy, precision, recall, pass@k 등이 있습니다.
- test set: 학습에 쓰지 않고 평가에만 사용하는 데이터입니다.
- regression test: 새 버전에서 예전에는 잘하던 것이 망가지지 않았는지 확인하는 테스트입니다.

### AI에서 어디에 쓰이는가

모델 개발에서는 학습이 끝난 뒤 반드시 eval을 봅니다. loss가 낮아졌다고 바로 배포하지 않습니다. 실제 task metric이 좋아졌는지 확인합니다.

LLM 서비스에서는 프롬프트를 조금 바꾸는 것만으로도 답변 품질이 달라집니다. 그래서 시스템 프롬프트, RAG 검색 방식, temperature, 모델 버전을 바꿀 때마다 eval이 필요합니다.

RAG 시스템에서는 검색 품질과 생성 품질을 따로 평가해야 합니다. 검색 단계에서 관련 문서를 못 찾으면, LLM이 아무리 좋아도 답변이 틀릴 수 있습니다. 반대로 좋은 문서를 찾았는데도 모델이 문서를 제대로 사용하지 못하면 생성 단계의 문제입니다.

강화학습 기반 정렬(RLHF 또는 preference tuning)에서도 human evaluation과 preference data가 중요합니다. 사용자가 더 선호하는 답변을 모델이 내도록 훈련하려면, 먼저 어떤 답변이 더 좋은지 비교 데이터가 있어야 합니다.

### 헷갈리기 쉬운 포인트

첫째, benchmark 점수는 모델의 전체 능력이 아닙니다. 특정 시험을 잘 본 것일 뿐입니다. 수학 benchmark 점수가 높다고 대화가 친절하다는 뜻은 아닙니다.

둘째, eval은 한 번 만들고 끝나는 것이 아닙니다. 서비스가 바뀌면 eval도 바뀌어야 합니다. 고객 질문이 달라지면 평가 데이터도 업데이트해야 합니다.

셋째, 자동 평가와 사람 평가는 서로 대체 관계가 아니라 보완 관계입니다. 자동 metric은 빠르고 싸지만, 미묘한 품질을 놓칠 수 있습니다. human evaluation은 품질을 잘 볼 수 있지만, 느리고 비용이 듭니다.

넷째, 학습 loss와 실제 품질은 연결되어 있지만 같지는 않습니다. loss는 중요한 신호지만, 최종 판단은 task에 맞는 eval로 해야 합니다.

## 2. 서빙과 추론 최적화

### 한 줄 직관

서빙(serving)은 학습된 모델을 실제 사용자 요청에 답하게 만드는 일이고, 추론 최적화는 더 빠르고 싸게 답하게 만드는 기술입니다.

### 개념 정의

모델 학습(training)은 모델이 데이터를 보며 파라미터를 조정하는 과정입니다. 반면 추론(inference)은 이미 학습된 모델을 사용해서 새 입력에 대한 출력을 만드는 과정입니다.

서빙(serving)은 이 추론을 실제 서비스 형태로 제공하는 일입니다. 사용자가 앱에서 질문을 입력하면 서버가 모델을 호출하고, 모델이 답변을 만들고, 다시 사용자에게 보내는 전체 과정이 serving에 포함됩니다.

추론 최적화(inference optimization)는 같은 모델을 더 빠르게, 더 많은 사용자에게, 더 낮은 비용으로 제공하기 위한 방법입니다. 대표적으로 latency 줄이기, throughput 높이기, quantization, KV cache 사용 등이 있습니다.

### 왜 이런 개념이 필요한가

모델이 똑똑해도 너무 느리면 서비스로 쓰기 어렵습니다. 사용자가 챗봇에게 질문했는데 첫 답변이 30초 뒤에 나오면 대부분 불편하다고 느낍니다.

또 비용도 중요합니다. LLM은 큰 행렬 연산을 많이 합니다. 사용자 1명이 질문할 때마다 GPU가 많은 계산을 해야 합니다. 하루에 100명이 쓰는 서비스와 100만 명이 쓰는 서비스는 완전히 다른 serving 전략이 필요합니다.

특히 LLM은 한 번에 답 전체를 만드는 것이 아니라 token을 하나씩 생성합니다. “오늘 날씨는 맑습니다”라는 문장을 만들 때도 내부적으로는 “오늘” 다음 token, “날씨” 다음 token, “는” 다음 token처럼 순서대로 예측합니다. 이 과정은 길이가 길수록 더 오래 걸립니다.

그래서 현대 AI 시스템에서는 모델 정확도만큼이나 serving 능력이 중요합니다. 실제 회사에서는 “성능 2% 좋은 모델”보다 “성능은 비슷하지만 비용이 절반이고 응답이 빠른 모델”이 더 좋은 선택일 수 있습니다.

### 아주 쉬운 예시

카페를 생각해 봅시다. 바리스타 한 명이 커피 한 잔을 만드는 데 2분이 걸린다고 합시다.

- 손님 1명: 2분 기다리면 됩니다.
- 손님 10명: 한 명씩 만들면 마지막 손님은 20분 가까이 기다릴 수 있습니다.

여기서 latency는 한 손님이 주문하고 커피를 받기까지 걸리는 시간입니다. throughput은 일정 시간 동안 몇 잔을 만들 수 있는지입니다.

AI 서비스도 같습니다. 어떤 LLM이 한 요청에 5초 걸린다고 합시다.

- 사용자 1명이면 괜찮아 보입니다.
- 동시에 1,000명이 접속하면 GPU가 감당하지 못할 수 있습니다.

이때 batching을 사용하면 여러 사용자의 요청을 묶어서 한 번에 계산할 수 있습니다. 커피로 비유하면, 같은 종류의 음료를 여러 잔 동시에 준비해서 전체 처리량을 높이는 것과 비슷합니다.

또 quantization은 큰 숫자를 조금 더 작은 표현으로 바꾸는 기술입니다. 예를 들어 모델 파라미터를 32-bit 숫자 대신 8-bit 숫자로 저장하면 메모리를 덜 씁니다. 대략적으로 32-bit는 숫자 하나에 4바이트, 8-bit는 1바이트를 쓰므로 저장 공간이 약 1/4로 줄 수 있습니다. 단, 너무 과하게 줄이면 정확도가 떨어질 수 있습니다.

### 개념 구조와 핵심 포인트

서빙 시스템에서는 보통 다음 요소를 함께 봅니다.

1. 모델 자체: 어떤 모델을 쓸지 정합니다. 큰 모델은 똑똑할 수 있지만 느리고 비쌀 수 있습니다.
2. 하드웨어: CPU, GPU, NPU 같은 계산 장치를 선택합니다.
3. 요청 처리 방식: 한 번에 하나씩 처리할지, 여러 요청을 batching할지 정합니다.
4. 메모리 관리: 모델 파라미터, hidden states, KV cache를 어떻게 저장할지 관리합니다.
5. 응답 스트리밍: LLM 답변을 token 단위로 바로바로 보내 사용자 체감 latency를 줄입니다.

LLM에서 KV cache는 매우 중요합니다. Transformer의 attention은 현재 token이 이전 token들을 참고하는 구조입니다. 매 token을 만들 때 이전 문맥의 key와 value를 다시 계산하면 낭비가 큽니다. 그래서 이전 token들의 key/value를 저장해 두고 재사용합니다. 이것이 KV cache입니다.

예를 들어 100개 token짜리 문맥이 있고 101번째 token을 생성한다고 합시다. 이전 100개 token에 대한 key/value를 이미 계산해 두었다면, 101번째 token은 저장된 정보를 참고하면 됩니다. 매번 처음부터 100개를 다시 계산하는 것보다 훨씬 효율적입니다.

하지만 KV cache도 메모리를 사용합니다. 사용자가 많고 문맥 길이가 길면 KV cache가 GPU 메모리를 크게 차지합니다. 그래서 긴 context를 제공하는 LLM 서비스는 메모리 관리가 매우 중요합니다.

### 핵심 수학 포인트

추론 속도는 결국 tensor 연산량과 메모리 이동량에 영향을 받습니다.

가장 단순하게 생각하면 linear layer는 입력 벡터와 weight matrix를 곱합니다. 입력 크기가 3이고 출력 크기가 2인 layer를 생각해 봅시다.

- 입력 x shape: (3,)
- weight W shape: (3, 2)
- 출력 y shape: (2,)

이 연산은 작은 예시에서는 금방 끝나지만, LLM에서는 hidden size가 수천이고 layer가 수십 개입니다. token 하나를 생성할 때마다 이런 큰 행렬 연산이 반복됩니다.

latency는 한 요청이 완료되기까지 걸리는 시간입니다. 예를 들어 질문 후 첫 token이 0.8초 뒤에 나오고, 전체 답변이 5초 뒤에 끝나면 사용자는 0.8초부터 답을 보기 시작합니다.

throughput은 단위 시간당 처리량입니다. 예를 들어 1초에 token 100개를 생성할 수 있다면 throughput은 100 tokens/sec입니다. serving에서는 사용자별 latency와 전체 throughput 사이의 균형이 중요합니다.

quantization은 숫자 표현의 정밀도를 낮추는 방식입니다. 예를 들어 0.123456 같은 값을 아주 정확히 저장하는 대신 0.12처럼 조금 거칠게 저장합니다. 많은 경우 모델은 작은 오차를 견딜 수 있습니다. 왜냐하면 neural network는 수많은 weight가 함께 작동하므로, 일부 숫자가 약간 둔해져도 전체 패턴은 유지될 수 있기 때문입니다. 하지만 작은 차이가 중요한 모델이나 task에서는 성능이 떨어질 수 있습니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- serving: 학습된 모델을 실제 요청에 응답하도록 운영하는 과정입니다.
- inference: 학습된 모델로 새 입력에 대한 출력을 계산하는 과정입니다.
- latency: 한 요청이 들어와 응답이 나오기까지 걸리는 시간입니다.
- throughput: 일정 시간 동안 처리할 수 있는 요청 수 또는 token 수입니다.
- quantization: weight나 activation을 더 낮은 bit 숫자로 표현해 메모리와 계산 비용을 줄이는 기술입니다.
- KV cache: Transformer에서 이전 token들의 key/value를 저장해 다음 token 생성에 재사용하는 캐시입니다.
- batching: 여러 요청을 묶어 한 번에 처리하는 방식입니다.
- streaming: 답변이 완성될 때까지 기다리지 않고 생성되는 token을 순서대로 보내는 방식입니다.

### AI에서 어디에 쓰이는가

LLM API, 챗봇, 번역기, 이미지 생성 서비스, 음성 인식 서비스 모두 serving이 필요합니다. 연구실에서 모델을 한 번 실행하는 것과, 실제 사용자 수천 명에게 안정적으로 제공하는 것은 다릅니다.

챗봇에서는 첫 token latency가 중요합니다. 사용자는 전체 답변이 끝나지 않아도 글자가 바로 나오기 시작하면 빠르다고 느낍니다. 그래서 streaming 응답이 많이 사용됩니다.

RAG 시스템에서는 검색 단계와 LLM 생성 단계가 모두 latency에 영향을 줍니다. 문서를 찾는 데 1초, LLM 답변 생성에 5초가 걸리면 전체 응답은 최소 6초 이상입니다. 따라서 검색 인덱스 최적화와 LLM serving 최적화를 함께 해야 합니다.

온디바이스 AI에서는 quantization이 특히 중요합니다. 스마트폰이나 노트북에서 모델을 돌리려면 메모리와 전력 사용을 줄여야 합니다. 32-bit 모델을 그대로 올릴 수 없을 때 8-bit 또는 4-bit quantization을 사용합니다.

### 헷갈리기 쉬운 포인트

첫째, latency와 throughput은 같은 말이 아닙니다. latency는 한 사람의 대기 시간이고, throughput은 전체 처리량입니다. 고속도로로 비유하면 latency는 내 차가 목적지까지 가는 시간이고, throughput은 1시간 동안 도로가 처리할 수 있는 차량 수입니다.

둘째, quantization은 무조건 좋은 것이 아닙니다. 메모리와 속도는 좋아질 수 있지만, 너무 낮은 bit로 줄이면 답변 품질이 떨어질 수 있습니다.

셋째, 큰 모델이 항상 좋은 serving 선택은 아닙니다. 모델 성능, 비용, 응답 속도, 사용자 수, 하드웨어 제약을 함께 봐야 합니다.

넷째, KV cache는 계산을 줄여 주지만 메모리를 공짜로 쓰는 것은 아닙니다. 문맥이 길수록, 동시 사용자가 많을수록 KV cache 메모리 부담이 커집니다.

## 3. AI 시스템 설계 전체 그림

### 한 줄 직관

AI 시스템은 “데이터를 모으고, 모델을 학습하고, 서비스로 제공하고, 사용자 반응으로 다시 개선하는” 하나의 순환 구조입니다.

### 개념 정의

AI 시스템 설계는 모델 하나만 고르는 일이 아닙니다. 데이터를 어떻게 모을지, 어떻게 정제할지, 어떤 모델을 학습할지, 어떻게 평가할지, 어떻게 배포할지, 사용 중 생기는 피드백을 어떻게 다시 반영할지를 모두 설계하는 일입니다.

전체 구조를 크게 나누면 data pipeline, training stack, inference stack, feedback loop로 볼 수 있습니다.

- data pipeline은 원본 데이터를 모델이 사용할 수 있는 형태로 만드는 흐름입니다.
- training stack은 모델을 학습시키는 코드, 하드웨어, optimizer, 분산 학습 환경을 포함합니다.
- inference stack은 학습된 모델을 실제 서비스에서 빠르고 안정적으로 실행하는 구성입니다.
- feedback loop는 사용자 반응과 오류 사례를 다시 수집해 다음 개선에 사용하는 순환입니다.

### 왜 이런 개념이 필요한가

초보자는 AI를 처음 배울 때 모델 자체에 집중하기 쉽습니다. “Transformer가 무엇인가?”, “LLM이 얼마나 큰가?”, “accuracy가 몇 퍼센트인가?” 같은 질문이 먼저 보입니다.

하지만 실제 AI 서비스는 모델 하나로 완성되지 않습니다. 데이터가 나쁘면 좋은 모델도 나쁜 결과를 냅니다. 평가가 부실하면 좋아진 것처럼 보이지만 실제로는 망가진 모델을 배포할 수 있습니다. serving이 약하면 모델이 좋아도 사용자는 느리다고 느낍니다. 피드백을 모으지 않으면 시간이 지나면서 사용자 요구와 모델 동작이 어긋납니다.

예를 들어 고객센터 챗봇을 만든다고 합시다. 단순히 LLM API만 연결하면 처음에는 답을 하는 것처럼 보입니다. 하지만 실제 운영에는 다음 문제가 생깁니다.

- 최신 환불 정책 문서를 모델이 모릅니다.
- 사용자 질문이 모호할 때 확인 질문을 해야 하는데 바로 답해 버립니다.
- 잘못된 답변을 했을 때 기록하고 고치는 시스템이 없습니다.
- 사용자가 몰리는 시간에 응답이 느려집니다.

이런 문제는 모델 크기만 키운다고 해결되지 않습니다. 시스템 전체 설계가 필요합니다.

### 아주 쉬운 예시

학교 급식 추천 AI를 만든다고 해 봅시다. 목표는 학생에게 “오늘 점심으로 무엇을 먹으면 좋을지” 추천하는 것입니다.

아주 작은 데이터 예시는 다음과 같습니다.

| 학생 | 좋아하는 음식 | 알레르기 | 오늘 추천 |
|---|---|---|---|
| A | 김밥 | 없음 | 김밥 |
| B | 우유 | 유제품 알레르기 | 우유 제외 메뉴 |
| C | 매운 음식 | 없음 | 떡볶이 |

여기서 data pipeline은 학생 선호도와 알레르기 정보를 모으고 정리하는 과정입니다. 만약 B 학생의 알레르기 정보가 빠지면 모델은 우유를 추천할 수 있습니다.

training stack은 이 데이터를 보고 추천 모델을 학습하는 과정입니다. “비슷한 선호를 가진 학생은 비슷한 메뉴를 좋아한다” 같은 패턴을 배울 수 있습니다.

inference stack은 실제 점심시간에 학생이 앱을 열면 빠르게 추천을 보여 주는 부분입니다.

feedback loop는 학생이 추천을 눌렀는지, 싫어요를 눌렀는지, 실제로 먹었는지를 다시 모아 다음 추천을 개선하는 과정입니다.

숫자로 보면 더 쉽습니다. 첫 주에는 추천 100번 중 60번만 만족했다고 합시다. 피드백을 반영한 뒤 둘째 주에는 100번 중 72번 만족했다면 시스템이 개선된 것입니다. 이때 중요한 것은 모델만 바뀐 것이 아니라 데이터와 평가와 피드백 흐름이 함께 좋아졌다는 점입니다.

### 개념 구조와 핵심 포인트

AI 시스템의 전체 흐름은 보통 다음 순서로 생각할 수 있습니다.

1. 문제 정의: 어떤 사용자 문제를 풀 것인지 정합니다.
2. 데이터 수집: 필요한 데이터를 모읍니다.
3. 데이터 정제: 중복, 오류, 개인정보, 이상치를 처리합니다.
4. 학습 또는 프롬프트/RAG 설계: 모델을 직접 학습하거나 기존 모델을 잘 활용합니다.
5. 평가: benchmark, eval, human evaluation으로 품질을 확인합니다.
6. 배포와 serving: 모델을 실제 요청에 연결합니다.
7. 모니터링: latency, 오류율, 비용, 사용자 만족도를 봅니다.
8. feedback loop: 실패 사례와 사용자 반응을 다음 개선에 반영합니다.

현대 LLM 시스템에서는 꼭 모델을 처음부터 학습하지 않을 수 있습니다. 이미 학습된 foundation model을 사용하고, 그 위에 RAG, tool use, prompt engineering, fine-tuning을 붙입니다.

예를 들어 회사 내부 문서 Q&A 시스템은 보통 다음처럼 설계합니다.

- 문서 수집: Google Drive, Notion, PDF에서 문서를 가져옵니다.
- embedding 생성: 문서를 작은 chunk로 나누고 embedding으로 바꿉니다.
- vector database 저장: 비슷한 의미의 문서를 검색할 수 있게 합니다.
- 질문 처리: 사용자 질문도 embedding으로 바꿔 관련 문서를 찾습니다.
- LLM 생성: 찾은 문서를 context로 넣고 답변을 생성합니다.
- eval/monitoring: 답변이 문서에 근거하는지 확인합니다.

여기서 embedding, attention, hidden states 같은 모델 내부 개념은 시스템 안에서 실제 역할을 가집니다. embedding은 검색을 가능하게 하고, attention은 LLM이 context 안의 중요한 token을 참고하게 하며, hidden states는 모델이 입력을 내부적으로 표현하는 중간 상태입니다.

### 핵심 수학 포인트

AI 시스템 전체를 수학적으로 보면, 여러 함수가 이어진 pipeline으로 볼 수 있습니다.

아주 단순하게 쓰면 다음과 같습니다.

입력 데이터 x → 전처리 f(x) → 모델 g(f(x)) → 후처리 h(g(f(x))) → 사용자 출력

예를 들어 사용자가 “환불은 며칠 안에 되나요?”라고 물었다고 합시다.

1. x: 사용자 질문 텍스트
2. f(x): 질문을 embedding으로 변환하고 관련 문서를 검색
3. g(f(x)): LLM이 문서를 참고해 답변 생성
4. h(g(f(x))): 금지 표현 제거, 출처 추가, 형식 정리

각 단계가 전체 성능에 영향을 줍니다. 모델 g가 좋아도 f에서 엉뚱한 문서를 찾으면 답이 틀릴 수 있습니다. h가 잘못 설계되면 좋은 답을 이상한 형식으로 바꿀 수 있습니다.

학습 관점에서는 loss, gradient, optimizer가 training stack의 중심입니다. 모델은 loss를 줄이기 위해 gradient를 계산하고, optimizer가 weight를 조금씩 업데이트합니다. 하지만 시스템 관점에서는 loss만 보지 않고 serving latency, 사용자 만족도, 비용도 함께 봅니다.

즉, 수학적으로 좋은 모델과 제품으로 좋은 시스템은 같은 말이 아닙니다. 모델 성능은 전체 시스템 성능의 중요한 부분이지만, 유일한 부분은 아닙니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- data pipeline: 원본 데이터를 수집, 정제, 변환해서 모델이 사용할 수 있게 만드는 흐름입니다.
- training stack: 학습 코드, 데이터 로더, GPU, optimizer, 분산 학습 도구 등 학습을 구성하는 전체 기술 묶음입니다.
- inference stack: 배포된 모델이 사용자 요청을 받아 응답을 만드는 serving 구성입니다.
- feedback loop: 사용자 반응, 오류 사례, 운영 데이터를 다시 개선 과정에 반영하는 순환입니다.
- monitoring: 서비스가 잘 동작하는지 latency, 에러, 비용, 품질을 계속 관찰하는 일입니다.
- drift: 시간이 지나 데이터나 사용자 행동이 바뀌어 모델 성능이 떨어지는 현상입니다.
- RAG: Retrieval-Augmented Generation입니다. 관련 문서를 검색한 뒤 LLM에게 함께 넣어 답변하게 하는 방식입니다.

### AI에서 어디에 쓰이는가

실제 AI 제품은 대부분 이 전체 그림 안에서 움직입니다. 추천 시스템, 검색 엔진, 챗봇, 사기 탐지, 의료 이미지 분석, 자율주행 인식 시스템 모두 데이터부터 피드백까지 이어지는 구조가 필요합니다.

LLM 앱에서는 inference stack과 feedback loop가 특히 중요합니다. 사용자가 어떤 질문에서 만족하지 못했는지 기록하고, 그 사례를 eval set에 추가하면 다음 버전에서 같은 실수를 줄일 수 있습니다.

기업용 AI에서는 data pipeline이 큰 비중을 차지합니다. 내부 문서가 흩어져 있고, 최신 문서와 오래된 문서가 섞여 있으며, 권한 관리도 필요합니다. 모델보다 데이터 연결과 보안 설계가 더 어려운 경우도 많습니다.

연구와 실무를 연결할 때도 이 그림이 중요합니다. 논문은 보통 모델 구조나 학습 방법 하나에 집중하지만, 제품은 데이터, 평가, 배포, 모니터링까지 모두 책임져야 합니다.

### 헷갈리기 쉬운 포인트

첫째, AI 시스템 설계는 “모델 고르기”보다 훨씬 넓습니다. 모델은 중심 부품이지만, 전체 제품은 아닙니다.

둘째, data pipeline은 단순한 전처리가 아닙니다. 데이터 품질, 권한, 최신성, 중복 제거, 라벨 품질까지 포함합니다.

셋째, feedback loop는 아무 데이터를 무조건 다시 학습에 넣는다는 뜻이 아닙니다. 잘못된 피드백이나 악의적 입력을 그대로 반영하면 모델이 나빠질 수 있습니다. 피드백도 검수와 평가가 필요합니다.

넷째, training stack과 inference stack은 목적이 다릅니다. training stack은 모델을 잘 배우게 만드는 데 집중하고, inference stack은 학습된 모델을 빠르고 안정적으로 제공하는 데 집중합니다.

### 1. benchmark 점수가 높아도 실제 서비스 품질이 낮을 수 있는 이유는 무엇인가요?

**정답**

benchmark 점수는 모델이 “정해진 시험 문제”를 얼마나 잘 푸는지 보여 주는 숫자입니다. 하지만 실제 서비스에서는 사용자 질문, 데이터 상태, 응답 속도, 안전성, 최신성, 비용 같은 요소가 함께 중요합니다.

그래서 benchmark 점수가 높아도 실제 사용자에게는 답이 느리거나, 엉뚱하거나, 최신 정보를 모르거나, 서비스 목적에 맞지 않아 품질이 낮게 느껴질 수 있습니다.

**설명**

benchmark는 여러 모델을 같은 기준으로 비교하기 위해 만든 평가 세트입니다. 예를 들어 수학 문제 benchmark, 코드 생성 benchmark, 독해 benchmark처럼 특정 task를 잘하는지 측정합니다.

하지만 실제 서비스는 benchmark보다 훨씬 복잡합니다. 사용자는 시험지처럼 깔끔한 질문만 하지 않습니다. 오타가 섞인 질문을 하기도 하고, 회사 내부 정책처럼 모델이 학습 때 보지 못한 최신 정보를 묻기도 합니다. 또 답이 맞더라도 너무 늦게 나오면 좋은 서비스라고 보기 어렵습니다.

LLM에서는 특히 benchmark 점수와 실제 품질 사이에 차이가 생기기 쉽습니다. 모델이 유명한 benchmark 문제를 이미 학습 데이터에서 봤을 수도 있고, benchmark는 “정답 여부”를 보지만 실제 서비스는 친절함, 안전성, 출처 표시, 지시 준수까지 보기 때문입니다.

즉 benchmark는 중요하지만, 그것만으로 모델의 전체 능력을 판단하면 위험합니다. 실제 제품에서는 별도의 eval, human evaluation, regression test, 사용자 로그 분석이 함께 필요합니다.

**예시**

두 챗봇이 있다고 해 봅시다.

모델 A는 수학 benchmark에서 90점을 받았습니다.  
모델 B는 수학 benchmark에서 82점을 받았습니다.

그런데 실제 고객센터 서비스에 넣어 보니 모델 A는 회사 환불 정책을 몰라서 자주 틀린 답을 합니다. 반면 모델 B는 RAG로 최신 환불 문서를 검색해서 답하고, 모르면 “문서에서 확인되지 않습니다”라고 말합니다.

이 경우 benchmark 점수만 보면 A가 좋아 보이지만, 실제 고객센터 서비스에서는 B가 더 좋은 모델일 수 있습니다.

**실전 연결**

실무에서는 모델을 배포하기 전에 benchmark만 보지 않습니다. 실제 서비스 질문과 비슷한 eval set을 만들고, RAG 검색 품질, 답변 정확성, latency, 안전성, 사용자 만족도를 함께 봅니다. LLM 앱에서는 프롬프트나 모델 버전을 조금 바꿔도 품질이 달라질 수 있기 때문에, 변경할 때마다 eval을 돌려서 “정말 좋아졌는지” 확인해야 합니다.

### 2. latency와 throughput은 어떻게 다르며, LLM 서비스에서는 각각 왜 중요한가요?

**정답**

latency는 한 요청이 들어온 뒤 응답이 나오기까지 걸리는 시간입니다. 쉽게 말해 “한 사용자가 얼마나 기다리는가”입니다.

throughput은 일정 시간 동안 시스템이 처리할 수 있는 요청 수나 token 수입니다. 쉽게 말해 “전체적으로 얼마나 많이 처리할 수 있는가”입니다.

LLM 서비스에서는 latency가 낮아야 사용자가 답변을 빠르게 느끼고, throughput이 높아야 많은 사용자를 동시에 처리할 수 있습니다.

**설명**

latency와 throughput은 비슷해 보이지만 보는 관점이 다릅니다.

latency는 개인 사용자 입장에서 중요합니다. 사용자가 챗봇에게 질문했는데 첫 글자가 10초 뒤에 나오면 답이 좋아도 답답하게 느낍니다. 그래서 LLM 서비스에서는 first token latency, 즉 첫 token이 나오기까지의 시간이 중요합니다. token은 LLM이 문장을 만들 때 사용하는 작은 단위입니다. 한국어에서는 단어 조각이나 글자 묶음처럼 생각하면 됩니다.

throughput은 서비스 운영자 입장에서 중요합니다. 한 명에게는 빠르게 답해도, 동시에 1,000명이 들어오면 시스템이 버티지 못할 수 있습니다. 이때 초당 몇 개의 요청을 처리할 수 있는지, 초당 몇 개의 token을 생성할 수 있는지가 중요합니다.

LLM은 답변 전체를 한 번에 만드는 것이 아니라 token을 하나씩 순서대로 생성합니다. 그래서 답변이 길수록 계산이 많아지고 latency도 길어질 수 있습니다. 동시에 사용자 수가 많아지면 GPU 메모리와 계산량이 부족해져 throughput 문제가 생깁니다.

이 둘은 항상 같이 좋아지기만 하지는 않습니다. 예를 들어 batching은 여러 요청을 묶어 한 번에 처리해서 throughput을 높일 수 있습니다. 하지만 어떤 사용자는 batch가 모일 때까지 조금 기다려야 해서 latency가 늘어날 수도 있습니다.

**예시**

카페를 생각해 봅시다.

한 손님이 커피를 주문하고 받기까지 3분 걸린다면, 그 3분이 latency입니다.

한 카페가 1시간에 커피 100잔을 만들 수 있다면, 그 100잔이 throughput입니다.

AI 서비스도 같습니다. 사용자가 질문하고 첫 답변을 보기까지 1초 걸리면 latency가 낮은 편입니다. 그리고 서버가 초당 500 token을 생성할 수 있다면 throughput이 높은 편입니다.

**실전 연결**

LLM API, 챗봇, 번역기, RAG 시스템을 만들 때 latency와 throughput은 핵심 운영 지표입니다. latency가 나쁘면 사용자가 서비스를 느리다고 느끼고, throughput이 낮으면 사용자가 몰릴 때 장애가 납니다. 그래서 실무에서는 batching, streaming, KV cache, quantization 같은 방법으로 응답 속도와 처리량을 최적화합니다. 단, 속도를 높이다가 답변 품질이 떨어질 수 있으므로 eval과 함께 봐야 합니다.

### 3. AI 시스템을 data pipeline, training stack, inference stack, feedback loop로 나누어 보면 어떤 장점이 있나요?

**정답**

AI 시스템을 여러 부분으로 나누어 보면 문제가 어디서 생겼는지 더 쉽게 찾을 수 있고, 각 부분을 따로 개선할 수 있습니다.

data pipeline은 데이터 준비, training stack은 모델 학습, inference stack은 실제 서비스 응답, feedback loop는 사용자 반응을 다시 개선에 반영하는 부분입니다.

이렇게 나누면 “모델이 나쁜가?”라는 막연한 질문 대신, “데이터가 문제인가?”, “평가가 문제인가?”, “서빙이 느린가?”, “피드백이 반영되지 않는가?”처럼 구체적으로 분석할 수 있습니다.

**설명**

초보자는 AI 시스템을 볼 때 모델 하나만 생각하기 쉽습니다. 예를 들어 “더 큰 LLM을 쓰면 해결되지 않을까?”라고 생각할 수 있습니다.

하지만 실제 AI 제품은 모델 하나로 완성되지 않습니다. 데이터가 부정확하면 좋은 모델도 잘못 배웁니다. 학습은 잘 되었지만 inference stack이 약하면 실제 서비스에서 너무 느릴 수 있습니다. 사용자가 어떤 답변을 싫어했는지 모으지 않으면 다음 버전에서 같은 실수를 반복합니다.

그래서 시스템을 나누어 보는 것이 중요합니다.

data pipeline은 원본 데이터를 수집하고 정제하고 모델이 사용할 수 있게 바꾸는 흐름입니다. 예를 들어 문서에서 중복을 제거하고, 개인정보를 지우고, 최신 문서만 남기는 일이 여기에 포함됩니다.

training stack은 모델을 학습시키는 구성입니다. 데이터 로더, GPU, optimizer, loss function, 분산 학습 도구 등이 포함됩니다. optimizer는 loss를 줄이도록 weight를 업데이트하는 방법입니다.

inference stack은 학습된 모델을 실제 사용자 요청에 연결하는 부분입니다. API 서버, GPU serving, batching, streaming, latency 관리 등이 들어갑니다.

feedback loop는 사용자 반응과 실패 사례를 다시 모아 다음 개선에 사용하는 순환입니다. 예를 들어 사용자가 “이 답변은 틀렸어요”라고 표시한 사례를 모아 eval set에 추가할 수 있습니다.

이렇게 나누면 전체 시스템을 더 안정적으로 설계하고 운영할 수 있습니다.

**예시**

회사 내부 문서 Q&A 챗봇을 만든다고 해 봅시다.

사용자가 “휴가 신청은 어떻게 하나요?”라고 물었는데 챗봇이 오래된 규정을 답했습니다.

이때 단순히 “LLM이 나쁘다”고 말하면 원인을 놓칠 수 있습니다.

문제는 data pipeline일 수 있습니다. 최신 휴가 규정 문서가 수집되지 않았을 수 있습니다.

문제는 inference stack일 수도 있습니다. 검색은 잘했지만 LLM에게 문서를 제대로 전달하지 못했을 수 있습니다.

문제는 feedback loop일 수도 있습니다. 예전에 같은 오류가 있었는데 기록하지 않아 계속 반복되었을 수 있습니다.

이렇게 부분별로 나누어 보면 고쳐야 할 위치가 더 선명해집니다.

**실전 연결**

실제 ML/DL/LLM 제품에서는 이 구조가 매우 중요합니다. 추천 시스템, 검색 엔진, 고객센터 챗봇, 의료 이미지 분석, 사기 탐지 시스템 모두 데이터 수집부터 배포와 피드백까지 이어지는 흐름이 필요합니다. 특히 LLM 앱에서는 RAG, prompt engineering, model serving, eval, monitoring이 함께 움직입니다. 모델만 바꾸는 것이 아니라 data pipeline, inference stack, feedback loop를 함께 개선해야 실제 서비스 품질이 좋아집니다.
