## 1. 평가와 벤치마크

### 한 줄 직관
모델 평가는 “이 AI가 실제로 일을 잘하는지”를 시험해 보는 과정이고, 벤치마크(benchmark)는 여러 모델을 같은 시험지로 비교하기 위한 공통 시험입니다.

### 개념 정의
평가(eval, evaluation)는 모델의 답이 얼마나 좋은지 측정하는 과정입니다. 예를 들어 번역 모델이면 번역이 자연스러운지, 분류 모델이면 정답 라벨을 맞혔는지, LLM이면 질문에 도움이 되는 답을 했는지 확인합니다.

벤치마크(benchmark)는 모델들을 같은 조건에서 비교하기 위해 만든 데이터셋과 평가 방식의 묶음입니다. 쉽게 말하면 “공통 시험 문제 + 채점 기준”입니다. 한 학생이 학교마다 다른 시험을 보면 실력을 비교하기 어렵습니다. AI 모델도 마찬가지입니다. A 모델은 쉬운 문제로 평가하고 B 모델은 어려운 문제로 평가하면 공정하지 않습니다.

여기서 중요한 점은 “평가 점수 = 모델의 전체 능력”이 아니라는 것입니다. 평가 점수는 특정 문제 묶음에서의 성능을 보여 줍니다. 그래서 실제 서비스에서는 자동 평가뿐 아니라 human evaluation, 실제 사용자 로그, 실패 사례 분석까지 함께 봅니다.

### 왜 이런 개념이 필요한가
모델을 학습할 때는 loss가 내려가는 것을 봅니다. 하지만 loss가 낮다고 항상 실제 사용자가 좋아하는 모델은 아닙니다. 예를 들어 챗봇이 다음 단어를 잘 맞히도록 학습되어 loss가 낮아졌더라도, 실제 답변이 길기만 하고 핵심을 놓칠 수 있습니다.

평가가 필요한 이유는 크게 세 가지입니다.

1. **모델 선택**: 여러 모델 중 어떤 모델을 서비스에 쓸지 고릅니다.
2. **개선 확인**: 새 데이터나 새 학습 방법이 정말 좋아졌는지 봅니다.
3. **위험 관리**: 환각(hallucination), 편향(bias), 안전성 문제를 찾습니다.

LLM 시대에는 평가가 더 어려워졌습니다. 이미지 분류처럼 “고양이/강아지” 정답이 딱 있는 문제도 있지만, LLM의 답은 여러 개가 모두 그럴듯할 수 있습니다. 그래서 task metric과 human evaluation을 같이 써야 합니다.

### 아주 쉬운 예시
스팸 메일 분류기를 생각해 봅시다. 이메일 10개가 있고, 실제로 스팸은 4개입니다.

- 모델이 10개 중 8개를 맞혔다면 accuracy는 8/10 = 80%입니다.
- 그런데 스팸 4개 중 2개만 잡았다면, 스팸을 놓친 비율이 큽니다.
- 사용자는 “정상 메일을 스팸으로 보내지 않는 것”도 중요하고, “진짜 스팸을 잡는 것”도 중요합니다.

이때 하나의 숫자만 보면 위험합니다. accuracy는 좋아 보이지만, 스팸 탐지라는 실제 목적에는 부족할 수 있습니다.

LLM 예시도 봅시다.

질문: “서울에서 부산까지 KTX로 얼마나 걸려?”

- 모델 A: “약 2시간 30분에서 3시간 정도입니다.”
- 모델 B: “KTX는 한국의 고속철도입니다. 서울은 수도이고 부산은 항구 도시입니다...”

둘 다 문장은 자연스럽지만, 실제 사용자에게 더 유용한 답은 A입니다. 이런 차이는 단순한 다음 단어 loss만으로는 잘 보이지 않습니다. 그래서 eval이 필요합니다.

### 개념 구조와 핵심 포인트
평가는 보통 다음 구조로 생각할 수 있습니다.

1. **평가할 task 정하기**
   - 번역, 요약, 질의응답, 코딩, 수학 문제 풀이, 검색 기반 답변 등입니다.

2. **평가 데이터 만들기**
   - 입력과 기대 답을 준비합니다.
   - 예: 질문 100개와 정답 100개.

3. **평가 기준 정하기**
   - 숫자로 재는 기준을 task metric이라고 합니다.
   - 예: accuracy, F1, BLEU, ROUGE, pass@k, win rate 등입니다.

4. **모델 출력 수집하기**
   - 같은 prompt, 같은 temperature, 같은 decoding 조건으로 비교해야 공정합니다.

5. **자동 평가 또는 사람 평가하기**
   - 자동 평가는 빠르고 싸지만, 미묘한 품질을 놓칠 수 있습니다.
   - human evaluation은 느리고 비싸지만, 실제 사용자의 느낌에 가깝습니다.

6. **오류 분석하기**
   - 점수만 보는 것이 아니라 “어떤 문제에서 왜 틀렸는가”를 봅니다.

핵심 포인트는 “좋은 benchmark는 실제로 풀고 싶은 문제를 잘 대표해야 한다”는 것입니다. 학교 시험이 암기력만 측정하면 창의력을 알기 어렵듯, AI benchmark도 범위가 좁으면 실제 능력을 과대평가할 수 있습니다.

### 핵심 수학 포인트
가장 단순한 평가는 비율입니다.

예를 들어 20문제 중 15문제를 맞히면:

- accuracy = 맞힌 개수 / 전체 개수 = 15 / 20 = 0.75 = 75%

하지만 데이터가 불균형하면 accuracy만으로 부족합니다. 예를 들어 암 진단 데이터에서 100명 중 95명이 정상이고 5명만 암이라고 합시다. 모델이 모두 “정상”이라고 하면 accuracy는 95%입니다. 하지만 암 환자 5명을 모두 놓쳤으니 좋은 모델이 아닙니다.

그래서 precision과 recall 같은 metric이 등장합니다.

- precision: 모델이 “양성”이라고 한 것 중 실제 양성의 비율
- recall: 실제 양성 중 모델이 잡아낸 비율

아주 작은 숫자로 보면:

- 모델이 스팸이라고 표시한 메일 5개 중 진짜 스팸이 4개라면 precision = 4/5 = 80%
- 실제 스팸 10개 중 모델이 4개를 잡았다면 recall = 4/10 = 40%

LLM에서는 정답이 하나로 고정되지 않는 경우가 많습니다. 그래서 “정답 문자열과 얼마나 겹치는가”만으로 부족할 수 있습니다. 이때 사람 평가(human evaluation), LLM-as-a-judge, pairwise comparison 같은 방법을 씁니다. 단, LLM-as-a-judge도 편향이 있을 수 있으므로 완전한 정답지는 아닙니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)
- **benchmark**: 여러 모델을 같은 조건에서 비교하기 위한 공통 시험 세트입니다.
- **eval / evaluation**: 모델 성능을 측정하는 과정입니다.
- **human evaluation**: 사람이 모델 출력을 직접 평가하는 방식입니다.
- **task metric**: 특정 task에 맞춘 측정 지표입니다. 예: accuracy, F1, pass@k.
- **accuracy**: 전체 중 맞힌 비율입니다.
- **precision**: 모델이 맞다고 주장한 것 중 실제로 맞은 비율입니다.
- **recall**: 실제 정답 중 모델이 찾아낸 비율입니다.
- **win rate**: 두 모델의 답을 비교했을 때 한쪽이 더 낫다고 선택된 비율입니다.

### AI에서 어디에 쓰이는가
평가와 benchmark는 AI 개발의 거의 모든 단계에 들어갑니다.

- **학습 중**: validation set의 loss와 metric을 보며 overfitting을 감지합니다.
- **모델 비교**: 같은 데이터로 작은 모델, 큰 모델, fine-tuned 모델을 비교합니다.
- **LLM 제품 개발**: 답변 품질, 환각률, 안전성, 거절 정책, 도구 사용 성공률을 평가합니다.
- **RAG 시스템**: 검색된 문서가 질문과 관련 있는지, 답변이 문서에 근거하는지 평가합니다.
- **배포 후**: 사용자 feedback loop를 통해 실패 사례를 수집하고 다음 개선에 반영합니다.

실전에서는 “벤치마크 점수 1등”보다 “우리 사용자의 실제 문제를 안정적으로 해결하는가”가 더 중요합니다. 그래서 회사들은 공개 benchmark뿐 아니라 내부 eval set을 따로 만듭니다.

### 헷갈리기 쉬운 포인트
- **benchmark 점수가 높으면 항상 좋은 모델인가?**  
  아닙니다. benchmark가 실제 사용 상황과 다르면 점수가 높아도 서비스에서는 별로일 수 있습니다.

- **loss가 낮으면 평가 점수도 항상 좋아지는가?**  
  대체로 관련은 있지만 항상 그렇지는 않습니다. 특히 LLM의 유용성, 안전성, 간결성은 loss 하나로 설명하기 어렵습니다.

- **human evaluation은 완벽한가?**  
  아닙니다. 사람 평가도 평가자의 취향, 피로도, 지시문에 영향을 받습니다. 그래서 평가 기준을 명확히 해야 합니다.

- **LLM-as-a-judge를 쓰면 사람이 필요 없는가?**  
  아닙니다. LLM 평가자는 빠르지만 편향과 오류가 있습니다. 중요한 제품에서는 사람 평가와 샘플 검토가 여전히 필요합니다.

## 2. 서빙과 추론 최적화

### 한 줄 직관
서빙(serving)은 학습이 끝난 모델을 실제 사용자가 쓸 수 있게 내놓는 것이고, 추론 최적화는 “답을 더 빠르고 싸고 안정적으로 만들기” 위한 기술입니다.

### 개념 정의
학습(training)은 모델이 데이터를 보며 파라미터를 조정하는 과정입니다. 반대로 추론(inference)은 이미 학습된 모델에 입력을 넣고 출력을 얻는 과정입니다. 사용자가 챗봇에 질문을 입력했을 때 모델이 답변을 생성하는 것이 추론입니다.

서빙(serving)은 이 추론을 실제 서비스 형태로 제공하는 전체 과정입니다. 모델 파일을 서버에 올리고, API를 만들고, 여러 사용자의 요청을 처리하고, 속도와 비용을 관리하는 일이 포함됩니다.

추론 최적화(inference optimization)는 모델의 품질을 크게 해치지 않으면서 더 빠르게, 더 적은 메모리로, 더 많은 요청을 처리하도록 만드는 방법입니다. 대표적인 용어가 latency, throughput, quantization, KV cache입니다.

### 왜 이런 개념이 필요한가
모델이 연구실에서 한 번 답을 잘 내는 것과, 실제 서비스에서 매초 수천 명에게 안정적으로 답하는 것은 완전히 다른 문제입니다.

예를 들어 어떤 LLM이 질문 하나에 답하는 데 20초가 걸린다고 합시다. 논문 실험에서는 괜찮을 수 있습니다. 하지만 사용자는 20초를 기다리면 답답합니다. 또 GPU 한 대가 동시에 2명만 처리할 수 있다면, 사용자가 많아질 때 비용이 폭발합니다.

그래서 실제 AI 제품에서는 다음 질문을 계속 던집니다.

- 한 사용자가 답을 받기까지 얼마나 걸리는가? → latency
- 1초에 몇 개의 요청 또는 token을 처리할 수 있는가? → throughput
- GPU 메모리에 모델과 중간 계산값이 들어가는가?
- 품질을 조금 포기하면 속도와 비용을 얼마나 줄일 수 있는가?

LLM은 특히 추론이 비쌉니다. 답변을 한 번에 통째로 만드는 것이 아니라 token을 하나씩 생성하기 때문입니다. “안녕하세요”라는 짧은 답도 실제로는 여러 token을 순서대로 예측합니다.

### 아주 쉬운 예시
식당을 생각해 봅시다.

- latency는 손님 한 명이 주문하고 음식을 받을 때까지 걸리는 시간입니다.
- throughput은 식당이 한 시간에 처리할 수 있는 손님 수입니다.

요리사가 한 명이고 한 접시에 10분이 걸리면 latency도 길고 throughput도 낮습니다. 요리 과정을 미리 준비하거나, 여러 주문을 묶어서 처리하거나, 재료를 더 작고 다루기 쉽게 만들면 더 빨라질 수 있습니다.

LLM에서도 비슷합니다.

예를 들어 한 요청이 100 token 답변을 생성한다고 합시다.

- token 1개 생성에 0.05초가 걸리면 100 token은 약 5초입니다.
- token 1개 생성에 0.02초로 줄이면 100 token은 약 2초입니다.

사용자 입장에서는 5초와 2초가 크게 다릅니다. 서비스 운영자 입장에서는 같은 GPU로 더 많은 요청을 처리할 수 있으므로 비용도 줄어듭니다.

### 개념 구조와 핵심 포인트
서빙과 추론 최적화는 다음 요소들이 함께 움직입니다.

1. **모델 로딩**
   - 학습된 weight를 GPU 또는 CPU 메모리에 올립니다.
   - 모델이 클수록 메모리를 많이 씁니다.

2. **입력 전처리**
   - 텍스트를 token으로 바꿉니다.
   - 이미지 모델이면 이미지를 tensor로 변환합니다.

3. **forward pass**
   - 모델이 입력을 layer별로 계산해서 다음 token 확률이나 예측값을 만듭니다.
   - 이때 attention, hidden states, matrix multiplication이 많이 사용됩니다.

4. **decoding**
   - LLM은 다음 token을 고르고, 그 token을 다시 입력에 붙여 다음 token을 예측합니다.
   - greedy decoding, sampling, beam search 같은 방식이 있습니다.

5. **동시 요청 처리**
   - 여러 사용자의 요청을 batch로 묶어 GPU를 효율적으로 씁니다.

6. **최적화 기법 적용**
   - quantization으로 weight를 작게 만듭니다.
   - KV cache로 attention 계산을 재사용합니다.
   - batching, speculative decoding, model parallelism 등을 적용합니다.

핵심 포인트는 “모델 품질, 속도, 비용, 안정성은 서로 trade-off가 있다”는 것입니다. 가장 큰 모델이 항상 서비스에 적합한 것은 아닙니다. 작은 모델을 잘 fine-tuning하고 RAG를 붙이는 편이 더 빠르고 안정적일 수 있습니다.

### 핵심 수학 포인트
추론에서 가장 많이 반복되는 계산은 행렬 곱(matrix multiplication)입니다. 아주 단순한 예를 보겠습니다.

입력 벡터가 `[2, 3]`이고, weight가 다음과 같다고 합시다.

```text
W = [[1, 0],
     [0, 2]]
```

그러면 출력은 대략 다음처럼 계산됩니다.

```text
[2, 3] × W = [2×1 + 3×0, 2×0 + 3×2] = [2, 6]
```

실제 neural network에서는 이런 계산이 수백만 번, 수십억 번 반복됩니다. LLM의 Transformer layer에서는 attention 계산과 feed-forward network 계산이 특히 큽니다.

추론 비용을 간단히 생각하면 다음 요소가 중요합니다.

- 파라미터 수가 많을수록 weight를 읽고 계산하는 비용이 증가합니다.
- sequence length가 길수록 attention 계산과 KV cache 메모리가 증가합니다.
- batch size가 커지면 한 번에 더 많은 요청을 처리할 수 있지만, 메모리 사용량도 커집니다.

KV cache는 LLM에서 매우 중요합니다. LLM이 token을 하나씩 생성할 때, 이전 token들의 key와 value를 매번 다시 계산하면 낭비가 큽니다. 그래서 이전 계산 결과를 저장해 두고 재사용합니다.

작은 예로, 문장 “나는 밥을” 다음에 token을 생성한다고 합시다. 다음 token “먹었다”를 만든 뒤, 다시 “나는 밥을 먹었다” 전체를 처음부터 계산하면 느립니다. KV cache는 앞부분 “나는 밥을”의 attention 관련 중간값을 저장해 두어 다음 계산을 빠르게 합니다.

quantization은 숫자의 정밀도를 낮추는 방법입니다. 예를 들어 weight를 32-bit float로 저장하면 숫자 하나가 32비트를 씁니다. 8-bit integer로 줄이면 대략 1/4 크기로 줄어듭니다. 대신 아주 미세한 값 차이는 잃을 수 있습니다. 그래서 속도와 메모리는 좋아지지만 품질이 조금 떨어질 수 있습니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)
- **serving**: 학습된 모델을 실제 사용자 요청에 응답하는 서비스로 운영하는 일입니다.
- **inference**: 학습된 모델이 입력을 받아 예측이나 답변을 만드는 과정입니다.
- **latency**: 요청 하나가 들어와서 응답이 나올 때까지 걸리는 시간입니다.
- **throughput**: 단위 시간에 처리할 수 있는 요청 수 또는 token 수입니다.
- **quantization**: weight나 activation의 숫자 정밀도를 낮춰 메모리와 계산 비용을 줄이는 방법입니다.
- **KV cache**: Transformer attention에서 이전 token들의 key/value 중간값을 저장해 다음 token 생성에 재사용하는 메모리입니다.
- **batching**: 여러 요청을 묶어서 한 번에 계산하는 방식입니다.
- **token/sec**: LLM이 초당 생성하거나 처리하는 token 수입니다.

### AI에서 어디에 쓰이는가
서빙과 추론 최적화는 실제 AI 제품의 핵심입니다.

- **챗봇 서비스**: 사용자가 답을 빨리 받아야 하므로 latency가 중요합니다.
- **검색 + RAG**: 검색, 문서 압축, 답변 생성까지 이어지므로 전체 pipeline latency를 봐야 합니다.
- **모바일 AI**: 메모리와 배터리가 제한적이라 quantization이 중요합니다.
- **실시간 음성/번역**: 사람이 말하는 속도에 맞춰 응답해야 하므로 지연이 작아야 합니다.
- **대규모 API 서비스**: throughput이 낮으면 GPU 비용이 너무 커집니다.

실전에서는 모델 자체만 보는 것이 아니라 tokenizer, prompt 길이, context length, batch scheduler, GPU 종류, network overhead까지 함께 봅니다. 같은 모델이라도 serving stack이 다르면 사용자 경험이 크게 달라집니다.

### 헷갈리기 쉬운 포인트
- **latency와 throughput은 같은 뜻인가?**  
  아닙니다. latency는 한 요청의 대기 시간이고, throughput은 전체 처리량입니다. batch를 크게 하면 throughput은 좋아질 수 있지만 개별 latency는 늘어날 수 있습니다.

- **quantization은 무조건 좋은가?**  
  아닙니다. 메모리와 속도는 좋아질 수 있지만, 너무 낮은 정밀도는 모델 품질을 떨어뜨릴 수 있습니다.

- **KV cache는 모델을 더 똑똑하게 만드는가?**  
  아닙니다. 같은 계산을 더 효율적으로 하게 만드는 기술입니다. 품질을 직접 올리는 것이 아니라 속도와 비용에 영향을 줍니다.

- **학습이 끝나면 서비스는 쉬운가?**  
  아닙니다. 실제 서비스는 장애 대응, 모니터링, 비용 관리, 보안, 사용자 feedback까지 포함합니다.

## 3. AI 시스템 설계 전체 그림

### 한 줄 직관
AI 시스템은 모델 하나가 아니라, 데이터가 들어오고, 학습되고, 배포되고, 사용자의 반응이 다시 개선으로 돌아오는 큰 순환 구조입니다.

### 개념 정의
AI 시스템 설계는 “모델을 어떻게 만들고, 어떻게 서비스하고, 어떻게 계속 개선할 것인가”를 전체적으로 설계하는 일입니다. 여기에는 data pipeline, training stack, inference stack, feedback loop가 포함됩니다.

초보자는 AI를 “모델 파일 하나”로 생각하기 쉽습니다. 하지만 실제 AI 제품은 훨씬 더 큰 시스템입니다. 데이터 수집, 정제, labeling, 학습, 평가, 배포, 모니터링, 사용자 feedback 수집, 재학습까지 연결됩니다.

즉, 모델은 중심 부품이지만 전체 제품은 아닙니다. 자동차에서 엔진이 중요하지만, 연료 공급, 브레이크, 계기판, 도로 환경까지 함께 봐야 하는 것과 비슷합니다.

### 왜 이런 개념이 필요한가
실제 AI 프로젝트가 실패하는 이유는 모델 구조를 몰라서만이 아닙니다. 오히려 다음 문제가 더 자주 발생합니다.

- 데이터가 지저분해서 학습이 잘 안 됩니다.
- 학습 데이터와 실제 서비스 데이터가 다릅니다.
- offline benchmark는 좋은데 실제 사용자 만족도는 낮습니다.
- 모델은 잘 만들었지만 serving 비용이 너무 큽니다.
- 배포 후 오류를 추적할 모니터링이 없습니다.
- 사용자 feedback이 다음 학습 데이터로 연결되지 않습니다.

그래서 AI 시스템을 볼 때는 “모델 성능”뿐 아니라 “데이터 흐름과 운영 흐름”을 봐야 합니다. 특히 LLM 이후에는 하나의 모델만 쓰는 경우보다 RAG, tool use, safety filter, memory, ranking, logging이 함께 들어가는 경우가 많습니다.

### 아주 쉬운 예시
고객센터 AI 챗봇을 만든다고 합시다.

1. 고객 문의 1만 건을 모읍니다.
2. 개인정보를 제거하고, 자주 묻는 질문을 분류합니다.
3. FAQ 문서를 검색할 수 있게 embedding을 만듭니다.
4. 사용자가 질문하면 관련 문서를 검색합니다.
5. LLM이 검색된 문서를 바탕으로 답변합니다.
6. 사용자가 “도움 됨/안 됨”을 누릅니다.
7. “안 됨” 사례를 모아 프롬프트, 검색 방식, 문서, 모델을 개선합니다.

여기서 LLM만 중요한 것이 아닙니다. 검색 문서가 틀리면 LLM도 틀린 답을 하기 쉽습니다. feedback을 모으지 않으면 같은 실패가 반복됩니다. latency가 너무 길면 사용자는 답이 좋아도 떠날 수 있습니다.

숫자로 아주 작게 보면:

- 하루 질문 100개 중 70개는 잘 답합니다.
- 20개는 문서를 못 찾아서 틀립니다.
- 10개는 문서는 찾았지만 답변 형식이 나쁩니다.

이 경우 모델만 바꾸기 전에 검색 품질과 prompt 형식을 먼저 개선해야 할 수 있습니다.

### 개념 구조와 핵심 포인트
AI 시스템은 보통 다음 흐름으로 볼 수 있습니다.

1. **data pipeline**
   - 데이터를 수집하고, 정제하고, 저장하고, 학습 가능한 형태로 만듭니다.
   - 텍스트라면 tokenization, 이미지라면 resize와 normalization, tabular data라면 결측치 처리가 들어갑니다.

2. **training stack**
   - 모델 구조, loss, optimizer, GPU 학습, checkpoint 저장, validation 평가를 포함합니다.
   - 여기서 gradient가 loss를 줄이는 방향으로 weight를 바꿉니다.

3. **evaluation layer**
   - 학습된 모델이 실제 목표에 맞게 좋아졌는지 확인합니다.
   - 공개 benchmark와 내부 eval set을 함께 봅니다.

4. **inference stack**
   - 모델을 API로 배포하고 실제 요청을 처리합니다.
   - serving, batching, KV cache, quantization, monitoring이 들어갑니다.

5. **product layer**
   - 사용자가 보는 UI, prompt, policy, 권한, 로그, 안전장치가 포함됩니다.

6. **feedback loop**
   - 사용자 반응과 실패 사례를 수집해 데이터, prompt, 모델, 평가 기준을 개선합니다.

핵심 포인트는 AI 시스템이 “일회성 프로젝트”가 아니라 “계속 돌아가는 개선 루프”라는 것입니다. 데이터가 바뀌고, 사용자 질문이 바뀌고, 제품 목표가 바뀌면 모델도 평가도 업데이트되어야 합니다.

### 핵심 수학 포인트
전체 시스템을 수식 하나로 설명할 필요는 없지만, 기본 흐름은 단순하게 볼 수 있습니다.

모델은 입력 x를 받아 출력 y를 만듭니다.

```text
model(x) = y
```

학습 단계에서는 정답 y_true와 예측 y_pred를 비교해 loss를 계산합니다.

```text
loss = difference(y_pred, y_true)
```

optimizer는 gradient를 이용해 loss가 줄어드는 방향으로 weight를 조금씩 바꿉니다.

```text
new weight = old weight - learning rate × gradient
```

아주 작은 숫자로 보면, weight가 2.0이고 gradient가 0.3, learning rate가 0.1이면:

```text
new weight = 2.0 - 0.1 × 0.3 = 1.97
```

이런 작은 업데이트가 매우 많이 반복되어 모델이 학습됩니다.

하지만 시스템 관점에서는 학습 수식만으로 충분하지 않습니다. 실제 사용에서는 입력 x의 분포가 바뀔 수 있습니다. 학습 때는 짧은 질문만 봤는데, 서비스에서는 긴 문서와 복잡한 질문이 들어올 수 있습니다. 이것을 data distribution shift라고 볼 수 있습니다.

또 LLM/RAG 시스템에서는 입력 x 자체가 여러 단계로 만들어집니다.

```text
user question → retrieval → context documents → prompt → LLM answer
```

따라서 최종 답변 품질은 LLM weight만이 아니라 검색 품질, prompt 구성, context 길이, decoding 설정, safety filter까지 함께 영향을 받습니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)
- **data pipeline**: 데이터를 수집, 정제, 변환, 저장해 학습이나 추론에 쓰기 좋게 만드는 흐름입니다.
- **training stack**: 모델 학습에 필요한 코드, GPU, optimizer, loss, checkpoint, 실험 관리 도구의 묶음입니다.
- **inference stack**: 학습된 모델을 실제 요청에 응답하도록 운영하는 serving 구조입니다.
- **feedback loop**: 사용자 반응과 실패 사례를 다시 개선 과정에 반영하는 순환 구조입니다.
- **monitoring**: 배포 후 latency, error rate, 품질, 비용 등을 계속 관찰하는 일입니다.
- **data drift / distribution shift**: 학습 때 본 데이터와 실제 서비스 데이터의 성격이 달라지는 현상입니다.
- **RAG (Retrieval-Augmented Generation)**: 검색으로 관련 문서를 가져온 뒤 LLM이 그 문서를 참고해 답하는 구조입니다.

### AI에서 어디에 쓰이는가
AI 시스템 설계 관점은 다음 상황에서 특히 중요합니다.

- **기업용 LLM 도입**: 사내 문서 검색, 권한 관리, 답변 근거 표시, 감사 로그가 필요합니다.
- **추천 시스템**: 사용자 행동 로그가 data pipeline으로 들어가고, 모델은 계속 재학습됩니다.
- **의료/금융 AI**: 모델 정확도뿐 아니라 설명 가능성, 기록, 안전성, 규정 준수가 중요합니다.
- **자율주행/로봇**: 센서 데이터, 실시간 추론, 실패 복구, 안전 제어가 함께 필요합니다.
- **개인화 서비스**: 사용자의 feedback loop를 통해 모델 또는 ranking이 계속 바뀝니다.

Embeddings도 시스템 안에서 자주 쓰입니다. 예를 들어 문서를 embedding vector로 바꿔 저장해 두면, 사용자의 질문과 의미가 가까운 문서를 빠르게 찾을 수 있습니다. 이때 embedding 모델, vector database, 검색 metric, LLM prompt가 모두 하나의 inference stack으로 연결됩니다.

### 헷갈리기 쉬운 포인트
- **AI 시스템 = 모델인가?**  
  아닙니다. 모델은 핵심 부품이지만, 데이터, 평가, serving, monitoring, feedback까지 포함해야 실제 시스템입니다.

- **좋은 모델을 쓰면 data pipeline은 덜 중요한가?**  
  아닙니다. 좋은 모델도 나쁜 데이터 위에서는 나쁜 결과를 냅니다. “garbage in, garbage out”은 AI에서도 그대로입니다.

- **배포하면 프로젝트가 끝나는가?**  
  아닙니다. 배포 후에 실제 문제가 드러납니다. monitoring과 feedback loop가 없으면 개선이 어렵습니다.

- **RAG를 붙이면 환각이 사라지는가?**  
  아닙니다. 검색 문서가 틀리거나, LLM이 문서를 잘못 읽거나, prompt가 불명확하면 여전히 환각이 생길 수 있습니다.

### 1. benchmark 점수가 높은 모델이 실제 서비스에서 항상 좋은 모델이라고 말할 수 없는 이유는 무엇인가요?

**정답**

benchmark 점수가 높아도 실제 서비스에서 항상 좋은 모델이라고 말할 수는 없습니다.

이유는 benchmark가 특정 문제 묶음과 특정 채점 기준에서의 성능만 보여 주기 때문입니다. 실제 사용자는 benchmark 문제와 다른 방식으로 질문할 수 있고, 서비스에서는 속도, 비용, 안전성, 환각, 사용자 만족도 같은 요소도 함께 중요합니다.

즉, benchmark 점수는 중요한 참고 자료이지만, 모델의 전체 실력을 완전히 대표하지는 않습니다.

**설명**

benchmark는 여러 모델을 같은 조건에서 비교하기 위한 “공통 시험지”입니다. 예를 들어 수학 문제 100개를 풀게 해서 몇 개를 맞혔는지 비교하는 방식입니다.

이런 평가는 매우 유용합니다. 모델 A와 모델 B를 공정하게 비교할 수 있기 때문입니다. 하지만 시험 점수가 높다고 해서 실제 업무를 항상 잘한다고 말할 수는 없습니다.

사람으로 비유하면, 영어 시험 점수가 높은 사람이 실제 외국인 고객 응대를 항상 잘하는 것은 아닐 수 있습니다. 시험에는 정답이 분명한 문제가 나오지만, 실제 대화에서는 말투, 상황 이해, 예의, 빠른 대응, 모르는 것을 인정하는 태도도 중요합니다.

AI도 마찬가지입니다. benchmark에서는 높은 점수를 받았지만 실제 서비스에서는 다음 문제가 생길 수 있습니다.

- 사용자의 질문 방식이 benchmark와 다를 수 있습니다.
- 답은 맞지만 너무 느릴 수 있습니다.
- 문장은 자연스럽지만 근거 없는 내용을 만들어낼 수 있습니다.
- 특정 분야에서는 잘하지만 우리 서비스의 데이터에는 약할 수 있습니다.
- 안전하지 않은 답변을 할 수 있습니다.
- 비용이 너무 커서 실제 운영이 어려울 수 있습니다.

특히 LLM에서는 정답이 하나로 고정되지 않는 경우가 많습니다. “좋은 요약”, “친절한 답변”, “실무에 도움이 되는 설명”은 단순히 맞고 틀림으로만 평가하기 어렵습니다. 그래서 benchmark뿐 아니라 human evaluation, 내부 eval set, 사용자 feedback, 실패 사례 분석을 함께 봐야 합니다.

**예시**

스팸 메일 분류 모델이 있다고 해 봅시다.

benchmark 데이터에서는 정확도 accuracy가 95%입니다. 겉으로 보면 매우 좋아 보입니다.

그런데 실제 서비스에서 확인해 보니 중요한 정상 메일을 스팸으로 자주 분류합니다. 사용자는 중요한 계약 메일을 놓치게 됩니다.

이 경우 benchmark 점수는 높지만, 실제 서비스에서는 좋지 않은 모델일 수 있습니다.

LLM 예시도 비슷합니다.

질문:
“우리 회사 환불 정책을 알려줘.”

모델이 benchmark에서는 높은 점수를 받았지만, 실제 회사 정책 문서를 제대로 참고하지 않고 일반적인 환불 정책을 지어내면 서비스에서는 위험합니다.

**실전 연결**

실제 ML/DL/LLM 개발에서는 공개 benchmark 점수만 보고 모델을 고르면 위험합니다. 그래서 회사들은 보통 자기 서비스에 맞는 내부 eval set을 따로 만듭니다. 예를 들어 고객센터 챗봇이라면 실제 고객 질문, 자주 틀리는 케이스, 법적 위험이 있는 질문을 모아서 평가합니다. RAG 시스템에서는 “검색된 문서가 질문과 관련 있는가”, “답변이 문서에 근거하는가”, “환각이 없는가”까지 함께 평가해야 합니다.

### 2. latency와 throughput의 차이를 식당 비유로 설명해 보세요.

**정답**

latency는 손님 한 명이 주문하고 음식을 받기까지 걸리는 시간입니다.

throughput은 식당이 일정 시간 동안 처리할 수 있는 전체 손님 수입니다.

즉, latency는 “한 요청이 얼마나 빨리 끝나는가”이고, throughput은 “전체적으로 얼마나 많이 처리할 수 있는가”입니다.

**설명**

AI 서비스에서 latency는 사용자가 요청을 보낸 뒤 응답을 받을 때까지 걸리는 시간입니다. 예를 들어 챗봇에 질문을 입력했는데 답이 나오기까지 2초가 걸리면 latency는 약 2초입니다.

throughput은 단위 시간당 처리량입니다. 예를 들어 어떤 LLM 서버가 1초에 100개의 token을 생성할 수 있다면 token/sec 기준 throughput이 100입니다. 또는 1분에 사용자 요청 500개를 처리할 수 있다면 요청 기준 throughput이 높은 것입니다.

식당으로 생각하면 더 쉽습니다.

latency는 한 손님의 체감 대기 시간입니다.

손님이 들어와서 김치찌개를 주문했습니다. 주문부터 음식이 나오기까지 10분이 걸렸다면, 그 손님 입장에서 latency는 10분입니다.

throughput은 식당 전체의 처리 능력입니다.

그 식당이 한 시간에 손님 60명을 받을 수 있다면 throughput은 높다고 볼 수 있습니다. 반대로 한 시간에 10명밖에 처리하지 못하면 throughput이 낮습니다.

중요한 점은 latency와 throughput이 항상 같이 좋아지는 것은 아니라는 것입니다.

예를 들어 식당이 주문을 10개씩 모아서 한 번에 요리한다고 합시다. 주방 입장에서는 효율적이라 한 시간에 더 많은 음식을 만들 수 있습니다. 즉, throughput은 좋아집니다. 하지만 첫 번째 손님은 주문이 충분히 모일 때까지 기다려야 하므로 latency는 길어질 수 있습니다.

AI serving에서도 비슷합니다. 여러 사용자 요청을 batch로 묶으면 GPU를 효율적으로 써서 throughput은 좋아질 수 있습니다. 하지만 batch가 모일 때까지 기다리면 개별 사용자의 latency는 늘어날 수 있습니다.

**예시**

아주 작은 숫자로 봅시다.

식당 A:
- 손님 한 명 음식이 2분 만에 나옵니다.
- 하지만 요리사가 한 명이라 한 번에 한 명만 처리합니다.
- latency는 낮지만, 많은 손님을 동시에 처리하는 throughput은 낮을 수 있습니다.

식당 B:
- 주문 10개를 모아서 한 번에 조리합니다.
- 한 번 조리하면 많은 손님 음식을 처리합니다.
- throughput은 높지만, 첫 손님은 주문이 모일 때까지 5분을 기다릴 수 있습니다.

LLM도 같습니다.

한 사용자가 답변을 받는 데 걸리는 시간이 latency입니다. 반면 GPU 서버가 1초에 총 몇 token을 생성하는지는 throughput입니다.

**실전 연결**

실제 LLM 서비스에서는 latency와 throughput을 모두 관리해야 합니다. 챗봇, 음성 비서, 실시간 번역처럼 사용자가 바로 응답을 기대하는 서비스는 latency가 매우 중요합니다. 반면 대량 문서 요약, 배치 번역, 로그 분석처럼 많은 작업을 한꺼번에 처리하는 경우에는 throughput이 중요할 수 있습니다. serving stack에서는 batching, KV cache, quantization, speculative decoding 같은 기법을 사용해 속도와 비용의 균형을 맞춥니다.

### 3. AI 시스템을 모델 하나가 아니라 data pipeline, training stack, inference stack, feedback loop로 나누어 보는 이유는 무엇인가요?

**정답**

AI 시스템을 여러 부분으로 나누어 보는 이유는 실제 AI 제품의 성능이 모델 하나만으로 결정되지 않기 때문입니다.

좋은 AI 시스템은 데이터 수집과 정제, 학습, 평가, 배포, 추론, 모니터링, 사용자 feedback까지 연결된 전체 흐름으로 동작합니다. 문제가 생겼을 때도 “모델이 나쁜가?”만 보면 원인을 찾기 어렵고, 어느 단계에서 문제가 생겼는지 나누어 봐야 정확히 개선할 수 있습니다.

**설명**

초보자는 AI를 “모델 파일 하나”로 생각하기 쉽습니다. 하지만 실제 서비스에서는 모델이 전체 시스템의 한 부품일 뿐입니다.

AI 시스템은 보통 다음 흐름으로 움직입니다.

data pipeline은 데이터를 모으고, 정리하고, 학습 가능한 형태로 바꾸는 과정입니다. 예를 들어 고객 문의 데이터를 모으고, 개인정보를 제거하고, 중복된 내용을 정리하는 작업이 여기에 들어갑니다.

training stack은 모델을 학습시키는 부분입니다. loss function, optimizer, gradient, GPU 학습, checkpoint 저장, validation 평가 등이 포함됩니다. 여기서 모델은 데이터를 보고 weight를 조금씩 조정합니다.

inference stack은 학습된 모델을 실제 서비스에서 실행하는 부분입니다. 사용자가 질문을 입력하면 모델이 답을 만들고, API 서버가 응답을 돌려줍니다. 여기에는 latency, throughput, batching, KV cache, quantization 같은 운영 요소가 들어갑니다.

feedback loop는 실제 사용자 반응과 실패 사례를 다시 개선에 반영하는 순환 구조입니다. 사용자가 “이 답변은 도움이 안 됐어요”라고 표시했다면, 그 사례를 모아 데이터, prompt, 검색 방식, 모델 평가 기준을 개선할 수 있습니다.

이렇게 나누어 보는 이유는 문제의 원인이 항상 모델 자체에 있지 않기 때문입니다.

예를 들어 LLM 챗봇이 틀린 답을 했다고 합시다. 원인은 여러 가지일 수 있습니다.

- data pipeline 문제: 문서 데이터가 오래되었거나 잘못 정리되었습니다.
- retrieval 문제: 관련 문서를 검색하지 못했습니다.
- prompt 문제: 모델에게 지시를 애매하게 했습니다.
- model 문제: 모델이 문서를 읽고 추론하는 능력이 부족합니다.
- inference 문제: context가 너무 길어서 중요한 내용이 잘렸습니다.
- feedback loop 문제: 같은 실패가 반복되는데도 개선 데이터로 모이지 않았습니다.

따라서 AI 시스템을 여러 층으로 나누어 보면 “어디를 고쳐야 하는지”를 더 정확히 알 수 있습니다.

**예시**

고객센터 AI 챗봇을 생각해 봅시다.

사용자 질문:
“지난달 결제 취소하면 환불은 언제 되나요?”

챗봇이 틀린 답을 했습니다.

이때 바로 “모델이 나쁘다”고 결론 내리면 안 됩니다.

작게 나누어 보면 다음 가능성이 있습니다.

1. data pipeline 문제  
환불 정책 문서가 최신 버전이 아닐 수 있습니다.

2. retrieval 문제  
정확한 환불 문서를 못 찾고, 비슷하지만 다른 문서를 가져왔을 수 있습니다.

3. prompt 문제  
“반드시 검색된 문서에 근거해서 답하라”는 지시가 약했을 수 있습니다.

4. inference stack 문제  
응답 시간이 너무 길어서 중간에 답변이 잘렸을 수 있습니다.

5. feedback loop 문제  
이 질문을 여러 사용자가 했는데도 실패 사례로 기록되지 않았을 수 있습니다.

즉, 답변 실패 하나에도 여러 원인이 있을 수 있습니다. 그래서 시스템을 구성 요소별로 나누어 보는 것이 중요합니다.

**실전 연결**

실제 ML/DL/LLM 프로젝트에서는 모델 성능만 보는 팀보다 전체 시스템을 보는 팀이 더 안정적인 제품을 만듭니다. 추천 시스템은 사용자 로그가 data pipeline으로 들어가고, 모델은 주기적으로 재학습되며, 배포 후 클릭률이나 구매 전환율을 모니터링합니다. RAG 기반 LLM 서비스는 embedding model, vector database, retrieval, prompt, LLM, safety filter, logging, feedback loop가 함께 움직입니다. 그래서 실전에서는 “모델을 바꿀까?”뿐 아니라 “데이터를 고칠까?”, “검색 품질을 올릴까?”, “평가 세트를 다시 만들까?”, “서빙 비용을 줄일까?”를 함께 판단해야 합니다.
