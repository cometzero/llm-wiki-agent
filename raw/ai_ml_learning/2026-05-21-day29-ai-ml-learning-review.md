## 1. RAG의 검색-생성 결합

### 한 줄 직관

RAG는 LLM에게 “기억만 믿고 답하지 말고, 먼저 관련 자료를 찾아본 뒤 그 자료를 보고 답하게 하는 방식”입니다.

### 개념 정의

RAG는 Retrieval-Augmented Generation의 약자입니다. 그대로 풀면 “검색(retrieval)으로 보강(augmentation)한 생성(generation)”입니다. 여기서 generation은 LLM이 문장을 만들어 답하는 능력이고, retrieval은 질문과 관련 있는 문서, 표, 코드, 매뉴얼, FAQ를 찾아오는 과정입니다.

쉽게 말하면 LLM을 시험 보는 학생이라고 생각할 수 있습니다. 그냥 “기억나는 대로 답해 봐”라고 하면 학생은 알고 있는 내용만으로 답합니다. 그런데 “이 참고자료 3쪽을 먼저 읽고 답해 봐”라고 하면 더 최신이고 더 정확한 답을 할 수 있습니다. RAG는 이 두 번째 방식입니다.

LLM 자체의 파라미터(parameter) 안에는 학습 때 본 패턴과 지식이 압축되어 있습니다. 하지만 회사 내부 문서, 오늘 바뀐 정책, 방금 업로드한 PDF, 개인 노트처럼 학습 이후에 생긴 정보는 모델 파라미터 안에 없습니다. 그래서 실제 서비스에서는 모델에게 모든 것을 외우게 하기보다, 필요한 정보를 검색해서 prompt에 넣어 주고 답하게 합니다.

### 왜 이런 개념이 필요한가

LLM은 매우 똑똑해 보이지만 몇 가지 약점이 있습니다.

첫째, 학습 시점 이후의 정보를 모릅니다. 예를 들어 모델이 2025년까지의 데이터로 학습되었다면 2026년에 바뀐 회사 규정은 모델 내부 지식에 없습니다.

둘째, 모르는 내용을 그럴듯하게 말할 수 있습니다. 이를 hallucination이라고 부릅니다. 한국어로는 보통 “환각”이라고 번역하지만, 실무에서는 hallucination이라는 영어 표현도 자주 씁니다. 중요한 것은 모델이 거짓말을 하려는 것이 아니라, 다음 토큰을 자연스럽게 예측하다 보니 없는 내용을 진짜처럼 만들 수 있다는 점입니다.

셋째, 모든 정보를 fine-tuning으로 넣는 것은 비효율적입니다. 사내 문서가 매일 바뀌는데 매일 LLM을 다시 학습시키는 것은 비용이 큽니다. 반면 RAG는 문서 저장소만 업데이트하면 됩니다.

그래서 RAG는 현대 AI 시스템에서 매우 중요합니다. “LLM 단독”이 아니라 “LLM + 검색 시스템 + 문서 저장소 + prompt 구성”으로 실제 답변 시스템을 만드는 핵심 패턴입니다.

### 아주 쉬운 예시

작은 FAQ가 있다고 해 봅시다.

- 문서 A: “환불은 구매 후 7일 이내에 가능합니다.”
- 문서 B: “배송은 보통 2~3일 걸립니다.”
- 문서 C: “비밀번호는 설정 화면에서 변경할 수 있습니다.”

사용자가 묻습니다.

> “어제 산 상품을 환불할 수 있나요?”

RAG가 없는 LLM은 일반적인 상식으로 “가능할 수도 있습니다. 판매자 정책을 확인하세요”라고 답할 수 있습니다. 하지만 RAG 시스템은 먼저 retrieval을 합니다. 질문과 가장 관련 있는 문서 A를 찾습니다. 그다음 prompt에 이렇게 넣습니다.

> 참고자료: 환불은 구매 후 7일 이내에 가능합니다.  
> 질문: 어제 산 상품을 환불할 수 있나요?  
> 답변:

그러면 LLM은 “네, 구매 후 7일 이내라면 환불 가능합니다”처럼 더 근거 있는 답을 만들 수 있습니다.

숫자로 아주 작게 보면, 질문과 문서의 관련 점수가 이렇게 나왔다고 생각할 수 있습니다.

- 질문 ↔ 문서 A: 0.92
- 질문 ↔ 문서 B: 0.20
- 질문 ↔ 문서 C: 0.11

RAG는 보통 점수가 높은 문서 A를 가져와 LLM의 입력에 붙입니다. 이때 붙이는 자료가 generation을 보강하는 augmentation 역할을 합니다.

### 개념 구조와 핵심 포인트

RAG는 보통 다음 단계로 이루어집니다.

1. 문서 준비: PDF, 웹페이지, 매뉴얼, FAQ 같은 원본 문서를 모읍니다.
2. Chunking: 긴 문서를 작은 조각(chunk)으로 나눕니다. 예를 들어 100페이지 문서를 500토큰 단위로 자릅니다.
3. Embedding: 각 chunk를 embedding vector로 바꿉니다. embedding은 문장 의미를 숫자 벡터로 표현한 것입니다.
4. 저장: embedding vector와 원문 chunk를 vector database에 저장합니다.
5. 질문 처리: 사용자의 질문도 embedding vector로 바꿉니다.
6. Retrieval: 질문 벡터와 가까운 문서 벡터를 찾습니다. 이것이 embedding search입니다.
7. Prompt 구성: 검색된 문서를 LLM prompt에 넣습니다.
8. Generation: LLM이 검색된 자료를 바탕으로 답변을 생성합니다.

핵심은 “찾기”와 “쓰기”를 분리한다는 점입니다. 검색 시스템은 관련 자료를 잘 찾는 일을 맡고, LLM은 그 자료를 읽고 자연스러운 답을 만드는 일을 맡습니다.

좋은 RAG 시스템은 단순히 top 3 문서를 가져오는 데서 끝나지 않습니다. 실제로는 다음 문제를 함께 다룹니다.

- chunk를 너무 작게 자르면 문맥이 부족합니다.
- chunk를 너무 크게 자르면 필요 없는 내용까지 prompt에 들어갑니다.
- 관련 없는 문서가 섞이면 LLM이 엉뚱한 답을 할 수 있습니다.
- 검색된 문서가 서로 모순되면 어떤 자료를 믿을지 정해야 합니다.
- LLM이 참고자료 밖의 내용을 덧붙이지 않도록 instruction design이 필요합니다.

### 핵심 수학 포인트

RAG의 수학적 핵심은 “질문과 문서를 숫자 벡터로 바꾸고, 가까운 벡터를 찾는다”입니다.

아주 단순하게 2차원 벡터로 생각해 보겠습니다.

- 질문: “환불 가능한가요?” → q = [1.0, 0.0]
- 문서 A: “환불은 7일 이내 가능” → dA = [0.9, 0.1]
- 문서 B: “배송은 2~3일” → dB = [0.1, 0.8]

질문 q와 문서 A는 방향이 비슷합니다. 질문 q와 문서 B는 방향이 다릅니다. 실제 시스템에서는 2차원이 아니라 384차원, 768차원, 1536차원처럼 훨씬 큰 embedding vector를 씁니다. 하지만 직관은 같습니다. 의미가 비슷한 문장일수록 벡터 공간에서 가깝게 놓이도록 embedding model이 학습되어 있습니다.

가까움을 재는 방법으로 cosine similarity를 많이 씁니다. 복잡하게 외울 필요는 없습니다. 핵심은 “두 벡터가 같은 방향을 바라보는가?”입니다.

예를 들어 두 문장이 완전히 관련 있으면 similarity가 0.9처럼 높고, 관련이 거의 없으면 0.1처럼 낮을 수 있습니다. RAG는 이 점수를 이용해 관련 문서를 고릅니다.

LLM 관점에서는 검색된 문서가 입력 토큰으로 들어갑니다. Transformer 안에서는 이 토큰들이 attention을 통해 질문 토큰과 상호작용합니다. 즉, RAG는 모델의 weight를 바꾸지 않고도 입력 context를 바꾸어 hidden state와 최종 답변을 바꾸는 방법입니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- RAG: Retrieval-Augmented Generation. 검색으로 외부 정보를 가져와 LLM의 답변 생성을 보강하는 방식입니다.
- retrieval: 질문과 관련 있는 문서나 데이터를 찾아오는 단계입니다.
- embedding search: 문장이나 문서를 embedding vector로 바꾼 뒤 가까운 벡터를 찾는 검색 방식입니다.
- augmentation: 모델 입력에 추가 정보를 붙여 답변 품질을 높이는 보강 과정입니다.
- chunk: 긴 문서를 검색하기 좋게 나눈 작은 조각입니다.
- context: LLM이 답변을 만들 때 참고하는 입력 정보입니다.
- hallucination: 모델이 근거 없는 내용을 그럴듯하게 생성하는 현상입니다.

### AI에서 어디에 쓰이는가

RAG는 실제 LLM 서비스에서 매우 자주 쓰입니다.

- 사내 문서 챗봇: 회사 규정, 업무 매뉴얼, 프로젝트 문서를 검색해 답합니다.
- 고객센터 AI: 제품 FAQ와 주문 정책을 찾아 사용자의 질문에 답합니다.
- 법률/의료/금융 보조 시스템: 최신 문서와 근거 자료를 함께 제시합니다.
- 코드베이스 Q&A: 저장소 안의 파일을 검색한 뒤 코드 설명이나 수정 방향을 제안합니다.
- 개인 지식 비서: 노트, 이메일, PDF, 회의록을 검색해 답합니다.

RAG가 중요한 이유는 LLM을 “고정된 기억을 가진 모델”에서 “외부 지식을 찾아 쓰는 시스템”으로 확장하기 때문입니다. 현대 AI 시스템에서는 모델 자체 성능도 중요하지만, 어떤 데이터를 어떻게 검색해서 넣어 주는지가 결과 품질을 크게 좌우합니다.

### 헷갈리기 쉬운 포인트

- RAG는 fine-tuning과 다릅니다. Fine-tuning은 모델 weight를 바꾸는 것이고, RAG는 보통 모델 weight를 그대로 두고 입력 context를 바꿉니다.
- RAG가 있으면 hallucination이 완전히 사라지는 것은 아닙니다. 검색이 틀리거나 LLM이 자료를 잘못 읽으면 여전히 틀릴 수 있습니다.
- 검색된 문서가 많을수록 항상 좋은 것은 아닙니다. 너무 많은 문서는 prompt를 흐리게 만들고 중요한 정보를 묻어 버릴 수 있습니다.
- RAG는 “검색 엔진 + LLM”을 단순히 붙이는 것보다 복잡합니다. chunking, embedding model, ranking, prompt 구성, 평가가 모두 중요합니다.

## 2. 임베딩 모델과 벡터 검색

### 한 줄 직관

Embedding model은 글, 이미지, 코드 같은 데이터를 “의미가 비슷하면 가까운 숫자 위치에 놓이도록” 벡터로 바꾸는 모델입니다.

### 개념 정의

Embedding model은 입력 데이터를 embedding vector로 변환하는 모델입니다. embedding vector는 여러 개의 숫자로 이루어진 표현입니다. 예를 들어 “강아지”라는 단어를 [0.2, 0.8, -0.1] 같은 숫자 묶음으로 표현한다고 생각할 수 있습니다. 실제 embedding은 보통 수백 개 또는 수천 개의 숫자로 이루어져 있습니다.

중요한 점은 숫자 하나하나를 사람이 직접 해석하기 어렵다는 것입니다. 첫 번째 숫자가 “귀여움”, 두 번째 숫자가 “동물성”처럼 딱 정해져 있는 경우는 드뭅니다. 대신 전체 벡터의 위치와 방향이 의미를 담습니다. “강아지”와 “고양이”는 둘 다 반려동물이므로 가까운 위치에 있고, “강아지”와 “비행기 엔진”은 의미가 멀기 때문에 먼 위치에 있을 수 있습니다.

Vector search는 이런 embedding vector들 중에서 질문 벡터와 가장 가까운 항목을 찾는 검색입니다. 전통적인 키워드 검색이 “같은 단어가 들어 있는가?”를 본다면, vector search는 “의미가 비슷한가?”를 봅니다.

### 왜 이런 개념이 필요한가

컴퓨터는 원래 텍스트의 의미를 바로 이해하지 못합니다. “환불”, “반품”, “돈을 돌려받고 싶어요”는 사람에게는 비슷한 말입니다. 하지만 단어만 보면 서로 다릅니다. 키워드 검색은 “환불”이라는 단어가 없으면 관련 문서를 놓칠 수 있습니다.

Embedding model은 이 문제를 줄입니다. 문장을 의미 기반 숫자 표현으로 바꾸면, 표현이 달라도 의미가 비슷한 문장을 찾을 수 있습니다.

예를 들어 사용자가 “돈을 돌려받을 수 있나요?”라고 물었습니다. 문서에는 “환불은 7일 이내 가능합니다”라고 쓰여 있습니다. 두 문장에 정확히 같은 단어가 많지 않아도, embedding space에서는 가까울 수 있습니다. 그래서 RAG, 추천 시스템, 검색, 중복 문서 탐지, 이미지 검색, 클러스터링에서 embedding이 매우 중요합니다.

LLM 내부에서도 embedding은 핵심입니다. 입력 token은 먼저 token embedding으로 바뀌고, Transformer layer를 지나면서 hidden state로 변합니다. 우리가 RAG에서 쓰는 문장 embedding은 별도의 embedding model이 만든 “검색용 의미 벡터”이고, LLM 내부의 hidden state는 “다음 토큰 예측을 위해 문맥을 처리하는 내부 표현”에 가깝습니다. 둘 다 데이터를 벡터로 표현한다는 점에서 연결됩니다.

### 아주 쉬운 예시

2차원 지도에 단어를 놓는다고 생각해 보겠습니다. 실제 embedding은 훨씬 고차원이지만, 처음에는 2차원으로 보면 쉽습니다.

- “강아지” → [1.0, 1.0]
- “고양이” → [1.1, 0.9]
- “햄스터” → [0.9, 1.2]
- “자동차” → [5.0, 5.0]

“강아지”와 “고양이”는 숫자가 비슷합니다. 둘 다 반려동물이고, 문맥에서 함께 등장하는 경우가 많기 때문입니다. “자동차”는 위치가 멀리 떨어져 있습니다.

검색 예시를 보겠습니다.

질문: “반려동물 사료 추천해 줘”

문서 후보:

- 문서 A: “고양이와 강아지 사료 고르는 법”
- 문서 B: “자동차 엔진오일 교체 주기”
- 문서 C: “노트북 배터리 절약 방법”

Embedding model은 질문과 문서 A를 가까운 벡터로 만들 가능성이 큽니다. 그래서 vector search는 문서 A를 가장 먼저 가져옵니다. 키워드가 완전히 같지 않아도 의미가 비슷하면 찾을 수 있다는 점이 핵심입니다.

### 개념 구조와 핵심 포인트

Embedding과 vector search의 전체 흐름은 다음과 같습니다.

1. 입력 준비: 문장, 문서 chunk, 이미지, 코드 조각 등을 준비합니다.
2. Embedding model 통과: 입력을 고정 길이 vector로 바꿉니다. 예를 들어 문장 하나가 768개의 숫자로 바뀝니다.
3. Vector database 저장: 각 vector와 원본 텍스트, 문서 ID, 제목 같은 metadata를 저장합니다.
4. Query embedding: 사용자의 질문도 같은 embedding model로 vector로 바꿉니다.
5. Nearest neighbor search: 질문 vector와 가장 가까운 vector들을 찾습니다.
6. 후처리: 점수, 날짜, 권한, 문서 종류 등을 고려해 최종 결과를 고릅니다.

여기서 중요한 포인트는 “문서와 질문을 같은 embedding space에 넣어야 한다”는 것입니다. 문서 embedding은 모델 A로 만들고 질문 embedding은 모델 B로 만들면 위치 기준이 달라져 검색 품질이 나빠질 수 있습니다. 같은 지도 위에 놓아야 거리를 비교할 수 있습니다.

또 하나 중요한 점은 vector database가 단순한 저장소가 아니라 검색 속도를 위한 구조를 갖고 있다는 것입니다. 문서가 100개라면 모든 벡터와 하나씩 비교해도 됩니다. 하지만 문서가 1억 개라면 매번 전부 비교하기 어렵습니다. 그래서 vector database는 approximate nearest neighbor search 같은 방법으로 “거의 가장 가까운 후보”를 빠르게 찾습니다.

### 핵심 수학 포인트

Embedding vector는 숫자 배열입니다. 예를 들어 어떤 문장 embedding이 3차원이라고 해 보겠습니다.

- q = [1, 0, 0]
- a = [0.9, 0.1, 0]
- b = [0, 1, 0]

q와 a는 방향이 비슷합니다. q와 b는 서로 직각처럼 다릅니다. 이때 cosine similarity는 방향이 얼마나 비슷한지 보는 값입니다.

아주 단순하게 보면:

- 같은 방향이면 similarity가 1에 가깝습니다.
- 전혀 다른 방향이면 0에 가깝습니다.
- 반대 방향이면 -1에 가까울 수 있습니다.

또 다른 방법은 거리(distance)를 보는 것입니다. 예를 들어 1차원 숫자에서 질문이 10이고 문서 후보가 11, 50이라면 11이 더 가깝습니다. 2차원에서는 [1, 1]과 [1.1, 0.9]가 가깝고, [5, 5]는 멉니다. 고차원에서도 원리는 비슷합니다.

Neural network 관점에서 embedding model은 입력 token들을 Transformer나 다른 encoder에 넣고, 마지막 hidden state들을 하나의 문장 vector로 요약합니다. 예를 들어 문장이 token 6개이고 hidden size가 768이면 내부 tensor shape는 대략 [6, 768]처럼 볼 수 있습니다. 문장 embedding을 만들 때는 이 token별 hidden state를 평균내거나, 특수 token의 hidden state를 사용하거나, 별도 pooling layer를 사용해 [768]짜리 vector 하나로 만듭니다.

학습할 때는 비슷한 문장 쌍은 가까워지게 하고, 관련 없는 문장 쌍은 멀어지게 하는 loss를 사용할 수 있습니다. 예를 들어 “환불하고 싶어요”와 “돈을 돌려받고 싶어요”는 가까워지게, “배송이 언제 오나요?”와는 상대적으로 멀어지게 학습합니다. 이때 gradient와 optimizer가 embedding model의 weight를 조정합니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- embedding model: 입력 데이터를 의미를 담은 vector로 바꾸는 모델입니다.
- embedding vector: 텍스트, 이미지, 코드 등을 나타내는 숫자 배열입니다.
- vector database: 많은 embedding vector를 저장하고 빠르게 검색하는 데이터베이스입니다.
- nearest neighbor search: 질문 vector와 가장 가까운 vector를 찾는 검색입니다.
- cosine similarity: 두 vector의 방향이 얼마나 비슷한지 재는 값입니다.
- metadata: vector와 함께 저장하는 문서 제목, 날짜, 권한, URL 같은 부가 정보입니다.
- pooling: token별 hidden state들을 하나의 문장 vector로 요약하는 과정입니다.

### AI에서 어디에 쓰이는가

Embedding model과 vector search는 현대 AI 시스템의 기반 부품처럼 쓰입니다.

- RAG: 질문과 관련 있는 문서를 찾습니다.
- Semantic search: 정확한 키워드가 없어도 의미가 비슷한 문서를 찾습니다.
- 추천 시스템: 사용자가 좋아한 상품이나 콘텐츠와 비슷한 항목을 찾습니다.
- 중복 탐지: 거의 같은 문서, 비슷한 질문, 유사한 고객 문의를 묶습니다.
- 이미지 검색: “빨간 신발 사진” 같은 텍스트와 비슷한 이미지를 찾습니다.
- 클러스터링: 비슷한 문서들을 자동으로 그룹화합니다.

실전에서는 embedding model 선택이 매우 중요합니다. 한국어 문서를 검색할 것인지, 영어 코드를 검색할 것인지, 짧은 FAQ를 검색할 것인지, 긴 논문을 검색할 것인지에 따라 좋은 embedding model이 달라질 수 있습니다. 또한 vector database 설정, chunk 크기, similarity 기준, metadata filter가 전체 시스템 품질에 큰 영향을 줍니다.

### 헷갈리기 쉬운 포인트

- Embedding은 사람이 읽기 쉬운 요약문이 아닙니다. 의미를 숫자 위치로 표현한 것입니다.
- 가까운 vector가 항상 정답은 아닙니다. 비슷해 보이지만 실제 질문 의도와 다를 수 있습니다.
- Keyword search가 쓸모없어진 것은 아닙니다. 실무에서는 keyword search와 vector search를 함께 쓰는 hybrid search도 많습니다.
- Vector database가 LLM 자체는 아닙니다. Vector database는 찾는 역할을 하고, LLM은 읽고 생성하는 역할을 합니다.
- 높은 similarity 점수만 믿으면 안 됩니다. 권한, 최신성, 문서 신뢰도 같은 metadata도 중요합니다.

## 3. 프롬프트 엔지니어링의 한계와 역할

### 한 줄 직관

Prompt engineering은 LLM에게 일을 잘 시키기 위한 “지시문 설계”이지만, 좋은 prompt만으로 모델의 지식, 추론 능력, 데이터 한계를 모두 해결할 수는 없습니다.

### 개념 정의

Prompt engineering은 LLM에 넣는 입력 문장, 지시문, 예시, 출력 형식, 제약 조건을 설계하는 작업입니다. 예를 들어 “요약해 줘”라고만 쓰는 대신 “초등학생도 이해할 수 있게 5문장으로 요약하고, 마지막에 핵심 용어 3개를 정리해 줘”라고 쓰면 모델의 답변이 달라집니다.

Instruction design은 prompt engineering 안에서도 특히 “모델이 무엇을 해야 하는지 명확히 지시하는 부분”을 말합니다. 어떤 역할을 맡길지, 어떤 순서로 생각할지, 어떤 형식으로 답할지, 무엇을 피해야 할지를 정합니다.

Prompt sensitivity는 prompt의 작은 변화에도 모델 출력이 달라지는 현상입니다. 예를 들어 “간단히 설명해 줘”와 “초보자에게 자세히 설명해 줘”는 답변 길이와 깊이를 크게 바꿉니다. 심지어 같은 의미처럼 보이는 문장도 모델에게는 다른 신호가 될 수 있습니다.

### 왜 이런 개념이 필요한가

LLM은 버튼처럼 하나의 정답만 내는 프로그램이 아닙니다. 입력된 token들을 바탕으로 다음 token의 확률분포를 계산하고, 그 확률에 따라 문장을 생성합니다. 그래서 입력 prompt가 바뀌면 내부 hidden state가 바뀌고, attention이 보는 문맥도 바뀌며, 최종 출력도 바뀝니다.

좋은 prompt는 모델이 가진 능력을 더 잘 꺼내게 도와줍니다. 특히 다음 상황에서 중요합니다.

- 출력 형식이 중요할 때: JSON, 표, 체크리스트 등
- 답변 수준을 조절해야 할 때: 초보자용, 전문가용, 짧은 요약, 긴 설명
- 모델이 참고해야 할 자료가 있을 때: RAG로 가져온 문서 사용
- 안전하거나 신중한 답변이 필요할 때: 모르면 모른다고 말하기
- 여러 단계를 거쳐야 할 때: 먼저 분류하고, 그다음 이유를 설명하고, 마지막에 제안하기

하지만 prompt engineering에는 한계도 있습니다. 모델이 모르는 최신 정보를 prompt 없이 알아낼 수는 없습니다. 모델의 context window보다 긴 문서를 모두 완벽히 기억하게 할 수도 없습니다. 계산을 항상 정확하게 하도록 보장하기도 어렵습니다. 그래서 실전 AI 시스템에서는 prompt만이 아니라 RAG, tool use, fine-tuning, evaluation, guardrail, logging을 함께 씁니다.

### 아주 쉬운 예시

같은 모델에게 같은 주제를 물어보되 prompt만 다르게 해 보겠습니다.

Prompt A:

> RAG 설명해 줘.

가능한 답변:

> RAG는 검색 증강 생성으로, 외부 문서를 검색해 답변 품질을 높이는 방법입니다.

Prompt B:

> AI를 처음 배우는 사람에게 RAG를 설명해 줘. 먼저 도서관에서 자료를 찾아보고 리포트를 쓰는 비유를 들고, 그다음 retrieval, augmentation, generation을 각각 한 문장씩 설명해 줘.

가능한 답변은 훨씬 친절하고 구조화됩니다. 모델이 새 지식을 얻은 것은 아니지만, 어떤 방식으로 답해야 하는지 더 분명해졌기 때문입니다.

숫자로 아주 작게 생각해 봅시다. 어떤 질문에 대해 모델이 세 가지 답변 스타일을 낼 수 있다고 합시다.

- 짧은 정의 스타일: 확률 0.45
- 예시 중심 스타일: 확률 0.30
- 수학 중심 스타일: 확률 0.25

Prompt에 “초보자용 예시를 먼저 들어라”라고 쓰면 예시 중심 스타일의 확률이 올라갈 수 있습니다. 즉 prompt는 모델의 다음 token 확률분포를 원하는 방향으로 밀어 주는 신호입니다.

### 개념 구조와 핵심 포인트

Prompt는 보통 여러 요소로 구성됩니다.

1. Role: “너는 친절한 AI 튜터다”처럼 모델의 역할을 정합니다.
2. Task: “이 문서를 요약하라”처럼 해야 할 일을 말합니다.
3. Context: 참고해야 할 배경 정보나 문서를 줍니다.
4. Constraints: “근거 없는 내용은 말하지 마라”, “5문장 이내로 답하라” 같은 제한을 줍니다.
5. Examples: 원하는 입력과 출력 예시를 보여 줍니다. 이를 few-shot prompting이라고 합니다.
6. Output format: JSON, Markdown, bullet list처럼 결과 형식을 지정합니다.
7. Evaluation hint: 좋은 답변의 기준을 알려 줍니다.

Prompt engineering의 핵심은 “모델에게 필요한 정보를 명확히 주고, 원하는 출력 기준을 분명히 알려 주는 것”입니다. 그러나 prompt를 길게 쓴다고 항상 좋아지는 것은 아닙니다. 길고 모순된 prompt는 오히려 모델을 헷갈리게 할 수 있습니다.

실전에서는 prompt를 한 번 작성하고 끝내지 않습니다. 여러 입력 사례로 테스트하고, 실패한 답변을 보며 prompt를 고칩니다. 예를 들어 모델이 자꾸 근거 없는 내용을 덧붙이면 “제공된 context에 없는 내용은 추측하지 말고, 부족하면 ‘자료에 없음’이라고 답하라”는 지시를 추가할 수 있습니다.

### 핵심 수학 포인트

LLM은 prompt를 token sequence로 받습니다. 예를 들어 “환불 규정을 설명해 줘”라는 문장은 여러 token으로 쪼개집니다. 각 token은 embedding vector로 바뀌고, Transformer layer를 지나면서 hidden state가 됩니다.

아주 단순하게 보면 모델은 다음 token의 확률을 계산합니다.

- Prompt: “환불은 구매 후”
- 다음 token 후보:
  - “7일”: 0.60
  - “30일”: 0.20
  - “불가능”: 0.05
  - 기타: 0.15

Prompt에 “다음 참고자료만 사용하라: 환불은 구매 후 7일 이내 가능”이라는 context를 넣으면 “7일”의 확률이 더 커질 수 있습니다. 즉 prompt는 모델의 파라미터를 직접 바꾸지는 않지만, 입력을 바꾸어 hidden state와 token probability를 바꿉니다.

Prompt sensitivity도 이 관점에서 이해할 수 있습니다. prompt의 단어 하나가 바뀌면 token embedding이 달라지고, attention 흐름이 달라집니다. 작은 차이가 뒤쪽 생성 과정에서 커질 수 있습니다. 특히 긴 답변에서는 초반 token 선택이 이후 문맥을 계속 바꾸므로 결과 차이가 커질 수 있습니다.

하지만 prompt에는 수학적 한계가 있습니다. 모델 weight 안에 없는 세부 지식은 prompt로 새로 생기지 않습니다. 긴 문서를 넣어도 context window라는 길이 제한이 있습니다. 계산 문제에서는 token probability가 자연스러운 답을 고르는 방식이기 때문에, 정확한 산술은 calculator tool이나 코드 실행이 더 안전할 수 있습니다. 그래서 prompt는 optimizer나 gradient처럼 모델을 학습시키는 도구가 아니라, 이미 학습된 모델의 동작을 입력 차원에서 조절하는 도구라고 볼 수 있습니다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- prompt engineering: LLM이 원하는 방식으로 답하도록 입력 지시문을 설계하는 작업입니다.
- instruction design: 모델에게 작업, 제약, 출력 기준을 명확히 지시하는 설계입니다.
- prompt sensitivity: prompt의 작은 변화에도 출력이 크게 달라질 수 있는 현상입니다.
- system prompt: 모델의 전반적 역할과 규칙을 정하는 상위 지시문입니다.
- few-shot prompting: 원하는 입력-출력 예시를 몇 개 보여 주고 따라 하게 하는 방식입니다.
- context window: 모델이 한 번에 읽을 수 있는 token 길이 제한입니다.
- tool use: 모델이 검색, 계산기, 코드 실행, API 호출 같은 외부 도구를 사용하게 하는 방식입니다.

### AI에서 어디에 쓰이는가

Prompt engineering은 거의 모든 LLM 기반 제품에 들어갑니다.

- 챗봇: 말투, 답변 길이, 금지 행동, 도움 방식 등을 정합니다.
- RAG 시스템: 검색된 문서를 어떻게 읽고 답할지 지시합니다.
- 데이터 추출: 문서에서 날짜, 금액, 이름을 JSON 형식으로 뽑게 합니다.
- 코딩 도우미: 수정 범위, 테스트 방식, 코드 스타일을 알려 줍니다.
- 평가 자동화: 모델 답변을 기준에 따라 채점하게 합니다.
- Agent 시스템: 계획 수립, tool use, 오류 처리 규칙을 정합니다.

현대 AI 시스템에서 prompt engineering은 중요하지만 “전부”는 아닙니다. 좋은 prompt는 모델의 능력을 안정적으로 끌어내는 인터페이스입니다. 그러나 데이터가 없으면 RAG가 필요하고, 반복되는 특정 형식 작업이 많으면 fine-tuning이 필요할 수 있고, 정확한 계산은 tool이 필요하며, 품질 관리는 evaluation이 필요합니다.

### 헷갈리기 쉬운 포인트

- Prompt engineering은 마법 주문이 아닙니다. 모델이 가진 능력과 입력 정보의 범위 안에서 결과를 조절합니다.
- 길고 복잡한 prompt가 항상 좋은 prompt는 아닙니다. 명확하고 모순 없는 prompt가 더 중요합니다.
- Prompt만으로 최신 지식을 보장할 수 없습니다. 최신 정보는 retrieval이나 tool use가 필요합니다.
- Prompt가 잘 작동해도 모든 입력에서 항상 안정적이라고 볼 수 없습니다. 다양한 테스트와 evaluation이 필요합니다.
- Prompt engineering과 fine-tuning은 다릅니다. Prompt는 입력을 바꾸는 것이고, fine-tuning은 모델 weight를 학습으로 바꾸는 것입니다.

### 1. RAG에서 retrieval과 generation은 각각 어떤 역할을 하나요? FAQ 예시를 떠올려 설명해 보세요.

**정답**

RAG에서 `retrieval`은 질문과 관련 있는 자료를 찾아오는 단계이고, `generation`은 그 자료를 바탕으로 LLM이 자연스러운 답변을 만들어 내는 단계입니다.

즉, RAG는 이렇게 나눠서 볼 수 있습니다.

- `retrieval`: “어떤 자료를 참고해야 하지?”를 해결
- `generation`: “그 자료를 읽고 어떻게 답해야 하지?”를 해결

FAQ 예시로 보면, 사용자가 “어제 산 상품을 환불할 수 있나요?”라고 물었을 때 retrieval은 “환불은 구매 후 7일 이내 가능합니다”라는 FAQ 문서를 찾아오고, generation은 그 문서를 바탕으로 “네, 어제 구매하셨다면 7일 이내이므로 환불 가능할 수 있습니다”처럼 답변을 만듭니다.

**설명**

RAG는 `Retrieval-Augmented Generation`의 줄임말입니다. 한국어로 풀면 “검색으로 보강한 생성”입니다.

LLM은 문장을 잘 만들지만, 모든 최신 정보나 회사 내부 문서를 스스로 알고 있지는 않습니다. 예를 들어 회사 환불 정책이 어제 바뀌었다면, LLM의 기존 지식만으로는 정확히 답하기 어렵습니다.

그래서 RAG는 먼저 외부 문서 저장소에서 관련 자료를 찾습니다. 이 과정이 `retrieval`입니다. 그다음 찾은 문서를 prompt에 넣어 LLM에게 보여 줍니다. LLM은 그 내용을 읽고 답변을 만듭니다. 이 과정이 `generation`입니다.

중요한 점은 “찾는 일”과 “말하는 일”이 분리되어 있다는 것입니다. 검색 시스템은 관련 문서를 잘 찾아야 하고, LLM은 그 문서를 잘 읽고 사용자에게 이해하기 쉬운 답을 만들어야 합니다.

**예시**

작은 FAQ가 있다고 해 봅시다.

- FAQ A: 환불은 구매 후 7일 이내 가능합니다.
- FAQ B: 배송은 보통 2~3일 걸립니다.
- FAQ C: 비밀번호는 설정 화면에서 변경할 수 있습니다.

사용자 질문:

“어제 산 상품을 환불할 수 있나요?”

이때 retrieval은 FAQ A를 고릅니다. 질문의 핵심이 “환불”이기 때문입니다.

그다음 generation은 이렇게 답합니다.

“네, FAQ에 따르면 환불은 구매 후 7일 이내에 가능합니다. 어제 구매하셨다면 일반적으로 환불 가능 기간 안에 있습니다.”

여기서 FAQ A를 찾는 것이 retrieval이고, 최종 문장을 만드는 것이 generation입니다.

**실전 연결**

실제 LLM 서비스에서는 RAG가 매우 중요합니다. 사내 문서 챗봇, 고객센터 AI, 법률 문서 검색, 코드베이스 Q&A 같은 시스템은 대부분 LLM 혼자 답하게 하지 않습니다. 먼저 관련 문서를 검색하고, 그 문서를 LLM의 context로 넣은 뒤 답하게 합니다. 이렇게 하면 hallucination, 즉 근거 없는 답변을 줄이고 최신 정보나 내부 자료를 반영할 수 있습니다.

### 2. Embedding model이 문장을 vector로 바꾸면, 키워드가 정확히 같지 않아도 검색할 수 있는 이유는 무엇인가요?

**정답**

Embedding model은 문장의 “겉으로 보이는 단어”만 보는 것이 아니라, 문장의 “의미”를 숫자 vector로 표현하기 때문입니다.

그래서 단어가 정확히 같지 않아도 의미가 비슷하면 embedding vector가 가까운 위치에 놓입니다. Vector search는 이 가까운 vector를 찾기 때문에, 키워드가 달라도 관련 문서를 검색할 수 있습니다.

예를 들어 “환불하고 싶어요”와 “돈을 돌려받고 싶어요”는 단어는 다르지만 의미는 비슷합니다. 좋은 embedding model은 두 문장을 비슷한 위치의 vector로 만들 수 있습니다.

**설명**

전통적인 키워드 검색은 보통 같은 단어가 들어 있는지를 중요하게 봅니다. 예를 들어 사용자가 “돈을 돌려받을 수 있나요?”라고 물었는데 문서에는 “환불은 7일 이내 가능합니다”라고 쓰여 있다면, 단순 키워드 검색은 “돈”, “돌려받다” 같은 단어가 없어서 이 문서를 약하게 볼 수 있습니다.

하지만 embedding model은 문장을 숫자 vector로 바꿉니다. 이 vector는 문장의 의미를 담은 숫자 위치라고 생각하면 됩니다.

예를 들어 아주 단순하게 표현하면 다음과 같습니다.

- “환불하고 싶어요” → [1.0, 0.1]
- “돈을 돌려받고 싶어요” → [0.9, 0.2]
- “배송은 언제 오나요?” → [0.1, 1.0]

앞의 두 문장은 숫자 위치가 가깝습니다. 둘 다 “환불”과 관련된 의미이기 때문입니다. 반면 배송 질문은 다른 의미라서 멀리 떨어져 있습니다.

이때 vector search는 질문 vector와 가장 가까운 문서 vector를 찾습니다. 이 과정을 `nearest neighbor search`, 즉 가장 가까운 이웃 찾기라고 부릅니다.

가까움을 재는 방법으로는 `cosine similarity`를 많이 씁니다. Cosine similarity는 두 vector가 얼마나 비슷한 방향을 가리키는지 보는 값입니다. 방향이 비슷하면 의미가 비슷하다고 판단할 수 있습니다.

**예시**

사용자 질문:

“돈을 돌려받을 수 있나요?”

문서 후보:

- 문서 A: 환불은 구매 후 7일 이내 가능합니다.
- 문서 B: 배송은 보통 2~3일 걸립니다.
- 문서 C: 비밀번호는 설정에서 변경할 수 있습니다.

질문에는 “환불”이라는 단어가 직접 나오지 않았습니다. 하지만 “돈을 돌려받다”는 의미상 환불과 가깝습니다.

Embedding model이 잘 작동하면 질문 vector는 문서 A의 vector와 가깝게 놓입니다. 그래서 vector search는 문서 A를 관련 문서로 찾아낼 수 있습니다.

**실전 연결**

이 원리는 RAG의 핵심 부품입니다. 사용자가 항상 문서에 적힌 정확한 단어로 질문하지는 않습니다. 고객은 “환불” 대신 “돈 돌려받기”, “취소하면 입금되나요?”, “결제 취소 가능해요?”처럼 다양하게 말합니다. Embedding model과 vector database를 사용하면 이런 표현 차이를 어느 정도 흡수할 수 있습니다. 그래서 semantic search, 추천 시스템, 중복 질문 탐지, 문서 클러스터링, 이미지 검색 등에서도 embedding이 널리 쓰입니다.

### 3. Prompt engineering이 중요한 이유와, prompt만으로 해결하기 어려운 한계 한 가지를 각각 말해 보세요.

**정답**

Prompt engineering이 중요한 이유는 LLM에게 작업 방식, 답변 수준, 출력 형식, 제약 조건을 명확히 알려 주면 더 원하는 방향의 답변을 얻을 수 있기 때문입니다.

하지만 prompt만으로는 모델이 모르는 최신 정보나 외부 문서를 자동으로 알게 만들 수 없습니다. 그런 정보가 필요하면 RAG, tool use, 검색 시스템 같은 다른 방법이 필요합니다.

정리하면 다음과 같습니다.

- 중요한 이유: LLM의 답변 방향과 형식을 조절할 수 있음
- 한계: prompt만으로 없는 지식, 최신 정보, 긴 문서 전체 기억, 정확한 계산을 완전히 해결할 수는 없음

**설명**

Prompt engineering은 LLM에 넣는 지시문을 설계하는 작업입니다. 단순히 “설명해 줘”라고 쓰는 것과 “AI를 처음 배우는 사람에게 쉬운 비유를 먼저 들고, 핵심 용어 3개를 정리한 뒤, 마지막에 실전 예시를 붙여 줘”라고 쓰는 것은 결과가 많이 다릅니다.

LLM은 prompt를 token sequence로 읽고, 그 입력을 바탕으로 다음 token의 확률을 계산합니다. 그래서 prompt가 달라지면 내부 hidden state가 달라지고, attention이 보는 정보도 달라지고, 최종 답변도 달라질 수 있습니다.

이 현상을 `prompt sensitivity`라고 합니다. Prompt sensitivity는 prompt의 작은 차이에도 출력이 달라지는 성질입니다.

예를 들어 “간단히 설명해 줘”라고 하면 짧은 답이 나올 가능성이 높고, “초보자에게 예시 중심으로 자세히 설명해 줘”라고 하면 더 친절하고 긴 답이 나올 가능성이 높습니다.

하지만 prompt engineering은 마법이 아닙니다. 모델의 weight 안에 없는 지식을 갑자기 만들어 내지는 못합니다. 예를 들어 오늘 바뀐 회사 정책을 prompt에 넣어 주지 않았는데 모델이 정확히 알 수는 없습니다. 이런 경우에는 검색으로 문서를 가져오는 RAG가 필요합니다.

또한 복잡한 계산은 prompt만으로 항상 정확히 처리하기 어렵습니다. 이런 경우에는 calculator tool이나 코드 실행 같은 tool use가 더 안전합니다.

**예시**

같은 질문이라도 prompt를 다르게 쓰면 답이 달라집니다.

Prompt A:

“RAG 설명해 줘.”

가능한 답변:

“RAG는 검색 증강 생성으로, 외부 문서를 검색해 답변 품질을 높이는 방법입니다.”

Prompt B:

“AI를 처음 배우는 사람에게 RAG를 설명해 줘. 도서관에서 자료를 찾아보고 리포트를 쓰는 비유를 먼저 들고, retrieval, augmentation, generation을 각각 한 문장씩 설명해 줘.”

가능한 답변은 훨씬 친절하고 구조화됩니다.

하지만 만약 회사의 최신 환불 정책이 문서에만 있고 모델은 그 문서를 보지 못했다면, 아무리 prompt를 잘 써도 정확한 정책을 보장하기 어렵습니다. 이때는 RAG로 최신 FAQ를 검색해서 prompt에 넣어 주어야 합니다.

**실전 연결**

실제 LLM 제품에서 prompt engineering은 거의 항상 필요합니다. 챗봇의 말투를 정하고, JSON 형식으로 데이터를 뽑게 하고, RAG에서 “검색된 문서만 근거로 답하라”고 지시하고, 코딩 도우미에게 수정 범위와 스타일을 알려 주는 데 쓰입니다. 하지만 좋은 AI 시스템은 prompt만으로 만들지 않습니다. 최신 지식은 RAG, 정확한 계산은 tool use, 반복적인 특정 작업은 fine-tuning, 품질 관리는 evaluation과 logging으로 함께 다룹니다. Prompt engineering은 LLM을 잘 움직이게 하는 중요한 인터페이스이지만, 전체 시스템 중 하나의 부품으로 이해하는 것이 좋습니다.
