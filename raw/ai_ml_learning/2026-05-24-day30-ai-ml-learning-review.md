## 1. 평가와 벤치마크

### 한 줄 직관

모델 평가는 “이 모델이 진짜 일을 잘하는지 시험해 보는 과정”이고, 벤치마크(benchmark)는 여러 모델을 같은 시험지로 비교하기 위한 공통 시험장이다.

### 개념 정의

평가(eval)는 AI 모델의 출력이 원하는 기준에 얼마나 맞는지 측정하는 일이다. 예를 들어 번역 모델이면 번역이 자연스러운지, 분류 모델이면 정답 클래스를 잘 맞히는지, LLM이면 질문에 맞는 답을 정확하고 안전하게 하는지를 본다.

벤치마크(benchmark)는 미리 정해진 데이터셋, 문제 형식, 채점 기준을 묶어 놓은 평가 세트다. 수능처럼 모두가 같은 문제를 풀어야 점수를 비교할 수 있듯이, AI 모델도 같은 benchmark를 풀어야 “모델 A가 모델 B보다 어떤 작업에서 더 낫다”라고 말할 수 있다.

하지만 AI 평가는 단순히 점수 하나로 끝나지 않는다. 모델이 수학 문제는 잘 풀지만 긴 문서 요약은 약할 수 있고, 영어는 잘하지만 한국어는 약할 수 있다. 그래서 실제 평가에서는 여러 task metric, human evaluation, 안전성 평가, 비용과 latency까지 함께 본다.

### 왜 이런 개념이 필요한가

모델을 학습할 때는 loss가 내려가면 좋아 보인다. 하지만 loss가 낮다고 해서 실제 사용자가 만족한다는 뜻은 아니다. 예를 들어 챗봇이 학습 데이터에서는 다음 단어를 잘 맞혔지만, 실제 질문에는 엉뚱한 답을 할 수 있다. 그래서 “학습 중의 숫자”와 “실제 사용 성능”을 이어 주는 평가가 필요하다.

또한 모델 개발은 선택의 연속이다. 더 큰 모델을 쓸지, 작은 모델을 fine-tuning할지, RAG를 붙일지, prompt만 바꿀지 결정해야 한다. 평가가 없으면 이 선택은 감에 의존한다. 반대로 평가가 있으면 “정확도는 3% 올랐지만 latency가 2배 느려졌다”처럼 구체적으로 비교할 수 있다.

LLM 시대에는 특히 평가가 더 중요하다. LLM의 답은 하나의 정답으로 딱 떨어지지 않는 경우가 많다. “좋은 요약”, “친절한 답변”, “근거 있는 답변”은 사람이 봐야 판단되는 부분도 많다. 그래서 자동 metric과 human evaluation을 함께 설계하는 능력이 실제 AI 시스템에서 핵심이 된다.

### 아주 쉬운 예시

스팸 메일 분류 모델이 있다고 하자. 테스트 메일 10개 중 진짜 스팸이 4개이고 정상 메일이 6개다.

모델이 10개 중 8개를 맞혔다면 accuracy는 80%다. 겉보기에는 좋아 보인다. 그런데 틀린 2개가 모두 “정상 메일을 스팸으로 잘못 분류한 경우”라면 문제가 크다. 사용자는 중요한 메일을 놓칠 수 있다.

이번에는 LLM 고객상담 봇을 생각해 보자. 질문 5개를 준비했다.

1. 환불 정책을 물어본다.
2. 배송 지연을 물어본다.
3. 개인정보 삭제를 요청한다.
4. 화난 고객이 불만을 말한다.
5. 정책에 없는 내용을 요구한다.

자동 metric으로는 답변에 필요한 키워드가 들어갔는지 볼 수 있다. 하지만 공손한지, 과장하지 않았는지, 실제 정책 밖의 말을 지어내지 않았는지는 사람이 직접 평가해야 할 수 있다. 이것이 human evaluation이 필요한 이유다.

### 개념 구조와 핵심 포인트

평가를 볼 때는 보통 네 가지를 나누어 생각하면 쉽다.

첫째, 무엇을 평가할 것인가다. 분류, 번역, 요약, 검색, 코딩, 추론, 안전성처럼 task를 먼저 정한다.

둘째, 어떤 데이터로 평가할 것인가다. 학습에 사용한 데이터로 평가하면 모델이 이미 본 문제를 다시 푸는 셈이 될 수 있다. 그래서 보통 validation set, test set, 실제 사용자 로그에서 분리한 평가셋을 쓴다.

셋째, 어떤 metric으로 볼 것인가다. 분류에서는 accuracy, precision, recall, F1 같은 task metric을 쓸 수 있다. 생성 모델에서는 exact match, BLEU, ROUGE, pass@k, win rate, human preference 같은 지표를 쓴다.

넷째, 점수를 어떻게 해석할 것인가다. benchmark 점수가 높아도 실제 제품에서 항상 좋은 것은 아니다. benchmark가 너무 오래되어 모델이 이미 비슷한 문제를 학습했을 수도 있고, 평가 데이터가 실제 사용자 질문과 다를 수도 있다. 그래서 좋은 평가는 “공통 benchmark + 우리 서비스에 맞춘 private eval + 실제 사용자 feedback loop”를 함께 사용한다.

### 핵심 수학 포인트

가장 기본적인 평가는 “전체 중 몇 개를 맞혔는가”에서 시작한다.

예를 들어 100문제 중 82문제를 맞히면 accuracy는 82/100 = 0.82, 즉 82%다. 이 수식은 단순하지만 중요한 기준선이 된다.

하지만 모든 오류가 같은 비용을 갖지는 않는다. 병원 진단 모델에서 “아픈 사람을 건강하다고 판단하는 오류”는 매우 위험하다. 이때는 recall이 중요할 수 있다. recall은 실제 양성 중 모델이 양성으로 찾아낸 비율이다. 실제 환자 10명 중 9명을 찾았다면 recall은 9/10 = 90%다.

LLM 평가에서는 확률과 평균도 많이 등장한다. 여러 질문에 대한 점수를 각각 계산한 뒤 평균을 낸다. 예를 들어 3개 답변의 점수가 1점, 0점, 1점이면 평균 점수는 (1+0+1)/3 = 0.67이다. 이 평균이 모델 버전끼리 비교하는 기준이 된다.

학습 중 loss는 토큰 예측이 얼마나 틀렸는지를 수치화한다. 하지만 eval metric은 실제 task 성공을 본다. 그래서 loss가 조금 좋아졌더라도 benchmark나 human evaluation에서 나빠질 수 있다. 실무에서는 loss, task metric, human preference, latency, 비용을 함께 보는 습관이 필요하다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- benchmark: 여러 모델을 같은 조건에서 비교하기 위한 표준 평가 세트나 과제 묶음.
- eval: evaluation의 줄임말. 모델 성능을 측정하는 절차 전체를 말한다.
- human evaluation: 사람이 직접 모델 출력을 보고 품질을 평가하는 방식.
- task metric: 특정 작업에 맞춘 점수 기준. 예: accuracy, F1, ROUGE, pass@k.

### AI에서 어디에 쓰이는가

평가는 모델 선택, prompt 개선, fine-tuning 여부 판단, RAG 품질 점검, 배포 전 안전성 검증에 쓰인다. 예를 들어 embedding 검색 시스템에서는 “정답 문서가 top-5 안에 들어오는가”를 평가할 수 있다. Attention 기반 LLM에서는 답변이 길어질수록 hidden states와 context 사용이 복잡해지므로, 긴 문맥 질의응답 benchmark로 실제 성능을 따로 본다.

또한 모델이 업데이트될 때마다 regression test처럼 eval을 돌린다. 새 모델이 평균 점수는 좋아졌지만 특정 고객 유형에서 나빠질 수 있기 때문이다. 그래서 현대 AI 제품은 “모델을 한 번 학습하고 끝”이 아니라 “계속 평가하고, 실패 사례를 모으고, 다시 개선하는” 구조로 움직인다.

### 헷갈리기 쉬운 포인트

benchmark 점수는 모델의 전체 능력을 완전히 대표하지 않는다. 시험 성적이 높아도 실제 업무를 잘한다고 보장할 수 없는 것과 비슷하다.

또 eval dataset이 학습 데이터와 섞이면 점수가 부풀려질 수 있다. 이것을 data contamination이라고 부른다. LLM benchmark에서 특히 자주 문제 된다.

마지막으로 human evaluation이 항상 완벽한 것도 아니다. 평가자마다 기준이 다를 수 있고, 비용이 많이 든다. 그래서 명확한 rubric, 여러 평가자, 자동 metric과의 조합이 필요하다.

## 2. 서빙과 추론 최적화

### 한 줄 직관

서빙(serving)은 학습된 모델을 실제 사용자가 부를 수 있게 운영하는 일이고, 추론 최적화는 같은 모델이 더 빠르고 싸게 답하도록 만드는 기술이다.

### 개념 정의

모델을 학습(training)하는 일과 모델을 서비스에서 실행(inference)하는 일은 다르다. 학습은 많은 데이터를 보며 파라미터를 업데이트하는 과정이다. 추론(inference)은 이미 학습된 파라미터를 사용해서 새 입력에 대한 출력을 만드는 과정이다.

서빙(serving)은 이 추론을 API, 앱, 검색 시스템, 챗봇 같은 실제 환경에서 안정적으로 제공하는 것이다. 사용자가 “이 문장을 요약해 줘”라고 요청하면 서버가 입력을 받고, tokenizer로 토큰을 만들고, 모델을 실행하고, 결과 토큰을 다시 문장으로 바꿔 돌려준다.

추론 최적화는 이 과정을 더 빠르게, 더 많은 사용자에게, 더 낮은 비용으로 제공하기 위한 방법이다. 여기에는 latency 줄이기, throughput 늘리기, quantization, batching, KV cache, GPU 메모리 관리 등이 포함된다.

### 왜 이런 개념이 필요한가

연구 노트북에서 모델이 한 번 잘 돌아가는 것과 실제 서비스에서 많은 사용자를 처리하는 것은 완전히 다른 문제다. 사용자는 답변을 30초 기다리고 싶어 하지 않는다. 회사는 GPU 비용을 무한히 낼 수 없다. 그래서 모델 품질만큼이나 빠르고 안정적인 serving이 중요하다.

LLM은 특히 추론 비용이 크다. 답변을 한 토큰씩 생성하기 때문이다. “안녕하세요” 같은 짧은 답은 금방 나오지만, 2,000토큰짜리 보고서를 만들면 모델을 반복해서 많이 실행해야 한다. 이때 KV cache를 잘 쓰지 않으면 이미 계산한 attention 정보를 계속 다시 계산하게 되어 매우 비효율적이다.

또 모델이 커질수록 GPU 메모리도 많이 필요하다. 70B 모델을 그대로 FP16으로 올리면 매우 큰 메모리가 필요하다. quantization을 사용하면 숫자 표현을 더 작게 만들어 메모리를 줄일 수 있고, 때로는 속도도 좋아진다. 단, 너무 많이 줄이면 품질이 떨어질 수 있다.

### 아주 쉬운 예시

식당 비유로 생각해 보자. 학습은 요리사가 레시피를 배우는 과정이다. 서빙은 손님이 주문했을 때 실제 음식을 빠르게 내는 과정이다. 레시피를 잘 아는 것도 중요하지만, 점심시간에 손님 100명이 몰리면 주방 동선, 재료 준비, 주문 묶음 처리도 중요하다.

숫자로 보자. 어떤 LLM이 한 요청에 평균 2초가 걸리고, 서버가 한 번에 1명만 처리할 수 있다면 10명은 대략 20초를 기다려야 한다. 그런데 batching으로 여러 요청을 묶어 GPU에서 동시에 처리하면, 10명을 6초 안에 처리할 수도 있다. 각 사용자의 체감 latency는 상황에 따라 달라지지만, 전체 throughput은 좋아진다.

KV cache 예시도 아주 작게 볼 수 있다. 모델이 “나는 오늘 학교에” 다음 단어를 만들고, 이어서 “갔다”를 만들려고 한다. 두 번째 단어를 만들 때 앞의 “나는 오늘 학교에”에 대한 attention 계산을 완전히 다시 하면 낭비다. KV cache는 앞에서 계산한 key/value 정보를 저장해 두었다가 다음 토큰 생성 때 재사용한다.

### 개념 구조와 핵심 포인트

서빙 시스템은 보통 입력 처리, 모델 실행, 출력 처리, 모니터링으로 나뉜다.

입력 처리에서는 텍스트를 token으로 바꾸고, 이미지라면 tensor 형태로 변환한다. 모델은 숫자 tensor를 받기 때문에 shape이 중요하다. 예를 들어 batch size가 4이고 sequence length가 128이면 입력 tensor shape은 대략 [4, 128]처럼 생각할 수 있다.

모델 실행에서는 GPU나 CPU에서 forward pass가 일어난다. 학습과 달리 gradient를 계산하지 않는다. 즉 optimizer도 쓰지 않고 파라미터 업데이트도 하지 않는다. 그래서 inference는 보통 training보다 메모리가 덜 들지만, 많은 요청을 빠르게 처리해야 하므로 다른 최적화가 필요하다.

출력 처리에서는 생성된 token을 문장으로 바꾸고, 필요하면 후처리나 safety filter를 적용한다. 운영 단계에서는 latency, throughput, error rate, GPU memory, queue length를 계속 관찰한다.

핵심은 trade-off다. 모델을 작게 만들면 빠르고 싸지만 성능이 떨어질 수 있다. 큰 모델은 답이 좋을 수 있지만 느리고 비싸다. quantization은 메모리를 줄이지만 정밀도 손실이 생길 수 있다. batching은 throughput을 높이지만 어떤 요청의 latency를 늘릴 수 있다.

### 핵심 수학 포인트

추론 최적화에서 가장 먼저 보는 숫자는 latency와 throughput이다.

latency는 한 요청이 들어와서 답이 나올 때까지 걸리는 시간이다. 예를 들어 한 질문에 0.8초가 걸리면 latency는 0.8초다.

throughput은 단위 시간에 처리한 양이다. 1초에 20개 요청을 처리하면 throughput은 20 requests/sec다. LLM에서는 1초에 생성한 token 수, 즉 tokens/sec도 자주 본다.

quantization은 숫자를 더 적은 bit로 표현하는 것이다. 예를 들어 원래 가중치 하나를 16-bit로 저장했는데 8-bit로 줄이면, 단순 계산으로 메모리를 약 절반으로 줄일 수 있다. 1,000개의 숫자가 각각 16-bit면 16,000bit가 필요하지만, 8-bit면 8,000bit가 필요하다.

KV cache는 attention 계산량과 관련된다. Transformer는 새 token을 만들 때 이전 token들과의 관계를 본다. sequence length가 길어질수록 attention 계산이 커진다. 이미 지나간 token의 key/value를 저장하면 다음 token 생성 때 중복 계산을 줄일 수 있다. 그래서 긴 대화, 긴 문서 요약, agent workflow에서 KV cache가 중요하다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- serving: 학습된 모델을 API나 제품에서 사용할 수 있게 운영하는 것.
- latency: 요청 하나가 들어와 결과가 나올 때까지 걸리는 시간.
- throughput: 일정 시간 동안 처리할 수 있는 요청 수나 token 수.
- quantization: 모델의 숫자 표현 bit 수를 줄여 메모리와 비용을 낮추는 기법.
- KV cache: Transformer가 이전 token의 key/value 계산 결과를 저장해 다음 token 생성에 재사용하는 캐시.

### AI에서 어디에 쓰이는가

챗봇, 검색 추천, 이미지 생성, 음성 인식, 코드 자동완성 모두 serving이 필요하다. 예를 들어 RAG 챗봇은 사용자 질문을 embedding으로 바꾸고, vector database에서 관련 문서를 찾고, LLM이 그 문서를 보고 답한다. 이 전체 과정의 latency가 길면 사용자는 느리다고 느낀다.

LLM serving에서는 KV cache와 batching이 실전 핵심이다. Attention은 이전 token 정보를 계속 참조하므로, 긴 문맥을 다룰수록 메모리 관리가 중요해진다. 또한 hidden states는 모델 내부에서 token별 의미를 담은 벡터인데, 이 벡터들이 여러 layer를 지나며 계산되기 때문에 큰 모델일수록 GPU 비용이 커진다.

실제 운영에서는 “가장 똑똑한 모델 하나”만 쓰지 않을 때도 많다. 쉬운 질문은 작은 모델이 처리하고, 어려운 질문만 큰 모델로 보내는 routing을 쓸 수 있다. 이렇게 하면 품질과 비용 사이의 균형을 잡을 수 있다.

### 헷갈리기 쉬운 포인트

latency와 throughput은 같은 말이 아니다. 한 사람에게 빨리 답하는 것과 많은 사람을 동시에 처리하는 것은 다르다. 어떤 최적화는 throughput은 높이지만 개별 latency는 늘릴 수 있다.

quantization은 무조건 공짜 성능 향상이 아니다. 메모리는 줄지만, 모델 출력 품질이 조금 흔들릴 수 있다. 특히 수학, 코드, 긴 추론 작업에서는 정밀도 손실이 더 민감할 수 있다.

KV cache는 모델의 “기억력” 자체가 아니다. 대화 내용을 이해해서 장기 기억으로 저장하는 것이 아니라, 같은 생성 과정에서 이전 token의 attention 계산을 재사용하는 실행 최적화다.

## 3. AI 시스템 설계 전체 그림

### 한 줄 직관

AI 시스템은 모델 하나가 아니라, 데이터가 들어오고 학습되고 배포되고 사용자 반응으로 다시 개선되는 전체 흐름이다.

### 개념 정의

AI 시스템 설계는 데이터 수집부터 모델 학습, 평가, 배포, 모니터링, feedback loop까지 이어지는 전체 구조를 설계하는 일이다. 많은 초보자는 “AI = 모델”이라고 생각하지만, 실제 제품에서는 모델이 한 부품일 뿐이다.

데이터 파이프라인(data pipeline)은 원천 데이터가 정리되어 학습이나 검색에 쓸 수 있는 형태가 되는 흐름이다. Training stack은 모델을 학습시키는 코드, 데이터 로더, GPU, loss, gradient, optimizer, checkpoint 관리 등을 포함한다. Inference stack은 학습된 모델을 실제 요청에 대해 실행하는 serving 구조다. Feedback loop는 사용자의 반응, 실패 사례, 평가 결과를 다시 데이터와 모델 개선으로 연결하는 순환 구조다.

좋은 AI 시스템은 이 네 가지가 끊기지 않게 연결되어 있다. 데이터가 나쁘면 모델이 좋아지기 어렵고, 학습이 잘되어도 serving이 느리면 제품이 실패할 수 있으며, 배포 후 feedback이 없으면 문제를 계속 놓친다.

### 왜 이런 개념이 필요한가

모델 성능만 보고 시스템을 만들면 실제 운영에서 자주 막힌다. 예를 들어 노트북에서 정확도 95%가 나온 이미지 분류 모델이 있다고 하자. 그런데 실제 서비스에서는 사용자가 어두운 사진을 올리고, 이미지 크기가 제각각이고, 서버는 트래픽을 버티지 못할 수 있다. 이때 문제는 모델 구조 하나가 아니라 데이터, 전처리, 평가, serving, 모니터링 전체에 있다.

LLM 앱도 마찬가지다. 단순히 “GPT API를 부른다”가 끝이 아니다. 사용자 질문을 어떻게 저장할지, 개인정보를 어떻게 제거할지, 어떤 문서를 retrieval할지, prompt를 어떻게 version 관리할지, 답변 실패를 어떻게 평가할지, 비용 폭증을 어떻게 막을지 설계해야 한다.

그래서 현대 AI 엔지니어링은 모델 이해와 시스템 이해가 함께 필요하다. embedding, attention, hidden states 같은 모델 내부 개념도 중요하지만, 그것이 데이터 파이프라인과 inference stack 안에서 어떻게 쓰이는지 알아야 실제 문제를 해결할 수 있다.

### 아주 쉬운 예시

학교 급식 시스템으로 비유해 보자. 좋은 급식을 만들려면 요리사만 있으면 안 된다. 식재료 주문, 보관, 조리, 배식, 학생 만족도 조사, 다음 메뉴 개선이 모두 필요하다.

AI 고객상담 봇도 비슷하다.

1. 고객센터 문서와 FAQ를 모은다. 이것이 data pipeline의 시작이다.
2. 문서를 잘라 chunk로 만들고 embedding을 계산해 저장한다.
3. 사용자 질문이 오면 비슷한 문서를 찾아 LLM에 넣는다. 이것이 inference stack이다.
4. 답변이 맞았는지 상담원이 확인하거나 사용자가 좋아요/싫어요를 누른다.
5. 자주 틀리는 질문을 모아 eval set을 만들고 prompt나 retrieval 방식을 고친다. 이것이 feedback loop다.

숫자로 보면 더 쉽다. 하루에 질문 100개가 들어왔고, 그중 20개에서 사용자가 “도움 안 됨”을 눌렀다고 하자. 이 20개를 모아 분석하면 모델이 약한 주제를 찾을 수 있다. 다음 버전에서 이 20개 중 12개를 개선했다면, 실제 제품 품질이 좋아졌다고 볼 수 있다.

### 개념 구조와 핵심 포인트

AI 시스템은 크게 네 층으로 볼 수 있다.

첫째, data pipeline이다. 데이터를 수집하고, 중복을 제거하고, 개인정보를 처리하고, label을 붙이고, train/validation/test로 나눈다. LLM이나 RAG에서는 문서를 chunking하고 embedding을 만들어 vector database에 넣는 과정도 여기에 들어간다.

둘째, training stack이다. 모델이 입력 tensor를 받고 예측을 만들며, loss를 계산하고, gradient로 파라미터를 업데이트한다. optimizer는 이 gradient를 사용해 모델의 weight를 조금씩 바꾼다. 이 과정에서 batch size, learning rate, checkpoint, distributed training 같은 요소가 중요하다.

셋째, inference stack이다. 학습된 모델을 실제 요청에 맞게 실행한다. 여기에는 tokenizer, model server, batching, KV cache, quantization, monitoring이 포함된다. 제품에서는 latency와 비용이 중요한 제약이 된다.

넷째, feedback loop다. 배포 후 사용자의 클릭, 신고, 수정 요청, human review, eval 결과를 다시 데이터와 모델 개선에 반영한다. 이 loop가 있어야 시스템이 시간이 지나며 좋아질 수 있다.

핵심 포인트는 “각 층은 서로 영향을 준다”는 것이다. 평가가 약하면 feedback이 흐려지고, 데이터가 약하면 training이 흔들리고, serving이 약하면 좋은 모델도 사용자에게 느리게 전달된다.

### 핵심 수학 포인트

전체 시스템의 수학은 복잡해 보이지만, 가장 단순한 흐름은 입력 x에서 예측 y_hat을 만들고, 정답 y와 비교해 loss를 계산한 뒤, gradient로 파라미터를 업데이트하는 것이다.

예를 들어 모델이 어떤 메일이 스팸일 확률을 0.7이라고 예측했다고 하자. 실제 정답이 스팸이면 y = 1이다. 예측 0.7은 완전히 틀리지는 않았지만 1.0과 차이가 있다. loss는 이 차이를 숫자로 나타낸다. optimizer는 loss를 줄이는 방향으로 weight를 조금 바꾼다.

Inference에서는 이 업데이트가 없다. 사용자가 새 메일을 넣으면 모델은 현재 weight로 확률만 계산한다. 이때 빠르게 계산하고 많은 요청을 처리하는 것이 중요하다.

시스템 관점에서는 평균과 분포도 중요하다. 평균 latency가 1초여도, 100명 중 5명은 10초를 기다린다면 사용자 경험이 나쁠 수 있다. 그래서 p95 latency 같은 지표를 본다. p95 latency가 3초라는 말은 요청의 95%가 3초 안에 끝났다는 뜻이다.

Feedback loop에서는 작은 개선을 반복한다. 예를 들어 eval 100문제 중 70개를 맞히던 시스템이 데이터 정리와 prompt 개선 후 78개를 맞히면 8문제만큼 개선된 것이다. 이 숫자가 다음 설계 결정을 이끈다.

### 배워야 할 용어 (영문 term 중심, 필요 시 한국어 설명 보조)

- data pipeline: 데이터를 수집, 정리, 변환, 저장하여 학습이나 추론에 쓸 수 있게 만드는 흐름.
- training stack: 모델 학습에 필요한 코드, 데이터, loss, gradient, optimizer, GPU 인프라 전체.
- inference stack: 학습된 모델을 실제 요청에 대해 실행하고 응답하는 serving 구조.
- feedback loop: 사용자 반응과 평가 결과를 다시 데이터, 모델, prompt, 시스템 개선으로 연결하는 순환 구조.

### AI에서 어디에 쓰이는가

모든 실제 AI 제품에 쓰인다. 추천 시스템은 사용자 행동 로그를 data pipeline으로 모으고, 모델을 학습하고, inference stack에서 실시간 추천을 만들고, 클릭 여부를 feedback으로 다시 사용한다.

LLM 서비스는 더 복합적이다. 문서를 embedding으로 변환해 검색하고, LLM의 attention이 관련 문맥을 참고해 답을 만들며, hidden states를 거쳐 다음 token 확률을 계산한다. 답변이 틀리면 eval set에 추가하고, prompt나 retrieval, fine-tuning 데이터로 다시 개선한다.

즉 지금까지 배운 개념들이 흩어진 지식이 아니라 하나의 시스템 안에서 연결된다. 데이터는 입력을 만들고, tensor shape은 모델 계산을 가능하게 하고, loss와 gradient는 학습을 만들고, benchmark는 품질을 확인하고, serving은 사용자에게 전달하고, feedback loop는 다음 개선을 만든다.

### 헷갈리기 쉬운 포인트

AI 시스템 설계는 꼭 거대한 회사만 하는 일이 아니다. 작은 개인 프로젝트도 데이터 저장, 평가 기준, 배포 방식, 사용자 피드백을 갖추면 이미 작은 AI 시스템이다.

또 feedback loop는 “사용자 데이터를 무조건 학습에 넣는다”는 뜻이 아니다. 개인정보, 동의, 품질 검수, 안전성 기준이 필요하다. 잘못된 feedback을 그대로 넣으면 모델이 오히려 나빠질 수 있다.

마지막으로 training stack과 inference stack을 혼동하기 쉽다. Training stack은 모델을 배우게 하는 곳이고, inference stack은 배운 모델을 사용하게 하는 곳이다. 학습에서는 loss, gradient, optimizer가 중심이고, 추론에서는 latency, throughput, serving 안정성이 중심이다.

오늘은 “모델 하나”가 아니라 실제 AI 시스템 전체를 보는 복습입니다.

### 1. benchmark 점수가 높아도 실제 서비스에서 모델이 항상 좋다고 말할 수 없는 이유는 무엇일까?

**정답**

benchmark 점수가 높아도 실제 서비스에서 항상 좋은 모델이라고 말할 수는 없습니다.

이유는 benchmark가 정해진 시험 문제일 뿐이고, 실제 사용자는 훨씬 다양하고 예측하기 어려운 질문을 하기 때문입니다. 또 benchmark 데이터가 실제 서비스 상황과 다를 수 있고, 모델이 benchmark와 비슷한 데이터를 이미 학습했을 가능성도 있습니다. 그래서 실제 서비스에서는 benchmark 점수뿐 아니라 사용자 만족도, 안전성, 응답 속도, 비용, 실패 사례까지 함께 봐야 합니다.

**설명**

benchmark는 여러 모델을 같은 조건에서 비교하기 위한 표준 시험지입니다. 예를 들어 수학 문제 benchmark, 코딩 benchmark, 번역 benchmark처럼 특정 능력을 재기 위해 만든 문제 묶음입니다.

하지만 시험 성적이 높다고 해서 실제 업무를 항상 잘하는 것은 아닙니다. 학교 시험에서 좋은 점수를 받은 사람이 실제 회사 업무에서 협업, 예외 처리, 고객 응대까지 모두 잘한다고 보장할 수 없는 것과 비슷합니다.

AI 모델도 마찬가지입니다. 어떤 LLM이 benchmark에서는 높은 점수를 받을 수 있습니다. 하지만 실제 서비스에서는 사용자가 오타가 섞인 질문을 하거나, 회사 내부 정책을 물어보거나, 긴 문서를 올리거나, 애매한 요구를 할 수 있습니다. benchmark가 이런 상황을 충분히 담고 있지 않다면 점수와 실제 품질 사이에 차이가 생깁니다.

또 하나 중요한 문제는 data contamination입니다. 이것은 평가에 쓰인 문제가 학습 데이터에 섞여 들어간 경우를 말합니다. 모델이 진짜로 문제를 푼 것이 아니라, 예전에 본 문제를 외워서 맞힌 것처럼 보일 수 있습니다. 이 경우 benchmark 점수는 실제 능력보다 높게 나올 수 있습니다.

**예시**

두 개의 챗봇이 있다고 해봅시다.

A 모델은 공개 benchmark에서 90점을 받았습니다.  
B 모델은 benchmark에서 84점을 받았습니다.

겉보기에는 A가 더 좋아 보입니다. 그런데 실제 쇼핑몰 고객상담 서비스에 넣어 보니 A는 환불 정책을 자주 지어내고, B는 회사 문서를 잘 참고해서 더 안전하게 답합니다.

이 경우 실제 서비스에서는 B가 더 좋은 선택일 수 있습니다. benchmark 점수만 보면 A가 이겼지만, 서비스 목적에는 B가 더 잘 맞기 때문입니다.

**실전 연결**

실무에서는 benchmark 하나만 보고 모델을 고르지 않습니다. 보통 공개 benchmark, 우리 서비스 전용 private eval, human evaluation, latency, 비용을 함께 봅니다. LLM 앱에서는 특히 “답이 맞는가”, “근거 문서를 잘 따르는가”, “hallucination을 줄였는가”, “사용자가 기다릴 만한 속도인가”를 같이 평가해야 합니다.

### 2. latency와 throughput은 어떻게 다르며, LLM serving에서 KV cache가 왜 도움이 될까?

**정답**

latency는 요청 하나가 들어와서 답이 나올 때까지 걸리는 시간입니다. 쉽게 말해 한 사용자가 체감하는 기다림입니다.

throughput은 일정 시간 동안 시스템이 처리할 수 있는 요청 수나 token 수입니다. 쉽게 말해 전체 처리량입니다.

KV cache는 LLM이 이전 token들에 대해 이미 계산한 attention 정보를 저장해 두었다가 다음 token을 만들 때 재사용하는 기술입니다. 그래서 같은 계산을 반복하지 않아도 되어 LLM serving을 더 빠르고 효율적으로 만들 수 있습니다.

**설명**

latency와 throughput은 둘 다 속도와 관련 있지만 같은 개념은 아닙니다.

latency는 “내 질문 하나가 얼마나 빨리 끝나는가”입니다. 예를 들어 사용자가 챗봇에 질문했을 때 답변 첫 문장이 나오기까지 1초, 전체 답변이 끝나기까지 4초가 걸렸다면 이것이 latency와 관련됩니다.

throughput은 “서버가 전체적으로 얼마나 많이 처리하는가”입니다. 예를 들어 한 서버가 1초에 30개의 요청을 처리하거나, LLM이 1초에 500개의 token을 생성할 수 있다면 이것이 throughput입니다.

LLM serving에서는 이 둘의 균형이 중요합니다. batching처럼 여러 요청을 묶어 처리하는 방식은 throughput을 높일 수 있지만, 어떤 사용자는 자신의 요청이 batch에 묶일 때까지 조금 더 기다릴 수 있습니다. 즉 throughput은 좋아지지만 개별 latency는 늘어날 수도 있습니다.

KV cache는 Transformer 기반 LLM에서 특히 중요합니다. LLM은 답변을 한 번에 통째로 만드는 것이 아니라 token을 하나씩 생성합니다. 예를 들어 “오늘 날씨는 맑습니다”라는 문장을 만들 때, “오늘”을 만들고, 그다음 “날씨는”을 만들고, 그다음 “맑습니다”를 만듭니다.

이때 매번 앞의 모든 token 관계를 처음부터 다시 계산하면 너무 비효율적입니다. KV cache는 이전 token들의 key/value 정보를 저장합니다. key와 value는 attention에서 사용하는 내부 계산 값입니다. attention은 “현재 token이 이전 token들 중 무엇을 얼마나 참고해야 하는가”를 계산하는 구조입니다. KV cache를 쓰면 이미 계산한 이전 token 정보를 재사용할 수 있어서 중복 계산이 줄어듭니다.

**예시**

아주 작은 문장을 생각해 봅시다.

모델이 다음 문장을 생성한다고 해봅시다.

“나는 오늘 학교에 갔다”

먼저 모델은 “나는”을 보고 다음 token을 만듭니다.  
그다음 “나는 오늘”을 보고 다음 token을 만듭니다.  
그다음 “나는 오늘 학교에”를 보고 다음 token을 만듭니다.

KV cache가 없다면 매 단계마다 “나는”, “오늘”, “학교에”에 대한 attention 계산을 계속 다시 해야 합니다.

KV cache가 있으면 앞에서 계산한 “나는”, “오늘”, “학교에”의 key/value 정보를 저장해 두고 다음 token 생성 때 재사용합니다. 마치 수학 문제를 풀 때 중간 계산을 적어 두고 다음 줄에서 다시 쓰는 것과 비슷합니다.

**실전 연결**

LLM 챗봇, 코드 생성기, 문서 요약 시스템에서는 답변이 길어질수록 KV cache의 효과가 커집니다. 긴 대화나 긴 문서를 다루는 RAG 시스템에서는 이전 token이 많기 때문에 attention 계산 비용이 커집니다. KV cache를 잘 관리하면 latency를 줄이고, GPU 사용 효율을 높이고, 더 많은 사용자를 처리할 수 있습니다. 실제 LLM serving에서는 batching, quantization, KV cache 관리가 비용과 속도를 좌우하는 핵심 기술입니다.

### 3. data pipeline, training stack, inference stack, feedback loop는 각각 AI 시스템에서 어떤 역할을 할까?

**정답**

data pipeline은 데이터를 모으고 정리해서 모델이 사용할 수 있는 형태로 만드는 흐름입니다.

training stack은 그 데이터를 사용해 모델을 학습시키는 구성입니다. 여기에는 loss function, gradient, optimizer, GPU, checkpoint 같은 요소가 포함됩니다.

inference stack은 학습된 모델을 실제 사용자 요청에 대해 실행하고 응답을 돌려주는 구성입니다.

feedback loop는 실제 사용 결과와 평가 결과를 다시 데이터, 모델, prompt, 시스템 개선에 반영하는 순환 구조입니다.

**설명**

실제 AI 시스템은 모델 하나만으로 완성되지 않습니다. 좋은 AI 서비스를 만들려면 데이터가 들어오고, 모델이 학습되고, 사용자가 요청을 보내고, 결과를 평가하고, 다시 개선되는 전체 흐름이 필요합니다.

data pipeline은 AI 시스템의 재료 준비 단계입니다. 데이터를 수집하고, 중복을 제거하고, 개인정보를 처리하고, label을 붙이고, 학습용과 평가용 데이터로 나눕니다. RAG 시스템에서는 문서를 chunk로 자르고, embedding을 만들고, vector database에 저장하는 과정도 data pipeline에 들어갑니다.

training stack은 모델이 배우는 단계입니다. 모델은 입력을 받아 예측을 만들고, 정답과 비교해서 loss function을 계산합니다. loss function은 모델이 얼마나 틀렸는지를 숫자로 나타내는 함수입니다. 그다음 gradient를 계산합니다. gradient는 loss를 줄이려면 모델의 weight를 어느 방향으로 바꿔야 하는지 알려주는 값입니다. optimizer는 이 gradient를 사용해 모델 파라미터를 조금씩 업데이트합니다.

inference stack은 배운 모델을 실제로 사용하는 단계입니다. 사용자가 질문을 보내면 tokenizer가 텍스트를 token으로 바꾸고, model server가 모델을 실행하고, 결과를 다시 문장으로 바꿔 응답합니다. 이 단계에서는 학습처럼 weight를 바꾸지 않습니다. 대신 latency, throughput, 비용, 안정성이 중요합니다.

feedback loop는 시스템을 계속 좋아지게 만드는 단계입니다. 사용자가 “도움 안 됨”을 눌렀거나, 사람이 답변 오류를 발견했거나, eval에서 실패 사례가 나왔다면 그 정보를 모읍니다. 그리고 다음 데이터 정리, prompt 수정, retrieval 개선, fine-tuning, 평가셋 보강에 사용합니다.

**예시**

AI 고객상담 봇을 만든다고 해봅시다.

먼저 회사 FAQ, 환불 정책, 배송 안내 문서를 모읍니다. 이것이 data pipeline의 시작입니다. 문서를 정리하고, 너무 긴 문서는 작은 chunk로 나누고, embedding을 만들어 vector database에 넣습니다.

그다음 필요하다면 상담 데이터로 모델을 fine-tuning합니다. 이때 loss를 계산하고 gradient로 weight를 업데이트합니다. 이것이 training stack입니다.

서비스가 시작되면 사용자가 “환불은 며칠 안에 되나요?”라고 묻습니다. 시스템은 관련 문서를 검색하고, LLM에게 문맥과 질문을 넣어 답변을 생성합니다. 이것이 inference stack입니다.

이후 사용자가 답변에 “도움 됨” 또는 “도움 안 됨”을 누릅니다. 상담원이 틀린 답변을 표시할 수도 있습니다. 이 실패 사례를 모아 평가셋에 추가하고 prompt나 검색 방식을 고칩니다. 이것이 feedback loop입니다.

**실전 연결**

현대 ML/DL/LLM 제품은 이 네 부분이 모두 연결되어야 안정적으로 좋아집니다. 추천 시스템은 사용자 클릭 로그를 data pipeline으로 모으고, training stack에서 모델을 학습하고, inference stack에서 실시간 추천을 만들고, 클릭 여부를 feedback loop로 다시 사용합니다. LLM 서비스도 마찬가지입니다. 문서 검색이 약하면 RAG 답변이 틀리고, 평가가 약하면 개선 방향을 모릅니다. 그래서 실전에서는 “모델 성능”뿐 아니라 데이터, 평가, serving, feedback까지 함께 설계하는 능력이 중요합니다.
